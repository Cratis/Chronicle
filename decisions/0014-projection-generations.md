# Give projections and reducers durable generations, publish one Active generation per materialization, and resolve reads explicitly

Proposed on 2026-10-20 for [Cratis/Chronicle#5157](https://github.com/Cratis/Chronicle/issues/5157), in [epic #5155](https://github.com/Cratis/Chronicle/issues/5155). Offered to woksin for a decision; not accepted or implemented. Number 0014 leaves 0013 to [PR #5097](https://github.com/Cratis/Chronicle/pull/5097).

## Context

A definition deployment, a historical rebuild, a serving switch and a query's version selection are different operations. Without durable identities and one serving authority, definition history and applied state remain ambiguous, replay work can interfere with live work, and a reader cannot name the state it needs. This record fixes the vocabulary and boundaries before the implementation issues choose APIs.

The following facts describe `origin/main` at `7d66588d83e44b750d02e65a5886533089827510`, not the proposed generation model:

- Definitions are registered by projection identifier; MongoDB replaces the stored definition for that identifier. `Projection.SetDefinition` rejects older software versions, replaces its grain state for admitted registrations, and notifies on a structural difference or legacy-storage upgrade. The comparer calls `ProjectionDefinitionNormalization.ForComparison`, which nulls the `ReadModel` identifier (hence ignoring a read-model/sink retarget), `InitialModelState` and metadata `LastUpdated`, `Tags`, `Version`. `IsActive` is still compared; `ProjectionDefinition` has no `Sink` property ([storage](https://github.com/Cratis/Chronicle/blob/7d66588d83e44b750d02e65a5886533089827510/Source/Kernel/Storage.MongoDB/Projections/ProjectionDefinitionsStorage.cs#L46-L61), [registration](https://github.com/Cratis/Chronicle/blob/7d66588d83e44b750d02e65a5886533089827510/Source/Kernel/Core/Projections/Projection.cs#L60-L114), [comparison](https://github.com/Cratis/Chronicle/blob/7d66588d83e44b750d02e65a5886533089827510/Source/Kernel/Core/Projections/Engine/ProjectionDefinitionComparer.cs#L35-L45), [normalization](https://github.com/Cratis/Chronicle/blob/7d66588d83e44b750d02e65a5886533089827510/Source/Kernel/Core/Projections/Engine/ProjectionDefinitionNormalization.cs#L21-L43), [definition](https://github.com/Cratis/Chronicle/blob/7d66588d83e44b750d02e65a5886533089827510/Source/Kernel/Concepts/Projections/Definitions/ProjectionDefinition.cs#L39-L86)). There is no retained generation/revision lineage in these paths.
- `ProjectionGeneration` already exists as `record ProjectionGeneration(uint Value) : ConceptAs<uint>(Value)`, with `FirstValue = 1U`, `First` and an `Unspecified` instance whose value is `uint.MaxValue`. It supplies value conversion, not a durable allocator or lifecycle. MongoDB saves its replacement definition under the `ProjectionGeneration.First` key ([concept](https://github.com/Cratis/Chronicle/blob/7d66588d83e44b750d02e65a5886533089827510/Source/Kernel/Concepts/Projections/ProjectionGeneration.cs#L6-L32), [save](https://github.com/Cratis/Chronicle/blob/7d66588d83e44b750d02e65a5886533089827510/Source/Kernel/Storage.MongoDB/Projections/ProjectionDefinitionsStorage.cs#L46-L61)).
- Full replay takes the observer into replay rather than continuing its normal live route. Replay completion goes through `CompleteReplay`; that clears replay state and returns a non-quarantined observer to routing. Generation rebuilds must not confuse that job lifecycle with publication of a new served definition ([routing](https://github.com/Cratis/Chronicle/blob/7d66588d83e44b750d02e65a5886533089827510/Source/Kernel/Core/Observation/States/Routing.cs#L151-L170), [completion](https://github.com/Cratis/Chronicle/blob/7d66588d83e44b750d02e65a5886533089827510/Source/Kernel/Core/Observation/Jobs/ReplayObserver.cs#L325-L361), [resume](https://github.com/Cratis/Chronicle/blob/7d66588d83e44b750d02e65a5886533089827510/Source/Kernel/Core/Observation/Observer.Replay.cs#L75-L152)).
- MongoDB's sink selects normal or replay collections through `_isReplaying`; after claiming replay under a temporary name, publication moves served to a revert name and claimed replay to served in two separate commands. SQL uses a transaction around its rename swap. These are replay-container mechanisms, not an atomic multi-generation serving contract ([MongoDB](https://github.com/Cratis/Chronicle/blob/7d66588d83e44b750d02e65a5886533089827510/Source/Kernel/Storage.MongoDB/Sinks/SinkCollections.cs#L45-L146), [SQL](https://github.com/Cratis/Chronicle/blob/7d66588d83e44b750d02e65a5886533089827510/Source/Kernel/Storage.Sql/Sinks/Sink.ReplayPromotion.cs#L22-L65)).
- `ReplayContext` holds `Type` (`ReadModelType`), `ContainerName` and `RevertContainerName` (`ReadModelContainerName`), and `Started` (`DateTimeOffset`). `ReadModelOccurrence` holds `ObserverId` (`ObserverId`), `Occurred` (`DateTimeOffset`), `Type` (`ReadModelType`), and the same two container-name fields. `ReadModelType` contains an identifier and a read-model generation, not an archived schema. Neither record stores a proven applied event cursor, so neither establishes that a retained snapshot is caught up ([context record](https://github.com/Cratis/Chronicle/blob/7d66588d83e44b750d02e65a5886533089827510/Source/Kernel/Storage/ReadModels/ReplayContext.cs#L10-L24), [occurrence record](https://github.com/Cratis/Chronicle/blob/7d66588d83e44b750d02e65a5886533089827510/Source/Kernel/Storage/ReadModels/ReadModelOccurrence.cs#L10-L22), [read-model type](https://github.com/Cratis/Chronicle/blob/7d66588d83e44b750d02e65a5886533089827510/Source/Kernel/Concepts/ReadModels/ReadModelType.cs#L6-L11)).
- `MaterializedReadModelStore` receives a `ReadModelDefinition`; its `GetSinkFor` calls the namespace's `Sinks.GetFor(definition)` without a projection-generation selector ([query resolution](https://github.com/Cratis/Chronicle/blob/7d66588d83e44b750d02e65a5886533089827510/Source/Kernel/Core/ReadModels/MaterializedReadModelStore.cs#L37-L64), [sink resolution](https://github.com/Cratis/Chronicle/blob/7d66588d83e44b750d02e65a5886533089827510/Source/Kernel/Core/ReadModels/MaterializedReadModelStore.cs#L88-L89)). Global projections route their materialization to the `NotSet` namespace's sink, while observer keys include the source namespace and sequence ([pipeline](https://github.com/Cratis/Chronicle/blob/7d66588d83e44b750d02e65a5886533089827510/Source/Kernel/Core/Projections/Engine/Pipelines/ProjectionPipelineManager.cs#L69-L98), [observer key](https://github.com/Cratis/Chronicle/blob/7d66588d83e44b750d02e65a5886533089827510/Source/Kernel/Concepts/Observation/ObserverKey.cs#L9-L19)).
- Reducers replace registered definition state, subscribe through a connected client and evolve definitions through replay plans. They need generation-specific client execution as well as separate storage ([registration](https://github.com/Cratis/Chronicle/blob/7d66588d83e44b750d02e65a5886533089827510/Source/Kernel/Core/Observation/Reducers/Clients/Reducer.cs#L57-L112), [evolution](https://github.com/Cratis/Chronicle/blob/7d66588d83e44b750d02e65a5886533089827510/Source/Kernel/Core/Observation/Reducers/Clients/Reducer.cs#L146-L207)). The existing evolution policy is `Automatic`, `PartialOnly` or `Manual`; this proposal retains those names ([policy](https://github.com/Cratis/Chronicle/blob/7d66588d83e44b750d02e65a5886533089827510/Source/Kernel/Core/Configuration/DefinitionEvolutionPolicy.cs#L8-L24)).

## Decision

Give each logical projection or reducer an immutable generation lineage and a separate immutable definition-revision history; build new generations in isolated containers while the current generation remains live, publish exactly one Active generation through the sink's single serving authority under an Orleans-owned fenced handover, retain displaced generations according to their actual following/snapshot behavior, and make ordinary reads follow Active while explicit versioned reads resolve and pin a named compatible generation. The numbered clauses below define this proposed contract; none describes an already available API.

### 1. Identity, revisions and materialization scope

A logical identity is `(EventStore, ProjectionId)` or `(EventStore, ReducerId)` with an explicit kind; it is not an application software version or a read-model schema generation. Reuse the existing `ProjectionGeneration` concept rather than replace it; extend its use with durable monotonic allocation per logical identity and the lifecycle/storage contract below. Allocate from `First` through `uint.MaxValue - 1`, reserve zero and `Unspecified`, never reuse a number, and fail allocation on exhaustion. Allocate immutable `DefinitionRevision` values within a generation. A generation's materialization identity adds the namespace for namespaced models, or the event-store-wide global scope for a shared model. Namespace-local states and cursors may differ even when the definition and generation number are shared.

Keep a canonical fingerprint and full definition snapshot for **every** revision, not just the current one. Canonicalize mapping, event-type capabilities, filters, keys, joins, children, scope, `InitialModelState`, the target `ReadModel` identifier and its resolved sink configuration; ordering without semantics is normalized. Reducers must declare an implementation revision/fingerprint: the kernel cannot infer a delegate's code changes. Deliberately separate operational activation flags (including `IsActive`, which the current comparer compares), connection IDs and promotion policies from semantic fingerprints. Explicitly classify read-model/sink retargets and initial-state changes even when the current comparer returns Same; a materialization-destination change requires a new isolated generation. Scope/key changes also require classification, not an assumption that the current comparer ignores them. Store fingerprint algorithm/version and verify full canonical equality on a hash match. No historical fingerprint is overwritten.

`FullReplay`, a semantics-changing reducer implementation or an explicit full rebuild creates a new generation with empty isolated storage, even when rebuilding the same revision to repair data. Admitted `NoAction` creates a new revision in the same lineage. Proven-safe `PartialReplay` creates a pending immutable revision in the same lineage and records per-partition adoption receipts; no served revision is advertised as fully applied before its proof completes. Unsafe/unknown evolution requires a full generation. [#5160](https://github.com/Cratis/Chronicle/issues/5160) owns shadow publication; [#5171](https://github.com/Cratis/Chronicle/issues/5171) must close the current partial-evolution safety gap before enabling it.

A registration matching any historical fingerprint reuses its immutable definition snapshot. It neither restores it nor cancels a candidate. The same fingerprint may occur in several repair generations; registration does not choose a materialization, and version-read bindings must identify one generation/revision explicitly or report ambiguity. An explicit desired-definition change, not an old replica's reconnect, supersedes a candidate; a deliberate return to the active fingerprint abandons that candidate without creating another generation. Keep desired, applied and per-materialization served revisions distinct.

### 2. Generation and observer identity

Import existing served state as generation 1 and keep its existing `ObserverId = ProjectionId` (or reducer ID). Later generations use a collision-checked generated ID such as `<id>@g<n>`, allocated with a durable unique binding to `(logical identity, generation, materialization scope)`. Reserve names atomically; fail on an existing unrelated owner, never parse an arbitrary user ID's suffix as a binding. Promotion and retirement do not rename observer state. Definitions, subscriber activation/deactivation, pipeline caches, bulk/replay handlers, futures, notifications and client dispatch all resolve the binding and explicit revision. They never interpret a generated observer ID as a new logical projection ID or fall back to a silo's latest cached definition.

Each generation has independent positions, failed partitions, jobs, locks and explicitly addressed sinks. Generation building does not flip a shared sink-wide replay flag. Join/child lookups stay inside the same generation. `Building` historical delivery uses replay observation semantics; live delivery in `Following`, `Active` and `Retired` does not. Generation lifecycle is separate from observer running state and handover phase.

### 3. Lifecycle

These are the **only** generation lifecycle states:

| State | Meaning | Allowed next states |
| --- | --- | --- |
| Building | Allocated, possibly waiting for admission, rebuilding history into isolated storage; never default-served. | Following, Abandoned |
| Following | Historical coverage is proven; follows live events before publication. | Active, Abandoned |
| Active | The one generation selected by the serving authority; follows live events. | Retired |
| Retired | Previously served, still follows live events and remains a bounded rollback target. | Active, Archived |
| Archived | Non-following snapshot with its last proven cursor vector, or explicitly unknown legacy position. | Removed |
| Abandoned | Unserved canceled, superseded or terminally failed build; drained before cleanup. | Removed |
| Removed | Containers are gone; immutable audit/identity metadata remains. | None |

Creation enters `Building`; migration alone imports the existing served generation as `Active`. Import old revert containers as `Archived`, never `Retired`. Retriable build failure stays `Building` with failure metadata. Queued/admitted, fenced, draining, promotion failed and waiting for a compatible client are operational metadata, not extra lifecycle states. Retrying an `Abandoned` or `Removed` generation allocates a new number.

Promotion pairs `Following → Active` with the previous `Active → Retired`; rollback pairs `Retired → Active` with `Active → Retired` through the same protocol. A zero rollback window immediately schedules `Retired → Archived`, not a fictional following snapshot. Removal always drains/archives or abandons first and honors read pins; no direct deletion of Active. An Archived generation cannot instantly roll back: rebuild a new generation or explicitly catch up into a new lineage before publication.

### 4. Storage names and one serving authority per sink

Persist a container binding per `(logical identity, materialization scope, sink, generation)`. The served name is the read model's existing container name `c`; a generation's reserved name is `c-g<n>` before provider-safe encoding. Persist the final physical name once. A bounded readable prefix plus a hash of the complete owner tuple leaves room for the generation suffix; apply the provider's identifier/namespace length and equality rules, quote SQL identifiers, reserve both served and generated names, and fail on collisions rather than silently truncate or adopt another owner's data. Multiple logical producers of one served name need an explicit shared materialization owner or fail admission. Database placement does not change. A sink's generation capability includes isolation, durable progress, fenced publication, recovery and pinned reads; an unsupported/custom sink rejects before allocating or mutating a build, rather than silently using the legacy swap.

**MongoDB:** physical generation collections keep their bound names permanently. The stable served name `c` becomes a read-only view whose `viewOn` names the Active physical collection. Change that view target with one `collMod`; the view target is the **sole serving pointer and linearization point**, not a pointer document plus a view. Default Chronicle reads and direct readers query the same view. Generation records' `ActiveGeneration` and served-definition metadata are derived, reconciled projections of it. Writers and pinned reads address physical collections, never the view. A lost swap response reads the view target to determine the result. The serialized owner checks expected old target, handover ID and epoch before publication; stale owners cannot publish a later conflicting command. Do not claim MongoDB DDL is part of a multi-document transaction.

This selects the view design, subject to a blocking supported-version/topology compatibility spike before implementation acceptance: query operators/index hints, direct-reader compatibility and physical-collection change streams must work as documented. Views do not provide collection writes, direct view change streams or every collection query feature. Initial collection-to-view conversion requires an explicit maintenance/compatibility boundary with direct readers coordinated; a write fence alone does not close the conversion gap. New installations start with the view. If the spike fails, return this proposal for a different single-authority contract; never fall back silently to two renames and call it atomic.

**SQL (PostgreSQL, SQL Server and single-node SQLite):** a non-Active generation lives in its bound `c-g<n>` table slot; Active occupies `c`. Fence and drain **all** affected generation writers and short-lived pinned reads, flush buffers, then transactionally rename A from `c` to its reserved generation slot and B from its slot to `c`. Update the generation-to-table bindings, authoritative `ActiveGeneration` row, serving epoch and handover receipt in that same database transaction. The committed row plus table mapping is one authority; neither an in-memory pointer nor a later grain-state write chooses a second answer. Conditional expected-epoch/old-generation checks reject stale publication. Rebind every renamed generation's writers under a fresh epoch and collect acknowledgments before releasing admission. Pin acquisition and mapping resolution serialize with publication; a pinned generation cannot accidentally follow the reused name `c` to a different generation. Direct default readers keep querying `c` across the transactional switch.

Only one sink is authoritative for a served materialization. Cross-database or multi-sink atomic promotion is not promised. All providers, including in-memory storage, must preserve these observable semantics or explicitly reject the capability.

### 5. Orleans ownership, fence and recovery

The `Projection` grain, whose [existing key is projection ID plus event store](https://github.com/Cratis/Chronicle/blob/7d66588d83e44b750d02e65a5886533089827510/Source/Kernel/Concepts/Projections/ProjectionKey.cs#L8-L19), has the **proposed extended role** of immutable definition/generation catalog and monotonic allocator; reducers receive an equivalent kind-qualified catalog. A new non-reentrant `IProjectionHandover` grain, keyed by `(EventStore, logical identity, materialization scope)`, owns durable materialization-generation state, container bindings, admission epoch and the promotion/rollback journal. For global scope there is exactly one event-store-wide owner, not one promotion owner per contributing namespace. It alone authorizes publication and retention; per-silo replay finalizers cannot promote independently. Large partition inventories live in revisioned storage rows owned by it, not one unbounded grain-state document.

Orleans single activation and serialized turns give one coordinator for the scope and serialize competing build, promote, rollback and retention requests. **They do not by themselves drain jobs, flush silo-local buffers, make sink DDL transactional or stop delayed external writes.** Persist handover ID, owner epoch, source/target, phase, deadline, inventory revision and cursor vector before issuing work. Close observer/job admission; poll admitted job grains with non-blocking `StopAndDrain(TimeSpan.Zero)` on later turns. Only `Drained`/`Completed` proves that barrier; timeout, missing storage or a stopped status does not. Never await a positive drain timeout in the observer turn its jobs call back into. This follows [decision 0011's drain/admission contract](https://github.com/Cratis/Chronicle/blob/7d66588d83e44b750d02e65a5886533089827510/decisions/0011-a-type-set-change-quiesces-the-observer-through-orleans-drain-and-admission.md).

After draining all admitted deliveries, jobs and callbacks and flushing every contributing writer, capture committed/scanned `N[K]`, where `K = (EventStore, Namespace, EventSequenceId)`. Require the incoming generation to prove coverage through every component, not merely a small numeric lag or a job's completion. Preserve failed/unfinished partition obligations below the shared cursor. Global publication freezes contributor admission, persists the complete contributor set and namespace-membership revision, and rechecks it at commit. Never compare namespace-local sequence numbers or take their maximum. [#5172](https://github.com/Cratis/Chronicle/issues/5172) must first establish safe global-scope admission; uncoordinated namespace replay of a shared materialization remains rejected.

The fence consists of closed admission, reconciled obligations, drained/flushed writers and sink-enforced owner/write epochs. Reject stale callbacks and stale writers at commit; single activation is not a substitute. MongoDB's immutable physical destinations allow B to continue beyond N without redirecting writes when the view changes. Any rename-based publication fences both A and B, persists their own committed vectors and rebinds all affected writers before release. An unreachable writer blocks/aborts before commit; it is not presumed drained. Resume each generation above its own proven committed/scanned position, not a copied job checkpoint.

Persist phases `Fencing → Draining → Swapping → Swapped → Releasing → Completed`, with pre-commit `Aborting`. After a crash or unknown acknowledgment, read the sink authority/receipt: before commit an expired attempt may abort after excluding delayed publication; after commit finish forward, reconcile lifecycle/served-definition metadata and release. Unknown authority leaves fences in place for recovery, never guesses rollback. Publication commands must be serialized and reconciled before any owner epoch is transferred; sink-side epoch admission must reject a delayed old-owner publish, including MongoDB view DDL. The compatibility spike must prove that enforcement, not assume a view update has a compare-and-swap predicate. Notifications are idempotent hints backed by authority/epoch rechecks.

### 6. Reads and notifications

An ordinary query reads **Active**, not newest registered, newest schema, newest software version, Building or Following. Resolve one serving epoch for the whole request (including joins/paging); concurrent publication can return the old complete generation or the new complete generation, never a mixture or empty interval. Default MongoDB reads use the served view, not a potentially stale cached `ActiveGeneration`. SQL reads coordinate binding/pins with the publication transaction. Code requiring multi-request consistency uses an explicit generation pin.

[#5163](https://github.com/Cratis/Chronicle/issues/5163) owns the explicit versioned-read API: a selector resolves a software-version registration to one `(generation, definition revision, schema)` with proven coverage, then obtains a retention pin. Software version alone is not generation identity and a raw physical name is not a selector. Explicit generation reads may inspect Following, Retired or Archived data with lifecycle/position metadata and an opt-in for unserved state. Building is diagnostic-only with an explicit incomplete-state acknowledgment. Removed, incompatible, unready or ambiguous selections fail with an actionable error; never fall back silently to Active. Pins are bounded, renewable leases that block deletion; SQL uses short operation pins to coordinate renames, not an indefinitely held database transaction. Version-pinned reads remain on that generation after promotion/rollback, and Archived reads promise a snapshot, not freshness.

Observable queries watch only their resolved generation. Publication broadcasts `GenerationActivated` with serving epoch, invalidates read/pipeline caches, rebinds physical change streams and sends one full reload/reset to default delta subscribers without an intermediate empty payload. Pinned subscribers stay pinned. Reconnect and missed-broadcast handling re-read authority; a MongoDB view target update is not assumed to deliver collection-change notifications.

### 7. Policy, retention, prerequisites and reducers

Keep `Automatic`, `PartialOnly` and `Manual` evolution policy. Full rebuild admission follows that policy: automatic starts a separate build; PartialOnly/Manual records the desired immutable candidate and recommendation without starting a full job. A recorded candidate may be `Building` with `BuildStarted = false`. Promotion is a separate permission, defaulting to operator/deployment-condition approval for application models; kernel-owned models may automatically promote once readiness is proven. [#5161](https://github.com/Cratis/Chronicle/issues/5161) owns conditions, audit and policy precedence. Stale registrations never grant promotion or cancellation authority.

Default retention is one following Retired generation for 24 hours and one Archived snapshot; keep `ReplayedVersionsToKeep` as the snapshot-count compatibility alias. Kernel-owned models retain neither by default. [#5162](https://github.com/Cratis/Chronicle/issues/5162) owns configuration and scheduling. Rollback is the same fenced publication with a Retired target and proven coverage; force may waive failed-partition policy, never coverage, drain, epoch or membership barriers. Each successful displacement gets a fresh rollback deadline; failed attempts do not extend it. Expiry/cap enforcement drains before archiving; pins defer removal. Cancellation/supersession drains a build into Abandoned before cleanup. Keep audit tombstones, definitions and identity bindings after physical removal.

Reducers are in scope for the same lineage, lifecycle, isolated sinks, reads and promotion guarantees. Rebuilding a reducer needs a declared implementation revision, an empty initial rebuild state and generation-aware client dispatch for both old and new implementations. No connected compatible target means waiting, not delivery to another version. [#5165](https://github.com/Cratis/Chronicle/issues/5165) owns exact client-version selection/admission and must explicitly cover reducers; reactor-only version routing is insufficient. [#5166](https://github.com/Cratis/Chronicle/issues/5166) owns ordered rebuild execution/parallelism, [#5167](https://github.com/Cratis/Chronicle/issues/5167) worker placement, and [#5168](https://github.com/Cratis/Chronicle/issues/5168) coverage/readiness/progress visibility. A position-distance estimate is never a publication proof.

For reactors, the related guarantee is **single delivery ownership and stable delivery identity across a reactor version change; external effects still need ReactorDelivery receipts/downstream idempotency**. [#5164](https://github.com/Cratis/Chronicle/issues/5164) owns the handover and stable lineage identity, preserving unfinished obligations and at-least-once retries. Reactor version ownership is not dual delivery to following projection generations, and it does not guarantee exactly-once side effects.

## Options considered

- **Isolated generation writers plus one fenced serving authority (chosen).** Keeps live serving independent of rebuild and makes versioned reads/rollback nameable, at the cost of additional storage and coordination.
- **One observer dual-writing old and new containers.** One position cannot describe independently rebuilt state or isolate failures; joins and replay/live ordering become ambiguous.
- **Latest software version or last registration wins.** A rolling deployment can replace definitions in either direction; a reconnect is not operator intent, and reducer execution could use the wrong code.
- **A new generation for every definition change.** Simple, but safe NoAction/partial evolution needlessly rebuilds history. Immutable revisions preserve its lineage without that cost.
- **Rename-only MongoDB serving.** Two renames expose a missing-name interval; replacing the target in one rename loses the displaced collection without a copy. Neither supplies the selected atomic visibility plus bounded rollback contract.
- **A MongoDB pointer document with a stable served view as another authority.** Two independent commits can disagree. A pointer-only design is viable only with an explicit compatibility change for every direct reader; it is not a silent fallback if the selected view fails validation.
- **Immutable SQL tables behind a served view.** Avoids writer rebinding but changes the stable served object from table to view and needs a separate compatibility contract. Transactional rename plus transactional bindings retains the served-table boundary.
- **Archived snapshots as instant rollback.** Their cursor can be old or unknown. Retired means following; snapshots need a new catch-up/rebuild proof.

## Default if unanswered

This remains proposed and authorizes no generation implementation or release. Keep the existing supported behavior, but do not advertise uninterrupted live rebuild, atomic multi-generation publication or version-selected reads. Ship the conservative safety prerequisites [#5170](https://github.com/Cratis/Chronicle/issues/5170), #5171 and #5172 on their own proof; do not enable unsafe partial/global paths while waiting. Delaying the decision blocks the dependent epic work and leaves deployment-time evolution operationally constrained.

## Timeline and scope

The decision holds for the generation feature in #5155 and its client/read/storage contracts. Import existing served state only after draining or explicitly repairing legacy replay sessions; preserve old observer IDs and schema history, label legacy snapshot positions unknown, and perform MongoDB's first conversion at the documented maintenance boundary. Additive storage/contracts come before enabling new writes; do not migrate legacy jobs by guessing their generation. Protocol/schema changes follow the repository's generated-wire workflow, not hand-edited generated output.

[#5169](https://github.com/Cratis/Chronicle/issues/5169) owns mixed-kernel-version rollout, capability negotiation and rollback floors. Application version coexistence does not prove kernel rollout safety. Gate generation enablement on compatible cluster capability; SQL multi-silo verification also depends on [#5127](https://github.com/Cratis/Chronicle/issues/5127). External side-effect transactions, distributed multi-sink atomicity and arbitrary cross-partition parallel projection execution are out of scope.

## Verification

**Done when:** woksin accepts the contract and the dependent implementation proves isolated live/build execution, one crash-recoverable serving authority, explicit read selection, following rollback, and reducer/version ownership on every supported sink. Acceptance of this document alone does not change `stage` to implemented or verified.

**Verify by:**

- Identity/storage specs preserve all revision snapshots, classify NoAction/PartialReplay/FullReplay, deduplicate historical registrations, and reject hash/name/observer-ID collisions, stale epochs and cross-generation cache resolution.
- State-machine specs exercise every allowed transition and reject all others, including deletion of Active and promotion of Archived. Cancellation, retries, retention pins and repeated promote/rollback preserve audit and fresh deadlines.
- Real MongoDB and SQL scenarios read concrete nonempty served data during builds, prove live freshness while candidate writes/failures stay isolated, and exercise joins/children/reducer clients with distinct expected old/new results. Empty-history cases are additional tests, not the only evidence.
- Fault injection at each fence/drain/publication/notification boundary includes two silos, lost responses and delayed old-owner writes/DDL after coordinator failover. Assert no partial publication, wrong-container write, premature release or guessed outcome. Test namespace vectors, contributor changes, pending obligations below a shared cursor and global admission refusal before coordinated support exists.
- Complete the blocking MongoDB view/query/direct-reader/change-stream and stale-publication fencing spike on supported versions/topologies. Exercise the explicit first-conversion maintenance boundary. SQL tests verify atomic rename/binding/receipt commit and pinned reads/writer rebinding on each provider, including rollback.
- Client/read integration tests cover default Active, compatible version resolution, unready/ambiguous/removed errors, diagnostic opt-in, retained pins, observable reset and missed notifications. Reducer execution never selects the wrong implementation; reactor handover tests prove delivery ownership/identity, not exactly-once external effects.

## Consequences

- Rebuild, serving and read-version choices become independent and auditable. Stable bindings and explicit revisions remove last-registration and per-silo-cache ambiguity.
- Following/Retired generations cost extra storage, writes and compatible reducer client capacity. Bounded retention and job placement become operational requirements, not optional polish.
- Publication adds durable orchestration, sink epochs, contributor vectors and recovery work. MongoDB view compatibility and enforceable stale-publisher exclusion are blocking acceptance evidence, not assumed properties of Orleans serialization.
- MongoDB direct-reader behavior changes at an explicit migration boundary; SQL keeps its stable served table but must rebind fenced writers and coordinate pins. No sink may weaken the guarantee silently.
- Open acceptance questions are whether the selected MongoDB view contract and stale-DDL fencing can be proven on supported topologies, and which explicit direct-reader migration boundary operators can accept. A failed proof returns this proposal for revision; it does not authorize a second serving pointer or weaker atomicity claim.
