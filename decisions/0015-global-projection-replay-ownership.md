# Give each global projection one replay owner and keep live writes on its served sink

Proposed on 2026-10-20 for [#5172](https://github.com/Cratis/Chronicle/issues/5172), part of [#5155](https://github.com/Cratis/Chronicle/issues/5155). The maintainer selected coordinated replay, not the refusal stopgap. This record remains proposed, not accepted or implemented. Number 0013 is reserved by [PR #5097](https://github.com/Cratis/Chronicle/pull/5097).

## Context

The following current-code claims refer only to `origin/main` at `45a1c2c13059096b41b8a96aa032860259898e7b`:

- A projection is subscribed with a separate `ObserverKey` for each namespace. Pipelines are cached by event store, source namespace and projection ID, but global projections resolve their sink in `EventStoreNamespaceName.NotSet`; the sink cache includes configuration and container, not the source namespace ([subscriptions][subscriptions], [pipeline][pipeline], [sink cache][sink-cache]). Consequently, source-local replay control can mutate a shared destination.
- Begin establishes context and retention in the observer's source namespace; end records the occurrence and evicts context there. Retention removes containers through that namespace's sink. These paths do not establish materialization-wide ownership ([handler][handler], [retention storage][retention-storage]).
- MongoDB begin changes `_isReplaying`, clears the selected collection, and routes pipeline access through that flag. Publication claims the replay collection, then renames served to revert and replay to served separately. SQL similarly sets shared replay routing and initializes its shadow, but its promotion uses a transaction and a promotion marker ([MongoDB routing][mongo-routing], [MongoDB promotion][mongo-promotion], [SQL routing][sql-routing], [SQL begin][sql-begin], [SQL promotion][sql-promotion]). A process-local cache or rename claim is not a cross-namespace replay owner.
- `Observer.Replay` enters replay state; that state starts/resumes a namespace-keyed observer job. Projection replay uses one ordered event-handling step from the beginning, rather than a vector of namespace readers. Finalization calls the replay service and then notifies the observer ([observer entry][observer-entry], [replay state][replay-state], [job preparation][job-preparation], [job finalization][job-finalization]). Keeping these namespace observers replaying would also stop their ordinary live route, rather than isolate a rebuild.
- Automatic definition evolution schedules replay per namespace; the replay recommendation calls the same observer entry point. The client replay API returns `Task<JobId>`, and the Core replay commands target a namespace observer ([evolution][evolution], [recommendation][recommendation], [client contract][client-contract], [replay command][replay-command], [partition command][partition-command]). These entry points must converge, not become separate replay implementations.
- `Projection` is an event-store/projection-keyed definition grain. Observer placement selects observer-capable silos. Kernel `Both` declarations lower to distinct namespaced and global definitions; kernel definitions are not rewindable. The replay handler also has kernel-specific zero-backup retention ([projection grain][projection-grain], [projection key][projection-key], [placement][placement], [kernel definitions][kernel-definitions], [handler][handler]). Ownership must cover global kernel paths without changing replayability policy.
- Job lookup and control are namespace-scoped: Stop/Resume/Delete validators check that namespace's manager, their handlers (including result-bearing variants) use it, snapshots use the manager, observable job lists read namespace storage, and step queries read namespace step storage. Returning a `NotSet` job ID alone does not make it discoverable or controllable from another namespace ([stop validation][stop-validation], [resume validation][resume-validation], [delete validation][delete-validation], [stop command][stop-command], [resume command][resume-command], [delete command][delete-command], [stop result][stop-result], [resume result][resume-result], [job views][job-views], [step view][step-view]).
- Live futures are source-namespace scoped, store their original event and paths, and are removed by ID after successful saves. Resolution can produce additional immediate sink writes; moving an observer cursor does not remove a stored future ([future identity][future-identity], [future persistence][future-persistence], [future removal][future-removal], [future resolution][future-resolution], [future saves][future-saves]).
- Projection replay currently finalizes even with failed steps/partitions, unlike reducer replay; only proven successful coverage can clear old failures. Live recovery starts at a failed partition's last-attempt sequence and clearing a failure can schedule catch-up. A scalar cutover cursor neither prevents those retries nor proves failure resolution ([partial replay behavior][partial-replay], [failure coverage][failure-coverage], [failure retry][failure-retry], [failure recovery][failure-recovery]). MongoDB bulk shutdown can explicitly return an unknown outcome, whereas SQL applies and saves within its write call; cancellation is not a universal durable drain receipt ([bulk uncertainty][bulk-uncertainty], [SQL write][sql-write]).
- Jobs and job steps use Cratis.Orleans storage providers; Chronicle's job-state converter handles derived state and typed request payloads. Existing namespace enumeration comes from the namespace grain, which also owns creation/removal ([job providers][job-providers], [job serialization][job-serialization], [namespace catalog][namespace-catalog]). These are extension points, not evidence that the proposed session protocol already exists.

The independently committed failing fixture `1b66dda33107ea9065cb4853f228178de1ccf5e4` demonstrates live routing diversion and repeated clearing with two namespace keys and real MongoDB collection-routing code, using substituted database operations. It is not a database or multi-silo test. The subsequent refusal commit `931434cf99de41a8b5268a4090d6c3192a6c4087` is an alternative, not this design's implementation or dependency.

[Decision 0014 on this baseline][generations-main] and its [proposed release-compatible revision][generations-revised] separate building from serving and require one authority per materialization. This record supplies that ownership for ordinary global replay **without** generation allocation, a generation lifecycle, binding-aware reads or a feature flag. It respects decision 0002's delivery-generation contract, decision 0006's bound provider-safe names, decision 0010's separation of event-type membership from connection capabilities, and decision 0011's acknowledged drain/admission rule; it does not enable their unrelated opt-in protocols ([0002][decision-0002], [0006][decision-0006], [0010][decision-0010], [0011][decision-0011]). No accepted record applies directly to these two documentation paths; these accepted contracts constrain the proposed implementation.

## Decision

A new non-reentrant `IGlobalProjectionReplayOwner` grain owns every rebuild of one global projection across all contributing namespaces. Namespace observers delegate replay admission and lifecycle messages to it and continue normal live delivery to the served container. The owner alone initializes an isolated destination, records source coverage, fences publication, promotes, records completion and authorizes retention. A second begin joins the same session and never clears anything. Publication preserves the existing served physical name; an acknowledged all-writer handover with a pre-publication time budget follows catch-up, not a namespace-local sink-wide replay toggle. Reconciliation after an uncertain outcome may exceed that budget.

### Owner, durable identity and delegation

The grain's canonical string key is `(EventStore, ProjectionId, Global)` encoded with the repository's compound-key convention. It deliberately excludes source namespace and initiating silo. Persist the resolved `(sink type, configuration, read-model type, container)` destination stamp and definition fingerprint in its session; a conflicting definition/destination cannot silently join. Queue a later rebuild only after the current session concludes, or abandon the unserved candidate after draining it. Never retarget an active session.

Use observer-role placement restricted to kernels advertising this protocol, not namespace affinity or a stateless worker. Orleans' directory gives one activation for this key and non-reentrant turns serialize competing begin/end decisions. No lifecycle method is `AlwaysInterleave`. Work progresses in separate turns; the owner never waits for a job that must call back into its held turn. This is the **coordination fence**, not proof that a database command issued by a lost activation has stopped.

Persist an owner control record and each session as **new internal job kinds** in the existing generic Cratis.Orleans job store. An internal state adapter uses a deterministic, collision-checked control-job identity for the complete owner key in the `NotSet` job scope; it is not a projection definition or an observer record. The control record retains the session pointer and monotonic attempt/owner epoch even while idle. Session job IDs are distinct; expose each through namespace-local references as specified below, and retain the canonical terminal journal until recovery and retention obligations conclude. Exclude control records from ordinary observer-job discovery and automatic successful-job deletion. Do not use a scan of unfinished namespace jobs as the uniqueness mechanism.

This design permits new opaque job payload types, but **no new database tables/columns, alterations to existing persisted record shapes, or event/read-model schema changes**. The adapter must provide conditional writes for this new control payload: MongoDB matches the complete previous control state/epoch in its job document; SQL compares the previous opaque job-state value in a transaction on the existing job row. This is a new adapter capability, not an assumption that ordinary job saves provide compare-and-swap. Lost save acknowledgments require rereading before another action. Prove conditional persistence and round trip on both job providers before relying on it; if that needs an additive Orleans extension, land it without changing required members of public interfaces or existing record schemas. A duplicate control identity with a different full key is an error, not hash-based aliasing. Large contributor/progress inventories use job-step payloads rather than an unbounded control record.

Before any sink operation, persist session ID, epoch, immutable destination/definition stamp, attempt-specific names, contributor inventory and phase. Proposed operational phases are `Preparing → Rebuilding → CatchingUp → Fencing → Publishing → Published → Releasing → Completed`; pre-publication failure may enter `Abandoning → Abandoned`. These are replay-job phases, not generation lifecycle states.

- `IProjections.Replay` and `ReplayObserver`, automatic full evolution and recommendations reach the owner **before** the namespace observer enters ordinary replay state. Preserve replayability, quarantine, disconnected and retirement admission checks; do not clear live observer positions or counts to start the separate build.
- `ProjectionReplayHandler` resolves scope first. Global begin/resume/flush/end/abandon delegate to the owner with session/epoch identity in internal calls. Cross-silo lifecycle broadcasts become idempotent notifications, not independent sink finalizers. Namespace jobs cannot promote, evict global context or run global retention.
- Begin persists admission and returns the same session `JobId` to concurrent compatible requests from A and B. Resume opens the recorded attempt without initialization. Flush acknowledges only that attempt's writer inventory. End requests publication; it cannot bypass coverage, failures or draining. Stale/duplicate callbacks have no state-changing effect, including after completion. Existing replay progress/completion waiting, including namespace `WaitForCompletion`, consult the joined owner session rather than treating the still-live observer as a completed replay. Session job pause/resume/cancel controls route through the owner; stopping a child cannot independently finalize the sink.
- Global `ReplayPartition` remains callable with its existing arguments and admission acknowledgment semantics. Initially it schedules/joins a complete global rebuild: rebuilding a shared key from only A could erase B's contribution. Do not run a destructive namespace-only partial replay on the shared sink. Namespaced partition replay is unchanged; narrower global repair is a later optimization requiring its own proof.

### Namespace-compatible job views and controls

Keep the canonical session J and control journal in `NotSet`, but create a **non-runnable namespace job reference with the same J** in each contributing namespace's existing job store. Its new internal request payload contains the owner key, canonical session ID and acknowledged view revision; it is not an independent replay job or an `IObserverJobRequest`. Create/acknowledge references before returning J to a caller or enlisting a new contributor. A conflicting namespace row with J fails admission, never aliases another job. Unrelated namespaces receive no reference and retain the existing not-found result. Do not ask Workbench, CLI or old `IProjections.Replay` clients to change namespace or interpret a new identifier.

Add a Core `GlobalReplayJobView`/resolver used by **all** job query, validator and command paths, leaving ordinary jobs on their current manager/storage route. Snapshots include the local reference, observable lists receive updates through namespace job storage, and `GetJobSteps` resolves its local reference to the canonical session's step view. Project canonical phase into existing `JobStatus`, `JobProgress` and status-history fields, deduplicate by J, and hide internal control/journal kinds. Show shared-session scope in existing Details; namespace views expose aggregate progress and caller-local steps, not other namespaces' event payloads. Updates are revisioned and may be eventual while running; begin/control responses and terminal completion wait for required reference acknowledgments. Owner recovery rebuilds stale references from the canonical journal before completing the call; a missing notification never turns a running replay into successful completion.

After the existing namespace authorization/existence checks, `StopJob`, `ResumeJob`, `DeleteJob` and the Stop/Resume `WithResult` variants resolve J to the owner, not to a runnable local job. Preserve existing DTOs, outcome types, validation text and ordinary-job semantics. Stop from any contributor pauses the **whole** session after draining its work, leaving live delivery served; resume joins that same session/attempt or follows uncertain-attempt recovery. A stop accepted before publication prevents publication until resumed; after publication intent, reconciliation/finish-forward cannot be canceled. A stop arriving then waits for a reconciled terminal state and returns the existing `JobIsCompleted` refusal through the result-bearing command; an unresolved outcome may time out/error, never falsely report a paused job. Resume of a still-running publishing job returns the existing `NotResumed` outcome. No new refusal enum or RPC is needed ([existing outcomes][job-outcomes]). Delete requests session-wide stop/abandon before publication or finish-forward after it, then removes all public references; it never deletes an active shared target or recovery journal. Persist deletion intent/tombstones so restart cannot resurrect a deleted view. Session completion/deletion is global, not one caller locally hiding a still-running shared job.

Automatic manager cleanup must recognize the reference kind as non-runnable and must not independently resume, delete, or mark it complete. Implement that through the new job-kind adapter and, if necessary, an additive Orleans hook; do not change required members of public interfaces. Namespace `WaitForCompletion` and job controls consult the same owner association. This is real stored job-view projection plus command routing, not only a UI overlay or a bare ID returned from `NotSet`.

### Explicit write destinations and one initialization

Keep `Live(served container)` and `Rebuild(session, attempt, physical container)` sink handles distinct, including pipeline caches, bulk buffers, joins/children, initial-state reads, futures and watermark checks. Candidate lookups must not read served state; source-event lookups and compliance context retain their actual source namespace. Candidate futures/changesets are attempt-local job data, not modifications to live namespace futures. A single namespace-local sequence number must not suppress another namespace's candidate writes: use `SinkWriteMode.Always` for admitted candidate application, with the source vector determining duplicate admission. Do not invent a synthetic event sequence number or use a scalar document watermark as cross-namespace coverage. An uncertain batch follows the fresh-attempt recovery rule below rather than reapplying potentially completed increments.

Every namespace's normal pipeline continues writing `Live`; no global begin calls the legacy mutable `BeginReplay` on that shared handle. Add an optional sink capability/internal adapter for explicitly addressed replay sessions; do not add required members to public user-implemented sink interfaces. Supply MongoDB, SQL and in-memory implementations with equivalent observable routing. An unknown provider cannot silently claim this capability.

Allocate a unique, length-safe, collision-checked physical candidate name per attempt; never reuse `replay-{served}` across owners. Create an empty candidate once, with the required schema/indexes. This is the single logical reset/begin: **there is no destructive clear on begin retry**. Persist preparation before admitting a writer. A repeated create may verify the same owned empty target; it may not clear an existing populated target. A conflicting/unverifiable object fails preparation. Resume and a second namespace begin reopen the prepared target. A lost create acknowledgment is reconciled from recorded physical identity before any write, or the unserved attempt is abandoned and a different name allocated.

### Input, ordering and catching up

The session replays the projection's configured event sequence in **every contributing namespace**, not only the caller's event log and not one synthetic merged log. For a log projection, this means every contributing namespace's log. Enumerate the namespace catalog, reconcile subscriptions and enlist every live writer through the owner before it can contribute. Include `NotSet` only if it is itself an actual source subscription; sink placement there does not make it an event source.

Persist the contributor set and an owner-managed membership revision. Namespace/subscription creation must enlist before first delivery; removal cannot discard a contributor while its session obligations exist. A namespace added during the build is replayed from its beginning and added to the vector. Reconcile catalog and enlisted writers before publication, with their admission closed. Namespace removal/history deletion during a build blocks publication until reconciled; never treat an unreadable log as empty. Previously forgotten/deleted history is not invented: inability to establish the contributor set is an explicit rebuild failure preserving served state.

For each `K = (Namespace, EventSequenceId)`, persist initial committed-storage tail `H[K]`, last fully flushed/scanned cursor `C[K]`, handled coverage and unresolved partition/future obligations. Read ascending sequence order within K using the admitted event types, filters and generation-delivery mode. Serialize candidate application across namespaces, in ordinal namespace order within persisted bounded rounds; parallel source reads may prefetch but cannot reorder application. Namespace sequence numbers are incomparable: neither their maximum nor wall-clock event timestamps form a global cursor. Cross-namespace noncommutative mappings have this replay order, not a promise to reconstruct the former live interleaving; live ordering is not changed by this fix.

Replay through H, then repeat finite tail-capture rounds above each C while ordinary live delivery keeps updating served. Read from durable event sequences rather than depending on a dual-write notification being delivered. Scan progress through filtered events is distinguished from applied progress; failed work below a cursor remains an obligation. A bulk acknowledgment alone is not full coverage. A candidate with unresolved **failed or uncertain writes** is not published over served data, even if a job has stopped. An ordinary deferred future is not a failed write: its durable transfer is part of coverage, not a reason to wait forever for a missing parent.

**Deliberate global-only failure-policy proposal:** this differs from today's projection finalization, which promotes despite failed projection work ([current behavior][partial-replay]). Report preparation/processing failure through existing job failure/`CompletedWithFailures` states and Details, leave served and its live recovery intact, and require explicit retry/resume rather than silently returning success or endlessly retrying. Successful replay calls, public signatures and default reads are unchanged; namespaced projections retain their current partial-promotion semantics. The MINOR justification is a safer failure result for the newly coordinated operation without a breaking contract/schema change, **not** a claim of identical failure behavior. Maintainer acceptance of this observable policy change remains open; if rejected, partial promotion needs a separate covered-versus-missing-partition design before implementation, not an undocumented fallback.

For handover, close **global materialization writer admission**, including new namespace enlistment, full/partition replay, catch-up/recovery jobs, future resolution/mutation and direct kernel projection paths. Drain admitted jobs, callbacks and all per-silo buffers; poll `StopAndDrain(TimeSpan.Zero)` in separate turns and require acknowledged drained/completed results. Then capture committed tails `N[K]`, finish the candidate through every N and flush it. Publication requires `C[K] >= N[K]` and every eligible operation accounted for as applied, excluded by the admitted policy, or durably deferred; no failed/uncertain writes may remain. Event appends themselves continue; delivery above N waits durably in the logs and resumes on served after publication. The fence covers deferred-state reconciliation as well as the physical swap; no hard maximum recovery pause is promised.

### Fenced publication plan: futures, failures and positions

Before publication intent, snapshot live futures and failure records **after** closing their mutation/retry admission and draining all old jobs/callbacks. Hold/reject administrative failure-clear/quarantine mutations through the same global observer gate until the plan is released; a separate command cannot invalidate the frozen inventory. Persist an immutable, paged `PublicationPlan` in the session's existing job-step payloads: frozen N/definition/membership revision, exact source records and hashes, candidate coverage evidence, deterministic action IDs and per-action acknowledgments. Plan construction never changes live obligations. No sink publication starts without the complete durable plan. A pre-publication abort discards only the plan/candidate and leaves live positions, futures and failures unchanged.

Candidate application records operation-level coverage after flush: source namespace/sequence, event type and generation, projection mapping/child path, parent identity and affected key. Match live futures using the **full stored operation identity**, not candidate future IDs, sequence alone or a document watermark; candidate IDs may differ and an event may have several effects. Include direct child application as well as resolved-future application: Z's deferred child can become a direct write when A's parent exists earlier in rebuild order. Ambiguous write/ledger acknowledgment abandons that candidate attempt; an optimistic cursor is not a substitute for evidence.

For each frozen live future, the plan either (a) removes its exact ID/payload because **that operation is incorporated** in the published candidate, or (b) preserves the original because it is not incorporated. Transfer candidate-only deferred obligations to the appropriate source namespace with IDs and full payloads fixed in the plan; match an existing live obligation by full identity instead of duplicating it. Candidate deferral is not grounds to remove an unincorporated live future. If a stored future cannot be matched or safely represented without losing effects, block publication rather than infer coverage. Do not use `RemoveAllForProjection` or acknowledge merely because its sequence is at/below N. Use a kernel-internal reconciliation path through the futures grain's existing ID-based persistence; update its in-memory list and evict/reinitialize affected pipeline futures trackers, never bypass a hot grain by deleting storage directly ([existing persistence/removal][future-persistence], [existing grain removal][future-removal]).

For each live failed-partition record, persist its ID, complete attempts/quarantine/hold/cursor snapshot and drained retry-job identities. Resolve/retire it only if the candidate proves the failed event's actual source, type/generation and **all eligible partition work through N**, including durable future transfer where processing deferred rather than failed. A frozen failure whose retry starts at s ≤ N must not survive with that obsolete retry range after publication. The plan removes its covered failure/skip marker, cancels its reminder and retires its old retry/catch-up jobs; subsequent catch-up begins strictly above N. A record containing a genuinely uncovered suffix above N is preserved with an exact rebase to the first unincorporated event using its existing cursor representation and attempt history, not blanket-cleared. If coverage cannot be proved for an overlapping range, or that rebase cannot be represented under the currently enabled recovery protocol, **block publication** instead of replaying s over the new model. Never enable the membership-recovery protocol or create a schema field just to express a rebase. Preserve unrelated/newer failures and observer-wide quarantine; adjusting derived failed counts is not an instruction to unquarantine the observer ([current proof checks][failure-coverage], [retry start][failure-retry], [resolution/catch-up][failure-recovery], [existing record fields][failure-record]).

After a **proven** sink publication, keep the gate closed and apply these actions, then update each namespace's live observer position to N and mark the plan complete before release. Each action is compare-by-ID-and-frozen-payload and idempotent: an already absent retired record or already installed transfer is acknowledged, a different record is a conflict and stays fenced. Store each acknowledgment durably; a crash between mutation and acknowledgment rereads that exact record and repeats/reconciles the same action, never constructs a new plan against half-mutated state. Recompute failure counts from remaining records; use recorded reminder/job IDs to finish cleanup even if the failure row disappeared first. Reject stale pre-fence resolver/retry callbacks by their recorded grant/job identity so they cannot recreate a removed future/failure or apply an old retry range. Recovery finishes the original plan forward before starting any live or future-resolving pipeline. Record/acknowledge pipeline cache eviction on every admitted silo as part of the plan; a restarted/rejoining silo recreates its handles/trackers before receiving another grant. Only after future/failure actions, cache invalidations and position writes are acknowledged may buffered events above N run; events and old retry/future effects already represented in the candidate must not run again.

### Provider publication and external-operation fence

Keep the served container name and direct-reader contract; introduce neither a view nor an Active binding. One container is the atomicity boundary, not several read models or sinks. The owner records expected physical identities and a publication intent before issuing any provider command.

- **MongoDB:** when retention requires a backup, prepare its unique empty collection and indexes/options **before fencing**, and preflight served size/copy throughput against the remaining handover budget. After writer drain, copy the stable served documents in bounded `_id`-ordered batches, without an unbounded server-side whole-collection copy command. Keep served in place during the copy. An unfenced pre-copy is not accepted as a consistent revert snapshot; without adding a change-capture/snapshot protocol, the full data copy necessarily consumes the fenced budget. Oversized collections fail the default preflight **before** pausing writers and require an explicit administrative budget extension, not a promise that every collection fits 30 seconds. Promote the candidate with **one same-database `renameCollection` to served with `dropTarget: true`**, not served-to-revert followed by candidate-to-served. This native replacement is the proposed publication point; supported topology/version tests must prove old-or-new visibility and unchanged read operators. Record candidate/served collection UUIDs in the job journal: after lost acknowledgment, served having the candidate UUID proves publication; an unrelated UUID is an error. No follow-up replay of the rename can move a different attempt's data. Change streams/cursors invalidated by replacement must rebind/reset through the normal query path; a request may retry, never recreate a temporarily missing served container. Empty-but-proven rebuilds are valid; row count is not coverage.
- **SQL:** use an exclusive materialization gate and one provider transaction for served-to-revert, candidate-to-served, constraint/index renaming and the existing replay-promotion receipt. Keep physical names unique per attempt; do not change the receipt schema. Transaction commit is publication. On a lost response, reconcile the receipt and physical table identities on the primary connection before retry/release. Prove the protocol on PostgreSQL, SQL Server and single-node SQLite, including readers using another connection and, for supported clustered providers, another silo; do not assume transactional DDL behaves identically on every provider. A provider failing that proof blocks its implementation, not a fallback to two exposed renames.

**Concrete writer admission, not a fictional database-session fence:** install a global-only admission wrapper where `ProjectionPipelineManager` constructs each pipeline, and require live handling, catch-up/retry, replay, future resolution and direct kernel invocation to enter it. Its grant spans the **whole pipeline batch/bulk window**, including future-store mutations and completion callbacks, not just the main `ApplyChanges`. `SaveChanges` already uses main, folded-future and separate immediate-future write paths, while physical sinks can buffer/flush internally; all must remain inside the grant ([construction][pipeline], [save paths][future-saves], [bulk completion][bulk-uncertainty], [SQL apply][sql-write]). Direct sink lifecycle/DDL runs only through owner journaled control actions. Add assertions/specs preventing a global write/future mutation through an unregistered path; do not assume that intercepting one sink overload fences the rest.

Before a batch starts, persist a grant in existing job-step payloads: owner epoch, source/pipeline key, silo incarnation, work/job ID, target attempt and source range. Batches arriving outside an active rebuild still require admission so begin can settle any pre-existing grant. Acknowledge completion only after all pipeline mutations, final flush and callbacks finish with **known** outcomes; `EndBulk` returning unknown outcome leaves the grant unsettled. Persist completion before returning the acknowledgment. Fencing closes new grants and polls existing work until each grant is settled; stale grants cannot start another batch or retry a callback under an old epoch. Bound bulk windows to work chunks that can drain; do not grant an unbounded job permission to keep issuing new writes forever. Cost: two durable journal updates and admission/completion round trips per batch/window, plus bounded journal retention, not a write per document. Batching must be measured for global projections; namespaced pipelines retain their existing path.

The journal records **kernel work grants**, not server operation/session IDs; no existing MongoDB or SQL method is claimed to offer a universal external-operation fence. In healthy execution, awaited writes and fully acknowledged flushes settle grants. After silo loss, an unknown write result or a lost completion acknowledgment, automatic publication is suspended unless a surviving writer can definitively settle the original work. A possibly applied candidate batch causes fresh-attempt recovery. An unsettled **served** grant cannot be made safe by allocating a fresh candidate or expiring a lease: a delayed old live write could hit the replacement served name.

The conservative first implementation requires an administrative quiescence barrier for an unprovable served grant: stop the recorded producer incarnation (including its retry loop), prevent rejoin, and verify at the database that its issued commands/transactions have finished or been canceled and drained. If sessions cannot be attributed to that producer, fence/stop all kernel writers to the affected database and verify that broader barrier; do not guess from process death or a driver timeout. No extra database inspection/cancellation privilege is silently required of normal kernel credentials. Persist the verified barrier acknowledgment in the owner journal before admitting a replacement writer or publication. Without that proof the session remains stopped/fenced with diagnostics, not successful. This intentionally sacrifices **unattended recovery availability**, not normal live/replay isolation. Acceptance of that operational restriction is an open maintainer decision; stronger automatic database fencing needs a separately proven provider design. Never reissue uncertain DDL or drop its source while it may still execute; reconcile MongoDB identities/SQL receipts before finish-forward.

The default **pre-publication work budget** is 30 seconds from admission closure, covering drain, tail application, plan preparation, backup copying and the decision to issue promotion. Check it between bounded copy/write batches and before promotion; before reaching the limit stop issuing work, drain outstanding commands, abandon the incomplete backup/candidate as appropriate and reopen served without publication. Do not silently retry an oversized backup in successive pauses. Preflight rejection and deadline abort are explicit stopped/failed job outcomes, not successful replay. Cancellation/drain may outlast the deadline, and once promotion is issued an unknown outcome or post-publication reconciliation may also outlast it: **30 seconds is not a hard bound on all delivery unavailability**. Large backups require an explicitly approved administrative budget extension; the API shape stays unchanged, but the pause/copy cost and lack of automatic success at the default budget are documented. Maintainer confirmation of this conservative bound remains open.

### Recovery, bookkeeping and rollout

On activation reload the control record/session, fence stale epochs and discover the admitted jobs/steps. Resume acknowledged coverage on the same candidate only when its writes and durable checkpoints reconcile. Because this design adds no per-row cursor vector or atomic write/checkpoint schema, an uncertain candidate batch is **not** replayed over potentially applied increments: abandon that physical attempt after draining and rebuild a fresh unique attempt from the beginning under the same logical session/job. Previously populated targets are never reset. This is safe restart recovery, not a claim of lossless incremental resume at every crash boundary.

Before publication, failure/abandonment leaves served untouched and live delivery available except while a fence is being reconciled. After a proven publication, recovery finishes forward: replay the recorded future/failure reconciliation plan, update namespace positions, record one occurrence, release writers, project terminal job views and notify completion. Lost completion responses reread the journal. Only successful publication, reconciliation and release permit successful completion of the public session job; a failed/abandoned job may terminate with its existing non-success status. Job preparation/namespace child completion is not replay success.

Store global replay context, occurrence and retention ownership in `NotSet`, using existing record shapes. Keep contributor vectors and the completion/deduplication journal in the session job, not extra fields in `ReplayContext` or `ReadModelOccurrence`. Reconcile duplicate occurrence writes by session's unique context timestamp and revert name before insertion. The owner applies retention once, only to completed owned backups with no active recovery obligation; never deletes served or any active attempt. Preserve the application's configured replay retention and kernel zero-backup policy. Namespace-scoped records remain readable but cannot authorize shared-container cleanup.

**Legacy sessions:** do not guess a global vector from namespace-local progress. Inventory every namespace's jobs, contexts and occurrences plus the shared replay/promoting/backup objects. Stop and acknowledged-drain old global replay jobs and their external operations, preserve ambiguous containers/records, disable their automatic resume/finalizers, then begin a new coordinated build from durable logs. Do not promote a legacy candidate or relabel its source-local occurrence as complete global coverage. An unresolved legacy operation blocks only that materialization's new replay; provide an administrative diagnostic and repair procedure. Namespaced sessions resume unchanged.

**Rolling upgrade:** new global replay admission is suspended during a mixed-protocol cluster; live served delivery and namespaced replay continue. Before the first new silo joins, deployment orchestration freezes global replay triggers (manual, recommendations and automatic evolution), drains legacy global sessions, and prevents old binaries from starting another. Old kernels cannot be made safe by an RPC they do not implement. After the last old silo leaves, verify a homogeneous observer/job/writer capability set, reconcile legacy inventory and reopen global replay automatically; this is not a generations flag or application opt-in. A version/capability check on new nodes alone is insufficient: deployment admission must exclude an old binary rejoining once new sessions exist. Downgrade requires draining new sessions and their retained job payloads first; never let an older job deserializer resume them. If deployment cannot enforce that boundary, coordinated replay must wait rather than mutate a shared sink unsafely.

### Compatibility and release

Target a **MINOR** release: coordinated cross-namespace live replay is additive behavior and introduces internal job kinds, while retaining all existing public signatures, commands, generated RPC names and fields. Do not require a generations release, feature flag, version selector, new database schema/migration or changed event/read-model/observer record. No existing protobuf field is renumbered; any diagnostics added to the wire are additive and generated from Core. Do not add abstract members to public user-implemented interfaces.

Versionless reads and the physical served name stay unchanged. Preserve automatic definition-evolution defaults ([current default][evolution-default]), replayability admission and successful replay/job completion meaning; global requests now return/join one session through namespace-local job references rather than several competing namespace jobs. The proposed global failure policy explicitly differs from legacy partial promotion, and the default backup budget can stop a replay instead of promoting; both require the maintainer confirmations below and user-facing MINOR release notes. Do not describe these failure-path differences as identical default behavior. `ReplayPartition` remains available with the safe broader rebuild described above. Namespaced replay and reducers are outside this change. Kernel-owned globals and the global half of `Both` use the same owner when replay is internally admitted; this does not make non-rewindable definitions publicly replayable or retain kernel backups unnecessarily. New protocol kernels use the fix by default after homogeneous-cluster preflight, not a default-off safety feature.

The existing refusal-only patch could ship independently as PATCH, but is **not** the selected delivery. Splitting implementation commits must not expose half-wired global admission in intermediate releases. The proposed revision of 0014 can later reuse this owner key, contributor inventory, admission/drain and recovery machinery, add a generation to candidate addressing and replace legacy-name publication with opt-in immutable bindings. This record does not import or implement its generation lifecycle, approval policy, following rollback or read-binding schema.

## Options considered

- **One global owner with explicit destinations:** chosen; scope matches the shared materialization and every contributing namespace is covered.
- **Refuse global replay:** bounds corruption but removes a useful operation and cannot rebuild the model; rejected as the final fix. Retain the red reproduction, not refusal assertions as acceptance criteria.
- **Namespace owners with namespaced shadows or a distributed begin lock:** neither establishes complete global coverage nor keeps shared live routing safe; isolated fragments cannot independently replace one shared model.
- **Ship all generations first:** provides a broader publication model but unnecessarily couples this bug fix to new read contracts and lifecycle/schema work; deferred to 0014.
- **Reuse the current MongoDB two-rename publication:** exposes a missing-name interval to direct readers; rejected. Binding/view conversion would alter default read behavior and is not the compatibility bridge selected here.

## Default if unanswered

Do not merge or enable an incomplete coordination path. Leave current behavior unchanged by this documentation-only proposal, with the known corruption risk explicit; operators should avoid global replay until the proper fix ships. The cost is unavailable safe global rebuild, not silent acceptance of namespace-local publication. This record does not accept or ship the separate refusal branch.

## Consequences

The owner aligns replay, coverage and retention with materialization scope and is a stepping stone to one owner per generated materialization. Live writes remain useful during a potentially long rebuild. Costs are extra isolated storage, namespace job references, operation-coverage/plan data, durable batch grants, an all-namespace job/vector, a budgeted pre-publication delivery pause, potentially expensive MongoDB backup copying and explicit deployment/recovery restrictions. Uncertain-command recovery or post-publication reconciliation can exceed the budget and may require an administrative database-writer barrier; the proposal does not promise unattended recovery or arbitrary-size backups within 30 seconds. Safety does not depend on external side effects happening exactly once. An uncertain database operation may delay recovery; correctness is not exchanged for an optimistic timeout.
