Cratis Chronicle's testing helpers let you check event appends and read model state without starting a separate kernel. Start with the in-process scenario your client supports, then use an integration test against a running kernel for behavior that depends on a connection, delivery to observers (event consumers), or persistent storage. In .NET, `Cratis.Chronicle.XUnit.Integration` provides that integration boundary with a running kernel and MongoDB through Testcontainers.

:::note[Client coverage]
Choose helpers for your client rather than assuming the same APIs or kernel behavior in every language:

| Client | In-process testing support |
|---|---|
| .NET | `Cratis.Chronicle.Testing` provides `EventScenario`, `ReadModelScenario<T>`, `ReactorScenario<T>` and `OccurrenceScenario<THandler>`. Integration fixtures are a separate package. |
| Kotlin | `io.cratis:chronicle-testing` provides `EventScenario` for appends and `ReadModelScenario` for reducers, not projection or reactor scenarios. See the [Kotlin testing guide](/chronicle/clients/kotlin/guides/testing/). |
| Java | `EventScenario` from `io.cratis.chronicle.testing` covers appends; the read-model examples call reducers directly. |
| TypeScript | `@cratis/chronicle/testing` exports `EventScenario` for appends, `ReadModelScenario` for reducers and supported projections, and `ReactorScenario` for reactor side effects. |
| Elixir | `Chronicle.Testing` starts a real `Chronicle.Client` against an in-memory kernel with `start_supervised_client/1` or `use Chronicle.Testing.Case`. `Chronicle.Testing.Assertions` provides helpers such as `assert_appended/3`. Use `Chronicle.Testing.Integration` for a live kernel. |

Examples use client tabs; unsupported tabs identify limits of that client's helper. The package and fixture setup below is for .NET.
:::

In .NET, use [Cratis Specifications](/testing-with-cratis/) to separate setup, the operation under test, and its expected outcome. Seed existing events in `Establish()` or a scenario's `Given` builder. Run the operation in `Because()`, then use each `[Fact]` to check an appended event, read model value, or side effect.

## Choosing the right test boundary

Choose the boundary from the question the spec needs to answer. A read model calculation does not need a database, but checking that its sink, the component that stores the model, wrote a document does. These are the .NET starting points:

| What to prove | Start with | What it does not prove |
|---|---|---|
| Event appends, constraint violations, sequencing | `EventScenario` | Network serialization, kernel connection, persistent storage writes |
| Read model projection or reducer logic | `ReadModelScenario<T>` | Sink writes, MongoDB queries, change stream subscription |
| Reactor side effects and event ordering | `ReactorScenario<T>` | Network observer registration, kernel event dispatch, automatic redelivery |
| Actual storage writes, kernel connectivity, change streams | `ChronicleInProcessFixture` / `ChronicleOutOfProcessFixture` | Isolation from other tests that share the same fixture host |

`ReactorScenario<T>` delivers each supplied event once. To check idempotence, meaning that handling the same event again does not repeat an unwanted side effect, write a spec that supplies the event twice.

The .NET integration fixtures available in `Cratis.Chronicle.XUnit.Integration` are:

- `ChronicleInProcessFixture`: runs the kernel in the test process and MongoDB through Testcontainers.
- `ChronicleOutOfProcessFixture`: runs the kernel in a separate container, also using Testcontainers.
- `ChronicleClientFixture`: provides the client-side base for integration tests.
- `ChronicleOrleansFixture`: hosts an Orleans-based kernel for testing Chronicle's own internals.

Only the in-process and out-of-process fixtures are documented here; the others are for framework or advanced scenarios.

## .NET packages

```xml
<PackageReference Include="Cratis.Specifications.XUnit" />
<PackageReference Include="Cratis.Chronicle.Testing" />
```

Use these references for Chronicle-only specs. `Cratis.Chronicle.Testing` brings in `Cratis.Arc` and `Cratis.Arc.Core`, including the ASP.NET Core shared framework, so you do not need separate Arc references unless you are overriding their versions.

### Application hosts that reference Testing

If your application host references `Cratis.Chronicle.Testing`, register the Chronicle client as usual. Testing keeps kernel commands and queries out of the application's Arc endpoints without changing application commands, queries, or authorization policies. Registration order between Arc and Chronicle does not matter.

A dependency-injection container that also hosts the kernel keeps its kernel commands and queries. The kernel still needs them to dispatch its own work through Arc. This includes the in-process silo used by the xUnit fixtures. Chronicle identifies that host through the kernel's administrator authorization policy, regardless of registration order.

For custom Arc providers, register individual `ICommandHandlerProvider` and `IQueryPerformerProvider` implementations. Do not replace the `IInstancesOf<ICommandHandlerProvider>` or `IInstancesOf<IQueryPerformerProvider>` collections. Testing rejects a replacement during client registration if it is already present, or at host startup if added afterward. The error explains how to register individual providers instead.

To add services during Chronicle client registration, implement `IChronicleClientServices` with a public parameterless constructor. Chronicle discovers it through the type universe and calls it for both web and non-web clients. Make its registrations safe to repeat: a host can register the client more than once. These hooks apply to the client container, not the isolated kernel pipeline.

### Matching versions

Match `Cratis.Chronicle.Testing` to your Chronicle client release. Chronicle and Arc have independent release numbers, so check that Testing release's NuGet dependencies for its Arc requirements rather than matching the numbers. If you use the `Cratis` meta-package, check its dependencies too.

If you need to override the Arc dependency with a compatible newer release, pin both `Cratis.Arc` and `Cratis.Arc.Core` to the same version in `Directory.Packages.props` and reference them directly in the test project. Alternatively, enable `CentralPackageTransitivePinningEnabled` there so the central pins apply to transitive dependencies. Align any other Arc runtime packages with that version, do not go below Testing's declared dependencies, and verify your scenarios after an override.

Use `Cratis.Testing` instead of `Cratis.Chronicle.Testing` when the same spec also tests Arc commands.

Application command execution scopes, including Chronicle transactions, wrap the application command in the outer Arc pipeline. The scenario's internal append pipeline excludes your application's `ICommandExecutionScope` implementations; they do not run again for each append. You therefore do not need to register their dependencies with the scenario harness.

## Explicit artifacts and lifetime

Artifacts are the event types, reducers, reactors, constraints, and migrations that a scenario needs to find. To choose them for one .NET run, pass `Defaults` configured with `ChronicleOptions.ExplicitArtifacts`. Those registrations feed scenario processing, not just discovery. A plain `ReactorScenario<T>` requires explicit reactor nomination; it does not discover an arbitrary class by its method signatures.

<ChronicleClientTabs snippet="testing/explicit-artifacts/scenarios" />

Create separate defaults and options for independent runs. Each scenario store captures its artifact registrations when created; changing shared options later does not change that store. Do not mutate `Defaults.Instance` or the default artifact provider to configure one run.

For xUnit integration tests, configure explicit artifacts before creating the fixture host, client, or store. The registrations live as long as the host: reusing it keeps the first snapshot, even after rediscovery. Derived fixtures in the same closed `ChronicleClientFixture<TChronicleFixture>` family share that host; separate hosts capture independent snapshots.

A fixture that overrides `ChronicleFixture.UsesPerContextMongoDBHost` to return `true` creates a fresh host for each test context. Each context then captures its own artifact snapshot.

Use `AutoDiscoverArtifacts = false` to disable assembly discovery while keeping explicit nominations and automatic client registration. `AutoDiscoverAndRegister = false` is different: it requires you to discover and register manually.

See the [.NET explicit registration reference](../clients/dotnet/explicit-artifacts) for peer conflicts, migration binding and custom-provider limits.

## .NET testing store identity

If your code distinguishes event stores or namespaces, give the test store the identity it expects. Construct `EventStoreForTesting(serviceProvider, artifacts, options, time, eventStore, @namespace, capabilities: null)` or `Defaults(artifacts, serviceProvider, options, time, eventStore, @namespace)`.

Pass an `EventStoreName` for `eventStore` and an `EventStoreNamespaceName` for `@namespace`. `EventStoreForTesting` requires a `ScenarioTime` clock; `Defaults` accepts a null clock.

The resulting store uses that identity for its `Name`, `Namespace`, event log, and unit-of-work operations. Pass the defaults to `ReadModelScenario`, `ReactorScenario` or `OccurrenceScenario` to use the same identity there. If you supply an explicit store to a reactor scenario, it uses that store's identity, including in delivered event contexts.

`EventScenario` has separate identity parameters; it does not inherit the defaults' store identity. See [EventScenario](events/scenario.mdx#per-run-artifacts-and-constraints) for its constructors.

Each store instance has isolated in-memory storage, even when identities match. Existing `EventStoreForTesting` and `Defaults` overloads still create their store as `testing` in namespace `default`.

## What the harness stands in for

The .NET helpers use Chronicle's projection and reducer engines, constraint evaluation, and reactor dispatch with its in-memory storage. By default, each scenario owns a store shared by its event log, named sequences, and in-process services. They bypass gRPC and the observer lifecycle, so a passing scenario does not establish network delivery or persistent storage behavior.

Use the [integration fixtures](#choosing-the-right-test-boundary) to check MongoDB sink writes, observer registration, or change stream checkpoints against a running kernel. In those tests, `IEventAppendCollection` records the client's append outcomes; it does not replace assertions on stored documents or observer state. Follow [Event append collection](event-append-collection) to set up a fixture and wait for a reactor's follow-up append.

Continue with [Test a slice](/chronicle/scenarios/test-a-slice/) to combine these boundaries in a slice, or [Testing with Cratis](/testing-with-cratis/) for the testing model across Specifications, Arc, and full stack slices.
