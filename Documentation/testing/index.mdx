Chronicle provides in-process scenarios for testing event appends and read models without a running kernel. The .NET testing library also covers reactor side effects and offers integration fixtures. `Cratis.Chronicle.XUnit.Integration` exercises the full client and kernel stack against MongoDB via Testcontainers when you need to prove storage, network, or full-stack behavior.

:::note[Client coverage]
The clients offer different in-process boundaries:

- **.NET:** `Cratis.Chronicle.Testing` provides `EventScenario`, `ReadModelScenario<T>` and `ReactorScenario<T>` for C# specs, alongside the separate integration fixtures described below.
- **Kotlin:** `io.cratis:chronicle-testing` provides `EventScenario` for appends and `ReadModelScenario` for reducers, but not projection or reactor scenarios. See the [Kotlin testing guide](/chronicle/clients/kotlin/guides/testing/).
- **Java:** `EventScenario` from `io.cratis.chronicle.testing` covers appends; the read-model examples call reducers directly.
- **TypeScript:** `@cratis/chronicle/testing` exports `EventScenario` for appends and `ReadModelScenario` for reducers and supported projections. It does not provide a reactor scenario; some .NET-only workflows below have explicit unsupported tabs.
- **Elixir:** No Chronicle-specific in-process scenarios; use the client against a running event store to test a Chronicle-backed slice. Unsupported tabs mark unavailable workflows.

Examples in this section use client tabs where the workflow is supported. Package instructions, named fixture APIs, and other .NET-only details are labeled as such.
:::

In .NET applications, Chronicle tests usually sit inside [Cratis Specifications](/testing-with-cratis/). That makes the event-sourced shape explicit: `Establish()` or a scenario's `Given` builder seeds facts that already happened, `Because()` appends or provides the event under test, and each `[Fact]` asserts the new facts, read model state, or side effect.

## Choosing the right test boundary

Start with the in-process scenarios your client supports. They test the slice without infrastructure; use a kernel-backed test when you need to prove behavior the client's scenario does not cover. The table below names the .NET scenarios and integration fixtures:

| What to prove | Start with | What it does not prove |
|---|---|---|
| Event appends, constraint violations, sequencing | `EventScenario` | Network serialization, kernel connection, storage write |
| Read model projection or reducer logic | `ReadModelScenario<T>` | Sink writes, MongoDB queries, change stream subscription |
| Reactor side effects and event ordering | `ReactorScenario<T>` | Network observer registration, kernel event dispatch, redelivery — each event is handed to the reactor once, so a repeated delivery (and the idempotence it requires) needs a spec that delivers the event twice |
| Actual storage writes, kernel connectivity, change streams | `ChronicleInProcessFixture` / `ChronicleOutOfProcessFixture` | Client isolation—the kernel is shared across tests |

The .NET integration fixtures available in `Cratis.Chronicle.XUnit.Integration` are:

- `ChronicleInProcessFixture` — an in-process Chronicle kernel with MongoDB via Testcontainers.
- `ChronicleOutOfProcessFixture` — a Chronicle kernel in a separate container, also using Testcontainers.
- `ChronicleClientFixture` — a base for integration tests that only need a Chronicle client reference.
- `ChronicleOrleansFixture` — an Orleans-based Chronicle kernel for testing Chronicle's own kernel internals.

Only the in-process and out-of-process fixtures are documented here; the others are for framework or advanced scenarios.

## .NET packages

```xml
<PackageReference Include="Cratis.Specifications.XUnit" />
<PackageReference Include="Cratis.Chronicle.Testing" />
```

`Cratis.Chronicle.Testing` brings in `Cratis.Arc` and `Cratis.Arc.Core` (version 22.19.1 or later), including the ASP.NET Core shared framework. Projects pinned to an older Arc version must upgrade. You do not need to reference Arc separately for Chronicle-only tests.

Use `Cratis.Testing` instead of `Cratis.Chronicle.Testing` when the same spec also tests Arc commands.

Application command execution scopes, including Chronicle transactions, belong to the outer Arc command pipeline. The in-process scenario helpers do not discover or invoke your application's `ICommandExecutionScope` implementations when processing an event append. Your application scopes still run around the application command; you do not need to register their dependencies with the scenario harness.

## What the harness stands in for

The .NET in-process scenario helpers run the real projection and reducer engines, constraint evaluation, and reactor dispatch — but substitute in-memory storage for the kernel's gRPC boundary and persistent event log. That substitution is what makes them fast and isolated, and it's also the boundary they don't cross.

When a .NET test needs to prove behavior **across** that boundary — that a projection's sink writes actually landed in MongoDB, that a reactor registered its observer subscription with a running kernel, that change streams fired and advanced the checkpoint — reach for the [integration fixtures](#choosing-the-right-test-boundary) and `IEventAppendCollection` instead. Those exercise the full client-to-kernel-to-storage stack.

For a worked example of `IEventAppendCollection` and the integration fixtures, see [Event append collection](event-append-collection). For the full slice testing story — how `/chronicle/scenarios/test-a-slice/` fits with the in-process helpers and the integration boundary — see [Test a slice](/chronicle/scenarios/test-a-slice/).

For the bigger testing model across Specifications, Arc, Chronicle, and full stack slices, see [Testing with Cratis](/testing-with-cratis/).
