<a id="eventscenario"></a>

Cratis Chronicle's .NET `EventScenario` tests code that appends to `IEventLog` or `IEventSequence` without a server, database, or network. It runs the kernel's append path against in-memory storage, so you can check event content and constraint outcomes before writing an integration test.

In a [Cratis Specification](/testing-with-cratis/), seed history with `EventScenario.Given`, append the events under test with `EventScenario.When`, then assert on the returned `AppendResult` or the event sequence. Call `EventLog.Append` or `EventSequence.Append` directly when you need other overload parameters.

The API names and kernel-backed behavior below describe .NET. Client tabs show alternatives where supported; other clients do not necessarily run the same kernel code.

## Why use EventScenario

Use `EventScenario` when the question is what your code appends or how it handles a rejected append. You can seed the history that makes a constraint relevant, attempt the next event, and inspect the outcome in one isolated spec. Use the [integration fixtures](../index.mdx#choosing-the-right-test-boundary) when the question depends on a kernel connection, observer delivery, or persistent storage.

## Installation

For a .NET spec, add `Cratis.Chronicle.Testing` and the Specifications test runner package to your test project:

```bash
dotnet add package Cratis.Specifications.XUnit
dotnet add package Cratis.Chronicle.Testing
```

`EventLog` and `EventSequence` expose the same selected sequence and share its in-memory storage. The default scenario uses `EventSequenceId.Log`. Pass `EventLog` to code that expects an event log, or `EventSequence` when it expects the generic `IEventSequence` interface.

Seeded events receive increasing sequence numbers and pass through the append path, including constraint checks. If a seed is rejected, `Given` throws `GivenEventAppendFailed` so the spec cannot continue with incomplete setup. Keep the operation you want to test out of `Given`; its result belongs in the act phase.

## Acting with When

Use `When` to attempt the append you want to assert on. It uses the same in-memory append path as `Given`, but returns an `AppendResult` for your assertions instead of treating rejection as a setup failure:

<ChronicleClientTabs snippet="testing/events/scenario/when-builder" />

Use the [append assertions](assertions) to check that result. If you supply several events to one `When`, the builder appends them in order and stops at the first failure, returning that failed result without attempting the remaining events. If all succeed, it returns the final append's result. This is a series of individual appends, not an atomic batch.

## Reading and observing read models

Read the state produced by your events through `scenario.ReadModels`. It builds projection and reducer results from the same storage used by `Given`, `When`, and direct `EventLog` appends, including events needed for child collections and joins. `Defaults.Instance.EventStore.ReadModels` belongs to a different store, so it cannot read this scenario's history.

For example, suppose your discovered `ProjectSummary` projects `ProjectOpened` and `ProjectRenamed`.
In an existing specification with an `EventScenario scenario` and an `EventSourceId projectId`:

1. Seed the project with `await scenario.Given.ForEventSource(projectId).Events(new ProjectOpened("Original"));`.
2. Act with `await scenario.When.ForEventSource(projectId).Events(new ProjectRenamed("Renamed"));`.
3. Read its current state with `var project = await scenario.ReadModels.GetInstanceById<ProjectSummary>(projectId.Value);`.
   The projected name is now `Renamed`. Use `await scenario.ReadModels.GetInstances<ProjectSummary>()`
   to read the collection instead.

A model-bound parent with a `[ChildrenFrom<T>]` collection works the same way. Seed the parent and
append each child to its own event source, supplying the parent identifier in the child event's
configured `parentKey` property. Reading the parent returns both children with their distinct keys.

To observe the collection, import `System.Reactive.Linq` and subscribe, for example with
`using var subscription = scenario.ReadModels.Observe<ProjectSummary>().Subscribe(projects => Console.WriteLine(projects.Count()));`.
The subscription receives the initial collection and receives it again after a successful append
changes the result. Await an emission signal in a specification rather than sleeping before an
assertion. Passive read models and event-target projections cannot be observed.

These reads use the in-process projection and reducer processors, not a running observer or a
production read-model sink. They do not cover production sink encryption or observer lifecycle.
Use [ReadModelScenario](../read-models/scenario.mdx) to specify a read model's transformations directly.

## Closing and reopening streams

`EventScenario` runs the same closed-stream check as the kernel. A scope closed with `EventSequence.CompleteStream`, or by an event type declared with `[ClosesStream]`, rejects later appends to it with a constraint violation named `closed-stream`.

Closing event types are found by the same discovery as other constraints. Append the closing event and assert on the rejection of a covered event:

Within one `AppendMany`, a covered event after a closing event is refused, and close, reopen, then a covered event succeeds. A manual closure on the same scope also refuses the reopening event, because a `ReopenedBy` event only lifts its own constraint's closure. See [Closing streams](../../closing-streams/index.mdx) for the rules.

## PII compliance

Personal data marked with `[PII]` passes through the kernel's encryption handler before entering in-memory event storage. Reads decrypt those values with keys held only by that scenario. The encryption schema follows the stored event generation's markings, using discovered compliance metadata providers. An undiscovered generation raises `EventSchemaNotDiscovered`; a provider that cannot be activated fails with its identity and underlying cause.

Use append-result and event-sequence assertions, or read through `EventLog` and `EventSequence`, to check successful appends and the values returned to readers. A plaintext round trip alone does not prove encryption at rest. Chronicle's own harness regressions inspect the protected content internally, but that raw-content inspection is not a public consumer assertion API.

The keys stay in memory and are not shared between scenarios. These tests cover event encryption and decryption, not database persistence, read-model sink encryption, or key-store durability. `EventScenario` does not support subject erasure. Test erasure against a running kernel and the intended storage provider; event [redaction](#redacting-events), covered below, is a different operation.

## Redacting events

`EventSequence.Redact(sequenceNumber, reason)` and `EventSequence.Redact(eventSourceId, reason, eventTypes)` run synchronously inside the scenario, through the same System-sequence reactor the kernel uses. When the call returns, the targeted events are `EventRedacted` in their original slots with their original event source. The stored payload keeps the reason and the original event type.

<ChronicleClientTabs snippet="testing/events/scenario/redact" />

Passing event types limits an event-source redaction to those types; passing none redacts every event of the source. Redaction works on the event log and on named sequences, and each scenario instance is isolated. See [Redaction](../../events/redaction.mdx) for the production behavior.

Only the two redaction requests are served. Other operations that run through the System sequence, such as `Revise`, fail with "… is not available in test scenarios". The redaction request itself is not recorded in a System sequence, and observers are not replayed because the scenario hosts none.

## Per-run artifacts and constraints

If your spec supplies generated event types or constraints at runtime, give it its own `IClientArtifactsProvider`. Create `new Defaults(artifacts)` and pass those defaults to `new EventScenario(defaults)`. The supplied provider controls event type discovery, serialization, and automatic constraint discovery instead of the process-wide default.

To replace automatic constraint discovery, pass an `ICanProvideConstraints` as the second argument. In the `(Defaults, ICanProvideConstraints?)` overload, `null` still discovers constraints from the supplied defaults. To disable constraints, pass an empty provider whose `Provide()` returns an empty list. In the older explicit-provider constructors, `null` means no constraints; constructors without run-specific defaults still use the shared artifact provider.

To select an identity while keeping automatic discovery, use `new EventScenario(eventSequenceId, eventStoreName, namespaceName)`. For run-specific artifacts, use `new EventScenario(defaults, eventSequenceId, eventStoreName, namespaceName)`. Neither overload takes a constraint provider; the existing explicit-provider overload still treats `null` as no constraints.

## Event generations

When you append an older event generation, discovered migrations run and store the migrated generations alongside the original content. The generation an ordinary read delivers is a separate choice. If a migrator has constructor dependencies, supply them through the service provider passed to `Defaults`.

## Isolation

Create a new `EventScenario` for each specification. Each instance starts with an empty sequence at sequence number zero, then accumulates state across calls. Dispose it after the specification to release its in-memory resources.

Keep runtime-supplied event types and constraints isolated too: use [per-run defaults](#per-run-artifacts-and-constraints) instead of changing the shared artifact provider.
