# ReactorScenario

`ReactorScenario<TReactor>` is a lightweight, in-process test utility that lets you verify reactor side-effects without a running Chronicle server, gRPC transport, or observer registration.

It activates a fresh instance of `TReactor` from the provided service provider and routes events directly through the `ReactorInvoker` — the same execution path used in production.

In a [Cratis Specification](/testing-with-cratis/), the event delivered to the reactor is the **when**, and the side effect captured by a mock, fake, or test double is the **then**. The scenario keeps that test in-process while still using the production reactor invocation path.

## Start with a pure function

A reactor that returns its side effects — the command or event that should follow — is a pure function of `(event, read model)`. Test that logic by constructing the reactor and calling the handler directly: no Chronicle server, no service provider, no mocks.

<ChronicleClientTabs snippet="testing/reactors/pure-function" />

Keep these as your default. They are the fastest specs, and because they assert your reactor's contract rather than Chronicle's internals, they keep passing as the framework evolves. A reactor that instead injects `IEventLog`/`ICommandPipeline` and acts in the method body cannot be tested this way — returning side effects is what makes the pure-function test possible.

## Reach for ReactorScenario to prove the wiring

Some behavior is the framework's contract, not your logic, and a direct call cannot reach it:

- Chronicle materializes the right read model for a handler-method parameter (including a custom `ICanResolveReadModelKey`);
- a constructor or method-parameter dependency resolves as expected;
- the right handler dispatches for a given event type;
- the produced side effect flows through the real invoker.

For those, `ReactorScenario<TReactor>` drives your reactor through the same in-process invocation path as production — accurate, but without a live Chronicle server, so specs stay fast. Its `ShouldHaveProduced<T>` assertion uses the same "then" as the pure-function test, so a spec graduates from one to the other without relearning how to assert.

## Installation

`ReactorScenario<TReactor>` is in the `Cratis.Chronicle.Testing` NuGet package:

```bash
dotnet add package Cratis.Specifications.XUnit
dotnet add package Cratis.Chronicle.Testing
```

## Basic usage

<ChronicleClientTabs snippet="testing/reactors/scenario/basic" />

`Given` is a fluent builder: call `ForEventSource(id)` to specify the event source, then `Events(...)` to route events through the reactor in order.

## Routed givens

When the reactor reads stream metadata from `EventContext`, supply that metadata with `OnStream(...)` before `Events(...)`:

<ChronicleClientTabs snippet="testing/reactors/scenario/routed-events" />

The handler receives the source type, stream type, and stream identifier you specified. Omitted or `null` values use `EventSourceType.Default`, `EventStreamType.All`, and `EventStreamId.Default`. Without `OnStream`, existing givens keep those defaults.

`OnStream` returns a new builder: you can reuse the original without changing its route. The route does not affect read models seeded with `ReadModel(...)`. The non-generic scenario for fluent registrations also accepts `OnStream` and passes the route to its callbacks.

## Observer filters

A class-based reactor with an `[EventSourceType]` or `[EventStreamType]` filter handles only matching givens. A typed `[FromEventSource<T>(stream)]` filter resolves both values from the registered event source definition:

<ChronicleClientTabs snippet="testing/reactors/scenario/observer-filters" />

The first two givens are ignored; only the matching payment produces a side effect. A reactor without these filters receives events on any route. `EventSourceType.Unspecified` and `EventStreamType.All` do not narrow delivery; an explicit `EventSourceType.Default` filter matches only that literal source type. Stream identifiers do not narrow these filters.

Every given event advances the sequence number, even if the filter skips it, matching the kernel's append-time numbering. Tag filters (`FilterEventsByTag`) are not applied: scenario givens do not carry tags. Use a kernel-backed integration specification to verify tag-based delivery.

## Injecting dependencies

Register the mocks and stubs the reactor depends on through the scenario's `Services` collection — the same `IServiceCollection` you use to configure an application. Logging is registered for you, so a reactor that injects `ILogger<T>` activates without any extra setup:

<ChronicleClientTabs snippet="testing/reactors/scenario/services" />

`Services` resolves both the reactor's constructor dependencies and any service-typed handler-method parameters. If a dependency is missing, the scenario throws `CannotActivateReactorForScenario`, naming the type it could not resolve.

You can also pass a pre-built `IServiceProvider` to the constructor when you need full control over registration:

<ChronicleClientTabs snippet="testing/reactors/scenario/injecting-dependencies" />

When neither is used, the scenario builds a provider from `Services` (with logging registered).

## Per-run artifacts

Pass a `Defaults` built with an `IClientArtifactsProvider` to use event types and other client artifacts
from one test run instead of the process-wide registry. The scenario's in-process event store uses the
same provider; a second scenario can supply a different registry without inheriting the first one's artifacts.
The optional service provider, side-effect handlers, and event store can still be supplied with this overload.

## Fluent registrations (.NET)

For a reactor configured with `ChronicleOptions.ExplicitArtifacts.RegisterReactor(id, define)`, use
`ReactorScenario(id, defaults)` without a type argument. Construct the defaults with your
`IClientArtifactsProvider`, optional service provider, and options as its three arguments.
`InMemoryClientArtifactsProvider` lets you supply just the event types and other artifacts needed
by that run, without assembly discovery.

The scenario builds the named fluent definition once against the run's event types. Drive it with
`Given.ForEventSource(id).Events(...)`; each call awaits every applicable callback and keeps event
sequence numbers contiguous across calls. Assert on the effects captured by your callbacks or test
doubles. An unknown reactor identifier throws `UnknownReactorId`, and a callback failure propagates
to the caller.

This scenario tests fluent handler behavior, not observer delivery, replay, quarantine, or transport
registration. Use a kernel-backed integration test for those boundaries. The existing generic
`ReactorScenario<TReactor>` remains the choice for class-based reactors and its produced-side-effect assertions.

## Asserting produced side effects

When a reactor returns a built-in event side effect or an asynchronous command, assert it directly with `ShouldHaveProduced<T>`, with no mocks or event-store wiring:

<ChronicleClientTabs snippet="testing/reactors/scenario/produced-side-effects" />

The scenario records everything the reactor returns — flattening collections and unwrapping cross-stream event wrappers — so `ShouldHaveProduced<T>()`, its predicate overload, and `ShouldNotHaveProduced<T>()` all work against events and commands alike. The raw list is available on `Produced`.

For a custom synchronous return type, register an `IReactorSideEffectHandler` in `scenario.Services` whose `CanHandleReturnType(Type)` claims that type, as you would in the host. The scenario records the result rather than executing the handler. Unclaimed synchronous types are rejected, just as they are in production; built-in event return types need no extra registration.

## Asserting produced destinations

An event's contents can be right while its destination is wrong. Use `ProducedEvents` to inspect each returned event together with its event source identifier, source type, stream type, and stream identifier:

<ChronicleClientTabs snippet="testing/reactors/scenario/produced-destinations" />

`ShouldHaveProduced<TEvent>(eventSourceId)` checks the destination source. The two-argument predicate overload receives a `ProducedEvent` and the typed event, so you can check both destination and contents. A failing destination assertion lists the recorded destinations. `Produced` and the existing content-only assertions remain unchanged; commands and other non-event side effects appear only in `Produced`.

Bare returned events use the reactor's context values: the source identifier comes from `ICanProvideEventSourceId` when implemented, otherwise from the triggering event. Reactor-level source and stream attributes and `ICanProvideEventStreamId` supply the remaining route values. Unset values use event-log defaults, not the triggering event's source or stream types or stream identifier. An `EventForEventSourceId` uses its own destination metadata instead, including an event source definition when specified. Collections preserve each event's destination.

The scenario records these events without appending them. If you supply explicit side-effect handlers, assert against those handlers instead; neither recording list is populated.

## Notes

- A fresh instance of `TReactor` is activated from the service provider for each `Events(...)` call, matching the production behavior where a new scope is created per event batch.
- Event handling uses the same `ReactorInvoker` as in production, so convention-based dispatch — where each handler method is matched by its event parameter type — works identically.
- The `.Received()` assertions in the examples come from [NSubstitute](https://nsubstitute.github.io/). Any mocking framework works.
