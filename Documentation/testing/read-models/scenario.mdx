# ReadModelScenario

A read model scenario lets you check projection or reducer output without a running Chronicle server or database. The examples below use client tabs when a workflow is available; the .NET-only options and behavior are identified in the prose.

In .NET, `ReadModelScenario<TReadModel>` auto-detects how the read model is backed — by a reducer, a fluent projection, or a model-bound projection — and routes events through the appropriate engine.

In a .NET [Cratis Specification](/testing-with-cratis/), the event history is the **given**, `Because()` feeds that history through the scenario, and the read model properties are the **then**.

## Why use ReadModelScenario

Integration tests against a live database are useful for proving storage and network behavior, but cost more to run. An in-process scenario tests the supported projection or reducer logic without that infrastructure; it does not replace a kernel-backed integration test.

## .NET installation

`ReadModelScenario<TReadModel>` is in the `Cratis.Chronicle.Testing` NuGet package:

```bash
dotnet add package Cratis.Specifications.XUnit
dotnet add package Cratis.Chronicle.Testing
```

## Basic usage

<ChronicleClientTabs snippet="testing/read-models/scenario/basic" />

Feed events for an event source through the scenario, then assert against the resulting read model. In .NET, use `Given.ForEventSource(id).Events(...)` and read `Instance`; TypeScript uses `given.forEventSource(id).events(...)` and awaits `instance`.

## Event input serialization

In the .NET scenario, seeded events for projection-backed read models pass through the `IEventSerializer` supplied by
`Defaults`, then through Chronicle's schema-aware JSON conversion. Projections therefore consume
the event's serialized representation, including serializer-owned property names, rather than a reflection
walk of the CLR object. This also avoids reflecting over the parent links inside a nonempty `JsonObject`
event property. Serialized content is re-read as case-sensitive JSON data before conversion, so a serializer's
case-insensitive CLR member matching cannot collapse distinct dictionary keys. This preserves JSON data
spelling; it is not a verification of the network marshaller or wire compatibility.

This fidelity applies to **event input** for fluent and model-bound projections. Reducers still receive typed
events directly. The optional initial read model state goes through the same schema-aware conversion: it is
serialized, re-read as case-sensitive JSON data, and converted against the read model's schema, so an initial
state may contain nonempty `JsonObject` values. Reducers receive the initial state as the typed instance.

## Pre-seeding read model instances

In .NET, use `Given.ForEventSourceId(id).ReadModel(instance)` to register a pre-built read model instance for
production code under test that calls `IReadModels.GetInstanceById`. This lets you test a service that
fetches a read model by ID without replaying events through a full projection:

<ChronicleClientTabs snippet="testing/read-models/scenario/preseeding-instances" />

`scenario.ReadModels` returns an `IReadModels` instance that intercepts `GetInstanceById` for registered
instances and delegates everything else to the real read model implementation. Only what you registered comes
back from it: the rest of that surface is the production one and wants a running Chronicle, so reading the
instances the scenario itself materialized means `Instances` or `InstanceForEventSourceId`, not `GetInstances`.

## Auto-detection

In .NET, `ReadModelScenario<TReadModel>` looks up a handler in the client artifacts registry — the same reflection-based
discovery Chronicle itself uses, over the project-referenced and package-referenced assemblies, resolved once per
process — in this order:

1. **Reducer** — a class implementing `IReducerFor<TReadModel>`.
2. **Fluent projection** — a class implementing `IProjectionFor<TReadModel>`.
3. **Model-bound projection** — `TReadModel` itself carries `[FromEvent<T>]` or `[Key]` attributes.

If none are found, `NoReadModelHandlerFound` is thrown.

## Define a projection for one run (.NET)

When a spec generates artifacts at runtime or needs a different mapping for the same read model, pass
`new Defaults(artifactsProvider)` to `new ReadModelScenario<MyReadModel>(null, defaults)` and call
`WithProjection(builder => builder.From<MyEvent>(from => from.Set(model => model.Name).To(e => e.Name)))`.
The callback uses `IProjectionBuilderFor<MyReadModel>` and replaces discovered projection selection for that
scenario only. Each scenario can have its own `Defaults`, artifact registry, and fluent definition; no wire
contract or process-wide projection registration is needed. The scenario's event store also uses that registry.

## Asking what Chronicle registered

In .NET, that registry is not private to the scenario. `scenario.ClientArtifactsProvider` hands out the very
`IClientArtifactsProvider` the scenario resolved its handler from, so a spec can ask what Chronicle registered
instead of re-deriving it by reflecting over its own assemblies:

<ChronicleClientTabs snippet="testing/read-models/scenario/registered-artifacts" />

It exposes every artifact kind Chronicle discovers — `EventTypes`, `Projections`, `ModelBoundProjections`,
`Reactors`, `ReadModelReactors`, `Reducers`, `ReactorMiddlewares`, `ConstraintTypes`, `UniqueConstraints`,
`UniqueEventTypeConstraints`, `RemoveConstraintEventTypes`, `EventTypeMigrators`, `EventSeeders`, and the
compliance and additional-event-information providers — including the classifications the registry draws
itself. An event type with a property-level `[Unique]` lands in `UniqueConstraints`, while one with a
class-level `[Unique]` lands in `UniqueEventTypeConstraints`; asking the registry gets that distinction right
without reimplementing it.

The property is read-only: reading it neither triggers nor alters registration, and every read hands out the
same instance.

> [!NOTE]
> The same registry is reachable without a scenario, as `Defaults.Instance.ClientArtifactsProvider`. Use that
> when the spec is not a `ReadModelScenario<TReadModel>` — it is the same process-wide instance.

## Strict event subscription

In .NET, the scenario mirrors the production projection engine by default, which filters an event source's stream down to the types the projection subscribes to — so seeding an unrelated audit or marker event is silently ignored. When you would rather be told, `WithStrictEventSubscription()` turns that silent skip into an `UnsubscribedEventSeeded` naming the offending event type:

This applies to projection-backed read models. A reducer only invokes the handlers it declares, so an unsubscribed seeded event is inherently a no-op there, exactly as at runtime.

## Child collections

In .NET, `[ChildrenFrom<TEvent>]` child collections are materialized the same way they are at runtime, so a spec can assert the child rows directly on `Instance`. The child `key` may be any value the runtime accepts:

- `string`, `int`/`long`, `bool`, `enum`, `Guid`
- the temporal primitives `DateOnly`, `TimeOnly`, `DateTime`, `DateTimeOffset`
- a `ConceptAs<T>` over any of the above

Both same-event-source children (parent and child events share one event source) and cross-stream children (child events on their own event source, linked with `parentKey`) are supported, and two events carrying the same child key merge into a single child — matching the real sink.

## Multiple instances (joins and cross-stream)

In .NET, `Instance` returns a single threaded result, which is ambiguous when events span more than one event source — for example a `[Join]`, whose join-source event materializes a second instance. For those specs, assert against a specific instance with `InstanceForEventSourceId`, which resolves the intended instance from the sink even when another source's event was seeded first:

<ChronicleClientTabs snippet="testing/read-models/scenario/multiple-instances" />

`Instances` exposes every materialized instance keyed by its event source id. Both are populated for projections; reducers are single-instance and expose their result through `Instance`.

If more than one instance materializes and you read `Instance`, it throws `MultipleInstancesMaterialized` rather than silently returning a blended object — a signal to reach for `InstanceForEventSourceId` or `Instances` instead.

> [!IMPORTANT]
> `InstanceForEventSourceId(id)` selects the right instance no matter the seed order, but a `[Join]` **value** is only populated when the joined-in (source) stream is seeded **before** the entity that joins it. The entity pulls the joined value as its own event is processed; a join-source event seeded afterwards resolves the entity's identity but leaves the joined value unset. Seed the source stream first, as the example above does.

## What the harness stands in for

The .NET scenario runs in-process, making this tier fast enough to use on every build; the price is that some of what a deployed Chronicle does is stood in for. None of it is a defect — but a spec whose subject lives in a substituted layer passes just as confidently as one whose subject does not, so it is worth knowing which is which before you rely on a green.

These are substituted for every scenario, whatever your read model looks like:

| Layer | What runs instead |
|-------|-------------------|
| The read model sink | An in-memory sink. Documents are held as objects and round-tripped through JSON, never through the encoding a real store uses. |
| Storage and the observer lifecycle | Nothing at all. There are no observers, no partitions, no failed-partition state, and no replay or rewind. |
| The event context | The sequence number is the event's position in what you seeded, and `Occurred` is a fixed base plus one tick per event. A reducer gets a context built differently again, with no `Occurred`. |
| The document key mapping | The `_id` ↔ identifier-property mapping a store performs is applied in C# instead. |
| The read model definition | Identifier, container and display name come straight off the CLR type and there are no indexes, where a deployed Chronicle uses your naming policy and the indexes you declared. |
| The client read surface | `scenario.ReadModels` is the production client surface; its read side wants a running Chronicle and refuses rather than answering. Read what the scenario materialized through `Instance`, `Instances` or `InstanceForEventSourceId`. |

Four more are substituted only for certain shapes — and because the harness can see which of those shapes your read model has, it tells you.

## Asking what a scenario substituted

In .NET, `Substitutions` reports the substituted layers your read model's own shape reaches. It is derived from the read model and its projection alone, so you can read it before seeding anything:

<ChronicleClientTabs snippet="testing/read-models/scenario/substitutions" />

| `Layer` | Reported when |
|---------|---------------|
| `Sink` | the document key is not a `Guid`, or the read model carries a class-level `[RemovedWith]` |
| `Compliance` | the read model's schema carries compliance metadata — a `[PII]` member, or a member typed as a `[PII]` concept |
| `JoinKeyResolution` | the read model or one of its child collections carries a `[Join]` |
| `DeferredKeyHandling` | a child collection takes its parent key from an event property rather than from the event source id |

`Compliance` is worth singling out, because it is the one whose absence looks most like success. A deployed Chronicle encrypts a read model's `[PII]` members on the way into the sink and releases them on the way out, keyed by the subject the event resolved to. `ReadModelScenario` projects and reads plaintext, so a value that a running system would store as ciphertext — or hand back empty because the subject was erased — reads back here exactly as you wrote it. Assertions about the *value* still hold; assertions about it being protected, about which subject it is keyed by, or about what erasure does to it, do not. `EventScenario` exercises event encryption and release, but does not verify read-model sink protection or support erasure. Cover read-model encryption, subject-key ownership at the sink, and erasure against a real kernel and store. This substitution is reported for both projection-backed and reducer-backed read models, and strict fidelity rejects both.

An empty list means nothing shape-dependent is being stood in for. Anything in the list is a claim your in-process spec cannot settle on its own — cover it against a real kernel and a real store as well.

To make that binding rather than advisory, opt in to strict fidelity. A read model that reaches a substituted layer then raises `ReadModelDependsOnSubstitutedLayer` instead of returning a result, so a suite can turn it on everywhere and have only the shapes that genuinely need a second tier change color:

## .NET notes

- `Instance` is `null` until `Given` is called, or if no events were processed.
- Each `Given.ForEventSource(id).Events(...)` call applies events to the specified event source. Call it multiple times to simulate events from different event sources.
- `Given.ForEventSourceId(id)` is an alias for `ForEventSource(id)` that also exposes `.ReadModel(instance)` for pre-seeding.
- Cratis Specifications provides `ShouldEqual`, `ShouldBeTrue`, `ShouldBeNull`, and related assertions. If you use Shouldly or FluentAssertions, translate the assertions to your project's style.
