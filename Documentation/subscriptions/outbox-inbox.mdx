# Outbox and Inbox

Cratis Chronicle uses an outbox and inbox to separate publishing an event from processing it in another service. The source publishes to its outbox, the kernel forwards subscribed events into the consumer's inbox, and the consumer processes that stored copy.

## The Outbox

The **outbox** is the source store's event sequence for publishing events to other stores. In C#, its well-known identifier is `EventSequenceId.Outbox`. A subscription selects which event types to forward from that sequence.

You do not need to create the outbox separately. Append events to it as you would to another event sequence. Appending to the source's ordinary event log alone does not publish an event to subscribers.

## The Inbox

An **inbox** stores the forwarded events in the consuming store. Each source has its own sequence, named `inbox-{sourceEventStore}`. For example, subscribing to `fulfillment-service` sends its matching events to `inbox-fulfillment-service` in the target store.

Forwarding preserves the source event's append tags, event-source identity, and stream-route metadata. Tag-filtered inbox observers can select those events. Events forwarded by earlier releases that dropped tags remain untagged; upgrading does not backfill them. [Compliance and PII](compliance-and-pii.md) explains how forwarding preserves subject identity and handles encryption keys.

## Lifecycle

The kernel stores subscription definitions for the target event store, independently of a client session. They survive client disconnections and are re-established when the kernel starts.

You can register the same definition under the same subscription ID at application startup without creating a duplicate. Reusing the ID with a changed definition updates the subscription; an ID alone does not make every registration identical.

## Event Flow

```text
Source event store               Target event store
─────────────────                ─────────────────
      Outbox                           Inbox
   ┌─────────┐   [subscription]   ┌─────────┐
   │ event A │ ─────────────────▶ │ event A │
   │ event B │ ─────────────────▶ │ event B │
   └─────────┘                    └─────────┘
```

The kernel's forwarding subscriber, `EventStoreSubscriptionObserverSubscriber`, receives events from the source outbox observer and appends them to the target inbox. Delivery into the inbox and processing by the consumer have separate progress: an event can have arrived even when a derived view has not updated.

A fresh subscription forwards matching retained outbox history from sequence number zero. Reconnecting the same subscription identity can instead resume from its saved forwarding progress. Replaying that source forwarding observer can append events to the inbox again; replaying a consumer inbox observer reprocesses rows already there. See [Subscription recovery](recovery) before choosing an operation.

## Reactors, Projections, and Reducers on the Inbox

Route each consumer observer to the inbox for the source it handles. In C#, [implicit subscriptions](implicit-subscriptions) infer that source from `[EventStore]` on the event contracts. With [explicit subscriptions](explicit-subscriptions), configure the observer's source or sequence separately; registering forwarding does not change a handler's input sequence.
