# Implicit Event Store Subscriptions

Cratis Chronicle can register forwarding and route C# observers automatically when their event contracts identify a source event store. Use implicit subscriptions when services share those contracts: the consumer handles the events it needs, and Chronicle routes it to that source's inbox without a separate subscription API call.

:::note[Client coverage]
This page describes C# attributes and NuGet packaging. For Kotlin, Elixir, or TypeScript, use the client APIs described in [explicit subscriptions](./explicit-subscriptions) rather than applying the C# setup.
:::

The source still needs to publish events to its outbox. Adding `[EventStore]` to a contract identifies its origin; it does not publish events or move them out of the source's ordinary event log.

## How Implicit Subscriptions Work

During client registration, Chronicle gathers the event types consumed by reactors, projections, and reducers and groups them by source store. For external sources, it registers a persistent forwarding subscription on the kernel and routes each observer to the corresponding inbox in the consumer's store.

For reactors and reducers using automatic sequence inference, one declared external source selects its inbox. A source matching the current store, or no declared source, selects the log. Fluent projections infer an inbox from one declared source even when it names the current store. These rules do not locate local publications. When producers reuse their own attributed contracts, explicitly select the sequence containing those publications, normally `EventSequenceId.Outbox`, as described below.

## Assembly-Level Configuration with `[EventStore]`

When contracts in an assembly share one source, apply `[EventStore]` once in `GlobalUsings.cs` or `AssemblyInfo.cs`. A type-level attribute takes precedence if a particular contract needs a different source.

### The `.Contracts` Project Pattern

Create a separate, thin project with the naming convention `{ServiceName}.Events.Contracts` to publish your event types:

```text
FulfillmentService.Events.Contracts/
├── AssemblyInfo.cs
├── ShipmentDispatched.cs
├── ShipmentFailed.cs
└── FulfillmentService.Events.Contracts.csproj
```

Keep the `.Contracts` project focused on event definitions and the dependencies needed to describe them. Consumers can then reference the contracts without taking a dependency on the source service's implementation.

### Project File Configuration

Set the package identity and metadata in the `.Contracts` project file. The example uses placeholder package versions; choose versions that match your application:

```xml
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <TargetFramework>net9.0</TargetFramework>
    <AssemblyName>FulfillmentService.Events.Contracts</AssemblyName>
    <PackageId>FulfillmentService.Events.Contracts</PackageId>
    <PackageVersion>1.0.0</PackageVersion>
    <Title>Fulfillment Service Event Contracts</Title>
    <Description>Shared event types published by FulfillmentService</Description>
    <Authors>Your Team</Authors>
    <RepositoryUrl>https://github.com/yourorg/FulfillmentService</RepositoryUrl>
    <RepositoryType>git</RepositoryType>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="Cratis.Chronicle" Version="1.0.0" />
  </ItemGroup>

</Project>
```

### Assembly-Level Attribute Definition

In your `.Contracts` project, create an **AssemblyInfo.cs** file or use **GlobalUsings.cs** to apply `[EventStore]` once:

### Option 1: Using AssemblyInfo.cs

```text
// FulfillmentService.Events.Contracts/AssemblyInfo.cs
using Cratis.Chronicle.Events;

[assembly: EventStore("fulfillment-service")]
```

### Option 2: Using GlobalUsings.cs (Recommended)

```text
// FulfillmentService.Events.Contracts/GlobalUsings.cs
global using System;
global using System.Collections.Generic;
global using Cratis.Chronicle.Events;

[assembly: EventStore("fulfillment-service")]
```

### Option 3: Using `<AssemblyAttribute>` in the .csproj (No C# File Needed)

You can apply the assembly-level `[EventStore]` attribute directly from your `.csproj`, without creating any C# file. Add an `<AssemblyAttribute>` item to your project:

```xml
<ItemGroup>
  <AssemblyAttribute Include="Cratis.Chronicle.Events.EventStoreAttribute">
    <_Parameter1>fulfillment-service</_Parameter1>
  </AssemblyAttribute>
</ItemGroup>
```

MSBuild emits `[assembly: Cratis.Chronicle.Events.EventStoreAttribute("fulfillment-service")]` in the generated `AssemblyInfo.cs` file, so you do not need a separate C# file for the attribute.

> **Note:** This approach requires `<GenerateAssemblyInfo>` to be `true` (the default). If your project sets `<GenerateAssemblyInfo>false</GenerateAssemblyInfo>`, the `<AssemblyAttribute>` item will have no effect since it relies on the auto-generated file.

### Projections

A fluent projection can build the consumer's view from forwarded events. Without an explicit sequence, one declared source selects `inbox-{sourceEventStore}` even when that source is the current store:

<ChronicleClientTabs snippet="subscriptions/implicit-subscriptions/projection" />

If the source service reuses these attributed contracts in its own fluent projection, select the sequence containing its publications. Normally, call `FromEventSequence(EventSequenceId.Outbox)` on the projection builder. These contracts register as public events, which the kernel rejects in the log. `EventSequenceId` is in the `Cratis.Chronicle.EventSequences` namespace. Without this explicit selection, the projection reads the inbox named for its own store, not its local publications.

After publishing an event to the source outbox, check for its copy in the consumer inbox and then for the read-model update. If the event arrives but the view does not change, investigate the projection rather than recreating the forwarding subscription.

## Subscription Lifecycle

Once registered, the forwarding definition survives client disconnections and kernel restarts. The kernel can continue forwarding matching outbox events while the consumer is offline. Consumer observers still need to run to process the inbox events.

Removing the consumer's handlers does not automatically remove the stored forwarding subscription. Implicit registrations use the source store name as the subscription ID. If the relationship is no longer needed, remove the consuming observers and remove the stored subscription through the [explicit subscription API](explicit-subscriptions).

## Mixing Event Stores Is Not Allowed

With automatic sequence inference, multiple distinct declared `[EventStore]` sources in one observer throw `MultipleEventStoresDefined` during registration:

<ChronicleClientTabs snippet="subscriptions/implicit-subscriptions/mixing-not-allowed" />

Unannotated local event types have no declared source and are ignored by this check. Mixing them with one external source does not throw: automatic routing selects that source's inbox, so the observer does not receive local events from its own log. Avoid mixing local and external handlers in one observer.

## Schema Registration and Metadata

Event type registration includes the source event store name in its metadata. Keep that name aligned with the publisher's configured store: Chronicle uses it to select the source outbox and derive the consumer's `inbox-{sourceEventStore}` sequence.

## When to Use Implicit Subscriptions

Use implicit subscriptions when the shared C# contracts describe where events come from and the consumer's observers determine which types it needs. Only those consumed types are selected for forwarding, not every type in the source store.

Use [explicit subscriptions](explicit-subscriptions) when the consumer needs to choose a stable subscription ID, manage the relationship at runtime, or select types through the API instead. For either approach, [Subscription recovery](recovery.mdx) helps locate a delivery failure before you replay events.
