An explicit subscription in Cratis Chronicle forwards selected event types from a source store's outbox into the consuming store's inbox. Register it through the client API when you need to choose the subscription ID, control which types arrive, or create and remove the relationship at runtime.

The source must publish the events to its Chronicle outbox. Explicit registration does not import events directly from an external system; see [Outbox and Inbox](outbox-inbox) for the publication and delivery flow.

:::note[Client APIs]
C# uses `eventStore.Subscriptions`. Elixir exposes `Chronicle.subscribe_to_event_store/3,4` and `Chronicle.unsubscribe_from_event_store/1,2`; TypeScript uses `store.subscriptions.subscribe` and `.unsubscribe`; Kotlin/Java exposes `store.eventStoreSubscriptions.subscribe`. Use each client's registration conventions. The ASP.NET Core startup patterns below apply to C#.
:::

## Setting Up an Explicit Subscription

In the consuming application, use the `Subscriptions` property on its `IEventStore`. The source name identifies the store to read from; the `IEventStore` you call determines where forwarded events are stored:

<ChronicleClientTabs snippet="subscriptions/explicit-subscriptions/basic" />

The three arguments are:

| Argument | Description |
|---|---|
| Subscription ID | A stable, unique string that identifies this subscription within the target event store |
| Source event store | The name of the event store whose outbox to subscribe to |
| Configuration callback | Optional — filters which event types to forward |

### Subscription ID

Choose a stable subscription ID that is unique within the target event store. The kernel stores the definition under this ID. Repeating an identical registration does not create another subscription; changing the definition under the same ID updates that subscription.

## Pin the Generation Your Application Understands

An event type's generation identifies a version of its schema. To keep forwarding on the generation your C# application understands, opt in per subscription with `WithGenerationDelivery(EventGenerationDelivery.Pinned)`.

A generic `WithEventType<T>()` pins the generation declared by that event type. An identifier-only declaration resolves to the single generation your client knows. Use the identifier-and-generation overload when the identifier is ambiguous or you have no .NET type for that contract.

<ChronicleClientTabs snippet="subscriptions/explicit-subscriptions/pinned-generations" />

Register the exact generation in both stores before subscribing, and upgrade every kernel node (silo) before opting in. The kernel validates the entire pinned request before changing definitions. Missing generations or conflicting generations for one event type fail registration; waiting longer for readiness cannot resolve them.

The source forwarding observer delivers the pinned generation for live events, catch-up, replay, and retries. The inbox stores that delivered generation rather than the event's original append generation. Protected values are decrypted using the selected source schema and encrypted again on the target append. Forwarding does not restore an erased target subject's key. If the target later loses the pinned schema registration, forwarding fails at that event without appending it or advancing past it.

Pins and the delivery policy survive restarts, reconnects, and identical registrations. To change them, register a deliberately changed definition under the same subscription ID. The kernel updates the source observer without an unsubscribe gap. Inspect `GetAll()` to read `GenerationDelivery` and `EventTypePins`, alongside the id-only `EventTypes`.

The default is `Compatibility`. Existing subscriptions continue to send generation 1 in their registration and retain their forwarding behavior. The global client generation-delivery option does not opt subscriptions into pinned delivery.

## Removing a Subscription

<ChronicleClientTabs snippet="subscriptions/explicit-subscriptions/unsubscribe" />

Calling `Unsubscribe` requests removal of the persistent definition. Once the kernel processes that removal, forwarding stops. Existing inbox events remain available to consumers; unsubscribing does not delete them.

Removing a subscription stops forwarding but does not erase its forwarding observer's progress. Recreating the same subscription identity can resume from that retained checkpoint, including catching up on events published while it was disconnected. A new identity with no retained progress starts from the beginning of the retained source outbox.

See [Subscription recovery](recovery) before replaying either the forwarding observer or a consumer inbox observer; these operations have different effects.

Identical registrations leave existing definitions unchanged. A deliberately changed registration updates
the same subscription, including its exact pins and delivery policy when you opt in.

## Subscription Lifecycle

The kernel persists the definition under the ID you supply and manages forwarding independently of the client connection. Subscriptions survive client disconnections and are re-established when the kernel starts, even if the consuming application is offline. Remove a subscription explicitly when the relationship is no longer needed.

## When to Use Explicit Subscriptions

Choose explicit subscriptions when the consumer owns the forwarding decision: which event types it needs, what to call the relationship, and when to remove it. Event contracts do not need to be distributed through a shared NuGet package.

For a C# application that shares contracts carrying `[EventStore]` attributes, [implicit subscriptions](implicit-subscriptions) can infer the source and register the types its observers consume. They do not mean that every event type in the source store is forwarded.
