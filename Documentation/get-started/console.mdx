title: Add Chronicle to a console app

Start with one book. Your console process connects to Chronicle, appends the fact that the book arrived, then queries until it can print the projected book. The kernel runs separately in Docker; it stores the event and builds the read model in its bundled MongoDB. You don't need Arc, a web host, or a dependency-injection container.

## Before you start

- Install the .NET 10 SDK and Docker, with Docker running.
- [Start Chronicle](/chronicle/get-started/#start-chronicle) using `cratis/chronicle:19.115.3-development` and wait for `Healthy`.
- Keep that container running throughout this guide and the tutorial. The application connects to `chronicle://localhost:35000` with the built-in development connection. Use this setup only on your own machine.

This path uses the released .NET package `Cratis.Chronicle` **19.115.3** and the matching development image. Other client tabs illustrate client-owned equivalents; the complete file layout and commands here are for .NET.

## Create the project

Run these commands from the directory where you keep your projects:

```shell
dotnet new console --framework net10.0 --name ChronicleQuickstart
cd ChronicleQuickstart
dotnet add package Cratis.Chronicle --version 19.115.3
```

The project contains a generated `Program.cs`. Replace it below; don't leave its top-level `Hello, World!` statement alongside the new entrypoint. All files in this guide go directly beside `ChronicleQuickstart.csproj`, without a namespace.

```text
Appended GetStartedBookAdded for <book-id>

```

`Quickstart` is the event-store name, not the project name. The default namespace keeps this example's events and read models together. The helper queries `GetStartedBook` through Chronicle; the default MongoDB sink materializes it as `GetStartedBooks`. No MongoDB driver or exposed database port is required for this query.

### Why poll after appending?

Appending commits a fact to the event log. Projection processing happens separately, so the read model is **eventually consistent**. `GetInstances<T>()` reads the current materialized state; it does **not** wait for projection catch-up. Even a healthy kernel and a successful append don't mean the view is ready.

The helper queries for this run's id and expected fields, then checks again on a 250 ms timer until it succeeds or reaches a 60-second observation deadline. It doesn't sleep for an assumed projection duration. The deadline bounds this example's wait, not Chronicle's delivery time or the preceding connection and append. A timed-out `WaitAsync` stops the local wait; it doesn't cancel server-side processing. Connection and query errors propagate rather than being hidden as retries.

## If you don't see the projected book

- **Connection or TLS failure:** check `docker ps`, the health command, and `docker logs chronicle`. Use `ChronicleConnectionString.Development` for this local image. Don't disable certificate validation for a production connection.
- **Container won't start:** check whether the name `chronicle` or host port `35000` is already in use. Inspect the existing container before stopping anything; don't remove data you need.
- **Observation timeout:** the exception identifies the book id, store, collection and last completed query result. Open [Workbench](https://localhost:35000), accept the local development certificate, and sign in as `Admin` with password `ChangeMeNow!`. Select `Quickstart`, inspect **Sequences** for `GetStartedBookAdded` and that id, then inspect the projection's status and failures. Save the exception and kernel logs before resetting anything. See [Troubleshooting](/chronicle/troubleshooting/).

Rerunning appends a **new** book with a new id; it doesn't retry or undo the previous append. If the event exists but the view remains stale, diagnose the projection before appending more. Removing a disposable development container discards its data; that is a reset, not a repair for a persistent store.

## Configure the MongoDB client

This optional reference is for direct database queries, **not part of the runnable project above**. Chronicle's `ReadModels` API doesn't need these conventions. To use a MongoDB driver instead, add `MongoDB.Driver` to your own query project and expose the development container's MongoDB port as described in the [two-port host setup](./choose-hosting-model#run-chronicle-locally). Connect a `MongoClient` to `mongodb://localhost:27017`, open `Quickstart` and select `GetStartedBooks` as an `IMongoCollection<GetStartedBook>`. For the tutorial's `Book` model instead, use `LibraryTutorial` and `Books`.
