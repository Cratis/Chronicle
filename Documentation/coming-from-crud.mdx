Cratis Chronicle records events and derives current state from them, rather than replacing a row whenever something changes. If you use EF Core, the main adoption decision is which changes need that history and which can stay as ordinary CRUD: create, read, update, and delete operations. You can use both approaches in the same application.

## The mental shift in one sentence

In CRUD, you store current state and update it; in Chronicle, you record what happened and derive current state from those facts. That derived state is a [read model](/chronicle/read-models/): data shaped for a query or screen, built from events instead of edited directly.

## How the pieces map

| You know (CRUD / EF Core) | In Chronicle |
|---|---|
| An entity with an identity | An [event source](/chronicle/concepts/event-source.md): the identity whose changes the events describe |
| `INSERT` a row | Append a "created" [event](/chronicle/concepts/event.md) |
| `UPDATE` a column | Append an event describing *what changed* (e.g. `AddressChanged`) |
| `DELETE` a row | Append a domain event such as `CustomerRemoved`; erasure is a separate compliance operation |
| `DbContext.SaveChanges()` | `EventLog.Append(...)` |
| `SELECT` / LINQ query | A query over a [read model](/chronicle/read-models/) built by a [projection](/chronicle/concepts/projection.md) |
| A computed/denormalized view | A purpose-built read model — make as many as you need |
| `ALTER TABLE` / EF migration | Use an [event type migration](/chronicle/concepts/event-type-migrations) when an event's shape changes; rebuild read models when their projection needs it |
| Optimistic concurrency token | A [concurrency scope](/chronicle/events/concurrency/) or [decision read](/chronicle/read-models/decision-reads/) that guards the append against intervening events |

## What stays the same

In a .NET application, you still use C# records and dependency injection. Your screens still query data and render results; they query read models rather than the event log itself. Keep EF Core and your existing database for data that only needs ordinary updates. Choosing Chronicle for one workflow does not require moving every table.

## What changes (and why)

A customer row tells you the address now. An `AddressChanged` event also records that a move happened, so you can later derive a relocation count or rebuild a view of those changes. Choose events that describe business facts, such as `CustomerRegistered` and `AccountClosed`, rather than recording every column assignment.

A projection defines how those events become a read model. By default, Chronicle materializes that model, meaning it stores the derived result for queries. Processing happens after the append, so a successful write does not mean the stored view already includes it. For read-after-write, you can wait for processing or use a suitable passive read model, computed from events on demand. [Read model consistency](/chronicle/read-models/consistency.md) explains those choices. A fresh read alone does not guard a later write against another request.

Removing a customer from a screen need not remove the customer's history. Your projection can react to a removal event and remove its read-model entry. A closed account also needs an explicit closing rule if later appends must be refused. For obligations that require erasing personal data, use [Compliance](/chronicle/compliance/) rather than treating a removal event as erasure.

## Not sure it's worth it?

Start with a workflow where the sequence of changes answers a question the current row cannot. If you only need the latest value and have no use for replay or history, CRUD may remain the simpler choice. [When to use event sourcing](/chronicle/concepts/when-to-use-event-sourcing/) helps you make that decision before changing the storage model.
