# TLS Configuration (Client)

Chronicle .NET clients connect over TLS and validate server certificates by default. For server-side TLS configuration, see [TLS Configuration (Server)](../hosting/configuration/tls.md). A server explicitly configured with `tls.enabled=false` instead requires `disableTls=true` in the connection string; that is cleartext HTTP/2, with no certificate validation or pinning.

## appsettings.json

```json
{
  "Cratis": {
    "Chronicle": {
      "ConnectionString": "chronicle://localhost:35000",
      "Tls": {
        "CertificatePath": "/path/to/certificate.pfx",
        "CertificatePassword": "your-password"
      }
    }
  }
}
```

## Properties

| Property | Type | Default | Description |
| --- | --- | --- | --- |
| CertificatePath | string | null | Path to the client certificate (PFX format) if mutual TLS is used; also used as a server certificate pin |
| CertificatePassword | string | null | Password for the certificate file |
| SkipCertificateValidation | boolean | false | When explicitly `true`, accepts any server certificate; when explicitly `false`, validates even loopback connections |

## Certificate validation

Remote connections validate the server's certificate by default. Trust the server's CA in the client environment or configure a matching certificate pin. The production image generates no certificate: without `Tls:CertificatePath` it stops at startup with "No TLS certificate is configured" — see [Production deployment](../hosting/production.md).

There is one local-development exception: with no validation setting supplied, a non-SRV connection targeting only `localhost` (case-insensitive), literal IPv4 loopback addresses in `127.0.0.0/8`, or literal IPv6 loopback `::1` skips validation. Mixed local/remote lists, private-network addresses, other hostnames (even if DNS resolves them to loopback), and all SRV lookups validate by default.

Set `skipTlsValidation=false` explicitly to require validation even on loopback:

An explicitly supplied `skipTlsValidation` value takes precedence over `Tls.SkipCertificateValidation`. With no connection-string value, an explicitly configured TLS option takes precedence over the loopback exception. Otherwise the defaults above apply.

For a temporary development opt-out, set `skipTlsValidation=true` or `Tls.SkipCertificateValidation = true`:

> [!WARNING]
> An opt-out accepts **any** server certificate and removes protection against man-in-the-middle attacks. Do not use it in production.

## Establishing trust

Trust the server's certificate authority on each client machine, or mount its CA certificate into application containers and add it to their trust stores. Alternatively, configure `certificatePath` with the matching certificate to pin it. A pin can allow an untrusted chain, including a self-signed certificate, but does not override a host-name mismatch or a missing certificate.

The .NET client logs one warning when validation is explicitly skipped for a non-loopback target or any DNS SRV lookup. This is a construction-time warning, not a reconnect warning; it lists server hosts and ports, not credentials. Loopback-only targets and connections with `disableTls=true` do not log this warning.

## Development setup

The Docker development images (`latest-development` and `latest-development-slim`) generate a self-signed certificate on every start when none is configured. A host client connecting through a published loopback port needs no certificate setup because of the exception above. Explicit `skipTlsValidation=false` disables that exception.

Container-to-container connections using Docker service names or Aspire resource names are not loopback. Configure and trust a certificate in the client container, configure a matching pin, or explicitly use `skipTlsValidation=true` for development only. Neither Docker nor Aspire automatically adds that opt-out. See [Aspire integration](../hosting/aspire) and the [upgrade note](../upgrading/index.md#net-client-server-certificate-validation).

To exercise validation in development, use a configured certificate whose CA is trusted by the client, or configure a matching pin, and set `skipTlsValidation=false`. The generated development certificate is not persisted or automatically trusted.

## Development vs production

- **Development**: loopback-only, non-SRV connections retain the no-setup experience unless validation is explicitly requested. Non-loopback connections validate by default.
- **Production**: give the server a verifiable certificate, install its CA in the client environment or configure a pin, and remove development opt-outs. Set `skipTlsValidation=false` explicitly if the production connection uses loopback.

## Troubleshooting

### Client connection errors

**Error**: "The remote certificate is invalid"

Validation now applies by default to remote connections. Check that:

1. The server certificate is valid, not expired, and matches the target host name.
2. The client trusts the issuing CA, including inside application containers, or has a matching certificate pin.
3. A local development connection uses the intended loopback endpoint. For other development endpoints, establish trust or use an explicit, temporary opt-out rather than relying on an omitted setting.
