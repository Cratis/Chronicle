Configure the Chronicle .NET client to choose which kernel and event store your application uses. Client settings control the connection and client behavior; they do not configure the kernel's ports, storage, or server-side limits. Those belong in [Hosting Configuration](../hosting/configuration/index.md).

This section covers .NET host configuration and direct `ChronicleClient` construction. The `appsettings.json` binding and `AddCratisChronicle` registration shown here are .NET APIs, not a shared configuration contract for every Chronicle client. See [Where the clients differ](../clients/where-the-clients-differ.md) for client-specific workflows.

## How client configuration flows

With the standard .NET host defaults, put bindable settings under `Cratis:Chronicle` in `appsettings.json`. Environment variables override file values; for example, `Cratis__Chronicle__EventStore` maps to `Cratis:Chronicle:EventStore`. If you customize the host's configuration providers, their order determines precedence.

The `configureOptions` callback on `AddCratisChronicle` runs after configuration binding, so values it sets override bound values. Custom providers and resolvers are different: supply those objects through the separate `configure` callback described in [Structural Dependencies](./structural-dependencies).

Start with the kernel endpoint and the event store your application will use:

```json
{
  "Cratis": {
    "Chronicle": {
      "ConnectionString": "chronicle://localhost:35000",
      "EventStore": "my-store"
    }
  }
}
```

Register the client on the host with `AddCratisChronicle`. It reads the section above; the example's `configureOptions` callback then selects `my-store` explicitly:

Use `IHostApplicationBuilder` for worker and console hosts, or `WebApplicationBuilder` for ASP.NET Core. Once registered, application services can resolve `IEventStore` through dependency injection.

The connection string above uses TLS, but the client skips server certificate validation by default. Before connecting beyond a trusted development environment, configure certificate trust and enable [TLS validation](./tls). See the [getting-started host guides](../get-started/toc.yml) for the surrounding application setup.

## Minimal setup

A client needs two settings: the kernel's connection string and the event store name. With the environment-variable form:

```bash
export Cratis__Chronicle__ConnectionString="chronicle://clientId:clientSecret@chronicle.example.com:35000"
export Cratis__Chronicle__EventStore="my-store"
```

Everything else has a default. For a kernel on `localhost:35000` the connection string can be omitted, and the client uses the built-in development credentials.

A production kernel needs a storage connection, because it has no embedded database. For example, with MongoDB or PostgreSQL:

```bash
export Cratis__Chronicle__Storage__Type=PostgreSql
export Cratis__Chronicle__Storage__ConnectionDetails="Host=db.example.com;Database=chronicle;Username=chronicle"
```

A production kernel also needs a TLS certificate and an encryption certificate; see [Production hosting](../hosting/production.md). Check [Settings that must match the kernel](must-match-the-kernel) when both sides are configured.

## Explicit artifacts

Register event types and other artifacts in code when you want to declare them where the application is assembled, or when their assemblies cannot carry Chronicle markers. Explicit declarations merge with marker-based discovery; they do not override conflicting identities.

<ChronicleClientTabs snippet="configuration/explicit-artifacts/composition" />

Configure these declarations before creating stores. Each store captures an immutable snapshot; later option edits do not alter existing stores or their reconnect registrations. Continue to the [.NET API reference](../clients/dotnet/explicit-artifacts) for registration rules and custom-provider compatibility.
