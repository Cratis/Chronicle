# DotNET client usage

When you call `ChronicleClient.GetEventStore` without a namespace, the Cratis Chronicle .NET client calls its `IEventStoreNamespaceResolver` to choose one. Passing a namespace explicitly bypasses the resolver. The client caches event-store handles by both store name and namespace, so obtaining the same selection again can return an existing handle.

The handle and its event log keep the selected namespace. Appends and reads do not resolve it again, even if the current tenant or principal changes. To work with another namespace, obtain the appropriate handle rather than reuse one selected for the previous tenant.

:::note[Client coverage]
This page covers direct and hosted .NET applications. [ASP.NET Core namespace resolution](./aspnetcore) covers selecting a namespace from HTTP context. These resolver and dependency-injection APIs belong to the .NET client.
:::

## IEventStoreNamespaceResolver

<ChronicleClientTabs snippet="namespaces/dotnet-client/resolver-shape" />

`Resolve()` returns the namespace name to use when an event-store handle is obtained. This example always returns the default namespace; a context-dependent resolver reads the current tenant or principal at that point.

## Built-in resolvers

### DefaultEventStoreNamespaceResolver

Always returns the default namespace. Use this when your application does not need to select separate namespaces. A directly constructed `ChronicleClient` uses this resolver when none is supplied, as does the non-web host integration unless you configure another resolver.

### ClaimsBasedNamespaceResolver

Resolves the namespace from the current principal's claims. This is useful when you have an authenticated user and want to map the tenant from a claim.

<ChronicleClientTabs snippet="namespaces/dotnet-client/claims-based" />

The examples read `ClaimsPrincipal.Current` and use either `tenant_id` or `custom_tenant_claim`. You can supply a principal-accessor callback when the principal comes from another context. If the principal is unauthenticated or the claim is missing or empty, the resolver returns the default namespace. Use that fallback only if it is appropriate for your application's tenant rules.

## Configuring in a hosted application

For an application using `IHostApplicationBuilder`, such as a worker service, configure the resolver through `ChronicleClientOptions` or supply an instance through `IChronicleBuilder`:

<ChronicleClientTabs snippet="namespaces/dotnet-client/hosted-app-configuration" />

The options form lets DI construct `TenantNamespaceResolver`; the builder form uses the instance you supply. In both cases, the host integration registers the resolver and client as singletons, so the resolver's dependencies must be safe to retain for the application's lifetime.

`IEventStore` is registered as scoped. When it is first resolved in a scope, its factory calls the resolver and obtains the handle for the configured store and selected namespace. This scoped registration does not make the resolver scoped or cause the handle to follow later tenant changes. Establish the tenant before resolving the store or its event log.

## Best practices

- Keep tenant selection stable while obtaining and using a handle
- Use the default namespace as a fallback only when your application permits it; otherwise reject missing tenant context before obtaining the handle
- Keep resolution lightweight; it runs when selecting a handle, not on every append or read

For web applications, see [ASP.NET Core namespace resolution](aspnetcore).
