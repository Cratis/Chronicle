---
title: "ASP.NET Core namespace resolution"
description: "Resolve the Chronicle namespace per request in ASP.NET Core, and the trust each built-in resolver assumes."
---

In an ASP.NET Core application, Cratis Chronicle can select a namespace from the current HTTP context. When DI first resolves `IEventStore` in the request scope, it calls the namespace resolver and obtains the matching event-store handle. The handle and its event log retain that namespace; keeping them beyond the request does not make them follow the next request's tenant.

If your multi-tenant setup is based on Arc Tenancy, you can map the current tenant to a namespace. See [Arc tenancy](/arc/backend/csharp/tenancy/).

## Built-in resolvers

### HTTP header resolution (default)

The default resolver reads the namespace from an HTTP header. Configure it through `ChronicleAspNetCoreOptions`:

<ChronicleClientTabs snippet="namespaces/aspnetcore/http-header-resolver" />

The example selects `my-event-store` and uses `x-cratis-tenant-id` for namespace selection. When the resolver runs, it returns the header's value if present, or the default namespace if the header is missing. Check that this fallback fits your tenant rules before using it for requests without tenant context.

:::caution[The caller chooses the namespace]
The header resolver reads the supplied value without authorizing it. If callers control the header, they control the namespace it selects. Use a trusted source for the tenant value, and enforce which tenants the authenticated caller may use before resolving the store. Selecting a namespace does not grant or verify access to it.
:::

### Subdomain resolution

The subdomain resolver extracts the namespace from the request host (for example, `tenant1.example.com`).

<ChronicleClientTabs snippet="namespaces/aspnetcore/subdomain-resolver" />

This resolver uses the first part of a host with more than two dot-separated parts, so `tenant1.example.com` selects `tenant1`. Without such a host, it returns the default namespace. The host-derived name still needs the same tenant-authorization checks as a header-derived value.

## Custom resolvers

Use a custom resolver when the built-in request mappings do not match where your application keeps its namespace. Implement `IEventStoreNamespaceResolver`, then supply an instance through `IChronicleBuilder` or configure its type for DI:

<ChronicleClientTabs snippet="namespaces/aspnetcore/custom-resolver" />

This resolver reads `Tenant:Namespace` from `IConfiguration`, falling back to the default namespace when the setting is absent. It selects from configuration, not from the caller's identity. For request-dependent selection, use a singleton-safe accessor such as `IHttpContextAccessor` to read the current context inside `Resolve()`. The web integration registers the resolver as a singleton; do not inject a request-scoped service directly into it.

## Configuration priority

1. Resolver set via `IChronicleBuilder.WithNamespaceResolver()` or `IChronicleBuilder.NamespaceResolver`
2. Type configuration (`EventStoreNamespaceResolverType`) when provided
3. Default HTTP header resolver
