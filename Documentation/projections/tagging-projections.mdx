# Tagging Projections

Tags provide a way to organize and tag your projections for better discoverability and management. Where supported, use your client's tag declarations to assign labels that describe the projection's purpose or domain.

Descriptive tags label the projection definition (`[Tag]` and `[Tags]` in .NET). They do not filter which appended events the projection observes. Use projection event declarations and event sequence selection to control projection input, and use reducer or reactor filters when you need metadata-based filtering for appended events. See [Filter reducers and reactors by appended event metadata](../events/filtering/index.md).

:::note[Client coverage]
C# supports `[Tag]`/`[Tags]`, and TypeScript supports `@tag`/`@tags` on projection classes and model-bound read models. Kotlin and Elixir do not support projection tags yet. The kernel stores and returns these tags with the projection definition; changing only tags does not trigger a replay or replay recommendation.
:::

## Best Practices

- **Use meaningful names**: Choose tag names that clearly describe the purpose or domain
- **Be consistent**: Establish tag naming conventions across your organization
- **Don't over-tag**: Apply only relevant tags; too many can reduce their usefulness
- **Group related projections**: Use tags to group projections that serve similar purposes

## Querying by Tag

Projection tags describe the projection and are stored with its definition. Chronicle does not use them to select or group projections, for example for rebuilds.
