# Projection AutoMap

A user profile needs a name and email from a creation event, then only a new name from a rename event. Writing every copy by hand adds little when the event and model already agree on those fields.

AutoMap is Cratis Chronicle's convention-based property mapping. It is enabled by default for fluent projections: declare the events the projection consumes, and matching properties can supply the view. Start from a [simple projection](simple-projection.mdx) in a registered Chronicle application; this page explains where that convention applies and when to take over explicitly.

## How AutoMap Works

For one event source, creation supplies both fields. A later rename supplies the name but has no email to map, so the existing email remains. These are incremental updates, not replacement of the whole model with each event's shape.

| Part of the contract | What to check |
| --- | --- |
| Subscription | Only declared event types contribute. AutoMap does not subscribe to unrelated events. |
| Names | Compare event and model names after the client's serialization naming policy is applied. |
| Types | Use compatible property types; a name match is not a request to parse or calculate a value. |
| Explicit mappings | A mapping for a target property takes precedence over its convention-based mapping. |
| Keys | Routing an event to a key and copying a property into the model are separate operations. |

The kernel resolves these mappings from the registered event and read-model schemas when it constructs the projection. The fluent callback is not an event handler. Aggregate-only subscriptions have a narrower rule, described below.

## Disable AutoMap

Turn AutoMap off when every copied field should be named in the definition. In the C# tab, `.NoAutoMap()` applies to the projection scope, not to a single `.From<TEvent>()` call. The account example maps its renamed fields and creation timestamp explicitly:

<ChronicleClientTabs snippet="projections/declarative/auto-map/disable" />

After disabling the convention, leaving a property out means this definition does not populate it automatically. Add [explicit mappings](set-properties.mdx) for every value the view needs.

## Re-enable AutoMap In A Child Scope

A team may need explicit root mappings while its member records already match their events. In a client with the corresponding child builder, re-enable AutoMap inside that scope. The C# example uses `.AutoMap()` on the child after `.NoAutoMap()` on the root:

<ChronicleClientTabs snippet="projections/declarative/auto-map/re-enable-child-scope" />

This changes the child's mapping convention, not its identity rules. The example still names the member identifier and routes member events with a child key. Follow [child collection mappings](children.mdx) for parent routing and removal. Calling `.AutoMap()` at an already-enabled root adds nothing.

## Aggregate-Only Events

Suppose an assignment's location comes from an arrangement event, while candidate events only increase a count. Both events happen to contain a location. Counting a candidate should not replace the assignment's location with the candidate's.

When every property operation for an event is an aggregate — `Count`, `Increment`, `Decrement`, `Add`, or `Subtract` in the C# API — Chronicle does **not** AutoMap that event's other properties. You do not need to disable AutoMap for this case:

<ChronicleClientTabs snippet="projections/declarative/auto-map/aggregate-only" />

After an arrangement event and two candidate events for the same key, the intended fields are the arrangement's location and a candidate count of two. The candidate locations do not replace the stored location. If you add a non-aggregate mapping to that subscription, it is no longer aggregate-only; review the other same-name fields again.

## When To Use AutoMap

Use convention when matching event fields are exactly what the view should expose. Use [Set mappings](set-properties.mdx) for different names, constants, context values, or an explicit list of copied fields; use [projection functions](functions.mdx) to accumulate rather than replace a value.

When a field is missing or unexpectedly changes, check these before turning AutoMap off everywhere:

- Is the event actually declared, and is AutoMap enabled in the affected scope?
- Do the serialized names and compatible types match?
- Does an explicit mapping already own that target property?
- Is the event subscribed only for aggregation, so its other fields are intentionally excluded?

Adding a same-name field to an event or model can change what convention maps. Review such schema changes against the projection, especially where several events can supply the same field. A [read-model scenario](../../testing/read-models/scenario.mdx) can check the event history and retained values without treating append success as proof of materialization.
