A composite key in Cratis Chronicle identifies a read model instance with several values instead of one. Use it when an order number, for example, is unique only within a customer: the customer ID and order number together select the order to update.

## Defining a composite key

Use `UsingCompositeKey<T>()` to map each part of the key. Configure the same parts for every event that updates the same order; both creation and shipping events must resolve to that order's key.

## ISO week keys

Pair `Occurred.Week` with `Occurred.WeekYear`, not the calendar `Occurred.Year`. ISO weeks can start in the previous calendar year or end in the next one. For example, December 30, 2024 is week 1 of week-year 2025, while January 1, 2021 is week 53 of week-year 2020. Using the calendar year would merge January 1 and December 30, 2024 into the same weekly key.

In .NET, use the `Week()` and `WeekYear()` extension methods from `Cratis.Chronicle.Properties`:

## Key composition rules

Use the same key structure for events targeting the same read model instance. Each part must retain its meaning across those events: if a key value changes, the event targets a different instance rather than renaming the existing one.

The combined values must distinguish the instances you want to keep separate. A typed key makes the mapped properties explicit, but it does not establish business uniqueness for you.

## Kernel compatibility

Projection declarations that specify a composite key type require Chronicle kernel v19.8.1 or later. Older kernels reject the type name when projecting events, so upgrade the kernel before deploying those declarations.

Fluent .NET projections emit untyped composite-key expressions, which remain compatible with older kernels. The updated kernel also reads those stored expressions without migration. The connection-time compatibility check covers wire versions, not this projection-expression behavior.

## Generating declarations from stored projections

When generating a declaration from an untyped fluent composite-key expression, Chronicle infers the type from the read model's `Id` property, or the child item's `Id` for a child collection. Nullable object types are supported. The .NET client includes the .NET key type name in the generated schema so the resulting declaration can be compiled again; the stored fluent expression remains untyped.

For a manually supplied schema without a key type name, generation uses `CompositeKey` as a placeholder. That declaration cannot recompile unless the schema defines a `CompositeKey` object with the mapped properties.

## Performance considerations

Choose key parts for identity, not as a promise about query performance. Check query and index behavior against the storage provider you use; a composite projection key does not by itself establish an efficient query plan.

If every event should update one shared instance instead, use a [constant key](./constant-key). To map metadata into values as well as keys, continue with [event context](./event-context).
