# Passive projection

A passive projection is a projection that is not actively materialized to a persistent store but can be queried on-demand for in-memory lookups. This is useful for scenarios where you need to construct read models from events without the overhead of maintaining persistent state.

This projection:

- Will not be actively maintained in persistent storage
- Can be read on demand through `ReadModels.GetInstanceById`
- Reconstructs the read model from events when requested

A read model declaring `[EventStream<TSource>(stream)]` is also passive, even without `.Passive()`. It stays keyed by event source ID but requires a stream-aware instance read; a key-only read is refused rather than mixing stream IDs. See [Read models scoped to one event stream](../../read-models/per-stream.mdx).

## How it works

When you call `GetInstanceById` on a passive projection:

1. The first read folds relevant events for the specified event source ID in memory.
2. Chronicle retains the computed state and its last handled sequence number in the immediate-projection activation.
3. Later reads reuse that state and apply newer events; if no relevant events were appended, the cached result is returned.
4. The result has no persistent read-model sink. If the activation loses its cache, a later read reconstructs it.

By-ID reads select one event source. A cross-source join or custom-key aggregation cannot generally
reconstruct the same answer as its materialized counterpart this way. See
[consistency models](../../read-models/consistency.md) before making an existing projection passive.

## When to use passive projections

Passive projections are ideal for:

- **Infrequent queries**: When read models are accessed rarely or sporadically
- **Current source state**: When you need an on-demand fold instead of waiting for materialization
- **Storage-sensitive scenarios**: When you want to avoid a persistent read-model sink
- **Temporary calculations**: For read models that are computed and discarded
- **Testing and debugging**: When you need to inspect event-driven state without persistence

## Performance considerations

- A cold read folds the history; a warm read can apply only the newer events.
- Passive projections trade persistent storage for read-time processing and cached memory.
- Plan for cold-read cost even when repeated reads benefit from the kernel's cache.
- Use bounded, source-local histories when read latency matters.
