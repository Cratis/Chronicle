# Passive projection

A passive projection in Cratis Chronicle computes a read model from events when you request it, rather than maintaining a stored result. Use it for source-local lookups when you want to read from event history without waiting for a background observer to update a read-model store.

The declaration disables background materialization. `ReadModels.GetInstanceById` instead reconstructs the requested instance from its event history.

A read model declaring `[EventStream<TSource>(stream)]` is also passive, even without `.Passive()`. It stays keyed by event source ID but requires a stream-aware instance read; a key-only read is refused rather than mixing stream IDs. ## How it works

When you call `GetInstanceById` on a passive projection:

1. Chronicle retrieves the subscribed event types for the requested event source ID, starting at the beginning of its history.
2. It applies the projection mappings in memory and returns the computed instance.
3. A later read repeats that work from the start rather than reusing the previous read-model state.

There is no persistent read-model sink, meaning no storage destination containing a materialized result. A read can include events you have just successfully appended without waiting for an observer, but it does not reserve that state against another writer. If the result drives a decision that must hold under concurrent writes, use a [decision-consistent read](../../read-models/decision-reads.mdx).

By-ID reads select one event source. A cross-source join or custom-key aggregation cannot generally
reconstruct the same answer as its materialized counterpart this way. See
[consistency models](../../read-models/consistency.md) before making an existing projection passive.

## When to use passive projections

Choose a passive projection when each lookup concerns one event source and replaying its history fits the request's latency requirements. Infrequent reads over short histories are a good fit: you avoid maintaining a stored result that callers rarely use.

Keep a projection materialized when it joins other sources, aggregates under a custom key, or serves frequent reads over long histories. Passive mode moves the work to read time; it does not remove that work.

## Performance considerations

Read cost grows with the number of relevant events for the source. A reactor or command that reads a passive model on every event repeats the full fold each time, so measure that path with representative histories.

For the trade-off between computing from events, reading stored state, and waiting for an observer, continue with [consistency models](../../read-models/consistency.md).
