Use a join in a Cratis Chronicle projection when one read model needs facts from separate event streams, such as a user and the group they belong to. The read model stores a join key, and Chronicle uses it to find the related events and apply their property mappings.

`On` selects the relationship; it does not rename properties. For this shape, explicitly map the group-created event's `Name` to `GroupName` and `Description` to `GroupDescription`, then map the rename event's `NewName` to `GroupName`. For example, add `.Set(m => m.GroupName).To(e => e.NewName)` inside the rename join. With AutoMap enabled, a group event's `Name` would otherwise target the user's same-named `Name` property, not `GroupName`. See [AutoMap](auto-map) to control name-based mapping.

## How joins work

A `From` event creates or updates a read model and can set the join key. When a related event arrives, Chronicle matches its key against the read model's `On` property and applies the joined mappings. For a default join, that event key is its event source ID.

Chronicle also resolves earlier joined events when processing a `From` event. This backfill lets a newly established relationship pick up data already present in the joined stream. Joined mappings run after `From` mappings, so they take precedence when both write the same property.

## Join scenarios

### Setting join keys

Set the join key from the event that establishes the relationship. The assignment mapping above uses `.UsingKey(e => e.UserId)` to select the user and `.Set(m => m.GroupId).ToEventSourceId()` to store the group ID. If your assignment event belongs to the user stream instead, map `GroupId` from the event's group-ID property rather than its event source ID.

### Joining on the key

Declare a join for each related event type you want to handle. Both group-created and group-renamed joins use `.On(m => m.GroupId)` because they refer to the same relationship. Their property mappings determine which group fields change.

### Joining by an event property

For a root join, `.UsingKey(e => e.X)` matches the read model's `On` property against that event property instead of the event source ID. If the property is missing or null, Chronicle falls back to the event source ID. Context, constant, and composite key expressions are not supported for root joins: Chronicle logs a warning and uses the event source ID instead.

Append the root before the keyed join event when its key differs from its event source ID. If the joined event arrives first, backfill still looks it up by event source ID, not by the explicit key property.

### Join precedence

Do not use arrival order to decide whether a `From` mapping or a join owns a property. On a `From` event, Chronicle resolves the latest stored event of each joined type before that event's sequence number and applies its mappings after the `From` mappings. A local write cannot clear a value that this join resolution reapplies; there is no dedicated "clear this joined value" operation.

If a field must reflect which fact happened most recently, store each fact separately, such as two timestamps, and compare them. The [CHR0042](../../code-analysis/CHR0042) analyzer warns when a `From` mapping and a join write the same property.

## Automatic mapping in declaration-language joins

In the declaration language, a `with <Event>` block inherits the projection's `automap` setting. Put `no automap` inside that block to use only explicit mappings, or `automap` to enable name-based mapping when the enclosing projection disables it. The setting also applies during backfill.

Per-join `automap` and `no automap` are declaration-language only: the .NET `JoinBuilder` and the C#, Kotlin, and TypeScript code generators do not express them. Generated code will not preserve a per-join override, so keep the declaration as the source of truth when using one.

## Performance considerations

A joined event can update several read models that refer to the same key. Consider how many instances share each relationship and how often the joined data changes when choosing what belongs in the projection.

For related data owned by one parent, compare [Children](children) and [Nested objects](nested). They model collections and optional objects within the parent rather than joining independent streams.
