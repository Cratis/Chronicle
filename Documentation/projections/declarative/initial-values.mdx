# Projection With Initial Values

Initial values give a Cratis Chronicle read model meaningful defaults before event mappings assign its properties. Use them for a draft status, an inventory threshold, or another starting value that events may leave unchanged. Chronicle captures this state in the projection definition; it is not a factory run for each event or query.

.NET exposes `WithInitialValues`, while TypeScript exposes `withInitialValues`. Kotlin and Elixir capture defaults declared on the read model itself.

## Basic Usage

In .NET or TypeScript, provide a callback that returns the starting model. The builder evaluates it while creating the definition, and event mappings later apply on top of the captured state.

For Kotlin, give every primary-constructor parameter a default so the client can construct the initial model without arguments. For Elixir, use `defstruct` defaults. These defaults become part of the registered projection definition rather than being supplied by a constructor when a stored document is read. See [The constructor may not run](../../concepts/designing-read-models#the-constructor-may-not-run) for why query-time construction is not a substitute for projection defaults.

## Why Use Initial Values

An event often describes only the fields that changed. Initial values let the remaining fields carry a deliberate starting value rather than relying on the client's or storage layer's representation of a missing property.

Choose defaults according to what readers need:

| Need | Example |
| --- | --- |
| Business defaults | A new order starts as draft until an event changes its status. |
| Non-null collections | A customer read model starts with empty address and tag collections. |
| Sentinel values | A timestamp starts at a known sentinel until the first event provides a real value. |
| Partial events | Inventory limits are configured once while stock events update only quantities. |

## Collections

For ordinary collection-valued properties, an empty collection can let consumers enumerate values without checking for `null`. A collection managed by `Children()` follows different rules, explained below.

<ChronicleClientTabs snippet="projections/declarative/initial-values/collections" />

:::caution
Initial values do not populate a child collection managed by `Children()`. Child add and remove operations own that path; a root event's initial array is dropped before it reaches the sink. Otherwise, an empty array could erase children already added during parallel replay. Declare the child collection non-nullable to have Chronicle materialize an empty collection on read. See [Empty child collections](/chronicle/read-models/empty-child-collections/).
:::

## Best Practices

Keep defaults deterministic because they are captured when the projection definition is built. Reading the current time in the callback would capture definition-build time, not the time a later read model instance is created. For a timestamp describing an event, map its [event context](event-context) instead.

Use initial values for starting state, not for facts that should be recorded in events. Once the defaults are in place, continue with [Set properties](set-properties) for assignments or [Functions](functions) for counters and running totals.
