# Joins

A model-bound join copies facts from a related event source into a read model. Use it when an order needs a customer's name or a line item needs product details, so the query can read those values from the model. In .NET, `[Join<TEvent>]` declares the source event and the model property used to find a match.

| --- | --- |
| `on` | Property on the read model holding the related identifier. If omitted at the root, it defaults to the annotated property itself. Specify it when the identifier is stored in another property. |
| `eventPropertyName` | Property to copy from the event. If omitted, it defaults to the annotated read model property's name. |

## Event Processing Flow

If `CustomerRegistered` and `ProductCreated` arrive first, their data is available when `OrderPlaced` creates the order and `LineItemAdded` adds a line. Chronicle resolves the matching stored events to fill in the customer and product fields.

Later, `ProductPriceChanged` updates the price on matching line items, and `CustomerProfileUpdated` updates the phone number on matching orders. A join therefore handles both data already present when the model is populated and related events that arrive afterward.

## Join vs SetFrom

Use `SetFrom` when a handled event directly updates the model selected by that event's configured key. Use `Join` when the model stores a reference to a related event source and needs values from its events. The join copies those values into the read model, a form of denormalization that avoids looking them up separately at query time.

## Join Precedence

When a `Join` and a local mapping (`SetFrom` or an auto-mapped `FromEvent` property) target the same property, the joined value takes precedence. When processing a local event that resolves the join, Chronicle finds the last matching joined event stored before that event's sequence number and applies the joined properties after the local mappings. A locally written value stays in place while no matching joined event is available.

:::caution
A local mapping cannot reset or clear a property a join has written. There is no "clear this joined value" operation. A `bool` latch that a local event sets and a joined event clears will keep the joined value, even when the local event is more recent. If the property must reflect which fact happened most recently, give each fact its own property, such as two timestamps, and compare them in the query. The [CHR0042](../../code-analysis/CHR0042) analyzer warns when a property is written from both sides.
:::

## Best Practices

Choose an `on` property that stores the related event source's identifier, and allow for missing data when a matching event has not arrived. Nullable properties can make that absence visible to readers.

For a single object with its own populate-and-clear lifecycle, continue with [Nested Objects](./nested.mdx). For independently identified items, use [Children](./children).
