Use `ChildrenFrom` in a Cratis Chronicle model-bound projection when one read model should contain independently updated items, such as an order and its lines. The collection mapping identifies which events reach the children, which item each event selects, and which parent instance contains it.

The child's `[Key]` member stores that identity. The .NET client discovers it, so this example does not need an explicit `identifiedBy`.

### Parameters

`key` selects the child identity from the incoming event. It defaults to `EventSourceId` when no event property is specified.

`identifiedBy` names the member holding that identity on the child. If omitted, the .NET client looks for a property or record parameter marked `[Key]`, then a property named `Id` ignoring case, then a property matching the event key name. If none is found, it falls back to `EventSourceId`.

`parentKey` selects the containing read model instance. If omitted, the .NET client first looks for an event property whose type matches the parent's `Id` type, excluding the child key property. If none matches, it uses the event source id.

When several event properties match the parent's `Id` type, the first in declaration order is used. Supply `parentKey` to remove that ambiguity, or when the parent identifier is not named `Id`. For example, use `parentKey: nameof(LineItemAdded.OrderId)` when `OrderId` in the event identifies the parent. An explicit value always takes precedence.

### What Works Recursively

The following .NET mapping attributes can be declared on child types, including nested children:

| Attribute | Works on Children |
|-----------|-------------------|
| `SetFrom` | ✓ |
| `AddFrom` / `SubtractFrom` | ✓ |
| `SetFromContext` | ✓ |
| `Join` | ✓ |
| `Increment` / `Decrement` / `Count` | ✓ |
| `ChildrenFrom` (nested children) | ✓ |
| `RemovedWith` / `RemovedWithJoin` | ✓ |
| `FromEvent` (class-level) | ✓ |

Keep each level's identity and parent routing explicit enough to follow. An update must reach the right parent collection as well as select the right child.

## Collections with no children

Before any child is stored, the collection field is absent rather than `[]`. Root writes leave child collection paths untouched so they cannot erase children already added.

When Chronicle's .NET reader materializes the model, a non-nullable collection becomes empty; a nullable collection stays `null`. Other readers can behave differently. [Empty child collections](/chronicle/read-models/empty-child-collections/) explains which readers apply this rule and why initial values cannot seed the collection.

## Best Practices

Start by checking the child identity and parent routing for every event that changes the collection, not just the add event. Mark the child's identity with `[Key]` or supply `identifiedBy`, and use an explicit `parentKey` where inference would be ambiguous.

If a related event should update a child without adding another item, continue with [joins](joins). For a quantity that rises and falls within each child, see [counters](counters).
