Model-bound projections let the read model describe how it is built. Instead of creating a separate `IProjectionFor<T>` class, you put the projection metadata directly on the read model type and Chronicle builds the projection definition from those attributes.

## Overview

Start with convention-based mapping and add explicit attributes only where the event and read model use different names. That keeps the common case small while still making the exceptions visible.

## Basic Example

<ChronicleClientTabs snippet="projections/model-bound/index/basic" />

In this example:

- `[FromEvent<AccountOpened>]` creates or updates an `AccountInfo` instance when an `AccountOpened` event is processed
- `[Key]` marks the read model identifier
- `Name` maps by convention because both the event and the read model use the same property name
- `Balance` uses `[SetFrom<TEvent>]` because the event property is called `InitialBalance`

## Discovery

Types are automatically discovered by the presence of:

- Class/record-level projection annotations such as `FromEvent` or `NotRewindable`, or event-sequence selection
- Member mapping attributes such as `SetFrom`, `AddFrom`, or `Join`

No explicit marker is required on the type. `[Passive]` alone is not a discovery signal: it configures
how an already-defined model is read, and can also configure a reducer model.

## Stable Projection Identity

By default, a model-bound projection uses the read model's fully qualified CLR type name as its identifier.
Use `[Projection(id: "...")]` from `Cratis.Chronicle.Projections` on a class, record, or record struct to
keep that projection identity when renaming the type or moving its namespace. When adding the attribute
to an existing projection, use its previous identifier:

<ChronicleClientTabs snippet="projections/model-bound/index/stable-identity" />

An absent or empty attribute ID keeps the full-name default. The ID is not trimmed or normalized.
Discovery, `RegisterReadModel<T>()` in client options, and runtime `Projections.Register<T>()` all use
the same identifier. Callback-defined projections use it as their default too; an explicitly supplied
callback ID takes precedence.

`[Projection]` is identity metadata, not a discovery marker or a mapping annotation. Keep the real
model-bound annotations such as `[FromEvent<TEvent>]`. `[Projection]` alone, or with only `[Passive]`,
does not make a model a projection. Its `eventSequence` argument configures fluent projections only;
model-bound event-sequence routing still uses `[EventSequence]` and the existing event-store rules.

Different local projection owners cannot share an ID. Chronicle rejects competing fluent, model-bound,
or explicit declarations before publishing the conflicting registration, identifying the ID and owner
types. Registering the same model-bound read model explicitly as well as discovering it is still one
projection; repeating that registration is allowed. Do not keep both the old and renamed owners locally.

A stable projection ID does not freeze the definition: Chronicle can still detect definition changes and
apply its normal evolution or replay behavior. It also does not preserve the read model's separate
identifier or storage container name; a type rename can still change those defaults.

## Key Features

Model-bound projections cover the common projection operations below. Specialized builder features,
such as fluent dynamic dictionary counters, do not all have attribute equivalents.

- **Property Mapping**: SetFrom, AddFrom, SubtractFrom, SetFromContext
- **FromEvery**: Set properties from all events
- **Counters**: Increment, Decrement, Count
- **Relationships**: Join, Children (with unlimited nesting depth)
- **Removal**: RemovedWith, RemovedWithJoin
- **Convention-based**: FromEvent for automatic property matching
- **Configuration**: EventSequence, NotRewindable, Passive
- **Variants**: Mutually exclusive read model shapes for the same logical entity
- **Fully Recursive**: All attributes work at any nesting level - children, grandchildren, and beyond

See the following pages for detailed information on each feature:

- [Basic Mapping](./basic-mapping) - SetFrom, AddFrom, SubtractFrom, SetFromContext
- [Set Constant Value](./set-value) - Set a property to a fixed value with SetValue
- [Clearing Values](./clearing) - Take a value away with ClearWith or a null SetValue
- [Convention-Based](./convention-based) - Automatic property mapping with FromEvent (equivalent to AutoMap)
- [FromEvery](./from-every) - Update properties from all events
- [FromAll](./from-all) - Subscribe to all event types without filtering
- [Counters](./counters) - Increment, Decrement, Count
- [Children](./children) - Managing child collections
- [Removal](./removal) - Removing read models and children with RemovedWith, RemovedWithJoin
- [Joins](./joins) - Joining with other events
- [Event Sequence Source](./event-sequence-source) - Reading from specific event sequences
- [Not Rewindable](./not-rewindable) - Forward-only projections
- [Passive](./passive) - On-demand projections
- [Variants](./variants) - Mutually exclusive read model shapes for the same logical entity

## When to Use

Start with model-bound attributes, use fluent mappings when the definition needs structure, and use
reducer code when state transitions are clearer; a self-reducing model is the default for new reducers.
[Choose how to build a read model](../choosing-a-read-model-style.mdx) works through the trade-offs.
