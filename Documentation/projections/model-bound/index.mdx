---

A model-bound Chronicle projection defines how events build a read model on the read model type itself. In .NET, attributes describe the event mappings, so you can keep the view's shape and update rules together without a separate `IProjectionFor<T>` class.

## Overview

Start with convention-based mapping and add explicit attributes only where the event and read model use different names. That keeps the common case small while still making the exceptions visible.

## Basic Example

<ChronicleClientTabs snippet="projections/model-bound/index/basic" />

When Chronicle processes `AccountOpened`, `[FromEvent<AccountOpened>]` creates or updates an `AccountInfo` instance. `[Key]` marks its identifier. `Name` maps by convention because the event and read model use the same property name; `Balance` needs `[SetFrom<TEvent>]` because the event calls the value `InitialBalance`.

## Discovery

The .NET client discovers model-bound projection types from their annotations:

- Class/record-level projection annotations such as `FromEvent` or `NotRewindable`, or event-sequence selection
- Member mapping attributes such as `SetFrom`, `AddFrom`, or `Join`

No explicit marker is required on the type. `[Passive]` alone is not a discovery signal: it configures
how an already-defined model is read, and can also configure a reducer model.

## Stable Projection Identity

By default, a model-bound projection uses the read model's fully qualified CLR type name as its identifier.
Use `[Projection(id: "...")]` from `Cratis.Chronicle.Projections` on a class, record, or record struct to
keep that projection identity when renaming the type or moving its namespace. When adding the attribute
to an existing projection, use its previous identifier:

<ChronicleClientTabs snippet="projections/model-bound/index/stable-identity" />

An absent or empty attribute ID keeps the full-name default. The ID is not trimmed or normalized.
Discovery, `RegisterReadModel<T>()` in client options, and runtime `Projections.Register<T>()` all use
the same identifier. Callback-defined projections use it as their default too; an explicitly supplied
callback ID takes precedence.

Keep model-bound annotations such as `[FromEvent<TEvent>]` when adding `[Projection]`. The latter
supplies identity metadata; it does not define mappings or trigger discovery. `[Projection]` alone,
or with only `[Passive]`, does not make a model a projection. Its `eventSequence` argument configures fluent projections only;
model-bound event-sequence routing still uses `[EventSequence]` and the existing event-store rules.

Different local projection owners cannot share an ID. Chronicle rejects competing fluent, model-bound,
or explicit declarations before publishing the conflicting registration, identifying the ID and owner
types. Registering the same model-bound read model explicitly as well as discovering it is still one
projection; repeating that registration is allowed. Do not keep both the old and renamed owners locally.

A stable projection ID does not freeze the definition: Chronicle can still detect definition changes and
apply its normal evolution or replay behavior. It also does not preserve the read model's separate
identifier or storage container name; a type rename can still change those defaults.

## Key Features

Start with the fields your query needs, then choose how events should populate them. Use direct
mappings for values on the entity, joins for facts about related entities, and children or nested
objects for structure inside the read model. Specialized builder features, such as fluent dynamic
dictionary counters, do not all have attribute equivalents.

## Limitations

Use a declarative `IProjectionFor<T>` when a mapping needs projection-specific scope that attributes
on CLR members cannot describe. These independent examples focus on the mappings that need that scope.

### Child or Nested Every-Mappings on Join-Only Events

Attributes on a child or nested CLR member cannot preserve an every-mapping for events handled only
by a join in that scope. Model-bound generation expands those context mappings over local `from`
events, so the join-only event's timestamp mapping is lost.

<ChronicleClientTabs snippet="projections/model-bound/index/limitations-child-every" />

Here `LastUpdated` belongs to each line and tracks both `ChildAuditItemAddedToOrder` and
`ChildAuditProductRenamed`. See [declarative FromEvery](../declarative/from-every.mdx)
and [joining children](../declarative/joins.mdx#joining-children).

### Join-Context Values

A `[Join<TEvent>]` on a CLR member selects an event payload property, not a value from the joined
event's context. `[SetFromContext<TEvent>]` defines a local event mapping, not a join-context mapping.

<ChronicleClientTabs snippet="projections/model-bound/index/limitations-join-context" />

The join maps both the product name and the joined event's occurrence time. See
[event context in children and joins](../declarative/event-context.mdx#event-context-in-children-and-joins).

### One CLR Type With Different Mappings

Attributes bind to the CLR type's members, not to each use of that type. One address type cannot
carry different mappings for its billing and shipping roles; use separately scoped declarative mappings.

<ChronicleClientTabs snippet="projections/model-bound/index/limitations-reused-type" />

Both properties use the same address type, but each nested scope selects its own event and source
property. See [multiple nested objects](../declarative/nested.mdx#multiple-nested-objects).

## Generated Model-Bound Code: Representability Limits

If you generate model-bound C# from a projection declaration, check the generated comments before
switching to it. The generator keeps supported mappings and writes a
`Not expressible with model-bound attributes` comment where attributes cannot preserve the declaration's
meaning. Compiling that code does not prove equivalent behavior. Keep the declaration or the generated
declarative projection as the authoritative version when one of these comments appears.

| Declaration feature | Model-bound generation limit |
| --- | --- |
| Child `every` mapping from a payload property, such as `Quantity = Quantity` | Child every-event expansion supports event-context and event-source-id mappings, not payload mappings. The unsupported mapping is commented rather than turned into a misleading attribute. |
| Child `every` mapping from a join-only event's context | Context mappings expand over the child's local `from` events. An event subscribed only through a join cannot receive that context mapping through those attributes. The ordinary join payload mapping is retained. |
| One record type reused in incompatible projection scopes | Attributes live on the record type, not on each use. The generator comments the conflicting record and omits its projection attributes rather than silently choosing the first scope. |

### Child Every-Event Mapping and a Join-Only Event

This declaration excerpt assumes an `Order` read model with a `Lines` collection and the named
events already registered. The child's audit timestamp must update both for `ItemAddedToOrder`
and for the join-only `ProductRenamed` event:

```pdl
projection Order => Proof.Pdl.Order
  from OrderPlaced
  children Lines identified by ProductId
    from ItemAddedToOrder key ProductId
    every
      LastUpdated = $eventContext.occurred
    join Product on ProductId
      with ProductRenamed
        ProductName = Name
```

The generator can retain the `ItemAddedToOrder` context mapping and the `ProductRenamed` name
join, but the generated child attributes do not preserve the timestamp update for that join-only
event. It includes this comment in the generated output:

```text
// Not expressible with model-bound attributes: every-mapping 'LastUpdated' for join event 'ProductRenamed' in children 'Lines'. Use the declarative projection.
```

Do not remove the comment and assume the remaining attributes are equivalent. Keep this mapping
in the [projection declaration](../projection-declaration-language/index.md) or use a
[declarative projection](../declarative/index.mdx). Likewise, keep child every-event payload mappings
in the declaration rather than moving them to a root `[FromEvery]`: that changes which object owns
the mapping. See [every-event mappings](./from-every.mdx) and [joins](./joins.mdx).

### A Reused Record With Conflicting Scopes

Suppose both `BillingAddress` and `ShippingAddress` use the same `Address` record with a `Name`
property. This declaration excerpt requires different subscriptions and mappings for each use:

```pdl
projection Order => Proof.Pdl.Order
  from OrderPlaced
  nested BillingAddress
    from OrderPlaced
      Name = CustomerName
  nested ShippingAddress
    from ProductRegistered
      Name = Name
```

One set of attributes on `Address` cannot describe those two scopes independently. The generator
omits the conflicting record's projection attributes and emits:

```text
// Not expressible with model-bound attributes: conflicting projection scopes for record 'Address'. Use the declarative projection.
```

Keep the scoped mappings in the declaration or declarative projection. If model-bound ownership
is important, use distinct record types for the distinct roles and define their mappings explicitly.
Reusing a record type is not inherently unsupported; the limitation is incompatible projection
requirements on the same type, including incompatible descendant scopes.

## When to Use

Use model-bound attributes when keeping mappings beside the read model makes the update rules easy
to follow. Move to fluent mappings when the definition needs more structure, or reducer code when
state transitions are clearer in code. A self-reducing model is the default for new reducers.
[Choose how to build a read model](../choosing-a-read-model-style.mdx) works through these trade-offs
before you commit to a style.
