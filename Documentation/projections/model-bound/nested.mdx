# Nested Objects

A nested model-bound projection lets events populate, update, or clear one nullable object inside a parent read model. Use it for an optional part of the view, such as a command definition, whose fields change together. Use a child collection when the parent can contain several independently identified items.

The examples below use the .NET `[Nested]` attribute. TypeScript exposes `@nested`, and Kotlin and Java expose `@Nested`; the Elixir model-bound API does not expose a nested-object declaration.

## Basic Lifecycle

Mark the nullable parent property as nested, then declare the populate events on the nested type. Add clear events if the relationship can end:

<ChronicleClientTabs snippet="projections/model-bound/nested/basic-lifecycle" />

The object starts empty. As events arrive:

1. The first populate event creates the nested object.
2. Later populate events update the existing nested object.
3. A clear event sets the parent property back to `null`.

## Parent Property

Put `[Nested]` on the parent property that holds the object. Keeping it nullable represents both the initial empty state and the state after a clear event:

The nested type is scanned for its own model-bound projection annotations, including `FromEvent`, `ClearWith`, and property mappings.

## Clearing Nested Objects

Apply a clear annotation to the nested type when one event should remove the nested object from the parent.

<ChronicleClientTabs snippet="projections/model-bound/nested/clear-with" />

Use multiple clear annotations when more than one event should clear the same nested object.

<ChronicleClientTabs snippet="projections/model-bound/nested/multiple-clear-events" />

You can also put the clear annotation on the parent property. This is useful when several parents share the nested type but different events end their relationships. To clear one member while keeping the nested object, put the annotation on that member. See [Clearing Values](clearing) for that distinction.

## Complete Example

The parent in this example keeps an optional command definition. Setting the command populates it, later events change selected fields, and clearing it leaves the parent read model in place:

<ChronicleClientTabs snippet="projections/model-bound/nested/complete" />

| Event | Effect on the nested object |
| --- | --- |
| `SliceCreatedForNestedComplete` | Creates the parent read model; the nested command remains `null`. |
| `CommandSetForNestedComplete` | Populates the command object. |
| `CommandRenamedForNestedComplete` | Updates the command name in place. |
| `CommandDefinitionUpdatedForNestedComplete` | Updates command definition fields in place. |
| `CommandClearedForNestedComplete` | Sets the command property to `null`. |

## Supported Nested Annotations

| Annotation | Works on nested type |
| --- | --- |
| `FromEvent` | Yes |
| `ClearWith` | Yes |
| `SetFrom` | Yes |
| `AddFrom` / `SubtractFrom` | Yes |
| `SetFromContext` | Yes |
| `Increment` / `Decrement` / `Count` | Yes |
| `Join` | Supported on a root-level nested object, not on a nested object inside a child collection. |
| `Nested` recursively | Yes |
| `ChildrenFrom` inside nested objects | Not supported by the kernel. |
| `NoAutoMap` | Yes |

## Best Practices

Keep the populate events on the nested type and place clear annotations where the lifecycle is owned: on that type for a shared lifecycle, or on the parent property for an owner-specific one. Use AutoMap while names match and add explicit mappings where they differ.

For multiple independent objects, move to a [child collection](children). Nested objects cannot contain child collections, and removal through a join is not supported for nested objects.
