---
title: Choose how to build a read model
description: Choose between projection mappings and reducer code, compare the same library view four ways, and plan a safe change of style.
---

Your library screen needs a book's title and current borrower. Registration, borrowing, and return
are separate events, but the screen needs one answer: **what should this view read after this history?**
Copying a title should not require a custom fold. A state-dependent calculation should not be hidden
inside mapping attributes either.

Cratis Chronicle has two execution families. **Projections** describe mappings that the kernel runs;
**reducers** run your code over an event and the previous state to return the next state. Attributes,
a fluent definition, and Projection Declaration Language (PDL) are different inputs to the projection
engine. Static methods on the model and methods on a separate reducer class are different homes for
reducer code. Moving the declaration is not the same decision as changing execution families.

## Which one should I pick?

Start with the transition the view needs, then choose where it belongs. The API names here follow the
C# examples; each client tab owns its declaration form and support notes.

1. If events set, clear, count, or add values directly, start with **[model-bound attributes](model-bound/index.mdx)**. Keep a small mapping beside the model.
2. If that mapping becomes hard to scan, use **[fluent `IProjectionFor<T>`](declarative/index.mdx)**. Give keys, joins, and hierarchy a separate definition, or keep the model attribute-free. The kernel still executes the mapping.
3. If the transition needs branching over previous state, start with a **[self-reducing read model](../reducers/self-reducing-read-models.mdx)**. Use a separate **[`IReducerFor<T>`](../reducers/getting-started.mdx)** when the fold needs constructor dependencies or should stay outside the model. Durable state belongs in the returned model, not mutable service fields.
4. Use an explicitly nominated **[plain reducer class](../clients/dotnet/explicit-artifacts.md#plain-observers-and-constraint-definers)** when its assembly cannot reference Chronicle. Nomination still requires supported method signatures.

Use **[PDL](projection-declaration-language/index.md)** when the definition belongs outside application
code, such as the Workbench, Screenplay, or an [ad-hoc query](projection-declaration-language/adhoc-querying.mdx).
It is another projection input, not the code-first default.

### Match the choice to your task

| You need… | Pick | Why |
| --- | --- | --- |
| A screen showing a book's title and current borrower | Model-bound attributes | The events directly set or clear properties. Keep those mappings next to the shape the screen reads. |
| A dashboard counting loans or summing amounts | A projection; attributes first | Counting, incrementing, adding, and subtracting are built-in operations. For one total across event sources, use a [constant key](declarative/constant-key.mdx); arithmetic alone does not require a reducer. |
| A library with a collection of books | Fluent projection when the attributes become hard to scan | [Children](declarative/children.mdx) describe child identity, parent routing, updates, and removal. Attributes support children too. |
| A book view with a member's details from another event source | A projection, often fluent | A [join](declarative/joins.mdx) correlates events across sources and updates the view. Reducers fold one event source at a time and have no native join operation. |
| Composite keys, context fields, or an attribute-free model | Fluent projection | The builder makes [key structure](declarative/composite-keys.mdx) and [context mappings](declarative/event-context.mdx) explicit without decorating the model. |
| A status that depends on the previous status and a rule | Self-reducing model | Branch on `current` and return the next state. The rule and state live together. |
| A running balance that ignores a debit under a guard | Self-reducing model | Read the previous balance, apply the guard, and calculate the result in code. This derives a view; it does not reject the already-appended debit. |
| A fold that needs a currency-rate service or clock | Separate `IReducerFor<T>` | Constructor injection is available during the fold. Static `Reduce` accepts only event, current, and optional context. Prefer recording the rate or time in the event: consulting today's service during replay can change yesterday's result. |
| A model distributed as a shared contract | Separate `IReducerFor<T>` for stateful logic; fluent projection for mapping | Keep behavior in the consuming application without adding transitions or mapping attributes to the contract. |
| An observer assembly that cannot reference Chronicle | Nominated plain class | Register it at the composition root and let Chronicle infer its one model from supported instance methods. Nomination does not relax signature validation. |
| An Arc application with queries and state transitions on one record | Self-reducing model with `[ReadModel]` and static query methods | Keep the state, static `Reduce` methods, and query surface together. Apply the version guidance below so reduction does not become an endpoint. |
| A definition edited in the Workbench or authored in Screenplay | PDL | The definition is text owned by the tooling workflow. Check Chronicle's supported expression subset and save settings. |

:::caution[Arc query discovery]
In Arc applications, keep `[ReadModel]`, static `Reduce` methods, and query methods on the same record.
With Arc versions before 22.90.0, use `[ReadModel(RequireQueryAttribute = true)]` and mark
intended query methods `[Query]`. From Arc 22.90.0, Arc excludes methods taking the read model
itself from automatic query discovery, so `Reduce` does not become a query endpoint.
See [Arc's model-bound queries](/arc/backend/csharp/queries/model-bound/) for the query contract.
:::

## One library view, four implementations

Suppose registration records a title and ISBN, borrowing records a member name, and returning clears
the loan. Compare four implementations against that same history.

and default artifact discovery. They are alternatives, not four builders to attach to one model.
Their purpose is to compare transitions; they are not a complete library command workflow.

These examples deliberately define registration as a reset of loan state. Borrowing sets the borrower;
returning clears it. Borrowing or returning without prior state creates a partial view with the book's
ID and no title or ISBN. This is a view policy, not an assertion that such a loan is allowed.

### Model-bound: describe the mapping on the model

<ChronicleClientTabs snippet="projections/choosing-a-read-model-style/model-bound" />

Chronicle discovers the mapping attributes and builds a projection definition. Registration sets the
bibliographic fields **and** resets both loan fields. The explicit clear matters when a book is
registered again after a loan; an omitted mapping would leave the old borrower in place.

### Fluent: keep the definition separate

<ChronicleClientTabs snippet="projections/choosing-a-read-model-style/fluent" />

AutoMap supplies `Title` and `Isbn` from registration. The explicit mappings set the ID and loan
fields, including clearing the borrower on registration and return. The same operations now live in
one separate definition rather than on individual model properties.

`Define` builds the registration definition. Its lambdas describe paths and operations; they are not
service-injected handlers called for each event. Moving to fluent gives the mapping more room, not
arbitrary business logic during processing.

### Self-reducing: keep transitions with the state

<ChronicleClientTabs snippet="projections/choosing-a-read-model-style/self-reducing" />

Here the returned model is the transition. In the C# form, the complete public static `Reduce` shape
is the discovery signal; no model instance or reducer marker is needed. Every handler accepts nullable
current state, including borrowing and returning. Either event may be the first in the available
history or may follow removal, so those handlers create a partial view when `current` is absent.

### Separate reducer: put the fold on an instance

<ChronicleClientTabs snippet="projections/choosing-a-read-model-style/reducer" />

The instance methods return the same transitions, but Chronicle activates the reducer through its
service provider. Choose that extra type when constructor dependencies or separation from the data
contract earn their place. Dependencies that consult today's clock or external data can make replay
produce a different answer; prefer facts recorded on the event.

A nominated plain reducer keeps the instance fold while its model is inferred at
[explicit registration](../clients/dotnet/explicit-artifacts.md). It is an integration option, not a
way to bypass the reducer contract.

### Check the results

Use the following as the behavioral contract for event source `book-42`. Compare fields after each
history, rather than assuming that similar-looking declarations have the same reset behavior:

| Event history | Title / ISBN | Borrowed? | Borrower |
| --- | --- | --- | --- |
| No events | No instance | — | — |
| Registered("Dune", "9780441172719") | Dune / 9780441172719 | false | not set |
| Registered → Borrowed("Avery") | Dune / 9780441172719 | true | Avery |
| Registered → Borrowed → Returned | Dune / 9780441172719 | false | not set |
| Registered → Borrowed → Registered("Dune", "9780441172719") | Dune / 9780441172719 | false | not set |
| Borrowed("Avery") without registration | not set | true | Avery |
| Returned without registration | not set | false | not set |

"Not set" means the field holds no value; each client represents that in its own way. `Id` is
`book-42` in every existing instance. Re-registration is an important row: it clears the loan just as
first registration does. Borrowing and returning without registration test the absent-state policy.

The snippets use distinct model names so the alternatives can coexist in source. Those names give
them different registered identifiers and default containers. Equal field values do **not** make them
interchangeable persisted documents.

The borrower's name is personal data. The snippets mark both the event member and the destination
member as personal data; a mapping does not transfer compliance annotations. In a real library, select the member
as the append's subject rather than accepting the book ID fallback. Review [read-model compliance](../compliance/read-models.mdx)
before deploying: projections retain per-property subject lineage, while reducer protection uses the
batch's default subject resolved from its first event. Output equality alone does not prove equal
subject ownership.

## Capabilities that change the choice

Once the basic transition fits, check the features the view also needs. This table uses the .NET
contracts; it is not a claim that every client exposes the same authoring surface. Consult the linked
pages and client tabs before choosing an API. The separate column covers `IReducerFor<T>` and nominated
plain instance reducers.

| Capability | Attributes | Fluent | PDL | Self reducer | Separate reducer |
| --- | --- | --- | --- | --- | --- |
| [Logic location](architecture.mdx) | Model metadata | Separate `Define` class | Declaration text | Static model methods | Instance methods on another class |
| [Dependency injection during fold](../reducers/getting-started.mdx) | No | No; DI can build the definition | No | No | Yes |
| [Joins across event sources](declarative/joins.mdx) | Yes | Yes | Yes | No native joins | No native joins |
| [Children](declarative/children.mdx) / [nested objects](declarative/nested.mdx) | Mappings | Mappings | Blocks | Your code | Your code |
| [Counters and sums](declarative/functions.mdx) | Operations; no dynamic dictionary-counter form | Operations, including dynamic dictionary counters | Operations | Your code, per source | Your code, per source |
| [Remove an instance](model-bound/removal.mdx) | Removal attributes | Removal builders | Removal blocks | Return null | Return null |
| [Variant groups](model-bound/variants.mdx) | `VariantOf` / `EntersOn` / `GlobalFor` | `VariantOf` / `EntersOn`; no `GlobalFor` equivalent | No native group block | No native group wiring | No native group wiring |
| [Passive reads](../read-models/consistency.md) | `[Passive]` on model | `.Passive()` | No native passive clause | `[Passive]` on model | `[Passive]` on model |
| [Append-metadata filters](filtering.mdx) | No | No | No | Tags, source type, stream type | Tags, source type, stream type |
| [Replay lifecycle hooks](../reducers/self-reducing-read-models.mdx#optional-replay-hooks) | No handler hooks | No handler hooks | No hook clauses | Static `Task` hooks; hook services allowed | Replay notification interfaces |
| [Decision reads](../read-models/decision-reads.mdx) | Admitted shapes only | Admitted shapes only | No direct .NET client-catalog registration path | Admitted without filters or constructor dependencies | Admitted without filters |
| [ReadModelScenario](../testing/read-models/scenario.mdx) | Yes | Yes | No direct PDL overload | Yes | Yes, including nominated plain classes |

Metadata subscription filters have no stream-ID option. Observer tags are descriptive labels, not
append-tag filters. For decision reads, check admission before building the workflow: the projection
must be a finite, flat event-log shape without joins or hierarchy, with a supported source key (or an
admitted stream-scoped key). PDL's save path also chooses effective sequence and generation settings;
do not assume a declaration has every configuration option of a code-authored projection.

## When it is the wrong fit

**Leave mappings when they obscure the transition.** Several branches over previous state or a
guarded calculation usually read better in a reducer. A fluent class does not change that boundary.
PDL also accepts Chronicle's supported projection expressions, not every Screenplay expression.

**Leave reducer code when it recreates projection machinery.** Counts and sums already have mapping
operations. Cross-source joins, custom aggregation keys, and mutually exclusive variants belong to
projections; reducers are event-source keyed. Replay runs reducer code again, so returning state is
not permission to send external effects or assume exactly-once execution.

### Choose freshness separately

A materialized view is updated asynchronously, whichever family builds it. A passive model computes
an answer on demand instead. Choose [materialized or passive reads](../read-models/consistency.md)
separately from authoring style: passive by-ID projection reads select one event source and cannot
generally reconstruct cross-source joins or custom-key aggregations. Passive is not a synchronous
append mode.

A fresh result also does not protect a command from another writer. Use
[decision reads](../read-models/decision-reads.mdx) only with an admitted shape when the decision must
remain valid until append. A classic reducer with filters or constructor dependencies other than
`ILogger<T>` is not admitted; self-reducing models are exempt from that dependency rule. See
[reducers as decision reads](../read-models/decision-reads.mdx#reducers).

## What it costs to switch later

You can keep event contracts, the read-model schema, the query surface, and the expected field values
when the new form expresses the same behavior. Storage continuity takes more care:

| What to check | Why it matters |
| --- | --- |
| Read-model identifier | In .NET it is the full model type name. Renaming or moving the model changes that identity. |
| Observer identifier and scope | Attributes default to the model's full name; fluent and separate reducer classes default to their own full names; self reducers default to the model's full name; PDL uses its declaration name. Explicit IDs can preserve observer identity, but store, namespace, and sequence also scope progress. |
| Container name | The default .NET naming policy pluralizes the short model name. A namespace move can keep the container while changing identity; a type rename usually changes both. Fluent projections can override the container; reducers have no equivalent override. A rename points reads elsewhere and does not copy data. |
| Replay or rebuild | Definition and reducer-implementation changes are evaluated under the configured evolution policy. Expect replay work or a recommendation; not every source edit triggers a full rebuild. Reusing an ID across projection and reducer kinds is not a state or schema migration. |
| Compliance lineage | A projection's per-property subject tracking and a reducer's batch/default subject protection differ. Keep model PII annotations and verify subject ownership, release, and erasure after a family change. |

Treat a switch as two checks: does the replacement derive the same answer, and can it take ownership
of the deployed view without losing its storage or compliance contract?

1. Record existing identifiers, scope, container, and configuration before editing. Preserve the identities you intend to keep; moving or renaming a type can change them.
2. Replace the old builder deliberately. A self model cannot share ownership with another reducer or projection in the same catalog. Moving to static methods also means replacing constructor dependencies and replay interfaces.
3. Run the same event histories against the replacement, then exercise registration and replay with the intended kernel and sink. Check stored-state compatibility, catch-up, query results, indexes, and compliance.
4. Inspect [registration outcomes](../clients/dotnet/registration-outcome.md) and [projection evolution and retirement](registration-lifecycle.md). Coordinate stopping the old writer before starting the replacement; a running client alone is not evidence that every definition registered.

Projection retirement retains its container, and successor recommendations concern projections, not
reducers. Reusing an ID across families does not migrate state or schema. Plan that rebuild explicitly.
