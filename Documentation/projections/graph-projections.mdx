# Graph projections

A graph projection projects events onto a **property graph**: nodes, edges and their properties. It works like a projection onto a document read model. It uses the same observer, the same event routing, the same key and property expressions, the same replay and the same failed partition handling. The difference is the target. Instead of folding events into one document per key, it turns each event into a few idempotent **operations** on nodes and edges.

The graph is what the events leave behind. Nothing writes to it directly.

## Nodes and edges

A **node** has a label, a unique key and properties. The label is the name of the type. A property is a primitive or an array of primitives. An object property is an error: model the object as a node of its own and connect it with an edge.

An **edge** connects two nodes. It has a type, such as `MEMBER_OF`, a source node, a target node and properties. By default an edge is identified by its type, source and target, so there is at most one edge of a type between two nodes. An edge type can name an **identifying property**, which allows several edges of the same type between the same two nodes.

A graph is named. Put `[Graph("Organization")]` on the types or on the assembly. Without it, the graph is named after the assembly's root namespace.

## Model-bound

Mark the types with `[Node]` and `[Edge]` and use the model-bound projection attributes on them. `[Key]` on a node marks its unique key. On an edge, `[Source<>]` and `[Target<>]` mark the members that hold the keys of the end nodes. Those members are not properties of the edge.

<ChronicleClientTabs snippet="projections/graph/model-bound" />

Properties are mapped by name from an event that has a property of the same name, or explicitly with the attributes you already know: `[SetFrom<>]`, `[SetFromContext<>]`, `[Increment<>]`, `[Decrement<>]`, `[Count<>]`, `[AddFrom<>]` and `[SubtractFrom<>]`. The node key is the event source id unless `[FromEvent<>]` names an event property.

## Edges with an identity

Give an edge a `[Key]` member to identify it among edges of the same type between the same two nodes. Every mapping of the edge must then say which event property holds the identity, with the `identity` argument or `UsingIdentity`. A sink that cannot hold several edges between the same pair of nodes rejects such an edge type.

<ChronicleClientTabs snippet="projections/graph/identified-edge" />

## One operation per item of a collection

An event that carries a collection can map each item to its own node or edge. Name the collection in the mapping's `ForEach` (contract `GraphNodeFromDefinition`, `GraphEdgeFromDefinition` and the two removed-with definitions). The key, source, target, identity and property expressions then run once per item, and they address the item's properties as `collection.property`, for example `slots.series`.

An event whose collection is absent or empty produces nothing for that mapping. Each operation is still keyed by the node key, or the edge's source, target and identity, so redelivery and replay stay idempotent. To retract the items of a collection, use a removed-with mapping with the same `ForEach`.

## The operations

A graph projection does not produce state diffs. For every event it produces a `GraphChangeset`, a list of five idempotent operations:

| Operation | What it does |
| --- | --- |
| `UpsertNode` | Creates the node when it does not exist and sets its properties. |
| `SetProperties` | Sets properties on a node or an edge that exists. Nothing is created. |
| `DeleteNode` | Deletes a node. With `detach`, the edges attached to it are deleted too; without, a node that still has edges cannot be deleted. |
| `UpsertEdge` | Creates the edge when it does not exist and sets its properties. |
| `DeleteEdge` | Deletes an edge. The nodes at both ends stay. |

Some rules follow from the operations:

- **Edges ensure their nodes.** An edge operation creates a bare end node, without properties, when it does not exist. A node mapping completes it later.
- **A projection owns what it declares.** It owns the edges and the node properties it maps, and it never deletes a node it did not declare.
- **Counters carry absolute values.** The engine reads the current value of the node or edge from the sink, applies the counter, and the operation carries the result.
- **Removing a node needs an explicit decision.** `RemovedWith` deletes the node. Set `detach` to delete its edges with it.

## Redelivery and replay

Every node and edge stores the **watermark**: the sequence number of the event that last wrote it. A write whose event sequence number is at or below the watermark is skipped. Redelivered and out-of-order events therefore do not apply twice. A bare node that only an edge has created has no watermark yet, so its node mapping can still write it.

Replay is **mark and sweep**. A replay starts a new generation for the replaying projection. An element of the projection that the replay has not written yet reads as absent, so counters are rebuilt from zero instead of counted on top of the previous result, and the first write replaces the element. When the replay ends, every element of the projection that was not written is deleted. Elements that other projections wrote, and nodes that only edges created, are never touched. A stale node that edges of other projections still point at stays as a bare node.

## Writing a graph sink

A sink implements `IGraphSink`, separate from the `ISink` of document read models, because the fold semantics of `ISink` do not apply. A graph sink:

- Applies a `GraphChangeset` with `ApplyGraphChanges`, subject to the watermark rule, and applies the operations of one changeset atomically.
- Stamps every element it writes with the owning projection and its replay generation, and implements `BeginReplay`, `ResumeReplay`, `EndReplay` and `LeaveReplay` as mark and sweep.
- Reports an element of the replaying owner that has not been rewritten as absent from `FindNode` and `FindEdge`.
- Creates its constraints and indexes from the graph definition in `EnsureSchema`.
- Reads instances for the Workbench with `GetNodes` and `GetEdges`.

The in-memory graph sink is the executable reference for these semantics, and every behavior has a specification.

## Read a graph with views

A **view** reads a graph back as a typed read model. It is anchored at one node and lists what to read from it: the node's properties, relations along edges to other views, and properties of the edge that was followed. Views only read. They do not change the graph, its schema or what is registered, and a graph without views behaves exactly as before.

Declare one view per consumer, shaped for what that consumer reads, rather than one shape shared by every screen.

### Declare a view

Mark the record with `ViewOf<TNode>`, naming the node it is anchored at. The view belongs to the graph of that node. A member is a property of the node, matched by name after the naming policy. The member with `[Key]`, or a member named `Id` when the node has no property of that name, reads the key of the node. `FromNode("property")` reads a node property that is named differently.

<ChronicleClientTabs snippet="projections/graph/views" />

### Nest views

`Follows<TEdge>` makes a member a relation: it follows the edge to the view at the far end. A collection member holds every related item, an empty list when there is none. A single member holds the one related item, or null. The direction is derived from the root of the view: from the source of the edge it is outgoing, from the target it is incoming. An edge whose source and target are the same node type, such as a group that is part of a group, needs an explicit direction, for example `Follows<PartOf>(GraphViewDirection.Outgoing)`.

Nesting is finite. A view cannot contain itself, directly or through other views; declare a separate view for each level you read.

### Read properties of the edge

`FromEdge` makes a member a property of the edge that was followed to reach the view, such as the date a person joined a group. Give it the property name when the member is named differently. A view that reads edge properties is only valid as the target of relations along one edge type.

### Query a view

`IGraph` is the entry point. `Nodes<TView>()` starts a query for the roots of a view. `Where` keeps the roots whose property equals a value, and `WhereRelated` keeps the roots that have at least one related item, optionally one whose properties equal given values. Clauses name members with selectors, never free predicates, so a query that compiles always translates. `ToList` returns every matching root and `FirstOrDefault` the first one, or null.

<ChronicleClientTabs snippet="projections/graph/views-query" />

Clauses only select roots. A relation always holds every related item, never only the ones a clause matched.

### Hydration

The read result arrives as neutral rows and is built into the view records. Values are converted from what the graph stores: a concept from the value it wraps, a `Guid` from its string, an enum from its name, a decimal from a number and a timestamp from its stored form. A property the graph does not have, such as on a bare node that only an edge has created, reads as null or the type's default.

### Test with GraphScenario

`GraphScenario` reads the views of the graphs it runs and queries them against its in-memory graph through `scenario.Graph`. Append events and query the views they leave behind, or put nodes and edges straight into the graph with `SeedNode` and `SeedEdge`.

<ChronicleClientTabs snippet="projections/graph/views-testing" />

### How reads execute

The client compiles a query to a backend-neutral `GraphQuery` and hands it to an `IGraphQueryExecutor`, which returns `GraphRow` trees. A host package that reaches the graph store provides the executor, and with it the `IGraph` an application uses; the Chronicle client does not read the store itself. `GraphViews.Discover` finds the views and the graphs they read from the client artifacts, and `QueryableGraph` combines the views with an executor. The in-memory executor of `GraphScenario` is the reference every executor is held to.

### Limits

- Nesting is finite, and there are no variable-length paths.
- Roots and related items are ordered by node key, then by the identity of an identified edge. There is no other ordering, no aggregation, no `or` and no ranges.
- Reads are eventually consistent with the event log and can see stale elements while a projection replays.
- A view that breaks a declaration rule is reported when the client registers its graphs and left out; the graphs and the other views still register.

## Analyzers

The code analysis package reports a graph or view declaration that cannot work:

- [CHR0066](../code-analysis/CHR0066.mdx): a node or an edge has an object property.
- [CHR0067](../code-analysis/CHR0067.mdx): a node does not have exactly one key, or an edge has more than one.
- [CHR0068](../code-analysis/CHR0068.mdx): a type is both a node or an edge and a read model.
- [CHR0078](../code-analysis/CHR0078.mdx): a view is anchored at a type that is not a node.
- [CHR0079](../code-analysis/CHR0079.mdx): a relation of a view follows a type that is not an edge.
- [CHR0080](../code-analysis/CHR0080.mdx): a relation of a view leads to a type that is not a view.
- [CHR0081](../code-analysis/CHR0081.mdx): a type is both a view and a node or an edge.
