# Appended event metadata and projections

Chronicle projections consume every event of the types declared in their mappings, regardless of
append metadata. To build a view or trigger an effect from only tagged events, use a reducer or
reactor alongside the projection. `[FilterEventsByTag]`, `[EventSourceType]`, and `[EventStreamType]`
do not narrow a projection's input.

## How projections select their input

Choose the input event types in the mapping definition. This order summary maps placement and
shipping events:

<ChronicleClientTabs snippet="projections/filtering/basic" />

The projection receives every event of those declared types. Adding a tag or stream type when
appending an order does not change whether the projection sees it.

Changing the mapped event types changes the state that can be built from history. Review
[definition evolution](registration-lifecycle.md#when-a-definition-changes) before deploying that
change: newly selected event types with existing history require a rebuild.

## Tagging projections

`[Tag]` and `[Tags]` on a projection label the projection definition for organizational purposes. They do not filter incoming events:

<ChronicleClientTabs snippet="projections/filtering/tagging" />

:::note[Client coverage]
C# supports `[Tag]`/`[Tags]`, and TypeScript supports `@tag`/`@tags` on projection classes and model-bound read models. Kotlin and Elixir do not support projection tags. The kernel stores and returns projection tags as descriptive metadata, without filtering incoming events or triggering a replay when only tags change.
:::
