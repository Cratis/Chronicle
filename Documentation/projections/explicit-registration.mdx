---
title: Chronicle projections — register a read model explicitly
description: Register a Chronicle read model and projection without assembly discovery. Choose a stable identifier and understand reconnects and ownership conflicts.
---

Register a Chronicle read model and its projection explicitly when assembly discovery cannot find
them, such as a library outside the scanned assemblies or a projection generated at runtime. In the
.NET client, explicit registration uses the same projection builder and kernel registration path as
discovered definitions.

Only the way the client learns about the definition changes. Reads still follow the model's
materialized or passive behavior, and a materialized projection still catches up asynchronously.
Registration does not make existing history appear in the sink before it returns.

## Register a projection defined in code

Define the projection with the same builder an `IProjectionFor<T>` class receives:

<ChronicleClientTabs snippet="projections/explicit-registration/declarative" />

By default the projection is identified by the read model's full type name, the same identity a
model-bound projection for that read model would have. Pass an identifier when the projection's
identity has to survive renaming the read model. Keep it stable: Chronicle tracks the projection's
position under that identifier.

A stable projection ID does not preserve every storage identity. Renaming the model can still change
its read-model identifier and default container. Plan that separately using
[the read-model migration checklist](choosing-a-read-model-style.mdx#what-it-costs-to-switch-later).

## Register a passive projection

A projection defined with `Passive()` is not materialized. Chronicle registers its read model without
a sink, so each read computes the instance from its events on demand:

<ChronicleClientTabs snippet="projections/explicit-registration/passive" />

A passive by-ID read selects one event source. Keep a view with cross-source joins or custom
aggregation keys materialized when that history is needed to reconstruct it. See
[passive projections](declarative/passive.mdx) before changing an existing model's consistency behavior.

## Register a model-bound read model

A read model whose projection is declared by [model-bound attributes](model-bound/) but is not in a scanned assembly can be registered by type:

<ChronicleClientTabs snippet="projections/explicit-registration/model-bound" />

`ReadModels.Register<T>()` recognizes a read model that no projection or reducer maintains yet, but that carries model-bound attributes, and registers its projection. `Projections.Register<T>()` does the same thing without the read model detour. A read model that discovery already found is not registered twice.

## Register while configuring the client

Registrations made on an event store are sent to Chronicle immediately when the client is connected. Anything registered before the connection is established, or re-established, is included in the next registration pass instead.

To declare registrations before the client exists, from hosting or dependency injection setup, add them to the client options. Every event store the client creates builds them when it discovers its artifacts. It includes them in its normal registration pass and registers them again after every reconnect:

<ChronicleClientTabs snippet="projections/explicit-registration/at-startup" />

Registrations on the options are captured when the store is constructed and built during discovery, which is on by default (`AutoDiscoverAndRegister`). Later options changes apply only to new stores; reconnect retains the original recipes. A projection that cannot be built is reported through the event store's registration outcome, like a discovered one.

Event types and the other artifact kinds can also be nominated without marker interfaces or attributes. See [explicit artifact registration](../clients/dotnet/explicit-artifacts) for the .NET composition APIs, peer conflicts and lifetime rules.

## Rules

- A read model has one builder: a projection or a reducer. Registering a second projection with a different identifier for the same read model is rejected. Registering the same identifier again replaces the definition.
- An explicit projection cannot claim a read model that a discovered projection already maintains.
- [Variants](declarative/variants) are wired together with their siblings during discovery, so a variant read model cannot be registered on its own.

After registering, inspect the [registration outcome](../clients/dotnet/registration-outcome.md) for
failed definitions. If you replace a definition under the same ID, the
[registration lifecycle](registration-lifecycle.md) determines whether historical data needs replay;
re-registering alone is not a storage migration.
