Concurrency dimensions on a Cratis Chronicle event source definition decide which competing appends can reject a write. Choose an account-wide boundary when every change matters, or a stream boundary when different parts of the history can progress independently. These .NET examples build on the general [concurrency scope model](../events/concurrency.mdx).

## What an append is guarded by

When you append without passing a `ConcurrencyScope`, the client captures the tail, the latest matching event position, and sends it as the expected position. The kernel rejects the append if a matching event arrived after that position. The definition's dimensions choose which routing values must match:

| The append goes through | The scope narrows to |
|---|---|
| No definition | The append's event source ID, event source type, event stream type and event stream ID |
| A definition whose dimensions are `None` | The same four values, as without a definition |
| A definition with dimensions | Only the dimensions it declares |

The four values are the routing values of an event. What each one means is in [Event source](../concepts/event-source.md), and how they build a scope is in [Concurrency](../events/concurrency.mdx#formalized-metadata-tags-for-concurrency). The client reads the tail with exactly the narrowing it sends, so the position and the check ask the same question. A dimension that is not declared is left out, not set to a default.

Leaving `EventSourceId` out of a nonempty declaration makes the condition apply across source ids. For example, a scope narrowed only to stream type and month sees matching events for every account. [CHR0062](../code-analysis/CHR0062.mdx) reports this at Info severity and offers a fix to include `EventSourceId`.

Keep a cross-source condition only when the rule needs it. A default scope captured during append does not protect state you read before that capture. Use [decision reads](../read-models/decision-reads.mdx) for decisions based on earlier state, and declared dimensions for stream-wide conditions such as shared numbering. [How guards are derived](../dynamic-consistency-boundary/how-guards-are-derived.mdx#declared-routing-on-a-definition) explains how those conditions combine.

## Which dimensions apply

Chronicle picks the dimensions with `ConcurrencyFor`:

1. If the stream declares any dimensions, those are used. The event source's dimensions are ignored.
2. Otherwise the event source's dimensions are used.
3. An append without a stream uses the event source's.

A stream cannot opt out. `None` on a stream means "not declared", so it inherits. To make a stream narrower or wider than its event source, declare the dimensions on the stream.

With that definition, the scopes are:

| Append | Dimensions used | Scope narrows to |
|---|---|---|
| `Onboarding` stream | the event source's: `EventSourceId` | Every event of this account, in any stream |
| `Transactions` stream, month `2026-04` | the stream's: `EventSourceId`, `EventStreamType`, `EventStreamId` | Events of this account in `Transactions` with stream id `2026-04` |
| No stream | the event source's: `EventSourceId` | Every event of this account |

These scopes do not filter by event type, so any event in the selected range counts. That suits a rule for which every change to the source or stream matters. When only particular event types affect the decision, use a [decision read](../read-models/decision-reads.mdx) or an explicit scope with `WithEventType`.

The check can be asymmetric. A `Transactions` deposit does not check `Onboarding` events, but an `Onboarding` append checks every event of the account, including deposits.

## What conflicts

Assume matching history already exists, and both writers capture their expected positions before either appends. The second append is rejected if the first event falls inside the second writer's scope:

| First writer appends to | Second writer appends to | Conflict? |
|---|---|---|
| Account A, `Transactions`, `2026-04` | Account A, `Transactions`, `2026-04` | Yes |
| Account A, `Transactions`, `2026-04` | Account A, `Transactions`, `2026-05` | No |
| Account A, `Transactions`, `2026-04` | Account B, `Transactions`, `2026-04` | No |
| Account A, `Transactions`, `2026-04` | Account A, `Onboarding` | Yes. The onboarding scope covers the whole account |
| Account A, `Onboarding` | Account A, `Transactions`, `2026-04` | No. The transactions scope does not cover onboarding |

A conflict is a normal result, not an exception. The append returns with `HasConcurrencyViolations` set and nothing is written. Read the new state, decide again and append again.

## The first append into a scope

A narrowed scope needs an event to compare with. When no event matches the narrowing yet, such as the first deposit of a new month, the client has no position to send and the kernel skips the check. By default two writers can both make the first append into a new stream and both succeed.

Turn on `ConcurrencyOptions.CheckFirstAppendIntoAScope`, or build the scope with `ExpectingNoMatchingEvent()` for one append, to check it. See [The first append into a scope is not checked by default](../events/concurrency.mdx#the-first-append-into-a-scope-is-not-checked-by-default). The result's `ConcurrencyCheckPerformed` tells you whether a check ran.

## Build an explicit scope

An append that passes its own `ConcurrencyScope` skips the dimension logic. This is how you guard a decision you made from earlier reads: capture the tail first, read the facts, decide, then append with that position.

<ChronicleClientTabs snippet="event-sources/concurrency/explicit-scope" variants="csharp" />

`ForEventSource<TSource>(stream, streamId)` resolves the source type and any supplied stream name from the definition, then uses the stream id you provide. It does not read the dimension flags. Add `WithEventSourceId` and `WithSequenceNumber` yourself to select the instance and expected position. An undeclared stream throws `EventStreamDoesNotBelongToEventSource`.

The scope retains a link to its definition, even through `with` copies. That lets the client catch a scope for `T.Onboarding` passed to an append through `T.Transactions`: it throws `ConcurrencyScopeStreamDoesNotMatchAppend` before sending the append. This check applies to `AppendThroughEventSource`, `AppendManyThroughEventSource` and `AppendPreparedThroughEventSource`, including their typed extension methods. [CHR0063](../code-analysis/CHR0063.mdx) warns when the mismatch is visible in source.

To intentionally guard one stream while writing another, use labelled `AppendMany` conditions. Ordinary `AppendPrepared` also stays independent because its prepared content has no definition route. The mismatch check does not refuse a scope without a definition link, one for another definition, or one without stream narrowing. `ConcurrencyOptions.AllowRouteScopeStreamMismatch = true` restores legacy acceptance for single-route APIs.

For an empty stream, `GetTailSequenceNumber` returns `Unavailable`. A narrowed caller-supplied scope treats that as an expectation that no matching event exists. An empty builder or wildcard-only scope does not become a whole-log expectation. Set `ConcurrencyOptions.SkipIncompleteExplicitScopes = true` only if you need the legacy behavior that skips incomplete scopes. The example explicitly converts to `EventSequenceNumber.BeforeFirst` to state the empty-stream expectation without depending on that switch.

A [decision read](../read-models/decision-reads.mdx) does the capture-then-read sequence for you. See [Dynamic Consistency Boundary](./dcb.mdx).

## A batch that needs two guards for one event source id

An `AppendMany` can require several guards for the same event source id. Every guard must hold against the state before the batch; if one fails, none of the events are appended.

When you pass no explicit scope for an id, the .NET client resolves every distinct route, including routes without definitions. Identical matching conditions, called predicates, share the earliest expected position. Different stream ids, stream types, source types or event-type filters retain separate guards; Chronicle does not widen them into a whole-source check. An unchecked entry never hides a later guarded entry.

For explicit guards, pass an ordered `IEnumerable<KeyValuePair<EventSourceId, ConcurrencyScope>>` to `AppendMany(events, correlationId, tags, concurrencyScopes)`. Labels may repeat for different predicates. This also supports writing just one event while guarding several streams. `AppendManyWithNamedTags` accepts the same list after its correlation id and tags parameters.

`EventsWithConcurrencyScopes.Entries` preserves every guard for reactor return values. Its legacy `ConcurrencyScopes` dictionary accessor works only with one scope per label and throws rather than discarding guards when a label repeats. The unit of work retains every enrolled predicate too. Conflicting expected positions for the same explicit predicate are refused; do not mix `ConcurrencyScope.None` with a real guard on the same label.

The connected kernel must advertise `concurrency-scope-conjunctions`. Without it, the .NET client throws `IncompatibleConcurrencyScopesForEventSource` before sending repeated labels. Upgrade the kernel, or deliberately choose one explicit scope that covers the entire decision. Splitting appends does not preserve a decision that needs both guards atomically.

## History mutations

Revisions and redactions do not advance the append position. Supported .NET decision reads also capture a mutation epoch, a version that changes when stored history is revised or redacted. The kernel checks it with the append position, so a changed epoch rejects the guarded append even when no new event arrived.

A scope containing only an append position does not gain that protection. For mutation paths or clients that do not carry the epoch, pause affected producers and drain in-flight decisions before changing history, then resume with fresh reads. See [history mutations and append conditions](../events/concurrency.mdx#revisions-and-redactions-are-outside-append-conditions).
