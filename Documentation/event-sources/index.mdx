title: Cratis Chronicle event sources and streams
description: Use Cratis Chronicle event source definitions to name event histories, route appends into streams, and choose concurrency boundaries for writers.
---

An event source is the thing whose history you record in Cratis Chronicle, such as a bank account or a shopping cart. An event source definition names that kind of thing and declares its streams and default concurrency dimensions, the fields that determine which appends can conflict. Append through the definition to reuse those names and concurrency settings across callers.

A stream is a named part of that history. An account might separate `Onboarding` from `Transactions`, then use a stream id to identify each month's transactions. The definition keeps the stream names in one place. The client validates the selected stream before sending an append, and the kernel checks the routing against the registered definition. You can still append without a definition; the plain APIs accept routing values and derive a default concurrency scope.

## The vocabulary

Four routing values identify where an event belongs. The definition supplies the source type and stream type; the caller supplies the instance ids.

| Term | What it is | Where it comes from |
|---|---|---|
| `EventSourceId` | The instance, such as one account | The caller, on every append |
| Event source type (`EventSourceType`) | The kind of event source, such as `Account` | The definition's name |
| Event stream type (`EventStreamType`) | A named process of the event source, such as `Transactions` | The name of a stream the definition declares |
| Event stream id (`EventStreamId`) | One instance of a stream, such as `2026-04` | The caller. Chronicle imposes no format |

Each event also records the name of the definition it was appended through, in `EventContext.EventSource`. It is empty for events that were appended without a definition.

A definition-derived guard covers all event types in the selected source or stream. Use it when every append in that range can affect the same decision. For a rule that depends on only some event types, a [decision read](../read-models/decision-reads.mdx) supplies a narrower condition based on the model you read.

The definition does not hold entity state or list the event types it owns. Routing belongs to the append, so the same event type can be appended through different definitions. Each event has exactly one event source and at most one stream.

## When to use a definition

Use one when:

- Events of one kind of entity are written from several places and the routing strings must agree.
- An entity has independent sub-histories, such as one stream per month, per author or per process step, and you want writers on different sub-histories not to conflict.
- You want [observers](./filtering.mdx) that handle only one stream.
- You want to close one stream and keep the rest of the entity open. See [Close a stream](./closing.mdx).

Skip it when every event of an entity can share one history and one guard. The plain append APIs are still valid and need no definition. See [Questions and pitfalls](./faq.mdx#when-should-i-not-use-a-definition).

## Client support

Event source definitions are supported by the .NET, [Kotlin](https://github.com/Cratis/Chronicle.Kotlin), [TypeScript](https://github.com/Cratis/Chronicle.TypeScript) and [Elixir](https://github.com/Cratis/Chronicle.Elixir) clients. The [Python client](https://github.com/Cratis/Chronicle.Python) has no definition API. The Kotlin, TypeScript, Elixir and Python packages under `Source/Clients` in this repository only hold generated kernel contracts. The examples in this section use .NET. Other clients have their own declaration and append APIs, and their concurrency behavior differs. Use their repositories for client-specific syntax and [Where the clients differ](../clients/where-the-clients-differ.md) for append and concurrency differences. The Workbench lists definitions registered with the kernel.
