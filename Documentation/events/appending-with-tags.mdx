---
title: Append Chronicle events with tags
description: Add plain or named tags when appending Chronicle events to categorize them, filter reducers and reactors, or find events by a runtime identifier.
---
Add tags when appending Chronicle events so you can categorize or find them without adding fields to the event payload. Use plain string tags to select events for reducers and reactors, or named tags to attach a name and value such as a checkout session identifier.

Custom tags do not take part in concurrency control. A [concurrency scope](./concurrency.mdx) narrows by the built-in metadata tags below and by event type.

## Built-in metadata tags

Chronicle maintains built-in metadata tags for event identity and stream routing:

- `EventSourceType`
- `EventSourceId`
- `EventStreamType`
- `EventStreamId`

You can add custom tags in addition to these built-in tags. For the full list and behavior, see [Event Metadata Tags](../concepts/event-metadata-tags.md).

## Custom tags

Pass plain string tags through the `tags:` argument when appending. Chronicle merges them with any static tags defined on the event type.

## Named tags

A named tag pairs a name with an exact value, for example `checkout-session` = `c-81f2`. Use one when you want to find events by a runtime identifier later. [Tagging](../concepts/tagging.mdx#named-tags) explains the matching rules and how to query by named tag.

### Append with named tags

Use `AppendWithNamedTags` to supply name/value pairs alongside any plain tags. The existing `Append` call remains unchanged.

<ChronicleClientTabs snippet="events/appending-with-tags/append-named-tags" />

In this example, `checkout-session` identifies the session and `sales-channel` records `web`. The plain `checkout` tag remains separate: named tags do not change plain-tag matching.

### AppendMany with named tags

Use `AppendManyWithNamedTags` to add named tags to every event in a batch. Each event can also carry its own named tags, so a transfer can share one identifier while the withdrawal and deposit retain different `ledger-side` values. Chronicle merges the two sets for each event:

- An exact duplicate of a name and value pair is kept once.
- The same name with a different value stays as a separate tag.

<ChronicleClientTabs snippet="events/appending-with-tags/append-many-named-tags" />

Transactional appends through a unit of work accept named tags the same way.

:::caution[Upgrade the Chronicle server first]
An older Chronicle server rejects named-tag appends instead of dropping the tags; the .NET client surfaces an `RpcException` with status code `Unimplemented`. MongoDB, SQL, and in-memory storage support named tags on an upgraded server. SQL reserves the table name `__cratis_named_tags` in each event-store namespace database; a conflicting table with that name causes every event-sequence operation in that namespace to fail with `NamedTagsTableCollision` on first access (migration is lazy), until the table is renamed.
:::

Named tags are plaintext and are not encrypted by the compliance features. Don't put secrets or personal data in them.
