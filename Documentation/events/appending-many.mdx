# Appending many

`AppendMany` stores several events in one atomic batch: either all are committed or none are. Use it when one decision produces several facts that must stay together, or when an import has a batch ready to write. Events in the batch can belong to different event sources.

> [!NOTE]
> With Cratis Arc and the Chronicle extension, a command handler can return events for Chronicle to append. See [Arc Chronicle commands](/arc/backend/csharp/chronicle/commands/).

If your workflow produces events across several calls and is not ready to send them yet, stage them in a [unit of work](./transactions.mdx) instead.

## How it works

Each item pairs an event with its event source id. Chronicle validates the batch before writing it, assigns sequence numbers in the order you supplied, and persists the events and their metadata atomically. It updates the event sequence state after the batch commits.

In the .NET client, each `EventForEventSourceId` can supply its own `Causation`, which records why that event happened. Chronicle keeps the current ambient causation chain first, then adds that event's explicit cause. An event without an explicit cause keeps only the ambient chain; it does not inherit another event's cause. Older kernels that do not support per-event causation ignore that field and store only the batch's ambient chain.

## Appending a batch once

`AppendManyOnce` appends events for one event source with a single `IdempotencyKey`. Chronicle derives a different key for each event from the batch key and the event's zero-based position (`IdempotencyKey.ForIndex`), so the batch is keyed per event. Retrying the same batch with the same key and the same events in the same order writes nothing new. There is also `AppendManyOnceWithNamedTags`. See [Appending](./appending#appending-once) for keys, outcomes, and conflicts.

<ChronicleClientTabs snippet="events/appending-many/once" />

`AppendManyResult.Outcomes` has one `AppendOutcome` per event, in the order you gave them. `IdempotencyConflicts` and `HasIdempotencyConflicts` report refused keys. Because a batch is atomic, check them before assuming the batch was written. `WasAlreadyAppended` is `true` when every event was already in the sequence.

### Keys on individual events

When a batch spans event sources, set `IdempotencyKey` on each `EventForEventSourceId` instead. If any event in the batch has a key, the batch is appended once. Events without a key are appended normally, so a mixed batch is valid and `Outcomes` reports `Appended` for them.

<ChronicleClientTabs snippet="events/appending-many/keyed-events" />

Keyed batches follow the same rules as a single keyed append: an older kernel throws `IdempotentAppendsNotSupported`, and keys are refused inside a unit of work and with effect receipts.

## When to use

Use a batch when you already have the events to commit together. If they depend on state you read, include [concurrency scopes](concurrency) captured before that read. Atomicity keeps the writes together; the scopes check whether a competing append changed the facts behind your decision.
