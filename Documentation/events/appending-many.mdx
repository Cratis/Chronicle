# Appending many

Appending many events in a single call is useful for batch workflows such as imports, migrations, or multi-step business operations.

> [!NOTE]
> With Cratis Arc and the Chronicle extension, you can append events as state changes coming out of a command using a more functional approach. See [Arc Chronicle commands](/arc/backend/csharp/chronicle/commands/).

Batch appends preserve ordering and reduce per-event overhead compared to appending each event individually.

AppendMany is transactional all the way to storage. Either all events in the batch are committed, or none are. Chronicle assigns sequence numbers in order, persists the events and metadata atomically, and updates the sequence state once the batch succeeds.

## How it works

- Each item in the batch pairs an event with the event source it belongs to.
- In the .NET client, each `EventForEventSourceId` can supply its own `Causation`. The current ambient causation chain is kept first, followed by that event's explicit cause. Events without an explicit cause keep only the ambient chain; they do not inherit another event's cause.
- Per-event causation requires an updated Chronicle kernel. Older kernels ignore the per-event field and store only the batch's ambient causation chain.
- The batch is validated as a unit and written atomically.
- Sequence numbers are assigned in the order provided.
- The event sequence state is updated once the batch commits.

## Appending a batch once

`AppendManyOnce` appends events for one event source with a single `IdempotencyKey`. Chronicle derives a different key for each event from the batch key and the event's zero-based position (`IdempotencyKey.ForIndex`), so the batch is keyed per event. Retrying the same batch with the same key and the same events in the same order writes nothing new. There is also `AppendManyOnceWithNamedTags`. See [Appending](./appending#appending-once) for keys, outcomes, and conflicts.

<ChronicleClientTabs snippet="events/appending-many/once" />

`AppendManyResult.Outcomes` has one `AppendOutcome` per event, in the order you gave them. `IdempotencyConflicts` and `HasIdempotencyConflicts` report refused keys. Because a batch is atomic, check them before assuming the batch was written. `WasAlreadyAppended` is `true` when every event was already in the sequence.

### Keys on individual events

When a batch spans event sources, set `IdempotencyKey` on each `EventForEventSourceId` instead. If any event in the batch has a key, the batch is appended once. Events without a key are appended normally, so a mixed batch is valid and `Outcomes` reports `Appended` for them.

<ChronicleClientTabs snippet="events/appending-many/keyed-events" />

Keyed batches follow the same rules as a single keyed append: an older kernel throws `IdempotentAppendsNotSupported`, and keys are refused inside a unit of work and with effect receipts.

## When to use

Use this approach when you already have a set of events that should be appended together. Each event can still target different event sources, and you can include concurrency scopes to validate the boundary across streams. See [Concurrency](concurrency) for details.
