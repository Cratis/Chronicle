# Overriding how a type appears in the schema

Chronicle generates a JSON schema for every event and read model, and that schema is what the kernel stores
against the event type and uses to materialize values back out. Most types map on their own — primitives
directly, and `ConceptAs<T>` types as their underlying primitive.

A type that serializes to something other than its shape needs to say so, or the generated schema describes
the CLR structure while the stored JSON holds whatever the converter wrote. Annotate the type with
`JsonSchemaType` to declare what it is really represented as:

<ChronicleClientTabs snippet="events/schema-representation/basic" />

The schema then describes a string, matching what the converter actually writes.

Two things are preserved through the override:

- **Compliance metadata.** A type marked `[PII]` keeps its compliance metadata after the redirect, so it is
  still encrypted per subject.
- **Nullability.** A nullable use of the type is still marked nullable in the schema.

An explicit `JsonSchemaType` always wins over what Chronicle would otherwise infer, including the `ConceptAs<T>`
handling.

:::note[Client coverage]
`JsonSchemaType` is currently C#-only.
:::

## Null, absent, and default values

For a nullable property, explicit `null` and an absent property are equivalent: reading either
back into the event type gives `null`. Chronicle can omit nullable nulls from stored content.
A non-null value is retained, including a nullable value type holding its type default, such as
`decimal?` with `0` or `int?` with `0`. Missing non-nullable values materialize as their type defaults
where the schema permits them; omission does not make a value nullable.

Compare appended and stored content through Chronicle's schema-aware `ContentComparison` /
`VerifyContent` path, not raw JSON equality. That path accounts for schema defaults and the
stored representation. Property presence in raw JSON is not a separate event fact.

## Defaulted concept properties

The .NET schema generator describes a defaulted concept property with its underlying type, format
and protection metadata, as well as its default. Older generators could emit only `{"default":null}`
for an optional concept constructor parameter. Values supplied for that property are still preserved
when the kernel encounters the older untyped schema.

A default-only property may gain its generated representation within an existing event generation,
without changing its default. This includes type, format, array items, enum members, string patterns
and lengths, nested object properties, and compliance or security metadata. Registration tolerates
the corresponding legacy shape in the opposite direction and retains the more precise stored schema,
including its protection metadata. A changed default or a changed already-typed property still
requires a new generation.

The .NET client sends the precise event schema only when the kernel advertises
`precise-event-type-schemas` during connection. Against an older kernel it registers the legacy
shape instead. Event-sequence sink definitions use the same capability gate; ordinary read-model
schemas always use the precise shape.

Registrations that supply only `Schema`, without a `Generations` list, are also checked for
compatibility with the stored generation. They can no longer overwrite an incompatible schema.

If you implement a custom `IJsonSchemaGenerator`, implement `GenerateLegacyEventType` as well as
`Generate`. The client calls it for kernels without the capability and for connections that do not
implement `IKernelCapabilities`, including testing or wrapped connections. Its default implementation
throws `LegacyEventTypeSchemasNotSupported`; it does not silently reuse the precise schema.

Adding protection metadata affects future appends, not historical plaintext; see
[Adding PII to an existing event type](../compliance/pii#adding-pii-to-an-existing-event-type).

## Exact decimal values

Use a decimal-formatted event property for amounts and other values that must retain decimal digits.
Chronicle carries these values as decimals through event storage, projections and read-model sinks;
it does not route them through a binary floating-point value. A concept wrapping a decimal has the
same representation as the decimal itself.

### Storage representation

| Provider | Event content | Decimal read-model property |
| --- | --- | --- |
| MongoDB | Decimal128 | Decimal128 |
| PostgreSQL | JSON decimal literal | NUMERIC |
| SQL Server | JSON decimal literal | DECIMAL(38,18) |
| SQLite | JSON decimal literal | Invariant decimal text in TEXT, plus a generated numeric sort key |
| In-memory | CLR decimal | CLR decimal |

The JSON payload on the wire remains a number, not an extended JSON object or a floating-point
approximation. Ordinary double and float properties keep their existing floating-point behavior.
An untyped BSON Decimal128 containing a fraction is read as a decimal, never truncated to an integer.

### Existing double values

When a decimal-formatted property was stored as a double by an older kernel, Chronicle reads the
double through its shortest round-trip text. For example, the stored double whose text is `193.58`
becomes the decimal `193.58`. This avoids introducing extra binary rounding digits on read. It
cannot recover significant digits that an earlier writer already lost.

Replay a read model to rebuild it from the event history. MongoDB read-model values written as
doubles are replaced with Decimal128 when the replay writes the decimal-formatted values.

### SQL Server limits

A SQL Server scalar decimal column supports at most 20 integer digits and 18 fractional digits.
Chronicle rounds scalar read-model values to 18 fractional digits, with midpoints rounded away
from zero, matching SQL Server's rounding. Computed values such as `1m / 3m` therefore project
successfully. Only values whose integer part exceeds 20 digits are refused. Event content retains
its original decimal precision. Existing DECIMAL(18,2) columns round the value further to their
own scale until replay replaces the table.
SQL Server returns decimals at its column's fixed scale; Chronicle removes redundant trailing zeros
when reading them. Numerical precision is retained, but arbitrary input trailing-zero scale is not:
`193.580` reads back as `193.58`, so `decimal.GetBits` can differ even though the values are equal.

### Upgrading existing SQL read models

The SQL migrator adds missing columns; it does not alter existing column types. Replay existing
SQL read models before relying on exact decimal writes. Replay creates a fresh table with the new
mapping and replaces the old table when the replay succeeds. This is required for SQLite's former
REAL columns and SQL Server's former DECIMAL(18,2) columns.

### Kernel shadow columns

SQL shadow columns are registered centrally, outside the projected columns and the EF model. They
are nullable without a default, are never materialized or released, and do not change the original
read-model properties. The current registry contains:

| Name pattern | Provider | Storage | Index |
| --- | --- | --- | --- |
| `__order_{column}` | SQLite, scalar decimal properties including decimal keys | Generated VIRTUAL TEXT | When the decimal property declares an index |

If a schema property collides with a shadow name (case-insensitively), the schema property wins:
the shadow is skipped and the kernel logs a warning. Registration still succeeds, but an operation
requiring that shadow refuses explicitly rather than using the schema property's value.

Existing tables gain missing shadows additively, without rewriting data. The registry also owns
indexes under `chronicle_shx_`, independently of declared `chronicle_idx_` indexes. Declared-index
reconciliation and table-renaming logic ignore shadow indexes, so old kernels cannot remove them.
After an old kernel promotes a replay table without shadows, ordinary EF reads and writes remain
unaffected. A shadow-specific operation repairs missing columns and indexes and retries once.
SQLite catalog probes include generated columns, so a restart does not attempt to add them again.

SQLite's original TEXT decimal columns preserve digits but still sort lexicographically in ad-hoc
SQL (`"10"` precedes `"9"`). Existing REAL-affinity tables still require replay for exact values;
non-text legacy values have NULL ordering keys. No floating-point conversion recovers lost precision.

The decimal ordering key is a fixed-width ASCII encoding under SQLite's default BINARY collation.
Numerically equal scales and all signed or scaled zeros have equal keys. NULL remains NULL and
sorts first ascending. Sink paging orders decimal keys by this encoding with the original key text
as a stable tie-breaker; scalar decimal candidate lookups compare the canonical key, admitting equal
scales without materializing unrelated parents. Ad-hoc numeric ranges must compare encoded keys,
not ordinary decimal strings. Arbitrary EF decimal expressions over the original property do not
use this encoding automatically.

Replay cannot undo precision already lost from the original event content. Check the source events
before assuming that a replay will recover an amount.
