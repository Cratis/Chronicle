# Overriding how a type appears in the schema

Chronicle generates a JSON schema for every event and read model, and that schema is what the kernel stores
against the event type and uses to materialize values back out. Most types map on their own — primitives
directly, and `ConceptAs<T>` types as their underlying primitive.

A type that serializes to something other than its shape needs to say so, or the generated schema describes
the CLR structure while the stored JSON holds whatever the converter wrote. Annotate the type with
`JsonSchemaType` to declare what it is really represented as:

<ChronicleClientTabs snippet="events/schema-representation/basic" />

The schema then describes a string, matching what the converter actually writes.

Two things are preserved through the override:

- **Compliance metadata.** A type marked `[PII]` keeps its compliance metadata after the redirect, so it is
  still encrypted per subject.
- **Nullability.** A nullable use of the type is still marked nullable in the schema.

An explicit `JsonSchemaType` always wins over what Chronicle would otherwise infer, including the `ConceptAs<T>`
handling.

:::note[Client coverage]
`JsonSchemaType` is currently C#-only.
:::

## Defaulted concept properties

The .NET schema generator describes a defaulted concept property with its underlying type, format
and protection metadata, as well as its default. Older generators could emit only `{"default":null}`
for an optional concept constructor parameter. Values supplied for that property are still preserved
when the kernel encounters the older untyped schema.

A default-only property may gain only its type, format and compliance or security metadata within
an existing event generation, without changing its default. Registration tolerates the corresponding
legacy shape in the opposite direction and retains the more precise stored schema. A changed
default, constraint or payload shape still requires a new generation.

The .NET client sends the precise event schema only when the kernel advertises
`precise-event-type-schemas` during connection. Against an older kernel it registers the legacy
shape instead. Read-model schemas always use the precise shape.

Adding protection metadata affects future appends, not historical plaintext; see
[Adding PII to an existing event type](../compliance/pii#adding-pii-to-an-existing-event-type).

## Exact decimal values

Use a decimal-formatted event property for amounts and other values that must retain decimal digits.
Chronicle carries these values as decimals through event storage, projections and read-model sinks;
it does not route them through a binary floating-point value. A concept wrapping a decimal has the
same representation as the decimal itself.

### Storage representation

| Provider | Event content | Decimal read-model property |
| --- | --- | --- |
| MongoDB | Decimal128 | Decimal128 |
| PostgreSQL | JSON decimal literal | NUMERIC |
| SQL Server | JSON decimal literal | DECIMAL(38,18) |
| SQLite | JSON decimal literal | Invariant decimal text in a TEXT column |
| In-memory | CLR decimal | CLR decimal |

The JSON payload on the wire remains a number, not an extended JSON object or a floating-point
approximation. Ordinary double and float properties keep their existing floating-point behavior.
An untyped BSON Decimal128 containing a fraction is read as a decimal, never truncated to an integer.

### Existing double values

When a decimal-formatted property was stored as a double by an older kernel, Chronicle reads the
double through its shortest round-trip text. For example, the stored double whose text is `193.58`
becomes the decimal `193.58`. This avoids introducing extra binary rounding digits on read. It
cannot recover significant digits that an earlier writer already lost.

Replay a read model to rebuild it from the event history. MongoDB read-model values written as
doubles are replaced with Decimal128 when the replay writes the decimal-formatted values.

### SQL Server limits

A SQL Server scalar decimal column supports at most 20 integer digits and 18 fractional digits.
Chronicle refuses a value that cannot fit exactly instead of allowing SQL Server to round it.
Values requiring a larger fractional scale can remain exact in event content, but cannot populate
that scalar read-model column. Choose a suitable read-model representation for those values.
SQL Server returns decimals at its column's fixed scale; Chronicle removes redundant trailing zeros
when reading them. Numerical precision is retained, but arbitrary input trailing-zero scale is not.

### Upgrading existing SQL read models

The SQL migrator adds missing columns; it does not alter existing column types. Replay existing
SQL read models before relying on exact decimal writes. Replay creates a fresh table with the new
mapping and replaces the old table when the replay succeeds. This is required for SQLite's former
REAL columns and SQL Server's former DECIMAL(18,2) columns.

Replay cannot undo precision already lost from the original event content. Check the source events
before assuming that a replay will recover an amount.
