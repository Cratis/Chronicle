# Getting events

Read events directly from Cratis Chronicle when you need to inspect an entity's history or diagnose the facts behind its current state. Use an event source read for one entity, a sequence-number read for a known position, or a metadata lookup when you do not need the payload.

The .NET examples use `IEventSequence` and its specialized `IEventLog`. For a history view that should not load everything at once, use [.NET keyset-paged reads](./paged-reads): pages advance by sequence number rather than by an offset. `GetPage` reads forward or backward within inclusive bounds; `GetLatest` starts at the tail and returns matching events newest first. Both return a continuation only when another matching page exists.

## Read metadata by sequence locator

Use `GetMetadataAt` when you already know an event's sequence number and need its context,
not its payload. The single-locator overload returns `null` for a missing event. The batch
overload returns an immutable dictionary keyed by sequence number and omits missing events.

<ChronicleClientTabs snippet="events/getting-events/metadata-at" />

A request accepts at most 500 locators, including duplicates. Chronicle rejects larger
requests before querying storage and removes duplicates from accepted requests. These are
point lookups, not reads of everything after a checkpoint.

Metadata includes routing, occurred time, correlation, causation, tags, subject, source name,
and the caused-by identity chain. It contains no payload, generation, content hash or
revision content, and does not release compliance-protected data. Identity names resolve
from storage on each read, so a rename appears on the next metadata read. See
[identity resolution](../concepts/correlation-identity-causation#identity-resolution-on-metadata-reads)
for the resolution statuses and privacy boundaries.

Your application must authorize access to the event store, namespace and requested events
**before** calling this API. Metadata can still contain personal information, including
identity names, tags and causation properties.

## Examples

### Read events for a single event source

The .NET example filters by event source and event types. Kotlin supports an optional event-source filter on `getFromSequenceNumber`, and Java's blocking wrapper accepts it too. Use TypeScript's `getForEventSourceIdAndEventTypes` to filter by event source and event types. Elixir provides `get_for_event_source/3`.

### Read from a checkpoint

<ChronicleClientTabs snippet="events/getting-events/from-checkpoint" />

The start position is inclusive: passing the last processed sequence number reads it again if it matches the filters. Save the next unread position when you want to resume without rereading that event. Kotlin, Java, and TypeScript expose `getFromSequenceNumber`; Elixir exposes `get_from_sequence_number/3`.

### Read the last events in a sequence

<ChronicleClientTabs snippet="events/getting-events/tail" />

This .NET example calculates a start position from the tail, reads forward, and trims the result in memory. It does not limit the server response to that count. Use [`GetLatest`](./paged-reads#read-the-newest-matching-events) for a bounded newest-first read, or [Getting state](./getting-state) if you need only the tail sequence number.
