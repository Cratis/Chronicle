Use `Append` to record one event for an event source, such as an order or an account. Chronicle writes it to an event sequence and returns a result that tells you whether the write succeeded or was rejected. The event log is the default sequence; you can also append to a custom sequence your system defines.

> [!NOTE]
> With Cratis Arc and the Chronicle extension, a command handler can return events for Chronicle to append. See [Arc Chronicle commands](/arc/backend/csharp/chronicle/commands/).

## How it works

Before the event is sent, the .NET client adds any [cross-cutting properties](./cross-cutting-properties) to its content. The Chronicle kernel does not add them. When it receives the event, it:

- Validates the event content against its registered JSON schema
- Associates the event with its event source
- Assigns the next sequence number
- Persists the event and metadata atomically
- Updates the sequence state

Check the append result before reporting success. A schema, constraint, or concurrency violation means Chronicle rejected the event without appending it. Correct the content or reconsider the decision against fresh state before trying again.

An infrastructure error is different: it can happen after storage accepted the event. A timeout or dropped connection can also leave you without a result. In either case, another unkeyed append can store the same fact twice. Use an [idempotency key](#appending-once) on the original attempt when you need safe retries. An [expected sequence number](./concurrency) or a [constraint](../constraints/) can also reject a duplicate, but you must resolve that rejection rather than assume the earlier write succeeded.

## When the outcome is unknown

`AppendOutcomeUnknown` means the event or batch may or may not be stored. Chronicle could not confirm the attempted slots by reading them back, or lost the response while awaiting an append grain call because a kernel silo became unavailable or the call timed out. **Do not retry blindly:** doing so can store the events twice.

Read the event source's events and look for the attempt's correlation id in their context. Append again only if those events are absent. A timeout or dropped connection without a result is also an unknown outcome, not proof that nothing was stored.

In the .NET client, check `result.Errors.Contains(AppendError.AppendOutcomeUnknown)` on `AppendResult` or `AppendManyResult`. The result is unsuccessful, but this is not a rejection: the write may have committed. After a unit-of-work commit, the same error is available from `unitOfWork.GetAppendErrors()`. Validation and constraint rejections retain their existing behavior. An older kernel may still report a generic command failure for node loss; absence of this typed error does not prove that nothing was stored.

Use an [idempotency key](#appending-once) on the original append and retry with that same key, so the retry is deduplicated.

## Verifying a possible duplicate

When an idempotency constraint or concurrency check identifies a previously stored event, compare its content before treating the attempted append as a duplicate. Do not reserialize a deserialized event: that can lose subtype properties and cannot distinguish erased personal data from an intact empty value.

In the .NET client, call `eventSequence.Prepare(event)` **before** attempting the append. Pass the returned `PreparedEvent` to `AppendPrepared(eventSourceId, preparedEvent)` and keep it while resolving the outcome. Preparation uses the store's event serializer, including polymorphic types and additional-information providers. Providers run once; append and verification reuse the same serialized snapshot even if the original object changes. To append prepared content through a registered event source, call `AppendPrepared<TEventSource>(eventSourceId, preparedEvent, eventStream, eventStreamId)`; it resolves routing and concurrency scope the same way as `Append<TEventSource>`.

Call `eventSequence.VerifyContent(sequenceNumber, preparedEvent, eventSourceId)` with the exact sequence number identified by your idempotency mechanism. Use the same sequence instance that prepared the event. The optional event source argument prevents comparing an event belonging to another source.

| Result | Meaning |
| --- | --- |
| `Equal` | The event type and complete released content of every stored generation match the attempted append's migrated representation on this backend, without detected conversion loss. |
| `Different` | The event type differs, or a difference in the appended original is proven directly or using recorded migrations. |
| `Unavailable` | Chronicle cannot establish equality or difference from complete content. Do not treat this as a duplicate. |

Comparison runs in the kernel, not on client CLR objects or encrypted event hashes. Protected values are masked before migration. For each derived generation, verification uses its recorded migration version when available; otherwise it uses the current migrations. A recorded version whose definitions are missing makes verification `Unavailable`. Every stored generation must have a migrated counterpart and a schema, and every conversion must preserve its declared values. Matching just the requested generation is insufficient: a downcast can discard the only difference between two events.

Verification identifies the appended original from stored append metadata or recorded provenance, never from the highest stored generation. If it cannot identify the original, the result is `Unavailable`. A direct difference in the original is `Different`. For a request in another generation, verification reconstructs the original using that request generation's recorded migrations from the appended source. Without that provenance, a mismatch reconstructed with current migrations is `Unavailable`, not `Different`. If the original matches but any derived generation differs, the result is also `Unavailable`: migration drift alone does not prove a difference in the original. `Equal` still requires every stored generation to match after complete release.

Each generation goes through the backend's append serialization. Stored documents are compared directly after strict release; they are not re-normalized through the schema. Provider overwrites of declared properties participate in comparison; undeclared properties discarded by append do not. Protected containers remain opaque during conversion, so their original nulls and undeclared members participate in comparison. Append migrates plaintext and protects each generation separately, but verification keeps protected values opaque. It only trusts a migration that carries a protected value across whole: a plain rename or move. If a migration reads a protected value in any other way (split, combine, value map, default, or any expression), copies it, moves it to an unprotected property, or produces a value it cannot have come from, the result is `Unavailable`, never `Equal` or `Different`, even when the value appears to survive. Attempted or stored content that contains the text `chronicle-verification:` is also `Unavailable`. Providers never run again during verification, and verification does not invent missing migrations.

Object property order does not matter; array order, property presence, and string values do. Numbers are compared exactly, ignoring only equivalent numeric spelling (such as `1.0` and `1`). Date/time offsets remain part of the stored string: equivalent instants with different offsets are not equal. In-memory storage retains decimal precision. MongoDB's decimal-to-double conversion is checked for loss: if the attempted value changes at that precision, verification returns **`Unavailable`**, never `Equal`. The same rule applies to other unrepresentable values, including enum values a backend would replace with a default. Schema defaults and omitted nulls follow append behavior. `Equal` describes the stored representation, not byte-for-byte equality of the original request.

Missing events, missing generations or schemas, redacted events, erased keys, unsupported protection handlers or storage providers, and failed releases produce `Unavailable`. **Revised events always return `Unavailable`, even if the requested generation was not itself revised. SQL storage currently returns `Unavailable` for all content verification:** it overwrites revisions without retaining revision history, so historical revisions cannot be ruled out. Backends must explicitly support reliable revision tracking before verification can compare content. Protected values also produce `Unavailable` when their schema does not identify a single non-null type, or when multiple protection handlers apply: Chronicle cannot safely recover the original value in those cases. Ordinary reads keep their existing empty-value behavior after erasure.

Prepared content is plaintext, just like an ordinary append request. Verification sends it in a request body and returns only the verdict, never the released stored content. Retain the snapshot only as long as needed. This checks **content**, not causation, tags, routing metadata, or whether the event belongs to the same business operation; your idempotency mechanism must establish that identity. Transport and storage failures can still fail the call and must not be interpreted as equality.

## Appending once

An idempotency key makes a retry safe. Append with the same key again and Chronicle writes nothing a second time. Use one when the outcome of an append is unknown, for example after a timeout, a dropped connection, or a restart in the middle of an operation.

In the .NET client, call `AppendOnce` with an `IdempotencyKey` (or `AppendOnceWithNamedTags` when the event carries [named tags](./appending-with-tags)). It takes the same optional arguments as `Append`.

<ChronicleClientTabs snippet="events/appending/once" />

Create keys explicitly with `new IdempotencyKey(value)`. There is no implicit conversion from a string. A key is 1 to 512 characters, and an empty or longer value throws `IdempotencyKeyNotValid`. Derive it from the business operation, not from a random value, so every retry of the same operation builds the same key.

> [!CAUTION]
> Never put personal data in a key. Chronicle stores the key with the event, so it is not covered by [compliance](../compliance/) erasure.

### Outcomes

`AppendResult.Outcome` reports what the call did. An unkeyed append always reports `Appended`.

| Outcome | Meaning |
| --- | --- |
| `Appended` | This call wrote the event. |
| `AlreadyAppended` | An event with the same key and the same content is already in the sequence. Nothing was written. |
| `AlreadyAppendedAfterErasure` | An event with the same key was written earlier and has since been erased. Nothing was written. |

`WasAlreadyAppended` is `true` for the last two.

### Key conflicts

A key that already identifies a different event is refused, not overwritten. The result reports it in `IdempotencyConflicts`, and `HasIdempotencyConflicts` is `true`. Check it explicitly; do not rely on `IsSuccess` alone. Each `IdempotencyKeyConflict` carries the key, the sequence number of the event that holds it, the stored event type, the generation you requested, and a reason:

| Reason | Meaning |
| --- | --- |
| `Content` | The key was used for an event with different content. |
| `Generation` | The key was used for the same event type in a different generation. |
| `Unverifiable` | The stored event cannot be compared with this one. |

Do not retry with a refused key. Either the two appends are different operations that need different keys, or the stored event is the one you meant to write.

### Kernels without support

Idempotent appends need a kernel that supports them. A keyed append never falls back to an unkeyed one, because that would remove the protection you asked for. Against an older kernel, `AppendOnce` throws `IdempotentAppendsNotSupported` and nothing is sent. Check `IEventSequence.SupportsIdempotentAppends` first when an older kernel might be connected.

### Where keys are not supported

Keys are refused with `IdempotentAppendsNotSupported`, and nothing is appended, in two cases:

- Events staged in a [unit of work](./transactions).
- Appends that carry an effect receipt.

The Kotlin, TypeScript, and Elixir clients do not have a keyed append API yet. See [where the clients differ](../clients/where-the-clients-differ#keyed-appends).

## AppendResult

In .NET, `AppendResult.IsSuccess` reports whether there are schema or other constraint violations, concurrency violations, or append errors. Inspect the corresponding collections to decide what to correct. For a keyed append, also check `HasIdempotencyConflicts`: `IsSuccess` alone does not report a refused key. See [Concurrency](./concurrency) and [Constraints](../constraints/) for handling rejected decisions.

## Schema validation

Chronicle validates every event's content against its registered JSON schema before persisting it. If the content does not conform to the schema — for example, a required property is missing or has the wrong type — the append fails and each problem comes back as a **constraint violation** of type `Schema`, with the offending path in its details — not as an error. In the .NET client that is an entry in `AppendResult.ConstraintViolations` while `AppendResult.Errors` stays empty, so check `IsSuccess` or the violations rather than the errors alone.

Schema validation runs before any other checks, so a schema error is returned immediately without touching the event sequence.

## Source and stream defaults

Omitted or empty append metadata is stored using these canonical values:

| Metadata | Stored default |
| --- | --- |
| Event source type | `Default` |
| Event stream type | `All` |
| Event stream ID | `Default` |

Single appends and batches use the same defaults. Nonempty values you supply are preserved exactly. In the .NET client, the resolved values also describe the append notification and the inputs to the concurrency strategy.

Earlier 18.x kernels could store empty metadata for single appends. Upgrading corrects new writes; it does not rewrite historical events or normalize their read-back metadata. If you compare historical routes, account for those legacy empty values only where your application intended the default route. Explicit metadata filters can still distinguish those older events from events carrying canonical defaults.

## Specifying when an event occurred

By default, Chronicle assigns the current server time as the event's `Occurred` timestamp when it persists the event. Some clients expose an explicit timestamp override for import and replay scenarios.

## When to use

Use a single append when the decision produces one event. If it produces several events that must commit together, use [Appending many](./appending-many). When the decision depends on state you read, capture a [concurrency scope](./concurrency) before reading, or use a [decision read](../read-models/decision-reads.mdx) to capture that position for you.
