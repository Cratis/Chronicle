Appending adds a single event to an event sequence. The event log is the default sequence, but you can also append to any custom sequence your system defines.

> [!NOTE]
> With Cratis Arc and the Chronicle extension, you can append events as state changes coming out of a command using a more functional approach. See [Arc Chronicle commands](/arc/backend/chronicle/commands/).

## How it works

When you append an event, Chronicle:

- Validates the event content against its registered JSON schema
- Applies any [cross-cutting properties](./cross-cutting-properties)
- Associates the event with its event source
- Assigns the next sequence number
- Persists the event and metadata atomically
- Updates the sequence state

The append returns an operation result you can use to detect schema errors, concurrency violations, constraint violations, and other append-time problems. This makes it safe to retry or revise without duplicating events.

## AppendResult

Appending returns an `AppendResult` that describes whether the operation succeeded and includes details about what went wrong when it fails. It can surface schema validation errors, concurrency violations, constraint violations, and other append-time problems. See [Concurrency](./concurrency) and [Constraints](../constraints/) for more on these cases.

## Schema validation

Chronicle validates every event's content against its registered JSON schema before persisting it. If the content does not conform to the schema — for example, a required property is missing or has the wrong type — the append fails and the errors appear in `AppendResult.Errors`.

Schema validation runs before any other checks, so a schema error is returned immediately without touching the event sequence.

## Source and stream defaults

Omitted or empty append metadata is stored using these canonical values:

| Metadata | Stored default |
| --- | --- |
| Event source type | `Default` |
| Event stream type | `All` |
| Event stream ID | `Default` |

Single appends and batches use the same kernel-owned policy. Nonempty values you supply are preserved exactly. SDKs can send omitted routing values without reproducing that policy. Concurrency filters are separate: an omitted filter means that dimension does not narrow the check, not that it should be filled from the append route.

Earlier 18.x kernels could store empty metadata for single appends. Upgrading corrects new writes; it does not rewrite historical events or normalize their read-back metadata. If you compare historical routes, account for those legacy empty values only where your application intended the default route. Explicit metadata filters can still distinguish those older events from events carrying canonical defaults.

## Append receipts

Receipt-aware clients request `IncludeReceipt` for a single append or `IncludeReceipts` for a batch. Successful acknowledgments then carry receipts derived from the metadata returned by storage. Omitting the option keeps the compact acknowledgment used by older clients, so a server upgrade does not unexpectedly enlarge their batch responses. It includes the assigned sequence number, event identity, source and stream routing, actual occurrence time, subject, tags, content hash, causation, and responsible identity. Clients can use that receipt instead of reconstructing persisted metadata from their inputs or local clocks.

A successful batch carries one receipt per input event, in the same order as the sequence numbers and input events. A rejected append has no persisted receipt. An SDK that reports a failed append attempt must not present that attempt as a stored event.

Receipt-aware clients require a kernel that exposes the receipt contract. Upgrade every kernel node before those clients; compatibility must be checked before sending an append, not discovered after the event has already been stored.

### Cost of a receipt

A receipt is roughly 400 bytes per event and largely repeats what the append sent, so a batch response grows by about that much per event. At Chronicle's default 100 MB message limit this is comfortable, but a large import that reads neither the receipt nor the append notification is paying for data it discards. The .NET client exposes `ChronicleOptions.IncludeAppendReceipts` to turn the request off; appended events and their sequence numbers are unchanged, and notifications then describe the request rather than the persisted event.

:::note[Receipt and read-back contexts are separate shapes]
A receipt is its own message rather than the event context returned by reads. Both now report the same information, including the event store and namespace an event belongs to, but the two carry different field numbers and a receipt flattens the event type. Consolidating them would change field types on a published contract, so they stay distinct until a major release.
:::

## Upgrading client routing defaults

Older Kotlin/Java and TypeScript/JavaScript clients supplied a stream type of `Default` and used the event-source ID as the stream ID when the caller supplied neither. Those are explicit wire values, so the kernel preserves them. They are different from the kernel defaults `All` and `Default`.

When upgrading to an SDK release that delegates omitted routing to the kernel, explicitly supply the former stream type and ID if your application must continue appending to those existing routes. The SDK release must document this behavioral change; a server upgrade alone does not rewrite the routes older clients explicitly send. Existing events are never rerouted automatically.

## Specifying when an event occurred

By default, Chronicle assigns the current server time as the event's `Occurred` timestamp when it persists the event. Some clients expose an explicit timestamp override for import and replay scenarios.

> [!WARNING]
> Specifying `occurred` bypasses the automatic server timestamp. Use this only for importing historical events or replaying data from an external system. Incorrect timestamps can break projections and reactors that rely on event ordering by time.

## When to use

Appending is lightweight and intended for single domain decisions that produce one event. When your decision spans multiple event sources, use concurrency scopes to enforce the boundary while keeping sequences independent. See [Concurrency](./concurrency) for details.
