## Seed onto an event stream

Pass an event stream type and identifier to `For` or `ForEventSource` to route seeds onto a
specific stream. The optional event source type defaults to `Default`. These overloads also
work on the builder returned by `ForNamespace`.

<ChronicleClientTabs snippet="event-seeding/seeding-with-csharp/stream-routed" />

Use `ForEvents` for per-event routing. Its `EventForEventSourceId` entries can specify an
`EventSource` definition type and an `EventStream` name; Chronicle resolves their routing
from the discovered definition and rejects contradictory explicit types. Entry tags are
combined with static event-type tags. Set `EventSource` whenever you use a typed `EventStream`:
without `EventSource`, the stream name is ignored and only the explicit `EventStreamType`
and `EventStreamId` determine stream routing. `ForEvents` uses the wrapper's routing and tags,
not its append-specific occurred time, subject, causation or structured named tags.

Routing is part of seed identity: identical payloads on different streams are separate seed
entries. Omitting routing preserves the defaults used by previously stored seed definitions,
so adopting this API does not append legacy seeds again.

Non-default routing requires a kernel that confirms seeding routing support. Against an
older kernel, `Register()` throws `EventSeedingRoutingNotSupported` before sending any
seed entries, including unrouted entries in the same buffer. Upgrade the kernel before
retrying that buffer. A buffer containing only default routing still registers against
older kernels.

## Namespace-scoped seed data

By default, seed data applies to all namespaces in the event store. To target a specific namespace, use `ForNamespace` to get a scoped builder:

The scoped builder supports the same `For<TEvent>` and `ForEventSource` methods as the global builder. Each namespace receives only its own scoped events in addition to any global events.

## Register corrected seed definitions without reconnecting

When registration fails, Chronicle retains the attempted entries in the event store's default `Seeding` buffer.
That makes retrying an unchanged idempotent batch safe after a transient failure. If the definitions themselves
were wrong, create an independent empty buffer so the corrected set is not combined with the retained set:

<ChronicleClientTabs snippet="event-seeding/seeding-with-csharp/corrected-seed-set" />

The new buffer uses the event store's existing connection, event types, serializer, and client configuration. A
failure from its `Register()` call still propagates normally.

## How it runs

- Seeders are automatically discovered at application startup.
- Seed batches are sent to the Chronicle Server when the event store connects.
- Every entry is applied once per namespace, and seeding is idempotent across restarts: entries that have
  already been appended are skipped on the next run.
- An entry that your seeder yields twice is two events, not one. Two events of the same type, on the same
  event source, carrying the same payload are two facts, and both are appended.
- Events are appended in batches of 100. A batch is validated as a whole before anything is written, so a
  single entry that violates a constraint means none of its batch is appended. The server reports the
  rejection at `Error` with the violations, leaves those entries unseeded, and fails registration. The remote
  client surfaces that failure through its normal transport error. Retry the unchanged buffer for a transient
  failure; after correcting the definitions, restart the process or use `CreateEventSeeding()` to offer a fresh set.

## Best practices

- Keep seed data minimal and deterministic.
- Use clear event source IDs to make debugging easier.
- Group seeders by scenario so you can remove or adjust them easily.
- Use build flags or runtime settings to prevent seeding in production.
- Use `ForNamespace` when seed data is tenant-specific or environment-specific to avoid polluting other namespaces.
