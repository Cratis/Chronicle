To seed a Cratis Chronicle event store in C#, implement `ICanSeedEvents` and define the initial events your application needs. The .NET client discovers your seeder and registers its events when it connects, giving a new environment a starting history without a separate append script.

Start with a running kernel and a connected [.NET client](../clients/dotnet/getting-started.md). Choose the scope before defining seeds: global seeds reach every namespace in the event store, including tenants created later. A namespace is a separate data scope within an event store. Use `ForNamespace(...)` for development or sample data that belongs only in a named namespace.

Pass an event stream type and identifier to `For` or `ForEventSource` to route seeds onto a
specific stream. The optional event source type defaults to `Default`. These overloads also
work on the builder returned by `ForNamespace`.

<ChronicleClientTabs snippet="event-seeding/seeding-with-csharp/stream-routed" />

The first call seeds the `Offices` stream `office-1` under `company-123` across namespaces. The second targets only `tenant-a`, using the same source but stream identifier `office-2`. Both record `Company` as the event source type.

Use `ForEvents` when individual entries need different routes. Its `EventForEventSourceId` entries can specify an
`EventSource` definition type and an `EventStream` name; Chronicle resolves their routing
from the discovered definition and rejects contradictory explicit types. Entry tags are
combined with static event-type tags. Set `EventSource` whenever you use a typed `EventStream`:
without `EventSource`, the stream name is ignored and only the explicit `EventStreamType`
and `EventStreamId` determine stream routing. `ForEvents` uses the wrapper's routing and tags,
not its append-specific occurred time, subject, causation or structured named tags.

Routing is part of seed identity: identical payloads on different streams are separate seed
entries. Omitting routing preserves the defaults used by previously stored seed definitions,
so adopting this API does not append legacy seeds again.

Non-default routing requires a kernel that confirms seeding routing support. Against an
older kernel, `Register()` throws `EventSeedingRoutingNotSupported` before sending any
seed entries, including unrouted entries in the same buffer. Upgrade the kernel before
retrying that buffer. A buffer containing only default routing still registers against
older kernels.

## Namespace-scoped seed data

`For` and `ForEventSource` on the top-level builder define global seeds. The server stores them per event store and applies them to every existing namespace and each namespace created later.

Opening a store for a new namespace creates that namespace. The kernel applies stored global seeds asynchronously; there is no guarantee they arrive before your application's first write. Do not rely on that timing for startup logic.

Use `ForNamespace` to get a builder that targets only one namespace. In this example, the product is global, while tenant-specific users and organization events stay in their named namespaces:

<ChronicleClientTabs snippet="event-seeding/seeding-with-csharp/namespace-scoped" />

The scoped builder supports the same `For<TEvent>` and `ForEventSource` methods as the global builder. Each namespace receives only its own scoped events in addition to any global events.
`ForNamespace(EventStoreNamespaceName.Default)` never sends those entries to another namespace.

## Authoritative global seed sets

An authoritative global seed set is the complete set of global seeds a program currently declares through its discovered seeders. Each declaration replaces that program's previous one, including when the new set is empty. Removing an entry from `ICanSeedEvents` stops it reaching namespaces created afterwards. Events already appended to existing namespaces are never retracted.

Explicitly queued globals work differently. Entries added through `eventStore.Seeding.For(...)` or an independent `CreateEventSeeding()` buffer remain append-only. A later declaration does not remove them, even if an identical seed was already declared. Use discovered seeders when future namespaces should follow your current definitions, and explicit additions when the entries should remain part of the stored global set.

Programs sharing a store can declare the same seed without multiplying it. A namespace receives the largest occurrence count from any program's declaration or explicit additions, not the sum across programs. For example, if one program declares an entry twice and another declares it once, the namespace receives two occurrences. Seed identity includes the event source, event type, content, tags, and routing.

Clearing one program's declaration leaves a seed in place if another program still declares it or has added it explicitly. Existing namespaces receive only missing occurrences; reducing a count never retracts events.

If a discovered seeder cannot be activated or its `Seed` method fails, the client logs the failing seeder types and keeps the previous global declaration. It sends no discovered global declaration during that registration and does not store the partial discovered set as explicit additions. Namespace-scoped and manually queued entries still register. The next registration retries discovery; a complete successful discovery then declares the global set.

Ownership uses `ChronicleOptions.ProgramIdentifier`, falling back to the entry assembly name when the option is still `"[N/A]"`. Set a distinct, stable `ProgramIdentifier` for each program sharing a store, so one program does not replace another's declaration.

Both the .NET client and kernel must support declarations for replacement to take effect. Older clients keep append-only behavior. A newer client can still register default-routed seeds against an older kernel, but that kernel ignores declarations and retains its stored globals. The first authoritative registration after upgrading also clears legacy stored global seeds whose owner was not recorded. Other programs' owned declarations and explicit additions remain stored.

### Clear stale development seeds

1. Upgrade both the .NET client and the kernel.
2. Remove the development seeder, or scope its entries with `ForNamespace(EventStoreNamespaceName.Default)`.
3. Start the application once so it declares its remaining global set, even if empty.

New namespaces no longer receive the removed declarations or legacy global entries. Existing namespaces keep
all events already appended. This does not remove explicitly queued globals.

## How it runs

With automatic discovery enabled, the .NET client discovers seeders at application startup. It sends the discovered global set once per event store name per connection lifetime, even if it opens stores for several namespaces. Reconnecting sends that global set again. Each namespace store still sends its `ForNamespace(...)` entries during registration.

Chronicle tracks successful occurrences in each namespace, so restarting skips events already appended. If your seeder yields the same entry twice, both occurrences are appended. That remains true when the event type, source, and payload are identical; rerunning the list skips those two successful occurrences.

Events are appended in batches of 100. A batch is validated as a whole before anything is written, so one constraint violation prevents every entry in that batch from being appended. The server logs the rejection at `Error` with the violated constraint names and counts, and leaves those entries unseeded.

A rejected batch does not fail registration and is not reported to the client. Check the server log even when registration returns successfully. The client clears its buffer after that return, so correcting the definitions alone does not offer them again: restart the process or use `CreateEventSeeding()` to register the corrected set. Retrying the retained buffer applies only to command or transport errors, not to a server-side batch rejection.

## Best practices

Keep the starting history small and deterministic, with source identifiers you can recognize in the log. Group seeders by feature or scenario so changes remain easy to trace. For tenant-specific or environment-specific data, choose `ForNamespace` and control whether the seeder runs through build flags or runtime settings.

After starting the application, open [Chronicle Workbench](../workbench/index.mdx), select the intended event store and namespace, and inspect the event log for the source identifiers in your seeder. For the first example, look for the registration event under `user-123` and the registration and verification events under `user-456`. Check the server log for rejected batches if events are missing. Restart with unchanged definitions and confirm those successful occurrences are not appended again.
