<span id="subscribe-reactors-to-external-event-stores"></span>

Cratis Chronicle can route a C# reactor to another event store's events using `[EventStore]` metadata. The declaration selects a local inbox sequence and creates or reuses the subscription that forwards matching events from the source store's outbox. Your handler reads those forwarded events from the inbox.

:::note[Client coverage]
Automatic inbox routing through these declarations is C#-only. The `[EventStore]` metadata and reactor registration options shown here are not available in Kotlin, Elixir, or TypeScript.
:::

## Automatic inbox routing

If you own the event contracts, declare their source with `[EventStore("...")]` on each event type or on their assembly. With no explicit event sequence on the reactor, Chronicle infers the inbox from that metadata.

<ChronicleClientTabs snippet="reactors/external-event-store-subscriptions/automatic-routing" />

The event type declares `fulfillment-service`, so the reactor observes `inbox-fulfillment-service`. The source must publish the events to its outbox; this subscription does not forward events from its event log. See [Implicit Event Store Subscriptions](../subscriptions/implicit-subscriptions) for the producer and consumer setup.

Keep inferred sources to one store per reactor. Conflicting event-type sources throw `MultipleEventStoresDefined` at startup. If the inferred source is the reactor's own store, Chronicle selects the local event log instead of an inbox.

## Observer-level EventStore for missing event metadata

If you cannot change the event contracts, put `[EventStore]` on the reactor instead. This selects the source for the reactor without requiring the attribute on its event types.

<ChronicleClientTabs snippet="reactors/external-event-store-subscriptions/observer-level-event-store" />

Here, the reactor observes `inbox-identity-service`, and Chronicle creates or reuses the outbox-to-inbox subscription for `identity-service`.

## Source event store from configuration

When configuration supplies the source name at runtime, register the reactor with `ReactorRegistrationOptions.FromEventStore(name)` instead of adding an `[EventStore]` attribute.

<ChronicleClientTabs snippet="reactors/external-event-store-subscriptions/configured-source-event-store" />

The supplied name selects `inbox-<store>` and creates the same implicit subscription. A different `[EventStore]` declaration or an explicit event sequence conflicts with this option.

Unlike source inference from event types, both the reactor-level attribute and the registration option always select `inbox-<store>`, even when the source equals the current store. In that case, Chronicle does not create a subscription.

## Implicit combined event type filtering

Chronicle combines the event types handled by participating reactors and reducers into one subscription filter per source event store. It also merges event types requested by projections. Only event types in that combined filter are forwarded from the source outbox to the target inbox, so adding another observer can expand what the shared subscription forwards.

## Explicit event sequence is not allowed with observer EventStore

A reactor-level source declaration already chooses the inbox sequence. Do not combine `[EventStore("...")]` or `ReactorRegistrationOptions.FromEventStore(name)` with any of these explicit sequence declarations:

- `[EventSequence("...")]`
- `[EventLog]`
- `[Reactor(eventSequence: "...")]`

These combinations throw `EventStoreCannotBeCombinedWithExplicitEventSequence` at runtime; registration options fail when the store is created. Analyzer rule `CHR0013` also catches the attribute combination at compile time, but does not check registration options.

## Forwarded metadata

Inbox forwarding preserves append tags along with event-source and stream-route metadata, so tag filters can select forwarded events. Events forwarded by earlier releases that dropped tags remain untagged; upgrading does not backfill them.
