Start by choosing the event your reactor handles, then decide what it needs to do: perform work directly, return a follow-up event, or read state before acting. The client determines how that handler is selected and which arguments it receives. The method-discovery and overload rules below describe C#; TypeScript's fixed arguments and returned-event dispatch are explained alongside them.

## Event Method Discovery

In C#, reactors use convention-based method discovery. Chronicle finds and invokes public methods that:

- Accept the event type as the first parameter
- Optionally accept further dependency parameters (the `EventContext`, read models, or services)
- Return `void`, `Task`, `Task<T>`, or a synchronous side-effect type (see below)

Event parameter types must be marked with `[EventType]`.

## When more than one method matches

C# discovery matches on the first parameter type, so a helper you extract out of a handler for readability — say a `Task<string> Enrich(OrderPlaced @event)` that the handler awaits — matches the same event type the handler does. When that happens, Chronicle picks one method per event type, in this order:

1. **A public method beats a non-public one.** Handlers are public by convention; anything else is an implementation detail, so a private helper never displaces the handler that calls it.
2. **The richest signature wins.** Between two methods of the same accessibility, the one taking the most parameters asked for the most context, so it is the more specific handler.
3. **Method name, ordinal**, so a genuine tie resolves the same way on every run rather than being left to reflection order.

A private method is still a valid handler when nothing else handles that event type — the precedence only decides between candidates, it does not disqualify any of them. If a helper is not meant to take part in dispatch at all, give it a first parameter that is not an event type.

## Taking Dependencies

In C#, a handler method can take additional parameters that Chronicle resolves when the method runs. Only the first parameter is fixed; it is the event that drives dispatch.

<ChronicleClientTabs snippet="reactors/event-processing/dependencies" />

TypeScript passes fixed arguments instead: the event, its context, `ReactorServices`, and `ReactorDelivery`. A handler can accept those optional later arguments, but Chronicle does not resolve arbitrary parameter types into those positions. `ReactorServices` supplies the observation's owning `eventStore`, its `readModels`, and a disconnect/shutdown `signal`; the fourth argument's `id` can key an application-owned receipt, as described in [Delivery identity](delivery-identity). Kotlin and Elixir's handler shapes are shown in [Getting started with reactors](getting-started).

In C#, each parameter after the event resolves as follows. A type counts as a read model only when a projection or reducer builds it; any other type, including a plain record, is requested from the service provider:

- An `EventContext` parameter receives the event context; its position does not matter.
- A read model — a type with a reducer or projection — is resolved directly by Chronicle, never through the service provider. A materialized read model (the default) is read from its sink, so it is **eventually consistent** and may not yet include the event being handled. Mark it `[Passive]` to compute it on demand by folding the requested event source's history when the reactor reads it. That avoids waiting for a materialized view, but does not establish a global freshness boundary or guard a later append. It suits a read model keyed by its event source id; a passive read of a projection that joins other event sources or uses a custom key misses their events.
- Any other type is resolved from the service provider.

## Event Source Isolation

Events are delivered per event source and in sequence order. Each reactor method is called for the specific event source that produced the event.

## Concurrency Across Partitions (.NET client)

Within one partition the .NET client runs batches strictly in arrival order. Different partitions of the same reactor can now be handled **at the same time**, up to a bound. Handlers for different event sources can therefore overlap, so shared state that is not thread-safe (for example a singleton service) must be safe for concurrent use. There is no ordering across partitions. Replay begin and end notifications wait for work in flight, and partition replay notifications run in order with that partition's events. Results are still reported to the Kernel one at a time.

The bound is `Reactors.MaxConcurrentPartitions` in [`ChronicleOptions`](../configuration/chronicle-options#reactors) and defaults to the processor count, at most 8. Set it to `1` to restore the previous behavior of handling one batch at a time.

## Error Handling

If a reactor method throws an exception, the failing event source partition is marked as failed and processing for that partition is paused. Once the underlying issue is resolved, processing resumes from the last successful event.
