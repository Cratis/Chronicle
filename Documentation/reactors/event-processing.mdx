A Cratis Chronicle reactor handler receives an event and runs the work that follows it. Choose a signature that supplies the context and dependencies that work needs, then account for how Chronicle orders delivery and reports failures.

The discovery and parameter-resolution rules below describe the .NET client. The examples include other clients where their handler APIs differ.

## Event Method Discovery

In .NET, Chronicle matches a method to the event type of its first parameter, not to its name. Make the handler public so its purpose is clear. It can request further parameters, such as `EventContext`, read models, or services, and return `void`, `Task`, `Task<T>`, or a synchronous side-effect type.

For attribute-based event discovery, mark the event parameter's type with `[EventType]`. Types nominated through [explicit artifact registration](../clients/dotnet/explicit-artifacts) do not need that attribute.

## When more than one method matches

A helper such as `Task<string> Enrich(OrderPlaced @event)` can match the same event as the handler that calls it. The .NET client chooses one method per event type using this precedence:

1. Public methods before non-public methods.
2. Methods with more parameters before methods with fewer parameters.
3. Method name in ordinal order to break a remaining tie.

A private method can still become the handler when no higher-priority method matches. To keep a helper out of dispatch entirely, give it a first parameter that is not an event type. Do not rely on a private modifier alone.

In .NET, `TResult` can be an event type or a sequence of known events: `IEnumerable<TEvent>`, `TEvent[]`, `List<TEvent>`, or `IReadOnlyList<TEvent>`. See [Returning Side Effects](side-effects) for supported return types and metadata resolution.

Do not carry C# overload conventions into another client. Kotlin and Java support event-typed handlers with optional context and resolvable arguments. TypeScript uses event-name conventions or explicit `@handles` mappings, and Elixir dispatches through `@handles` and `handle/2`. Returned-event handling also varies by client; [Returning side effects](side-effects) covers those differences.

## Taking Dependencies

In .NET, keep the event first and add parameters for the data or services the handler needs. Chronicle resolves them when it invokes the method, so the event determines dispatch while the remaining parameters support the work:

<ChronicleClientTabs snippet="reactors/event-processing/dependencies" />

For .NET parameter resolution, a type counts as a read model only when a projection or reducer builds it. An `EventContext` parameter receives the context wherever it appears after the event, and `ReactorDelivery` receives the current delivery. A read model parameter is resolved by Chronicle; other types, including a plain record, come from the service provider.

A materialized read model is read from its sink, the storage the projection or reducer writes to. That read is eventually consistent and may not include the event being handled yet. Mark the read model `[Passive]` to compute it from event history when requested instead. Passive reads are scoped by event source ID: a projection that joins other sources or uses a custom key can miss events through this path.

Other clients have their own dependency APIs. Kotlin and Java support argument resolvers, while TypeScript can receive a services argument containing the owning event store and its read models. Elixir's handler receives the event and context. Select the matching client example rather than applying .NET parameter-resolution rules to all clients.

### Resolving the read model key

By default, .NET resolves read model parameters using the event context's `EventSourceId` as the key. If the read model uses another key, implement `ICanResolveReadModelKey` on the reactor and return the `ReadModelKey` to use:

The resolved key applies to every read model parameter across all of that reactor's handler methods. Use this .NET interface only when those read models share the same key selection.

## Event Source Isolation

Events for one event source form a partition and are delivered in sequence order. Each handler invocation belongs to the source that produced the event. This ordering does not extend to events from other sources.

## Concurrency Across Partitions (.NET client)

Within one partition, the .NET client runs batches in arrival order. Different partitions of the same reactor can run at the same time, so shared services must be safe for concurrent use. There is no ordering across partitions.

Replay begin and end notifications wait for work in flight. Partition replay notifications run in order with that partition's events, and results are reported to the kernel one at a time.

The concurrency bound is `Reactors.MaxConcurrentPartitions` in [`ChronicleOptions`](../configuration/chronicle-options#reactors). It defaults to the processor count, capped at 8. Set it to `1` if the handler must process only one batch at a time.

## Error Handling

If a reactor method throws, its event source partition is marked as failed and pauses without advancing past that event. Fix the cause, then retry the failed partition so processing can resume from its last successful position. See [Replay](replay) for the recovery APIs, and use [Delivery Identity](delivery-identity) when an external effect might have succeeded before the handler failed.
