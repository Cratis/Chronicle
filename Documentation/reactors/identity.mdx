---
title: Reactor identity when renaming or moving code
description: Keep a Cratis Chronicle reactor's stored id when renaming or moving code to retain its processing position and avoid a new observer catching up.
---

Keep a reactor's stored id when renaming or moving its code so Cratis Chronicle retains the same observer and processing position. In C#, the default id is the full type name, including its namespace. Renaming the class or changing that namespace creates a different observer unless you pin the existing id explicitly.

For a reactor that is already deployed, use its current stored id. If that id is `MyApp.Orders.SendWelcomeEmail`, pin that exact value before moving or renaming the class. Replacing it with a friendlier name creates a new identity, even though the declaration is now explicit.

## Why side effects run again

By default, a new observer catches up from the beginning of its event sequence as ordinary observation, not replay. Its handlers can repeat historical notifications or external writes. `OnceOnly` excludes replay, so it does not suppress this initial catch-up. If a genuinely new reactor should ignore history, use [StartAtTail](start-at-tail) for its first registration. See [What OnceOnly guarantees](once-only.mdx#what-it-does-and-does-not-guarantee) before relying on either marker.

Preserving the old id retains its processing position, but does not provide exactly-once execution. Recovery can still re-deliver an event. Use [delivery-keyed duplicate protection](delivery-identity.mdx) for side effects that must not repeat; a stable id also keeps existing delivery receipts recognizable.

## Find and remove abandoned observers

Use the Workbench's **Observers** page or `cratis chronicle observers list` to compare stored ids with the ids your application declares. Inspect an apparently abandoned observer before removing it: another service or namespace may still use it.

If the identity change was accidental, put the old id back in the reactor declaration. Removing the old observer does not transfer its position to the new one or undo side effects the new one has already performed.

Removal affects the whole event store, across namespaces, and refuses while the observer is running or subscribed anywhere. See [Removing an observer](../concepts/observers.mdx#removing-an-observer).

For a C# deployment, check the [.NET discovery diagnostics](../clients/dotnet/discovery-report.md) before registration for likely identity changes. Investigate each finding against the stored observer: a rolling deployment can hide a rename while the old instance is still subscribed.
