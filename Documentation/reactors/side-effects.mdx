title: "Returning Side Effects from Reactor Handler Methods"
description: "Return events from a reactor handler and let Chronicle append them, and why such handlers are marked [OnceOnly]."
---

Return a follow-up event when the outcome of handling one event should be recorded in the event log. Chronicle awaits the handler and appends the supported events it returns. You can instead call an append API inside the handler when you need to choose append options or inspect the result yourself. Neither choice makes a payment, email, or other external effect safe to repeat automatically.

The client determines which return shapes and extension mechanisms are supported. The C# examples and reference sections below use C# return types, metadata providers, and side-effect handlers; TypeScript has a separate result hook and event-return path.

:::note[Client coverage]
C#, Kotlin, Java, Elixir, and TypeScript support returned events through their client-specific handler shapes. Kotlin and Java accept a single event, an `EventForEventSourceId`, or a `List` of either; from `io.cratis:chronicle` 6.5.0 a returned list is appended as one transaction, as in C#, and earlier versions appended its events one at a time. Elixir's `handle/2` returns `:ok`, `{:error, reason}`, or `{:ok, event_or_events}`; the events (a single event, a list appended atomically, or `EventForEventSourceId` entries for other event sources) are appended for you. See [Getting started with reactors](getting-started) for each client's declaration and registration.
:::

In TypeScript, return a known event, an `EventForEventSourceId`, or an array mixing those shapes. Chronicle awaits the result and offers it to the configured `reactorResultHandler` first. Returning `true` from the hook means it handled the entire result; returning `false` lets Chronicle append recognized events through one `appendMany` call. Unrecognized values are ignored by the built-in dispatch. Throw from the hook when handling fails. This hook is not the C# `IReactorSideEffectHandler` extension mechanism described below.

For an explicit TypeScript append, use the owning store from `ReactorServices`, await the append, and check its `isSuccess`. Throw on an unsuccessful result so the observation is not acknowledged as successful; prevalidation or transport failures can also reject the call. [Event Processing](event-processing) explains the fixed event, context, services, and delivery arguments. Returned events and explicit appends are not automatically one transaction with the triggering delivery. Make retries and replay safe; the [delivery identity](delivery-identity) can key a receipt your application owns.

> **Important**: Side-effect appends are not fire-and-forget. If a recognized returned event fails to append — a constraint violation, a concurrency conflict, or an error — the reactor's partition fails with the failure details and is retried per the observer's retry policy. See [Error handling](#error-handling) for the different treatment of unsupported return values.

## Targeting a Specific Event Source Id

A bare returned event normally targets the *triggering* event's source ID. C# can redirect that target for the whole reactor via [`ICanProvideEventSourceId`](#icanprovideeventsourceid). When the follow-up event belongs to a different entity, return an `EventForEventSourceId` with that entity's ID instead.

In TypeScript, a bare return uses the triggering source ID, stream ID, and subject. The reactor's `@eventSourceType` and `@eventStreamType` decorators supply source and stream types for bare returns; without a declared stream type, the triggering stream type is kept. Each returned `EventForEventSourceId` keeps its own target metadata instead. Explicit append calls do not inherit those decorators: choose their routing through append options. [Filtering](filtering) explains the separate effect these decorators have on which events the reactor receives.

> **Two modes in C#**: a **bare event** uses the reactor's resolved metadata — its `[EventStreamType]`/`[EventSourceType]` attributes and `ICanProvide*` interfaces. An **`EventForEventSourceId`** is the *explicit* mode: it is self-describing and uses only the values on it, so the reactor's metadata does **not** apply (an unset field takes the append default such as `EventStreamType.All`, and an omitted `Subject` is resolved from the event). Reach for a bare event when you want "use my reactor's config", and an `EventForEventSourceId` when you want "I'll specify exactly where and how".

In C#, you can also **mix** the two in a single `IEnumerable<object>`, `object[]`, `List<object>`, or `IReadOnlyList<object>` return — each bare event uses the reactor's resolved metadata and the triggering event source id, while each `EventForEventSourceId` keeps its own. ## Add concurrency scopes to returned events

In C#, return `EventsWithConcurrencyScopes` when the decision is only valid against the exact event-log state the reactor read. It submits an ordered list of `EventForEventSourceId` values and its concurrency scopes through one `AppendMany` call. This is a C# return type, not a TypeScript return shape:

<ChronicleClientTabs snippet="reactors/side-effects/with-concurrency-scopes" />

Here the reactor appends only if no later event for the triggering source has appeared since `BookReserved`. Chronicle materializes the events and copies the scope dictionary when you create the result, then submits both together. A failed constraint, concurrency check, or append fails the reactor partition; Chronicle never splits the return into partial appends.

A scope entry with `ConcurrencyScope.NotSet`, or a missing entry for an event source id in the batch, asks the configured concurrency strategy to resolve that source's scope. Use `ConcurrencyScope.None` when you explicitly want no check for a key. Chronicle passes every other scope through unchanged.

The event list preserves the order you supplied to the append operation. That does not impose a global processing order on observers: events targeting different source partitions can be observed independently. The scope dictionary also holds one scope per `EventSourceId` key; it cannot represent multiple independent scopes under the same key.

## Duplicate protection for returned events

In C#, the built-in result handlers append each returned event with an [idempotency key](../events/appending) that Chronicle derives from the [delivery identity](delivery-identity), the reactor's effect epoch and the event's position in the returned value. When the same delivery comes back, the kernel recognizes the keys and does not append the events a second time. This covers redelivery after a failed partition recovers, catch-up and replay: a returned event lands once per delivery.

What this does not cover is anything outside the event log. A payment call, an email or a webhook made inside the handler still runs again on every redelivery. Guard those with a receipt keyed by `ReactorDelivery`, as described in [Delivery identity](delivery-identity#keys-for-returned-events).

- **A key you set yourself is kept.** If an `EventForEventSourceId` already carries an `IdempotencyKey`, Chronicle leaves it alone and keys only the events that have none. Use `delivery.IdempotencyKeyFor("name")` to derive a stable key for a named effect.
- **Older kernels append unkeyed.** Against a kernel that does not advertise idempotent appends, returned events are appended without keys and Chronicle logs one warning per reactor. A key you set yourself on such a kernel throws `IdempotentAppendsNotSupported`, because silently dropping it would remove the protection you asked for.
- **The in-process testing package advertises the capability.** `ReactorScenario` records returned events by default instead of appending them. When you give it the real side-effect handlers, `Cratis.Chronicle.Testing` appends them with keys, like a current kernel does, so redelivering an occurrence does not append the events again.
- **Changed output is refused, not overwritten.** If the handler returns something different for a delivery that was already appended, the kernel reports a conflict and the partition fails. The failure message names the remedy: raise the [effect epoch](delivery-identity#when-to-bump-the-effect-epoch) or mark the handler [`[OnceOnly]`](once-only).
- **Build returned events from stable inputs.** Derive the returned events from the triggering event and from state that does not change between deliveries. A payload carrying a fresh `Guid`, the current time or the result of a lookup that has since changed counts as changed output when the delivery comes back, so the partition fails instead of appending a duplicate. Take such values from the triggering event, or derive them from the delivery identity.

## Custom Return Type Handlers

In C#, extend the pipeline by registering a custom `IReactorSideEffectHandler`. TypeScript uses the configured `reactorResultHandler` described above instead of this interface:

<ChronicleClientTabs snippet="reactors/side-effects/custom-handler" />

Chronicle registers its built-in handlers and reactor metadata providers when you call `AddCratisChronicle`, including in standalone hosts. Register custom handlers under `IReactorSideEffectHandler` or their concrete type in the host's service collection. Handlers discovered from other loaded libraries only participate when registered; merely loading an assembly does not activate its integration.

To return your custom side effect synchronously, implement `CanHandleReturnType(Type)` on the handler to claim its declared type. Mark the return type with `[ReactorSideEffect]` from `Cratis.Chronicle.Reactors.SideEffects` so analyzer [CHR0054](../code-analysis/CHR0054.mdx) accepts it. The marker may be applied to classes, structs, or interfaces; types deriving from a marked base class or implementing a marked interface are also accepted. It only informs the analyzer: it does not register a handler or make the type supported at runtime.

Existing handlers default to `false` and can still handle asynchronous `Task<T>` results without a marker. A handler can also claim a declared `IEnumerable<T>` return type; it must process the collection at invocation time. Arrays and `IEnumerable<T>` implementations of marked types are accepted by the analyzer, but the handler must claim the declared collection type, not only its elements. Returning a type that no handler claims synchronously is rejected during registration.

## Supported Return Types

In C#, the `IEnumerable<T>` entries below also accept `T[]`, `List<T>`, and other types implementing `IEnumerable<T>` (such as `IReadOnlyList<T>`), including when wrapped in `Task<TSequence>`. Multidimensional arrays are not supported.

| Return type | Handler invoked |
|---|---|
| `TEvent` | `EventResultHandler` — appends single event to the triggering/reactor event source id |
| `Task<TEvent>` | `EventResultHandler` |
| `IEnumerable<TEvent>` | `EventsResultHandler` — appends each event |
| `Task<IEnumerable<TEvent>>` | `EventsResultHandler` |
| `EventForEventSourceId` | `EventForEventSourceIdResultHandler` — appends to the event source id carried by the value |
| `Task<EventForEventSourceId>` | `EventForEventSourceIdResultHandler` |
| `IEnumerable<EventForEventSourceId>` | `EventsForEventSourceIdResultHandler` — appends all as one transaction |
| `Task<IEnumerable<EventForEventSourceId>>` | `EventsForEventSourceIdResultHandler` |
| `EventsWithConcurrencyScopes` | `EventsWithConcurrencyScopesResultHandler` — appends its ordered events and scopes as one transaction |
| `Task<EventsWithConcurrencyScopes>` | `EventsWithConcurrencyScopesResultHandler` |
| `IEnumerable<object>` mixing events and `EventForEventSourceId` | `MixedSideEffectsResultHandler` — bare events use reactor metadata, each `EventForEventSourceId` keeps its own; all appended as one transaction |
| Custom `T` or `IEnumerable<T>` claimed by a registered handler | The claiming `IReactorSideEffectHandler` processes the return value |
| `void` / `Task` | No side effects appended |

## Error handling

If a recognized side-effect append fails, Chronicle marks the reactor partition as failed. The append failure does not roll back external work the handler already performed. Keep that work safe to repeat before recovering the partition.

In C#, a non-null return value that no side-effect handler claims also fails the partition instead of being discarded and acknowledged. Register a handler for the returned type (or return a supported event), then retry or rewind the observer to continue processing.

TypeScript's built-in dispatch instead ignores values that are not recognized event returns. Use `reactorResultHandler` for an application-owned return type, return `true` only after handling it fully, and throw on failure. A recognized-return append failure or a thrown hook error fails processing; merely returning an unrecognized object does not.
