A Cratis Chronicle reactor can return follow-up events instead of calling `IEventLog` itself. The client appends those events after the handler completes, so the handler can focus on deciding what happened next. Returned-event appends and external calls have different duplicate-protection requirements, described below.

:::note[Client coverage]
C#, TypeScript, Kotlin, Java and Elixir support returned-event appends, but their return contracts differ. TypeScript accepts an event, an `EventForEventSourceId`, or an array mixing the two, and submits the events through `appendMany`. Kotlin and Java (`io.cratis:chronicle`) accept a single event, an `EventForEventSourceId`, or a `List` of either. Elixir's `handle/2` returns `:ok`, `{:error, reason}`, or `{:ok, event_or_events}`; the last form appends an event or list, including `EventForEventSourceId` entries targeting other sources. The metadata, derived-key and custom-handler sections below describe the C# APIs. See [Getting started with reactors](getting-started) and [Event Processing](event-processing) for client-specific handler setup.
:::

A returned-event append is part of handling the triggering event. If that append fails, the reactor partition fails with the append details and recovery follows the observer's retry policy. This includes constraint violations, concurrency conflicts and append errors. See [Error handling](#error-handling).

## Add concurrency scopes to returned events

If your decision is valid only against the event-log state the reactor read, use concurrency scopes to reject an append when that state has changed. In C#, return `EventsWithConcurrencyScopes` to submit an ordered list of `EventForEventSourceId` values and its scopes through one `AppendMany` call:

<ChronicleClientTabs snippet="reactors/side-effects/with-concurrency-scopes" />

Here the reactor appends only if no later event for the triggering source has appeared since `BookReserved`. Chronicle materializes the events and copies the scope dictionary when you create the result, then submits both together. A failed constraint, concurrency check, or append fails the reactor partition; Chronicle never splits the return into partial appends.

A scope entry with `ConcurrencyScope.NotSet`, or a missing entry for an event source id in the batch, asks the configured concurrency strategy to resolve that source's scope. Use `ConcurrencyScope.None` when you explicitly want no check for a key. Chronicle passes every other scope through unchanged.

The event list preserves the order you supplied to the append operation. That does not impose a global processing order on observers: events targeting different source partitions can be observed independently. The scope dictionary also holds one scope per `EventSourceId` key; it cannot represent multiple independent scopes under the same key.

## Duplicate protection for returned events

In C#, the built-in result handlers derive an [idempotency key](../events/appending) from the [delivery identity](delivery-identity), the reactor's effect epoch and each returned event's position. On a kernel that supports idempotent appends, repeating those keys with the same output does not append another copy. This applies when recovery, catch-up or replay repeats the same delivery identity; it does not guarantee a single handler invocation.

If an `EventForEventSourceId` already has an `IdempotencyKey`, Chronicle keeps it and derives keys only for events without one. Use `delivery.IdempotencyKeyFor("name")` for a named effect. Keep the order of returned events stable because their positions are part of the derived keys.

A kernel that does not advertise idempotent appends receives returned events without derived keys, and Chronicle logs one warning per reactor. A key you set yourself instead throws `IdempotentAppendsNotSupported`; it is not silently dropped. Automatic duplicate protection therefore depends on the kernel capability.

Changed content under an existing key causes a conflict and fails the partition. Derive output from the triggering event and stable state: a fresh `Guid`, the current time or a changed lookup result can cause unintended conflicts. If changed output is intentional, review the [effect epoch](delivery-identity#when-to-bump-the-effect-epoch) before allowing new appends. Use [`[OnceOnly]`](once-only) if replay should skip the handler; it does not repair an ordinary failed delivery.

A payment, email or webhook inside the handler is outside this protection and can run again. Use a receiver's idempotency support or an application-owned receipt, with the transaction and failure-window handling in [Delivery identity](delivery-identity#keys-for-returned-events).

To exercise returned-event appends in `Cratis.Chronicle.Testing`, supply the real side-effect handlers to `ReactorScenario`. By default, the scenario records returned events instead of appending them.

## Custom Return Type Handlers

In C#, register a custom `IReactorSideEffectHandler` to process a return type beyond the built-in event forms:

<ChronicleClientTabs snippet="reactors/side-effects/custom-handler" />

Chronicle registers its built-in handlers and reactor metadata providers when you call `AddCratisChronicle`, including in standalone hosts. Register custom handlers under `IReactorSideEffectHandler` or their concrete type in the host's service collection. Handlers discovered from other loaded libraries only participate when registered; merely loading an assembly does not activate its integration.

To return your custom side effect synchronously, implement `CanHandleReturnType(Type)` on the handler to claim its declared type. Mark the return type with `[ReactorSideEffect]` from `Cratis.Chronicle.Reactors.SideEffects` so analyzer [CHR0054](../code-analysis/CHR0054.mdx) accepts it. The marker may be applied to classes, structs, or interfaces; types deriving from a marked base class or implementing a marked interface are also accepted. It only informs the analyzer: it does not register a handler or make the type supported at runtime.

Existing handlers default to `false` and can still handle asynchronous `Task<T>` results without a marker. A handler can also claim a declared `IEnumerable<T>` return type; it must process the collection at invocation time. Arrays and `IEnumerable<T>` implementations of marked types are accepted by the analyzer, but the handler must claim the declared collection type, not only its elements. Returning a type that no handler claims synchronously is rejected during registration.

## Supported Return Types

In C#, the `IEnumerable<T>` entries below also accept `T[]`, `List<T>`, and other types implementing `IEnumerable<T>` (such as `IReadOnlyList<T>`), including when wrapped in `Task<TSequence>`. Multidimensional arrays are not supported.

| Return type | Handler invoked |
|---|---|
| `TEvent` | `EventResultHandler` — appends single event to the triggering/reactor event source id |
| `Task<TEvent>` | `EventResultHandler` |
| `IEnumerable<TEvent>` | `EventsResultHandler` — appends each event |
| `Task<IEnumerable<TEvent>>` | `EventsResultHandler` |
| `EventForEventSourceId` | `EventForEventSourceIdResultHandler` — appends to the event source id carried by the value |
| `Task<EventForEventSourceId>` | `EventForEventSourceIdResultHandler` |
| `IEnumerable<EventForEventSourceId>` | `EventsForEventSourceIdResultHandler` — appends all as one transaction |
| `Task<IEnumerable<EventForEventSourceId>>` | `EventsForEventSourceIdResultHandler` |
| `EventsWithConcurrencyScopes` | `EventsWithConcurrencyScopesResultHandler` — appends its ordered events and scopes as one transaction |
| `Task<EventsWithConcurrencyScopes>` | `EventsWithConcurrencyScopesResultHandler` |
| `IEnumerable<object>` mixing events and `EventForEventSourceId` | `MixedSideEffectsResultHandler` — bare events use reactor metadata, each `EventForEventSourceId` keeps its own; all appended as one transaction |
| Custom `T` or `IEnumerable<T>` claimed by a registered handler | The claiming `IReactorSideEffectHandler` processes the return value |
| `void` / `Task` | No side effects appended |

## Error handling

If a returned-event append fails, Chronicle marks the reactor partition as failed. In C#, a non-null return value that no side-effect handler claims also fails the partition instead of being discarded and acknowledged. Register a handler for that type, or return a supported event, before recovering the partition. Check [Delivery identity](delivery-identity) first if the handler also makes an external call: recovery can invoke it again.
