Cratis Chronicle reactors handle recorded events to trigger application work, such as sending a notification or calling an external API. Use a reactor when that work belongs after an event has been stored, rather than in the code that appends it.

A reactor reads an event sequence and keeps its own observation position: the point it has reached in that sequence. Chronicle uses this position to resume processing after a restart.

```mermaid
flowchart LR
    E[Event appended] --> R[Reactor]
    R --> S["Side effect (notify · call an API)"]
    R -.->|via command pipeline| C[New command]
```

## Key Concepts

A handler is the application method that runs for an event type. Its event context supplies metadata such as the event source ID and sequence number. Each client has its own way to declare and register handlers; [Getting Started](getting-started) shows the differences.

Events from one event source, such as one order, are handled in sequence order within their partition. Different partitions can progress independently. If handling fails, inspect and retry the failed partition rather than restarting the reactor's entire history.

Replaying a reactor runs it against event history again. Decide which effects are safe to repeat before using that workflow. [Once-only processing](once-only) excludes work from replay, but does not prevent redelivery during recovery. Use [delivery identity](delivery-identity) when protecting an external effect from repeated delivery.

## When to Use Reactors

Reactors are a good fit when you need to:

- Trigger notifications or workflows when specific events occur
- Synchronize with external systems
- Start background processing after a business fact has been recorded
- Emit follow-up events based on patterns in the event stream

If you need a queryable view of event history instead, use a [projection](/chronicle/projections/) or [reducer](/chronicle/reducers/). Those build data to read; a reactor runs application code in response to a recorded fact.
