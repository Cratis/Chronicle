# Unique event type constraint

A unique event type constraint allows a fact to happen once per event source, such as initializing a project once per project id. Unlike a unique property constraint, it checks whether the event has occurred, not whether a value belongs to another source. You can also declare a release event when the rule should reset for a new cycle.

In .NET, declare the rule with `builder.Unique<TEventType>()` inside `IConstraint`. The client's default artifact discovery finds these implementations without separate registration. See [Declarative constraints](index.mdx) for client-specific API differences.

## Releasing a constraint

Without a release event, the constraint means "at most one, ever". That fits project initialization, but not an employee who works another shift tomorrow.

Call `.RemovedWith<T>()` to name the event that ends a cycle. Only a covered event after the most recent removal blocks the next append. In this example, ending the employee's shift allows another shift to start:

<ChronicleClientTabs snippet="constraints/declarative/unique-event-type/releasing" />

The removal applies to the most recently declared unique event type constraint. It is per event source: one employee ending their shift opens only their own next cycle.

A cycle can end in more than one way, so chain `.RemovedWith<T>()` once for each event that ends it. Every one of them releases the constraint on its own, and the cycle ends at whichever was appended most recently:

Declaring several event types under one name makes them a single constraint, and the removal events declared across those declarations all apply to it.

The [model-bound form](../model-bound/unique-event-type) expresses the same thing with `[RemoveConstraint]` on the event that ends the cycle.

## Scoping the constraint

Within a namespace and event sequence, the default rule is "at most one per event source identifier". For one open loan per borrower per branch, represent the branch as a stream id and call `PerEventStreamId()` before declaring the constraint. The borrower can then have one open loan at each branch:

<ChronicleClientTabs snippet="constraints/declarative/unique-event-type/scoping" />

Use `PerEventStreamType()` or `PerEventSourceType()` when those dimensions distinguish the cycles instead. The dimensions of the event being appended decide which cycle it belongs to:

| Scope | One cycle per |
|---|---|
| *(none)* | event source identifier |
| `PerEventSourceType()` | event source identifier + event source type |
| `PerEventStreamType()` | event source identifier + event stream type |
| `PerEventStreamId()` | event source identifier + event stream id |

Chain several of them and every declared dimension has to match for two events to share a cycle — one differing dimension is a different cycle.

Within one scope, a second covered event is refused until a removal event in that same scope opens the next cycle. Returning a loan at one branch does not release the borrower's loan at another branch.

### Custom storage providers

Scoping is enforced by the storage provider, so a provider has to be able to see which scope an append belongs to. The storage interface `IUniqueEventTypesConstraintsStorage` therefore has two members:

| Member | Narrows by | Who should implement it |
|---|---|---|
| `IsAllowedWithinScope(definition, eventSourceId, scope)` | the appending event's typed dimension values | every provider |
| `IsAllowed(definition, eventSourceId, scopeKey)` | a single flattened string key | every provider, for compatibility — it stays abstract on the interface |

The kernel calls `IsAllowedWithinScope`. If your provider implements only `IsAllowed`, the interface's default implementation flattens the scope into the same string key the provider already received. This preserves compatibility, but not isolation between scopes whose dimension values contain the key's separator characters.

Implement `IsAllowedWithinScope` with a separate comparison for each typed dimension to enforce scoped isolation. You must still supply `IsAllowed` because it remains abstract. A compatibility wrapper can send an empty or omitted key to an unscoped `IsAllowedWithinScope` lookup. For a non-empty key, throw `NotSupportedException` rather than guess at dimensions that cannot be reconstructed.

The providers shipped with Chronicle — MongoDB, SQL and in-memory — implement the typed member and narrow natively per dimension. Calling their `IsAllowed` with a non-empty key throws `NotSupportedException` rather than answering against a scope it cannot reconstruct; an empty or omitted key is an unscoped lookup and is answered as one.

## Appending several events at once

The kernel checks events in call order, including claims made earlier in the same call. Two covered events for the same event source and scope violate the constraint even if neither is stored yet. A removal event earlier in the call opens a new cycle for a covered event later in it. If constraint validation fails, none of the call's events are appended.

Each event type still cannot occur twice — that is the single-type case of the same rule. What sharing the name adds is that the *first* of them to be appended blocks all of the others.

The check runs inside the append, rather than in an application validator that reads first and writes later. A separate read can let competing commands both observe "no terminal event yet"; declaring the constraint gives the kernel the rule to check before storing either outcome.

## How constraints are enforced

The Chronicle Kernel evaluates the registered rule during append, regardless of which client writes the event. The rule stays within its namespace, event sequence, and selected scope. See [Constraint or decision read](../index.md#constraint-or-decision-read) for the enforcement limits and for rules that need to count or compare state.
