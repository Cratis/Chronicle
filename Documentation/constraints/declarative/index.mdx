# Declarative constraints

Declarative constraints keep an append-time rule in a dedicated class rather than on an event type. Use them when several events share one uniqueness rule, when a violation needs a dynamic message, or when you want to control the constraint's name. In .NET, implement `IConstraint` and describe the rule through its fluent builder, chaining calls that select the events, properties, and release behavior.

For a rule that belongs directly on an event type or property, start with [Model-bound constraints](../model-bound/). Both approaches send definitions to the Chronicle Kernel, where the append is checked.

:::note[Client coverage]
Kotlin and Java provide `IConstraint`/`IConstraintBuilder` and can combine different event types in one property constraint. They do not provide `RemovedWith` to release a claim, `WithName` for a custom name, or a dynamic message callback. Their unique event type API is `uniqueFor`.

Elixir uses a standalone module with `use Chronicle.Events.Constraint`, or event-type-attribute macros in the model-bound form. Both forms support name-based grouping and releasing claims. Use the client tabs for the syntax and limits of the selected client; the .NET method names below do not imply matching APIs in every language.
:::

## Constraint types

| Rule you need | Constraint |
|---|---|
| Reserve a value, such as a project name, so another event source cannot claim it | [Unique property](unique) |
| Allow an event only once per event source, or once per cycle ended by a release event | [Unique event type](unique-event-type) |
| Stop later appends in a selected scope after a closing event | [Closing stream](closing-stream) |

## Discovery

The .NET client's default artifact discovery finds `IConstraint` implementations in the assemblies it scans and registers their definitions with the Kernel during client startup. You do not need to register each class separately when using that discovery.
