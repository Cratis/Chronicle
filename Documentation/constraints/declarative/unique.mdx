# Unique property constraint

Use `builder.Unique(...)` inside an `IConstraint` implementation to enforce that a property value is unique across one or more event types. The constraint fires if any tracked event would introduce a duplicate value.

Chronicle discovers all `IConstraint` implementations automatically — no registration is needed.

## Re-claiming a value

A unique property value belongs to an event source, not to a single append. The same event source may append its current value again without violating the constraint. If it claims a different value, the new value replaces its previous claim, freeing the old value for another event source.

Do not constrain a property containing the event source's own id to prevent a second event on that source: it will re-claim its own value and pass. To allow an event type only once per event source, use a [unique event type constraint](unique-event-type) instead.

## Keeping every value

When one event source accumulates many identifiers, call `.WithMode(UniqueConstraintMode.PerValue)` to keep all of them reserved. The default, `PerEventSource`, keeps only the source's current value. Per-value mode is available through the .NET client for now.

<ChronicleClientTabs snippet="constraints/declarative/unique/per-value" />

Each mapping version id remains unavailable to other event sources even after the project registers another version. The owning source may reclaim any of its values without a violation. `.RemovedWith<MappingVersionRemoved>(e => e.VersionId)` releases only the value carried by the removal event, provided that source owns it. `.RemovedWith<MappingVersionsRemoved>()` releases all values that source holds in the constraint's scope.

For a composite value, pass removal-property expressions in the same order as the constrained properties. An event with no constrained properties present claims nothing and leaves earlier values reserved. `.IgnoreCasing()` applies to both claiming and releasing values.

## Scoping to the event log

By default a constraint applies to every event sequence its event types are appended to, and each sequence keeps its own index. When an event type is a domain fact that is also forwarded to the outbox, the forwarded copy claims the value in the outbox's index, and only a removal event appended to the outbox can release it. Call `.ForEventLog()` to apply the constraint to the event log alone, or `.ForEventSequences(...)` to name other sequences. The kernel neither validates nor indexes the constraint for a sequence it does not apply to:

<ChronicleClientTabs snippet="constraints/declarative/unique/event-log-only" />

The declaration covers every constraint defined on that builder, wherever in the chain it is called, and calling `.ForEventSequences(...)` again adds to the sequences already named. A builder without either call applies its constraints to every event sequence.

Changing the sequences takes effect when the client next registers its constraints. The kernel then rebuilds, in every namespace, the index of each sequence the constraint now applies to but did not before, from the events already in that sequence. A sequence the constraint no longer applies to stops validating it, and its index is no longer read until the constraint applies there again, when it is rebuilt.

## How constraints are enforced

When a constraint is registered, the Chronicle Kernel creates the indexes required to enforce it. Constraints are evaluated server-side during append, ensuring data integrity regardless of the client.

## Rebuilding an index

When a constraint changes, Chronicle rebuilds its index from the event sequence in log order. It clears all claims in each scope before replaying that scope's first event, so stale claims do not block historical values.

While an index rebuild is running, Chronicle refuses appends governed by that index with `ConstraintIndexUnavailable` in the append result's errors. Nothing is stored, so retry the unchanged append after a delay. Appends not governed by a rebuilding index continue normally. Governed appends resume once the rebuild handover and any pending repair finish.

If the rebuild step cannot hand over to the event sequence, Chronicle keeps refusing governed appends rather than risk accepting duplicates against an incomplete index. You can spot this when governed appends keep failing with `ConstraintIndexUnavailable` after the constraint's reindex job step has failed, and the Kernel log has a warning that starts with `Constraint index rebuild terminal handoff failed` or `Constraint index rebuild cancellation handoff failed`. To recover, resume the failed reindex job (for example `cratis chronicle jobs resume <JOB_ID>`), or restart the Kernel. Both are safe: Chronicle catches the index up from the event sequence before it accepts governed appends again.

If the store rejects a duplicate claim during the rebuild, Chronicle logs a warning, skips that claim, and continues. The first historical claimant keeps the value until an event releases or replaces it. The step persists skipped-claim counts per constraint and reports them in its completion progress message, for example `Skipped 3 duplicate claims: UniqueEmail=2, UniqueName=1`. The report contains constraint names and counts only, not claimant identities, values, or hashes; collision-free rebuilds leave the progress message unchanged.

Revising an event moves the claims it made: Chronicle releases the value the old content held and refolds the index from the revised position before the next governed append. Revisions made before this behavior shipped left stale claims behind. If you revised events of a constrained type before upgrading, rebuild that constraint's index once so the stale claims are released.
