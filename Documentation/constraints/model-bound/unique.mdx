# Unique property constraint

Adorn a property with `[Unique]` to enforce that the **value of that property is unique** across every event of this type in the event store.

Chronicle discovers `[Unique]`-adorned properties automatically and registers the constraints with the Kernel when the client starts.

## Re-claiming a value

A unique property value belongs to an event source, not to a single append. The same event source may append its current value again without violating the constraint. If it claims a different value, the new value replaces its previous claim, freeing the old value for another event source.

Do not constrain a property containing the event source's own id to prevent a second event on that source: it will re-claim its own value and pass. To allow an event type only once per event source, use a [unique event type constraint](unique-event-type) instead.

## Keeping every value

If one project accumulates many version ids, retaining only its latest id lets another project reuse an earlier one. Set `Mode = UniqueConstraintMode.PerValue` to reserve every value until you explicitly release it. The default, `PerEventSource`, keeps the replacement behavior described above. Per-value mode is available through the .NET client for now.

<ChronicleClientTabs snippet="constraints/model-bound/unique/per-value" />

Appending two different version ids for the same project now keeps both reserved. Another project cannot claim either; the original project may append either again without a violation. `ScheduleVersionRemoved` releases only the id carried by that event, and only if its event source owns that value. `ScheduleVersionsRemoved`, which declares no removal properties, releases all values held by that event source in the constraint's scope.

For a composite value, list removal properties in the same order as the constrained properties. A value-carrying event with no constrained properties present claims nothing and does not release earlier values. Properties sharing a constraint name must declare the same mode.

## Strongly-typed properties

`[Unique]` works on `ConceptAs<T>` properties — the idiomatic way to model a domain value in Cratis. Chronicle treats the concept as the underlying primitive it wraps (`string`, `Guid`, and so on), so a uniqueness rule on a strongly-typed `EmailAddress` or `OrganizationNumber` behaves exactly like one on the raw primitive, and registers and enforces identically through the [declarative](../declarative/unique) form too:

## Grouping constraints across event types

When multiple event types share the same constraint `name`, Chronicle groups them into a single constraint. A value introduced by any of the participating events is checked against all others:

<ChronicleClientTabs snippet="constraints/model-bound/unique/grouping" />

Both events now participate in the same `UniqueEmail` constraint, so neither `UserRegistered` nor `UserEmailChanged` can introduce an email address that already exists.

## Scoping to the event log

By default a constraint applies to every event sequence its event type is appended to, and each sequence keeps its own index. When the event is a domain fact that is also forwarded to the outbox, the forwarded copy claims the value in the outbox's index, and only a removal event appended to the outbox can release it. Set `EventSequences` on `[Unique]` to apply the constraint only to the sequences you name. The kernel neither validates nor indexes it for any other sequence:

<ChronicleClientTabs snippet="constraints/model-bound/unique/event-log-only" />

When several properties share a constraint name, the event sequences declared on each are combined. A property that sets no `EventSequences` means every event sequence, and that wins: if any property sharing the name leaves it unset, the constraint applies to every event sequence.

Changing the sequences takes effect when the client next registers its constraints. The kernel then rebuilds, in every namespace, the index of each sequence the constraint now applies to but did not before, from the events already in that sequence. A sequence the constraint no longer applies to stops validating it, and its index is no longer read until the constraint applies there again, when it is rebuilt.

## Violation message

The `message` parameter is optional. Chronicle produces a default violation message when one is not supplied. C# supports a custom violation message, and so do Kotlin and Java from `io.cratis:chronicle` 6.5.0: the client that registered the constraint puts its message on the violations its appends return, with `{detailKey}` placeholders filled in from the violation details. ## How constraints are enforced

The Chronicle Kernel reads the `[Unique]` and `[RemoveConstraint]` attributes when the client connects and creates the indexes it needs. Every subsequent append is checked against those indexes server-side, so no constraint logic runs in client code.
