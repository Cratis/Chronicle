# Unique property constraint

A Cratis Chronicle unique property constraint prevents different event sources from claiming the same value, such as an email address or handle. The source that owns a value can append it again without a violation, so use this rule to protect ownership of a value rather than to prevent repeated events.

In .NET, apply `[Unique]` to the event property. The client discovers the declaration on registered event types and sends its constraint definition to the Kernel when it starts.

## Re-claiming a value

A unique property value belongs to an event source, not to a single append. The same event source may append its current value again without violating the constraint. If it claims a different value, the new value replaces its previous claim, freeing the old value for another event source.

Do not constrain a property containing the event source's own id to prevent a second event on that source: it will re-claim its own value and pass. To allow an event type only once per event source, use a [unique event type constraint](unique-event-type) instead.

## Keeping every value

If one project accumulates many version ids, retaining only its latest id lets another project reuse an earlier one. In .NET, set `Mode = UniqueConstraintMode.PerValue` to reserve every value until you explicitly release it. The default, `PerEventSource`, keeps the replacement behavior described above. Elixir exposes the same retention choice through `:mode`; the example here uses the .NET attribute.

<ChronicleClientTabs snippet="constraints/model-bound/unique/per-value" />

Appending two different version ids for the same project now keeps both reserved. Another project cannot claim either; the original project may append either again without a violation. `ScheduleVersionRemoved` releases only the id carried by that event, and only if its event source owns that value. `ScheduleVersionsRemoved`, which declares no removal properties, releases all values held by that event source in the constraint's scope.

For a composite value, list removal properties in the same order as the constrained properties. A value-carrying event with no constrained properties present claims nothing and does not release earlier values. Properties sharing a constraint name must declare the same mode.

Both events now participate in `UniqueEmail`. A user can change to an unclaimed email address, but neither the registration event nor the email-change event can claim an address held by another event source. Under the default retention mode, changing the address frees the user's previous one.

## Scoping to the event log

An event sequence is a separately indexed collection of events, such as the event log or outbox. By default, a constraint applies to every sequence its event type is appended to. Forwarding an event to the outbox therefore claims its value in the outbox's index too; a removal event in the log does not release that outbox claim.

If the rule should protect only the event log, set `EventSequences` on the .NET `[Unique]` attribute. The Kernel neither validates nor indexes the constraint for sequences outside that selection:

<ChronicleClientTabs snippet="constraints/model-bound/unique/event-log-only" />

When properties share a constraint name, their event sequence selections are combined. If any of those properties leaves `EventSequences` unset, the combined constraint applies to every sequence. Set the selection on every participating property to keep the rule limited to the log.

Changing the sequences takes effect when the client next registers its constraints. The kernel then rebuilds, in every namespace, the index of each sequence the constraint now applies to but did not before, from the events already in that sequence. A sequence the constraint no longer applies to stops validating it, and its index is no longer read until the constraint applies there again, when it is rebuilt.

## How constraints are enforced

The client reads the model-bound declarations and registers constraint definitions. The Kernel builds the indexes and checks appends against them server-side. Clients also resolve custom violation messages for the append results they return.

For case-insensitive matching or scope configuration beyond the attribute's options, use the [declarative unique property constraint](../declarative/unique).
