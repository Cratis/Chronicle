title: Cratis Chronicle unique event type constraints
description: Declare a Cratis Chronicle unique event type constraint to allow an event once per source, then release it with a named removal event.
---
A Cratis Chronicle unique event type constraint allows an event type once per event source until a removal event releases the constraint. Use it when repeating the event would contradict the domain, such as initializing the same project twice.

Declare the rule on the event type itself. In .NET, apply `[Unique]` to the class; the client discovers it on registered event types and sends the constraint definition to the Kernel when it starts.

Without a custom message, Chronicle uses its default violation message. The name identifies the rule; the message explains the rejected append to its caller.

## Releasing a constraint

Declare a removal event when the lifecycle can start again. In .NET, apply `[RemoveConstraint]` to that event type. Appending it releases the named constraint for its event source, allowing another event of the constrained type:

<ChronicleClientTabs snippet="constraints/model-bound/unique-event-type/releasing" />

The removal declaration must name the constraint exactly. In .NET, TypeScript, Kotlin, and Java, the default name is the event class name. Elixir defaults to the event type id. An explicit name keeps the connection visible on both events.

In .NET, several removal event types can name the same constraint, so each way of ending a lifecycle can release it. Kotlin and Java accept only one removal event type per constraint name; registration keeps the first one it finds.

## How constraints are enforced

The client reads the model-bound declarations and registers constraint definitions. The Kernel checks appends against those definitions and the event history; it does not read .NET attributes itself.

If you need to reserve a value across different event sources instead of limiting event occurrences, use a [unique property constraint](unique).
