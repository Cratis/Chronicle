---
title: Encrypt operational secrets in Cratis Chronicle
description: Mark non-personal secrets with [Encrypted] in Cratis Chronicle to encrypt them at rest, choose their key scope, and keep them separate from PII erasure.
---

Use `[Encrypted]` in Cratis Chronicle to encrypt a non-personal operational secret at rest without including it in personal-data erasure. A partner credential or webhook signing secret can need this protection even though it is not data about a person.

If the value is personally identifiable information (PII), use `[PII]` instead. That marker encrypts personal data and includes it in Chronicle's erasure mechanism for the General Data Protection Regulation (GDPR). The [Security overview](/chronicle/security/) explains how choosing the wrong marker can make a non-personal secret unreadable when a person's key is erased.

## `[PII]` and `[Encrypted]` never mix

Choose one marker for each value. `[PII]` and `[Encrypted]` select different keys and erasure behavior; combining them is invalid, not extra protection. Schema generation rejects a property that resolves both markers. In .NET, it throws `PIIAndEncryptedCombinedNotSupported`:

<ChronicleClientTabs snippet="confidentiality/encrypted/pii-and-encrypted-restriction" />

Use `[PII]` for personal data and `[Encrypted]` for non-personal operational secrets. In .NET, [CHR0053](/chronicle/code-analysis/CHR0053/) catches directly visible combinations at compile time. Schema generation also catches combinations inherited through a marked concept type.

## Why the two keys are never the same

A record can contain both a personal email address marked `[PII]` and a non-personal partner credential marked `[Encrypted]`. A subject identity tells Chronicle who a protected value belongs to. Even when both values resolve to the same subject, Chronicle stores their keys under different identifiers. Erasing the person's PII leaves the credential's key untouched, so the credential can still be decrypted.

The kernel keeps these operations separate:

- `[Encrypted]` key identifiers use a reserved prefix that the PII path does not produce.
- The compliance entry points `DeleteEncryptionKeyFor` and `AllowNewEncryptionKeyFor` refuse identifiers with that prefix.

The confidentiality API exposes no equivalent erasure operation. Use `[PII]` for personal data that needs to participate in erasure; `[Encrypted]` does not provide that behavior.

## Scope

`EncryptionScope` determines which values share an encryption key. It does not change the encryption algorithm:

<ChronicleClientTabs snippet="confidentiality/encrypted/scope-enum" />

Choose the scope that matches the secret's ownership:

| Scope | Values that share a key |
| --- | --- |
| `EncryptionScope.Subject` (default) | Values with the same compliance identity in the event store namespace. This is the subject, or the event source id when none is set, but the key remains separate from any `[PII]` key for that identity. |
| `EncryptionScope.Namespace` | Every value marked with this scope in a given event store namespace, regardless of the document's subject. |
| `EncryptionScope.Global` | Every value marked with this scope across the whole Chronicle installation, including every event store and namespace. |

For example, use `Namespace` for a webhook signing secret shared across the partner integrations in that namespace. `Global` shares a key more broadly, across event stores as well as namespaces. Neither scope is available for `[PII]`: personal-data erasure remains tied to the compliance identity. See [Compliance](/chronicle/compliance/) for that workflow.

## Constraints

### EventSourceId is not supported

Keep the event source identifier in plaintext: Chronicle needs it to correlate events and locate subject-scoped keys when no subject is set. In .NET, schema generation throws `EncryptedNotSupportedOnEventSourceId` for identifier types derived from `EventSourceId` / `EventSourceId<T>` that themselves carry `[Encrypted]`.

Applying `[Encrypted]` directly to an event source identifier property or record parameter is also prohibited. [CHR0052](/chronicle/code-analysis/CHR0052/) catches directly marked members whose types derive from `EventSourceId<T>` at compile time. ## Client coverage

Use `[Encrypted]` in .NET, `@encrypted()` in TypeScript, `@Encrypted` in Kotlin/Java, or the `encrypted` macro in Elixir. The examples above show each client's syntax. These clients emit security metadata for the kernel to apply encryption and reject a value that resolves both PII and encryption metadata during schema generation.

For read model decryption, continue to [Releasing PII and encrypted values](/chronicle/read-models/releasing-pii/). It explains which reads decrypt values automatically and how to release an instance outside that path.
