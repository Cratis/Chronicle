Some values in an event log are sensitive without being personal data — an API key exchanged with a partner, a webhook signing secret, a third-party access token. They need to be unreadable in storage. They have no data subject, and there is no lawful erasure request that could ever be about them.

## Without `[Encrypted]`

Without a dedicated mechanism, a team reaches for one of two wrong tools:

- **Store it in plaintext**, and it sits in the event log — and every backup, replica, and read model built from it — readable by anyone with database access, forever, because the event log is immutable.
- **Mark it `[PII]`**, because that is the encryption mechanism Chronicle already has. This is worse than it looks: `[PII]` enrolls the value in GDPR right-to-erasure. A secret that was never personal data becomes destroyable by a request that was never about it — and if the same subject also has real personal data, the two would share one stored key, so erasing the subject's PII would destroy the secret too.

## With `[Encrypted]`

`[Encrypted]` is a security measure, not a compliance one. It encrypts a value at rest exactly like `[PII]` does — same shared key-provisioning and value-encoding machinery under the hood — but it is provisioned under a **deliberately disjoint key identity**, and there is no erasure path for it at all: nothing reachable from `[Encrypted]`'s key can delete it. A subject that carries both a `[PII]` value and an `[Encrypted]` value has the two protected under genuinely different keys, and erasing the subject's PII leaves the `[Encrypted]` value fully readable.

## Choosing between `[PII]` and `[Encrypted]`

| | `[PII]` | `[Encrypted]` |
|---|---|---|
| Protects | Personal data about a natural person | An operational secret with no data subject |
| Erasable | Yes — GDPR right-to-erasure | **No** — there is no lawful basis for erasure, and no API exposes a way to delete the key |
| Key identity | The compliance subject (or event source id when none is set) | Disjoint from PII, even for the same subject |
| Lives under | `Cratis.Chronicle.Compliance.GDPR` | `Cratis.Chronicle.ProtectedValues` |

The two attributes cannot both apply to the same value — see [Encrypting operational secrets](encrypted-values) and [CHR0053](/chronicle/code-analysis/CHR0053/).

## Trust model

When authentication is enabled, Chronicle authenticates every client, but it does not yet limit what an authenticated application may do to particular event stores. Any application with valid credentials is trusted with every event store on the kernel.

### Who this affects

This matters when one kernel serves parties that should not trust each other:

- a shared kernel that hosts applications owned by different teams or customers;
- Workbench users who should see only some event stores;
- multi-tenant hosting where one tenant must not reach another tenant's store.

If one kernel serves one application, or applications that already trust each other, nothing changes for you.

### What an authenticated application can do today

On any event store on the kernel, an authenticated application can:

- append events;
- read events, including personal data that Chronicle decrypts when it releases `[PII]` and `[Encrypted]` values;
- register a deployment generation and fingerprint;
- create and use namespaces;
- subscribe one event store to another. The subscription forwards events into the target store and copies their encryption keys with them.

Namespaces isolate data; they do not authorize the caller. See [Tenancy](/chronicle/tenancy/).

### Mitigations

Until per-application entitlements are available, isolate untrusted parties through deployment:

- Run a separate kernel for each trust boundary, each with its own storage and credentials.
- Restrict who can reach the kernel with network isolation or mutual TLS, so only the applications of one trust boundary can connect.
- Set `Authentication.EnforceAdministratorPolicyForOperations=true` so operational recovery on the `System` event store, security management and kernel reset refuse non-administrators instead of logging a warning. See [Authentication](/chronicle/hosting/configuration/authentication/#audit-mode-for-existing-operations). Operations on application event stores stay available to every authenticated application, and ordinary store work is not scoped.

Per-application entitlements are proposed in [decision 0022](https://github.com/Cratis/Chronicle/blob/main/decisions/0022-per-application-event-store-entitlements.md) and tracked in [#5410](https://github.com/Cratis/Chronicle/issues/5410).
