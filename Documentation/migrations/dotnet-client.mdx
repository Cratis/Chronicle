To evolve an event schema with the Cratis Chronicle .NET client, keep a record type for each generation and define a migrator between each adjacent pair. The client discovers these declarations and registers them with the kernel, which applies the transformations when events are appended.

## Prerequisites

- A Chronicle-enabled .NET application
- The existing event record and the new schema it needs to support

This guide uses attributes to identify event generations. If your contracts must stay free of client attributes, use [explicit registration](explicit-registration) instead. Before deploying a new generation, follow the [kernel rollout guidance](./#migrations-happen-in-place).

## Marking event types with generations

Keep the old record and introduce the new shape with an explicit generation number. Both records represent the same event type: Chronicle connects them through their event type id, not their C# class names.

<ChronicleClientTabs snippet="migrations/dotnet-client/generations" variants="csharp" />

Generation 2 splits `Name` into `FirstName` and `LastName`. Its record, `MigrationsDotnetClientAuthorRegistered`, declares the stable id with `[EventType]`. The older `MigrationsDotnetClientAuthorRegisteredV1` uses `[EventTypeGenerationFor<MigrationsDotnetClientAuthorRegistered>(1)]` to take its id from that declaration. You can rename either record without maintaining two copies of the id string.

:::note[Using an explicit id on every generation]
You can still put `[EventType]` on every generation; this style is not deprecated. Pass exactly the same explicit id string on each record and vary `generation:`. Omitting an id makes it fall back to the CLR type name, which can make the records unrelated event types. Prefer `[EventTypeGenerationFor<T>]` for previous generations to avoid that mismatch.
:::

Here, `Upcast` splits the old `Name`, while `Downcast` combines the new fields into the shape generation 1 expects. The base class reads `From` and `To` from the endpoint attributes, whether `[EventType]` or `[EventTypeGenerationFor<T>]`; you do not set the numbers again in the migrator.

The base constructor rejects different event type ids with `MigrationGenerationsMustShareEventTypeId` and non-adjacent generations with `InvalidMigrationGenerationGap`. Each migrator must bridge exactly one step: `To == From + 1`.

With the default discovery setup, migrators are found at startup without explicit registration. Keep one migrator for each transition. If two classes claim the same generation pair for one event type, `EventTypeMigrators.GetMigratorsFor` throws `MultipleMigratorsForSameEventTypeGeneration`.

## Migration operations

Declare property operations inside `builder.Properties(pb => ...)`. The target expression names a property in the generation you are producing; source expressions refer to the generation you are reading. `DefaultValue` supplies a literal instead of reading a source property. See [Event Type Migrations](../concepts/event-type-migrations.mdx) for the operation semantics.

### Split

Extracts one segment of a string property by splitting on a separator and taking the part at a given index.

<ChronicleClientTabs snippet="migrations/dotnet-client/split" variants="csharp" />

`PropertySeparator.Space` is a built-in constant. Any string is also implicitly convertible to a `PropertySeparator`, so `":"` works directly for colon-delimited fields. `SplitPartIndex.First` (index 0) and `SplitPartIndex.Second` (index 1) cover the most common cases; pass any `int` for deeper splits.

### Combine

Concatenates multiple source properties into a single string target property, joining with a separator. The second argument is a `PropertySeparator` — use the built-in `PropertySeparator.Space` or pass any string (e.g. `":"`).

### DefaultValue

Supply a literal value when the source generation has no value for a target property:

<ChronicleClientTabs snippet="migrations/dotnet-client/default-value" variants="csharp" />

Object defaults use the client's JSON naming policy for their members, with `[JsonPropertyName]` taking precedence. Object values in `MapValues` follow the same rules so they can match serialized payloads. Scalars and concepts keep their serialized values; enums use their underlying numbers.

If you upgrade from a client that did not apply the naming policy to object literals, the resulting migration content and hash change under camelCase or custom policies. Newly derived content uses the corrected names; already-derived generations are not corrected. Upgrade clients of the same event store together where possible: alternating registrations from old and new clients can replace the definition repeatedly, invalidate its cache and re-subscribe pattern capture. Registering the same definition again is idempotent.

## Properties inside a nested object

Use a member expression to reach a property inside a nested object. This example adds a description to the event's `Price` object:

<ChronicleClientTabs snippet="migrations/dotnet-client/nested-property" variants="csharp" />

Chronicle resolves each member in `e => e.Price.Description` to its JSON name. `[JsonPropertyName]` takes precedence over the client's naming policy; without explicit names, camelCase produces `price.description`. The kernel reads that path through the nested object and creates missing objects when writing the target. The same path handling lets `RenamedFrom(m => m.Price.Amount, e => e.Amount)` move a top-level value into `Price`.

Typed source and target expressions use this resolution for every operation, including bidirectional value maps. Raw string paths on `IEventMigrationPropertyBuilder` are already JSON paths and remain exactly as supplied. Use the serialized names, including any `[JsonPropertyName]` names: `price.description` is not converted again under a custom naming policy. Existing raw-string paths need no naming-policy workaround.

Path resolution does not rewrite a separator or a scalar literal, and these builders do not describe arbitrary custom-converter transformations. Object literals follow the serialization rules described under `DefaultValue`.

Registration checks paths against the generation schemas. An undeclared path is rejected with `InvalidMigrationPropertyForEventType`, identifying the path to check.

## Properties inside the elements of a collection

Use `Select` to address a property on every element: `DefaultValue(m => m.Days.Select(day => day.Activity), "work")` supplies the default where an element has no activity. Under camelCase, the path is `days[].activity`; raw string paths can use the same form.

The kernel applies the operation to each element and preserves the collection. `RenamedFrom` and `MapValues` use the same form when their source paths share the `days[].` prefix. A path into a collection without `[]` is rejected instead of replacing the collection with an object.

## Multi-generation migrations

## How registration works

When your application connects, the .NET client discovers migrators through `IClientArtifactsProvider`. It invokes `Upcast` and `Downcast` to capture their declarations, then sends the generation schemas and declarative migration expressions to the kernel during event type registration.

The kernel applies those definitions on append without invoking your C# migrator again. Registering a new generation also starts the [background backfill](./#background-upcasting-for-new-generations) for existing events in the default namespace's event log. Registration and backfill completion are separate: an accepted definition does not mean every historical event already has the new generation. See [Registration](../concepts/event-type-migrations.mdx#registration) for the shared model.

## Validation: missing migrators

When generation validation is enabled, the kernel rejects an event type above generation 1 if its migration chain is incomplete. `MissingEventTypeMigrators` means no migrators were supplied. A chain that has no transition from generation 1 produces `MissingFirstGenerationForEventType`; a later gap produces `MissingMigrationForEventTypeGeneration`.

```text
Cratis.Chronicle.Events.Migrations.MissingEventTypeMigrators:
  Event type 'AuthorRegistered' is at generation 3 but no migrators are registered for it.
```

Before deploying, check that every adjacent generation pair has one `EventTypeMigration<TUpgrade, TPrevious>` subclass and that the old record types remain discoverable. If registration fails, use the reported event type and generation to find the missing transition rather than adding a direct jump to the current generation.
