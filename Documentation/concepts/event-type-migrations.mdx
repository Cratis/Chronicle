Event type migrations enable you to evolve your event schemas over time while maintaining
compatibility with existing events. When an event type changes, you can define **upcasters**
and **downcasters** that automatically transform events between different generations.

## Why Migrations?

In evolving systems, event schemas naturally change:
- Properties are added or removed
- Properties are renamed
- Complex properties are split or combined

Chronicle's migration system allows you to:
1. Define declarative transformation rules
2. Automatically store all generations of an event when appending
3. Read events in any generation format

## Defining Migrations

To define a migration, you declare a migrator for one pair of generations: the newer generation and the one before it. The migrator states an **upcast** (how to build the newer generation from the older one) and a **downcast** (how to build the older generation from the newer one). Chronicle reads the generation numbers from the two event types, so you do not repeat them in the migrator.

<ChronicleClientTabs snippet="concepts/event-type-migrations/defining-migrations" />

The previous generation takes its event type id from the current generation rather than carrying an id of its own, so the two generations cannot drift apart through a hand-typed, mismatched id.

:::note[Give every generation the same event type id]
Chronicle treats two generations as one event type only when they resolve to the same event type id. A previous generation that ends up with a different id is an unrelated event type: the migration never applies, and registration fails at kernel startup with an `EventTypeSchemaChanged` error. For the C# attributes that make this impossible by construction, and for the older explicit-id style, see [Marking event types with generations](../migrations/dotnet-client.mdx#marking-event-types-with-generations).
:::

## Generations of one event type

A generation is one version of an event type's shape. Generation 1 is the first. Each later generation has its own schema, and consecutive generations differ by exactly one step: the number of a migrated generation is always the previous number plus one. A migrator bridges one such step, so an event type at generation 3 needs a migrator for 1→2 and another for 2→3.

Every generation of an event type shares one event type id. Only the generation number varies. The [generation validation rules](../migrations/validation.md) describe what the kernel rejects when this chain is incomplete.

For the C# syntax, see [C# client usage](../migrations/dotnet-client.mdx#marking-event-types-with-generations).

### Value map

The operations above move values between properties. A **value map** changes the values themselves — it states which value in one generation is which value in the other. This is what you reach for when an enum is renumbered, or a status code takes on a new set of values, and the old numbers now mean something the new generation spells differently.

You declare a value map on the migration itself rather than inside the upcast or the downcast:

<ChronicleClientTabs snippet="concepts/event-type-migrations/map-values" />

A map declared this way is applied **in both directions**: forward when upcasting, inverted when downcasting. The pair of values is one fact about the two generations, so you state it once and the two directions cannot drift apart.

Three things are worth knowing:

- **Values the map does not mention are carried across unchanged.** A map says what changed meaning; it is not an exhaustive listing of an enum that is free to grow.
- **Two values collapsing onto one have no single inverse**, so the first pair declared for a target value is the one that represents it going back.
- **The map does not have to stay on the same property.** The two property expressions may name different properties, in which case the map also carries the value across — covering a rename and a re-valuing in one statement.

The value map is applied *before* the upcast and the downcast run, so a direction that states its own transformation for the same property keeps it.

### Value maps in one direction

A single map assumes the translation is symmetric. When it is not, for example several old values collapse onto one new value and the way back has to make a choice the forward map cannot state, declare the value map for one direction only, inside the upcast or the downcast. Because the value map on the migration runs first and the direction's own statement keeps its result, each direction can then carry its own translation for the same property.

For the C# syntax, see [C# client usage](../migrations/dotnet-client.mdx#mapvalues).

## Properties inside a nested object

An event's payload is rarely flat. A value object groups related values, and that inner object evolves on its own schedule. Every operation above addresses a nested property by the same path you would use for a top-level one, and Chronicle resolves the path one segment at a time: reading walks into the object, and writing creates the objects along the way when the stored payload does not carry them yet. That also lets a migration restructure a payload, for example by renaming a value that used to sit at the top level into the object it now belongs to.

A path that leads nowhere is rejected at registration with `InvalidMigrationPropertyForEventType`, which names the path so you can see which segment is wrong. Separators, default values and mapped values are literals and are never renamed. These operations describe property paths. They are not arbitrary custom-converter transformations.

For the C# syntax, including how typed expressions resolve to JSON names, see [C# client usage](../migrations/dotnet-client.mdx#properties-inside-a-nested-object).

## When no operations are needed

Adding or removing an **optional** property, at any depth, needs a migrator for the generation pair but no operations inside it. Chronicle converts a payload by walking the *target* generation's schema. Upcasting leaves a property the older payload never carried absent, and downcasting drops a property the older generation does not declare. The migrator only has to exist so the generation chain is complete.

Reach for a default value when absent is the wrong answer and you want a specific value instead.

For the C# syntax, see [C# client usage](../migrations/dotnet-client.mdx#when-you-need-no-operations-at-all).

## Chaining several generations

When an event type spans more than two generations, declare one migrator per consecutive pair. Chronicle chains them: an event appended at generation 1 is upcast 1→2 and then 2→3, and all three generations are stored. Always migrate between consecutive generations, never directly from 1 to 3.

For the C# syntax, see [C# client usage](../migrations/dotnet-client.mdx#multi-generation-migrations).

## How Migrations Work

When an event is appended to the event store:

1. Chronicle identifies the event's current generation
2. The migration system retrieves all registered migrations for the event type
3. **Upcasting**: If there are higher generations, the event is transformed upward (1→2→3)
4. **Downcasting**: If there are lower generations, the event is transformed downward (3→2→1)
5. All generations are stored in the event sequence

This ensures that:
- Older consumers can still read events in their expected format
- Newer consumers can read events with the latest schema
- The generation an event was appended as is stored as written. Current backfills only add missing generations; they do not overwrite stored ones. Earlier backfills may already have overwritten content, and SQL revisions still replace content in place. The other generations hold only what the migrations produce: the example above splits a name on spaces, so for "Mary Ann Smith" the upcast generation 2 keeps "Mary" and "Ann" and drops "Smith". Write migrations that keep every part a consumer needs.

## Opt in to pinned observer delivery

Client reactors and reducers can request the generation their handlers subscribe to, rather than
receiving the appended generation live and the highest stored generation on replay. In the .NET
client, set `ChronicleOptions.EventGenerationDelivery` to `EventGenerationDelivery.Pinned` before
connecting; see [the .NET client option](../clients/dotnet/getting-started.md#pin-reactor-and-reducer-generations).
The default remains `Compatibility` in this major version. Upgrade every kernel silo before opting in.

For pinned observers, the kernel selects the subscribed generation's content and hash and releases
protected values with that generation's schema on live, catch-up, replay, and partition-retry delivery.
`EventContext.EventType.Generation` is the delivered generation; `EventContext.AppendedGeneration`
records the original append generation, or is null for older events where it is unknown.

If the pinned generation has not been stored yet, the kernel releases the known appended generation
(or the highest stored generation for legacy events) and migrates it for that delivery only. It does
not persist this result or cache plaintext. Such a delivery has `EventHash.NotSet`, because it has
no durable stored hash. Erased personal data stays erased through the migration.

A revised event is delivered from its latest revision, migrated to the pin when necessary. Its hash
is the revision's stored hash only when the revision already matches the pin; otherwise it is
`EventHash.NotSet`. SQL revisions made before this release cannot be distinguished from original
content: those rows keep the existing generation-selection behavior until revised again.

A reactor or reducer can pin only one generation per event type. Registration rejects unregistered
generations and handlers for multiple generations of the same type. If a pinned generation disappears
from the registered definition later, delivery fails explicitly rather than substituting a schema.
For reactors and reducers, changing a pin or delivery mode does not itself trigger a replay; request
one when you need to rebuild prior state.

The .NET option also opts typed materialized projections into pinned delivery. Each `From`, `Join`, child,
key, parent-key, and removal clause uses the generation it names, including events read from storage
to resolve joins or parent keys. A pinned projection can name only one generation per event type
across all its clauses, including children and nested objects; registration rejects conflicting pins,
just as it does for reactors and reducers. Different event types can pin different generations.
Strongly consistent reads of a pinned projection (`GetInstanceById`, stream-scoped reads, Workbench
snapshots and previews) use the same generation selection and release as its observer. Like observers,
a read fails when its pinned generation is unavailable.
Live, catch-up, and replay use the same generation-selection and release boundary.

For a PDL definition saved with `GenerationDelivery = Pinned`, a bare `from PersonRegistered` resolves
to the latest registered generation when you save it. That resolved generation is persisted as the
pin; registering a newer generation later does not move it. The same rule applies to join and removal
references, including those in children and nested objects. Saving the declaration again resolves its
names against the generations registered at that time.

PDL, which is owned by Screenplay, does not have generation-qualified event references. Use the
[.NET projection builders](../projections/declarative/simple-projection.mdx) or model-bound attributes
with the CLR event type for the generation you want when a clause must pin an explicit generation.
Compatibility definitions keep the existing bare-name and identifier-only dispatch behavior.

Webhooks opt in separately, per registration, with the .NET builder's
`WithGenerationDelivery(EventGenerationDelivery.Pinned)` or Core's `GenerationDelivery` property.
Their subscribed event types supply exact generation pins, which remain fixed until you deliberately
update the registration. The HTTP payload envelope is unchanged, including `GenerationalContent`;
only the selected content, delivered generation, and hash follow the pin. See
[webhook generation delivery](../webhooks/index.mdx#pin-the-generation-your-endpoint-understands).

Event-store subscriptions also opt in separately with
`WithGenerationDelivery(EventGenerationDelivery.Pinned)`. The target application's declared event types
supply exact pins for the source outbox observer. The kernel delivers those generations on live,
catch-up, replay, and retry, then appends the delivered generation to the target inbox. Both stores
must have that exact generation registered; a missing target generation fails forwarding without
appending or acknowledging the failing event. Pins survive reconnects and identical registrations;
only a deliberate registration update changes them. See
[pinned subscription delivery](../subscriptions/explicit-subscriptions.mdx#pin-the-generation-your-application-understands).

`GenerationalContent` remains on delivered events for compatibility in this major version. The global
client option does not change immediate/passive or wildcard (`all`) projections, webhooks,
captures, or event-store subscriptions.

## Protected values

Adding protection metadata within an existing generation affects future appends only. Creating a
new generation also leaves the original generation's stored content untouched. Neither approach
encrypts historical plaintext in place; see
[Adding PII to an existing event type](../compliance/pii#adding-pii-to-an-existing-event-type) and
[Event redaction](../events/redaction) for the policy and remedy.

Migration expressions operate on plaintext, including values protected by `[PII]` or
`[Encrypted]`. Split, combine, and value-map operations therefore see the original
values rather than ciphertext.

Before storing a generated generation, Chronicle applies that generation's protection
metadata under the original event's subject, falling back to its event source when no
subject was supplied. This also protects default values in classified target properties.
Keep the appropriate metadata on every target property that carries personal or
confidential data; a migration does not replace that schema declaration.

When a new generation is registered, backfill covers the **default namespace's event log only**.
It migrates from the known appended generation's base content, not a separate revision. For
legacy events whose appended generation is unknown, it uses the highest stored base generation
without inferring an appended generation. Each added generation records that source, whether
it is the known appended generation, and a content-addressed migration-definition version.
Content, hash, and provenance are written together, guarded against concurrent revision or
redaction. A conflicting write is re-read and retried once; a second conflict is logged and skipped.
Changing a migration alone does not rewrite existing generations.

Register new generations **only after every kernel silo has been upgraded**. Older workers can
still run replace-all backfills during a rolling upgrade.

Before transforming the source, Chronicle releases its content under the original subject. Erasing that subject's PII
keys also makes protected PII in the generated generations unavailable; independent
confidentiality keys are not erased by a PII erasure request.

## Registration

Migrations are discovered and registered when your application connects to Chronicle.
You declare the migrators, and the client then:

1. Discovers all migrators in the application
2. Captures the upcast and downcast declarations from each one
3. Converts the declarations into JmesPath transformations
4. Sends the definitions to the kernel during event type registration

For the C# discovery details, see [How registration works](../migrations/dotnet-client.mdx#how-registration-works).

## Catching Misuse Early

The checks below are C# items: two runtime checks and two [code analysis](../code-analysis/index.md) rules exist specifically to stop a broken migration before it ever reaches a real event log. The kernel enforces the [generation validation rules](../migrations/validation.md) for every client.


- **`MigrationGenerationsMustShareEventTypeId`** — thrown from `EventTypeMigration<TUpgrade, TPrevious>`'s constructor the moment `TUpgrade` and `TPrevious` resolve to different event type ids. This turns the old style's classic mistake — an omitted or mismatched id on the previous generation — into a loud failure at application startup instead of a confusing, silent rejection at the kernel.
- **`MultipleMigratorsForSameEventTypeGeneration`** — thrown by `EventTypeMigrators.GetMigratorsFor` when two different migrator classes both claim to bridge the same generation pair for one event type. Exactly one migrator may own a generation transition.
- **[CHR0037](../code-analysis/CHR0037)** flags a migration whose two generations don't resolve to the same event type at compile time — including validating, for the new attribute, that `[EventTypeGenerationFor<T>]`'s `T` really is the migration's `TUpgrade`.
- **[CHR0049](../code-analysis/CHR0049)** flags `[EventTypeGenerationFor<T>]` when `T` isn't itself marked with `[EventType]` — the referenced type must carry the real identity directly, not another generation marker.

## Best Practices

1. **Derive the previous generation's id from the current one (C#: `[EventTypeGenerationFor<T>]`)**: it resolves the event type id from the current generation's own `[EventType]`, so the two can never drift apart the way a hand-typed id on both generations can
2. **Incremental generations**: Always migrate between consecutive generations (1→2, 2→3, not 1→3)
3. **Reversible transformations**: Ensure downcast can recreate the original structure where possible
4. **Default values**: Use a default value operation for new properties that didn't exist in older generations
5. **Test migrations**: Verify both upcast and downcast transformations work correctly
6. **Document changes**: Keep track of what changed between generations in your event types
