Cratis Chronicle keeps application changes as **events**, then uses **observers** to turn those facts into queryable state or actions. A projection builds a view, a reducer computes state in application code, and a reactor performs work in response to a change. Use this overview to understand which part of your application belongs in each role.

For example, an order's `OrderPlaced` and `OrderShipped` events share an **event source**, the identity that groups its history. A **read model** might show the order's current status. That view is derived from the events; it is not a replacement for the history.

## Read model consistency

A **materialized** read model is stored in a database and updated as its observer processes events. Reads are served from that stored view, which can lag behind a new append. A **passive** read model instead computes state on demand from the relevant event-source history. [Projections and reducers](./observer-patterns.md) can supply these views for queries, validation rules, command handlers, or [aggregate roots in Arc](/arc/backend/csharp/chronicle/aggregates/defining-an-aggregate-root/).

Reading fresh state does not protect a later append from another writer. If a business rule must still hold when writers race, use a [decision-consistent read](../read-models/decision-reads.mdx), which guards the append against relevant changes, or a [constraint](./constraints.md) enforced by the kernel. Follow those guides before treating a query result as a concurrency guarantee.
