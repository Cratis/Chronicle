Tags in Cratis Chronicle serve two different tasks: event tags help you select stored events or filter delivery, while descriptive tags label observer and read-model definitions. Use named event tags when you need to find the events from a particular batch, run or session.

## Overview

Plain tags are strings such as `analytics` or `customer.registration`. Event types can declare them through attributes, and an append can add more at runtime. Reactors, reducers and projections are observers: they process appended events. Tags on their definitions describe their responsibility; they do not select the events they process. Read-model definitions can carry descriptive tags too.

In .NET, `[Tag]` and `[Tags]` are interchangeable ways to declare plain tags. You can mix the two attributes; Chronicle merges their tags.

A [named tag](#named-tags) keeps a name and value separate, such as `import-batch` = `4711`. Use this form for a runtime identifier rather than encoding it into a plain tag.

## Named tags

A plain tag such as `checkout` or `audit` identifies a category. A named tag identifies which import batch, workflow run or checkout session produced an event. Keeping `import-batch` and `4711` separate lets you query the name with any value, or just the values you need, without parsing a string such as `import-batch:4711`.

### Appending named tags

You supply named tags with `AppendWithNamedTags` (or `AppendManyWithNamedTags` for a batch). Unlike plain tags, there is no attribute that declares them on an event type.

<ChronicleClientTabs snippet="concepts/tagging/named-tags" />

Named tags and plain tags are stored separately. The `[Tag]` attribute and the `tags` values above still produce plain tags, and a named tag never appears in the plain tag list. [Appending with Tags](../events/appending-with-tags.mdx#named-tags) covers batch appends and how per-event and call-level named tags combine.

### Names and values

Names and values compare exactly, using ordinal, case-sensitive matching. `Import-Batch` and `import-batch` are different names. A name cannot be empty or whitespace; a value can be empty and can contain separators such as `:`, `.` or `,` because Chronicle does not parse it.

One name can have several values on the same event. Each distinct name/value pair is a separate tag, and exact duplicates are kept once.

### Querying by named tag

The Chronicle server's event sequence service answers named-tag queries through two operations: `QueryEventsWithNamedTags` returns a page of events, and `SequenceHistogramWithNamedTags` returns event counts over time. Each criterion takes one of three forms:

| Criterion | Matches events that carry |
| --- | --- |
| Name only | The name, with any value |
| Name and a value | Exactly that name and value |
| Name and a set of values | The name with any of those values |

An event matches when it satisfies any one of the criteria. The named-tag criteria then combine with every other filter on the query: event source, event source type, event stream type, correlation ID, event types, plain tags, and the occurred date range. A named-tag query needs at least one criterion, and a criterion with an empty set of values is rejected. Neither case turns into a query that returns everything.

### Before you use named tags

:::caution[Upgrade the Chronicle server first]
Named-tag appends and queries use server operations that older Chronicle servers don't have. An older server rejects the call, and the .NET client surfaces it as an `RpcException` with status code `Unimplemented`. The tags are never dropped silently, and a query is never widened to ignore its named-tag criteria. Appends without named tags keep using the existing operations, so they are unaffected.
:::

MongoDB, SQL (SQLite, PostgreSQL, and SQL Server), and in-memory storage support named-tag appends and queries. SQL stores them in a companion table named `__cratis_named_tags` in each event-store namespace database. That name is reserved for Chronicle. If a conflicting table already exists, every event-sequence operation in that namespace fails with `NamedTagsTableCollision` on first access (migration is lazy) and continues to fail until the conflicting table is renamed.

:::danger[Never put secrets or personal data in a named tag]
Named tags are plaintext, indexed metadata. [PII encryption](../compliance/pii.mdx) and the other compliance features protect event content, not tags, so a named tag is never encrypted. Event exports include named tags too. Use identifiers that are safe to show to anyone who can read the event sequence.
:::

## Best practices

Choose stable names that describe a category someone will search for, and use the same spelling for related events or definitions. Dot notation, such as `customer.registration` and `customer.profile`, can make a naming convention readable; it does not turn a plain tag into a structured query.

Keep runtime identifiers in [named tags](#named-tags). A batch number or session ID is a value to match, not a new category. Add labels only when they help a reader distinguish the event or definition.

## Using tags

To restrict which events a reducer or reactor receives, configure [event-tag filtering](../events/filtering/by-tag.mdx). The filter reads tags stored with each event, not the labels on the observer definition.

Chronicle does not use observer labels to activate, select or group observers. For examples focused on reactor definitions, continue with [tagging reactors](tagging-reactors.mdx). To carry a batch or session identifier into an append, see [appending with named tags](../events/appending-with-tags.mdx#named-tags).
