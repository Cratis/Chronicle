---
title: Store geospatial values in Chronicle
description: Chronicle supports Point, LineString and Polygon values in events and read models, with GeoJSON serialization and format-aware storage.
---

Cratis Chronicle supports geographic points, paths and areas as typed values in events and read models. Use `Point`, `LineString` and `Polygon` for a location, route or boundary that a projection or reducer needs to carry into a view.

The .NET types come from Cratis.Fundamentals in the `Cratis.Geospatial` namespace. Kotlin and Java use the types in `io.cratis.fundamentals.geospatial`, with GeoJSON adapters supplied by their Chronicle client. Elixir and TypeScript clients do not expose equivalent geospatial types.

## Geospatial types

`Point` represents one location, with longitude before latitude as in GeoJSON. `LineString` joins points into a path. `Polygon` defines an area with an outer boundary, or shell, and optional inner boundaries, or holes. A `LinearRing` supplies the closed loop of points used for a polygon boundary.

## JSON schema

The .NET schema generator describes a geospatial value as a leaf: an object carrying its format, with no sub-properties. The format identifies the type for storage and materialization, which turns stored content back into typed values:

```json
{ "type": "object", "format": "point" }
{ "type": "object", "format": "linestring" }
{ "type": "object", "format": "polygon" }
```

The .NET storage path materializes each geometry as one typed value. Its GeoJSON converter owns the coordinates and other members inside that value. Flattening them into event or read-model properties would cause coordinates to be dropped during conversion.

Storage sinks use the format annotation to recover the typed value. The Workbench also uses it to recognize and display a geographic field.

On the wire, the value itself is GeoJSON:

```json
{
  "pickedUpAt": { "type": "Point", "coordinates": [10.7522, 59.9139] }
}
```

Longitude comes first, then latitude, matching both GeoJSON and the `Point` constructor.

## Geospatial values alongside PII

An event may contain both a location and personally identifiable information (PII), such as a venue location beside an organizer's name. When a property is marked `[PII]`, Chronicle's compliance pass visits the whole document, including the geospatial value.

An unmarked geospatial value stays in plaintext. The pass treats it as one value instead of descending into its GeoJSON members, which have no separate schema properties for `[PII]` markers. Decide whether the location itself is personal data before storing it; a public venue and a person's precise location have different privacy implications.

:::caution[Don't mark a geospatial value `[PII]`]
`[PII]` on a geospatial property encrypts the whole GeoJSON object into a single ciphertext string. An ordinary round trip succeeds, but after [subject erasure](../compliance/erasing-a-subject) the released value is empty and cannot be materialized as a `Point`, `LineString` or `Polygon`. Reading the entire read model then fails, not just that property.

A personal location stored this way cannot survive the erasure path. Keep the geospatial value out of the person-scoped document, or store the sensitive part as a separate `[PII]` value beside a coarser location that is safe to retain.
:::

## Storage

### MongoDB sink

The MongoDB read-model sink uses the following BSON (binary JSON) shapes, which differ from the GeoJSON wire format above:

**Point**: Flat document with `longitude` and `latitude`

```json
{ "longitude": 10.456, "latitude": 42.123 }
```

**LineString**: Array of points

```json
[
  { "longitude": 10.456, "latitude": 42.123 },
  { "longitude": 11.789, "latitude": 43.456 }
]
```

**Polygon**: Document with `shell` (outer ring) and `holes` (inner rings)

```json
{
  "shell": [
    { "longitude": 0, "latitude": 0 },
    { "longitude": 10, "latitude": 0 },
    { "longitude": 10, "latitude": 10 },
    { "longitude": 0, "latitude": 10 },
    { "longitude": 0, "latitude": 0 }
  ],
  "holes": []
}
```

Chronicle registers these BSON serializers automatically.

### SQL sink

Geospatial types appear as objects in the schema, so the SQL read-model sink stores them in JSON columns. No additional migration or configuration is required for these types.

## Workbench display

The Chronicle Workbench recognizes geospatial format markers in event schemas and renders them as human-readable strings rather than expanding nested structures:

```text
Point: lat: 42.123, long: 10.456
LineString: [lat: 42.123, long: 10.456], [lat: 43.456, long: 11.789]
Polygon: shell with 5 points, 0 holes
```

Once the event and read-model properties are defined, use [declarative projections](../projections/declarative/simple-projection.mdx) to build the view. If the event contains personal data, review [PII protection](../compliance/pii.mdx) before choosing what location detail to retain.
