# Indexing Read Models

A read model is stored in a collection or table, and the store needs indexes to read it efficiently.
You could create those indexes yourself, but you would have to create them again every time the
container is recreated — and Chronicle recreates it on its own, during a replay.

The `[Index]` attribute moves the decision to where it belongs: onto the read model. You declare
which properties are indexed, and Chronicle creates them every time the container is built.

The MongoDB sink supports the full property path. The SQL sink creates non-unique indexes on
top-level scalar columns and nested JSON scalar paths for SQLite, PostgreSQL, and SQL Server,
including replay shadow tables.

## SQL storage

SQL stores nested objects and arrays in JSON columns. A nested scalar declaration uses an expression
index on SQLite (`json_extract`) or PostgreSQL (`#>>`). PostgreSQL casts numeric and boolean leaves
to their schema types. SQL Server indexes a non-persisted computed column using `JSON_VALUE`, with
bounded string keys and precise numeric casts. These columns do not store a second copy of your
read-model data; adding them changes metadata only. The index itself still requires a build.

| Declaration | SQLite | PostgreSQL | SQL Server |
| --- | --- | --- | --- |
| Top-level scalar | Column index | Column index | Column index |
| Nested scalar | Expression index | Typed expression index | Computed-column index |
| Path through an array | Warning; not created | GIN with `jsonb_path_ops` on the containing JSON column | Warning; requires SQL Server 2025 JSON indexes |
| Object without a scalar leaf | Warning; not created | Warning; not created | Warning; not created |

GIN indexes support JSON containment and JSONPath predicates, not arbitrary scalar comparisons.
Queries must use the indexed expression and compatible casts for the database to use an expression
index. Chronicle does not rewrite your application queries.

SQL Server bounds newly projected indexed strings to a supported key size; existing unbounded
columns are not resized during activation. A declaration on an unbounded column produces a warning
and requires a replay to apply the bound. The combined nonclustered key must fit in 1700 bytes.
Nested string keys use `nvarchar(450)`, truncating index values beyond 450 characters without changing
the stored JSON. Numbers use `decimal(38,18)`. An incompatible value or unsupported computed
expression fails visibly in the kernel log; Chronicle does not fall back to
persisted computed columns or alter the stored values.

Kernel index definitions can carry multiple ordered properties and descending directions. The
existing client `[Index]` attribute still declares a single ascending property. A composite SQL
index is created only when every path is supported; arrays cannot be mixed into a composite.
MongoDB supports compound keys but rejects multiple array paths in one definition. Legacy flat-path
updates preserve existing ordered definitions rather than flattening or deleting them.

Index names are deterministic and stay within provider identifier limits. Single ascending scalar
index names remain unchanged. Changes to property order, direction, or expression produce a different
name. Replay promotion preserves the complete index definition, including expressions and directions;
SQLite rebuilds indexes inside the swap transaction because it cannot rename them.

Routine activation adds missing indexes without pruning existing ones. An explicit definition
reconciliation removes undeclared Chronicle-owned indexes and unused Chronicle-owned computed
columns, but preserves user indexes and computed columns still used by an index.

## Why it lives on the read model

Chronicle replays a read model by building it into a **shadow container** — a separate collection or
table — and swapping that in when the replay completes. The container the application reads from
afterwards is therefore not the one it read from before: it is a new one, and it only has the
indexes that were created on it.

That is the reason `[Index]` exists. Because the declaration travels with the read model's
definition rather than being applied to a container by hand, Chronicle can recreate the indexes for
whichever container it is currently building — the original one, or the shadow one a replay is
filling. An index created manually against the live collection does not survive the swap; a declared
one does.

It is also why this is declarative rather than store-specific. `[Index]` says *what* should be
indexed; each sink decides *how*. On MongoDB that means an ascending index built in the background
and named `chronicle_idx_<path>`; another store expresses the same declaration its own way.

## When it takes effect

Indexes are ensured when Chronicle sets up storage for the read model — when the sink is first built
for it, and when a replay begins filling its shadow container. Creating an index that already exists
is skipped, so this is safe to run repeatedly.

Adding `[Index]` to a read model that is already in production applies on the next start of the
kernel. It does not require a replay — the index is created against the existing container.

## What it does not do

`[Index]` does not give you a query surface. Chronicle's read model API is keyed, and indexing does
not change that — see [Querying Read Models](./querying.md) for what to do when you need to search a
read model by something other than its key. What indexing does is make *that* work efficient, whether
the query comes from Chronicle's own key lookups or from your code going to the store directly.
