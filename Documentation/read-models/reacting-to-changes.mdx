---
title: Reacting to Read Model Changes
description: React to a read model being added, modified or removed with a convention-based IReadModelReactor, instead of subscribing to the watch stream yourself.
---

[Watching a read model](./watching-read-models) hands you a raw stream of changes: you subscribe, filter, branch on whether the instance was removed, and dispose the subscription yourself. When all you want is *"when an account appears, send a welcome; when it changes, sync it downstream"*, that plumbing is noise.

A **read model reactor** removes it. You write a class, name a method after the change you care about — `Added`, `Modified` or `Removed` — and Chronicle dispatches to it. It is a convenience layer over the [Watch APIs](./watching-read-models): the same delivery underneath, none of the subscription bookkeeping.

## Write the reactor

Implement the `IReadModelReactor` marker interface and add a method named `Added`, `Modified` or `Removed`. The method name selects the change it reacts to, and the first parameter selects which read model is watched.

<ChronicleClientTabs snippet="read-models/reacting-to-changes/reactor" />

There is nothing to register. Reactors are discovered and started automatically, and their subscriptions are tracked and cleaned up when the client is disposed. React to as many read models as you like — one method per change, per model.

:::note[Kotlin and Java]
The JVM client does not discover read model reactors. Register each one with `ReadModelReactors`, as the Kotlin and Java tabs show, and stop them when your application shuts down.
:::

## Return side effects

A handler can append events, exactly like a [reactor side effect](../reactors/side-effects). Return a single event, a collection, an `EventForEventSourceId`, or a mix, and Chronicle appends them. The `[EventStreamType]` and `[EventSourceType]` attributes on the reactor are honored when it does.

## The three change types

| Method | Reacts to |
| --- | --- |
| `Added` | The read model instance was created for the first time. |
| `Modified` | The read model instance changed. |
| `Removed` | The read model instance was removed. |

For **projection-backed** read models and **active reducer-backed** read models with dispatchable event handlers whose read model is not `[Passive]`, the change type and causing event context come from the kernel. `Added` versus `Modified` reflects persisted state rather than whether this client has seen the key. The context includes the causing event's sequence number, occurrence time, and correlation ID.

A late subscriber or a client reconnecting to an existing model receives `Modified` for its next change, not an inferred `Added`. Removing a reducer-backed model reports `Removed` with no model instance; recreating it reports `Added`. An unchanged reduction produces no notification. Multiple events reduced in one batch produce one net change with the last event's context.

## Watch through the materialized read model

Apply the `[Materialized]` attribute to observe the materialized read model API instead of the change stream. Chronicle then deduces the change type by comparing successive materialized windows.

<ChronicleClientTabs snippet="read-models/reacting-to-changes/materialized" />

Reach for this only when you specifically want the materialized view — most reactors do not need it, and it trades away some fidelity, described next.

## When the fit is imperfect

A read model reactor is convenient, not transactional. Design for that:

:::caution
**Side effects are best-effort.** Returned events are appended fire-and-forget — a failure is logged, but nothing pauses or retries, because a read model reactor has no partition to fail. Ordering across rapid changes is not guaranteed. Make every handler **idempotent**: it may run again after a reconnect.
:::

- **Materialized fidelity is reduced.** The materialized API delivers full windows of already-deserialized instances, so the change type is inferred by comparing serialized values keyed by `id`, and the `EventContext` carries only the model key — no event sequence number. On SQL, several changes within one polling interval can collapse into one `[Materialized]` dispatch.
- **Legacy local reducers have reduced fidelity.** Inactive reducers, reducers for `[Passive]` read models, and reducers without dispatchable event handlers keep their local callback path. Their first non-removal is `Modified`, not an inferred `Added`; removals are `Removed`. Their context carries the model key, not the causing event's sequence number. This path does not remotely watch another client's active reducer. Upgrading code that relied on a first-seen local `Added` requires handling `Modified` instead.
- **Kernel watching remains best-effort.** Reducer change streams have the same watcher-cache, reconnect, and replay behavior as projection change streams. They do not add transactional side effects, exactly-once delivery, or an ordering guarantee across rapid changes.

When you need transactional, ordered, replayable reactions, react to the **domain event** with a [reactor](../reactors/) rather than to the derived read model.
