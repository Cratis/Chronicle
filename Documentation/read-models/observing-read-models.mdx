Keep a book list current with `IReadModels.Observe<T>()` in the .NET client. Subscribe once, show the current collection, and replace the list with each later snapshot. Chronicle supplies the stored view; [Watch](watching-read-models.mdx) is the alternative when you need individual changesets instead.

## Subscribe to a collection

Start with a registered read model maintained by an active projection or reducer, using a client, kernel, and sink that support collection observation. Subscribe to the returned subject and keep the subscription for as long as the screen or service needs updates:

<ChronicleClientTabs snippet="read-models/observing-read-models/basic" />

The first emission is the complete current set, including an empty set when there are no instances. Later emissions replace that set as processing changes the view; they are not a record of every appended event. Every stored instance is included, so use a [paginated materialized observation](materialized-pagination.mdx) for a large dataset.

Chronicle resolves the registered sink container and converts stored keys to your read model's key property. You do not need a property named `Id` or a direct MongoDB collection. The kernel releases PII and encrypted values before sending the collection.

The namespace is the event store's namespace at the time you call `Observe`. Keep observations within the lifetime of the tenant scope that created them.

You should first see the current book list, possibly empty, then a replacement list after relevant processing changes it. Protect a last-copy borrowing decision in the [command's guarded read](consistency.md#choosing-the-right-model); if its response needs its own write back, [wait for that append's observers](consistency.md#read-after-write--waiting-for-a-materialized-read-model) separately.

## Lifetime and errors

Each call creates its own observation, independent of `Watch` and other calls to `Observe`. The server stream starts with the first subscriber. Additional subscribers share that stream and immediately receive its latest collection.

Disposing the last subscription closes the stream. Calling `OnCompleted` on the subject or disposing the subject also closes it. A stopped observation does not reopen: call `Observe` again to start a new one.

Stream, deserialization, and filter failures reach subscribers through `OnError`. Chronicle does not automatically resubscribe; the consumer decides when to reconnect.

## Boundaries

- Existing or custom `IReadModels` implementations that do not override `Observe` remain usable through their existing APIs. Calling `Observe` on them throws `ReadModelCannotBeObserved`; they must implement or forward it to support collection observation.
- Passive read models have no materialized sink; `ReadModelCannotBeObserved` refuses them.
- Event-target types publish events instead of storing a collection; they are refused with the same exception.
- A type without a known projection or reducer raises `UnknownReadModel`.
- Materialized reads are eventually consistent. SQL polls for changes, so several writes between polls can appear as one snapshot. Use `Watch` when you need projection changesets rather than snapshots.
- The [testing event store](../testing/read-models/scenario.mdx#observing-read-models) rebuilds collections from its event log; it does not exercise server streams or database notifications.
