<a id="materialized-read-models"></a>

Chronicle's `Materialized` API reads pages of read model instances from their configured storage without replaying events. Use it when a list or data grid needs a window of current stored state rather than every instance at once.

That stored state is called *materialized* because a projection or reducer has already built it and written it to a *sink*, Chronicle's read model storage. It is eventually consistent: an appended event may not have reached the sink when you read. Passive read models have no materialized sink.

Client APIs express paging differently. Elixir's `Chronicle.ReadModels.query/2` uses page/page-size. TypeScript uses skip/take and an `AsyncIterable` for page observations; Kotlin uses skip/take and `Flow`. Java exposes blocking reads and callback or publisher observations through `ReadModelsJavaBridge`. Follow your example's client tab; the named paging concepts and ASP.NET endpoint below are .NET host code.

:::note
The .NET `Materialized` API retrieves or observes a window; it does not provide field filters, custom sorting, aggregation, counts, full-text search, or joins. For those queries, use the sink's native query capabilities. Elixir's `query/2` also returns paging metadata, including a total count.
:::

## What Materialized Access Covers

`GetInstances` reads a window once; `ObserveInstances` keeps sending replacement snapshots of that window. Both use the registered read model's sink, so you do not need to open its MongoDB collection or SQL table just to page through instances.

The window limits what your consumer receives, but it is not a guarantee about query cost. In .NET, an offset that is not a multiple of the page size can fetch a larger covering range and slice it locally. `InstanceCount.Unlimited` explicitly requests all instances. Choose a bounded page size for a list that may grow.

## Observing Changes

For a complete live collection with optional client-side filtering, use [Observing Read Models](observing-read-models.mdx). `IReadModels.Observe<T>()` has no 50-instance default window; `Materialized.ObserveInstances` below observes only the requested page.

In .NET, `ObserveInstances` returns an `IObservable<IEnumerable<TReadModel>>`. A subscription receives the current page, then replacement page snapshots as the sink reports changes. Replace the displayed window with each emission rather than appending the items to it.

<ChronicleClientTabs snippet="read-models/materialized-pagination/observing" />

Observation follows the sink's notification mechanism:

- MongoDB uses native change streams.
- SQL (PostgreSQL, SQL Server, SQLite) reads the current page on subscription, then polls the stored rows and total count for changes. Pages are ordered by the read model key. Set `Cratis:Chronicle:Sql:LiveQueryPollIntervalSeconds` to change the polling interval (default: 2 seconds). Failed polls are retried with backoff.

Several writes between SQL polls can appear as one updated snapshot. Snapshot delivery can also coalesce updates while a slower consumer catches up. Use [read model watching](watching-read-models) when you need projection changesets rather than replacement pages.

Dispose the subscription when its consumer closes. For coroutine or iterator-based clients, cancel or end the observation using that client's lifetime mechanism.

## When to Use the Materialized API

Choose a materialized read when the screen needs a bounded window of stored state. Choose a materialized observation when that window should update without the application repeatedly issuing reads; the sink may still poll internally.

For a small list that needs every instance, [observe the complete collection](observing-read-models.mdx). If the screen needs a field filter or a user-selected sort order, query the sink directly instead of fetching pages and filtering each page afterward. Filtering after paging does not produce a page of matching results.

## Comparison with On-Demand GetInstances

In .NET, the difference is whether you need the complete collection or a stored window:

| | `ReadModels.GetInstances<T>()` | `ReadModels.Materialized.GetInstances<T>()` |
|---|---|---|
| Data source | The sink for a materialized read model; event replay for a passive one or when you pass an event count | Materialized sink |
| Consistency | Eventual for stored state; passive reads fold the event log on demand | Eventual; no fixed delay is guaranteed |
| Result size | All instances from the read | A skip/take window |
| Filtering/sorting | Client-side after retrieval | No query parameters for either; use the sink directly |
