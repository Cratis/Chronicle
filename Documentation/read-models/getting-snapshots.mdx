Chronicle read model snapshots reconstruct how one instance reached its state by replaying events grouped by correlation ID, the identifier linking them to an operation. Use them to investigate an unexpected projection result: each snapshot puts the resulting state beside the events that produced it.

`GetSnapshotsById` returns reconstructed projection states, not saved copies of earlier database rows. Reducer-backed models return an empty history because the server does not run their client-side fold. For reducers, test that fold with a [read-model scenario](../testing/read-models/scenario.mdx).

## How snapshots are grouped

Each snapshot represents the cumulative read model state after one correlation group. A correlation ID ties related events to an operation, such as a command or import batch. It is not proof that those events formed a database transaction; the grouping depends on the IDs recorded with the events.

Every snapshot includes:

| Field | Meaning |
| --- | --- |
| Read model | The read model state after that correlation group was applied |
| Events | The events that were applied for that group |
| Occurred | The timestamp of the first event in the group |
| Correlation ID | The identifier that ties the related events together |

## Cost and limits

Snapshot retrieval reads the relevant history and replays the projection through each correlation group. Long histories cost more to reconstruct; a custom projection key can also require reading the event sequence before selecting the events for that key.

Use snapshots for diagnosis, not as the normal read path for a list or frequently requested value. A snapshot explains the state produced by replaying recorded events through the registered projection. It does not establish an access audit trail or recover every earlier version of the projection's logic.

If you only need the latest value, [read a single instance](getting-single-instance). For a page of stored instances without replay, use [materialized reads](materialized-pagination.mdx).
