When you need one read model and you have its key, ask Chronicle for it by key. You always call the same operation; what differs is where the answer comes from.

Chronicle knows whether the read model is **materialized** — whether an observer writes its state to a sink. If it is, the kernel reads the stored instance and releases any PII before returning it. If it is not — a passive read model has no observer and therefore no sink — the kernel rebuilds the instance from the events that feed it. You do not choose between the two at the call site; the read model's own definition decides.

## How it works

The client sends the read model type and key to the kernel. The kernel resolves the read model's definition and takes one of two paths:

- **Materialized read model** — the kernel looks the instance up in the sink by key, releases compliance-protected values, and returns it. The cost is a single storage lookup regardless of how long the event history is. The instance is as current as the observer that wrote it, so it is eventually consistent.
- **Passive read model** — the kernel replays the relevant events through the projection or reducer that owns the read model and returns the result. The instance reflects every event appended up to that call, so it is strongly consistent. The cost grows with the length of the history.

The materialized path is also the only one that sees the whole picture for a projection that joins across event sources or resolves keys from other events. Replay walks one event source, so it cannot reconstruct state that was built from events belonging to a different key.

## Read by key

The read model type must already be registered by the client, either as a model-bound projection, a declarative projection, or the read model produced by a reducer.

## Guarding a command decision (.NET)

When a command decides from a read model, use the additive `GetInstanceForDecision<T>(key)` API instead of `GetInstanceById<T>`. It returns a `ReadModelInstance<T>` with a nullable `Instance`, `SequenceNumber`, and `EventTypes`. `ToConcurrencyScopes()` returns a dictionary entry keyed by the **read** event source, scoped to exactly the projection's event types (including removal events):

```csharp
var read = await eventStore.ReadModels.GetInstanceForDecision<AccountBalance>(accountId);
var scopes = read.ToConcurrencyScopes();
await eventStore.EventLog.AppendMany(events, concurrencyScopes: scopes);
```

This operation uses a separate generated service and **always computes from the event log**, even when the read model is materialized. It folds that key's matching events through the current projection definition on every read, so its cost grows with the key's history; it never trusts a sink watermark, replay progress, or an observer's eventual consistency. An absent result with a removal at sequence R carries R. A key with no matching events carries `EventSequenceNumber.Unavailable` in the read; the scope turns that into `BeforeFirst` so an intervening first matching append is rejected. With `InitialModelState`, a never-created key instead returns the initial JSON state as a non-null `Instance` (with no events folded and `SequenceNumber.Unavailable`); its scope still expects no matching event. Neither case silently skips the concurrency check. The scope protects matching **event appends**, not changes to the projection definition made after the read. `Revise` and `Redact` mutate events in place without advancing the event-log tail; a decision based on the old content can still commit. `ToConcurrencyScope()` remains available only for appends to the **same event source as the read key**: used as another source's append scope, it checks that other source instead. Use the keyed `ToConcurrencyScopes()` with `AppendMany` when appending elsewhere.

Only projections on the event log whose events all resolve their keys directly to their event source ID are admitted. Joins, child or nested hierarchies (including `Nested`, conservatively refused), custom/constant keys, reducers, projections subscribing to all event types, an unknown definition, and unspecified keys receive a typed `DecisionReadRefused` reason instead of an unsafe scope. Other event sources and non-projected event types do not affect the decision watermark. Ordinary `GetInstanceById` behavior is unchanged. In in-process test scenarios, explicitly seed a `ReadModelInstance<T>` with its watermark and event types using `EventStoreForTesting.RegisterDecisionRead(read)`; an ordinary seeded instance has no reliable watermark. Unseeded decision keys fail in-process with an exception telling you to use `RegisterDecisionRead`, because the testing grain factory cannot serve kernel decision reads. Against a kernel predating the decision-read service, the call fails with gRPC `Unimplemented` (not a typed decision refusal).

## Missing instances

If no instance exists for that key, clients return their normal "not found" shape: `null`, `nil`, or an empty result depending on the language. Treat that as "no state exists yet," not as a projection failure. For a materialized read model this covers both a key that was never created and one that has been removed — the observer is authoritative, so Chronicle does not fall back to a replay that would resurrect it.

If the read model type itself is unknown, that is a configuration error, not a missing instance. The kernel rejects the lookup with an error naming the requested read model identifier. Use the registered identifier rather than its container name, and register the projection, reducer, or read model before querying it.

## Choosing which you get

Because the read model's definition decides the path, choose when you design the read model rather than when you query it.

Leave the read model materialized — the default — when:

- The same data is read often, or read from lists, dashboards, and user interfaces.
- The event history for a key can grow long.
- A brief lag between an append and the read reflecting it is acceptable.
- The projection joins events across event sources.

Mark the read model passive when:

- A command needs the exact current state before making a decision.
- You append an event and immediately need to read the state it creates.
- The event history for each key stays short.
- The read model is queried rarely relative to how often its events are appended.
