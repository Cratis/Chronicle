---
title: Decision-consistent reads
description: Guard an event-log append against changes to an event-source-keyed projection read for a decision.
---

Use a decision read when a rule depends on state you read first: a count, a stock, a status, a limit. A decision read folds a projection from the event log in a fresh session and gives you a guard for the append that follows. If an event that could change the read model arrives for the same source after the read, the guarded append reports a concurrency violation and writes nothing.

| The guard | What it does |
|---|---|
| Notes the log position before it folds | Events appended while you decide are caught |
| Watches the key and the model's event types | An unrelated event type, or a change for another source, does not conflict |
| Guards an absent model too | A concurrent creation conflicts |
| Is optimistic concurrency | Nothing is retried for you and nothing is locked |

For a unique value or a create-once rule, a [constraint](../constraints/index.md) is simpler and cheaper. A plain read through `IReadModels` or an injected read model guards nothing, even when it is passive. [Choosing how a rule holds](../dynamic-consistency-boundary/choosing.mdx) compares the options, [Scenarios](../dynamic-consistency-boundary/scenarios.mdx) shows each as code, and the measured cost is in [What a decision read costs](../dynamic-consistency-boundary/choosing.mdx#what-a-decision-read-costs). To see exactly what a guard covers, read [How guards are derived](../dynamic-consistency-boundary/how-guards-are-derived.mdx).

## Your first decision read

A workshop has a fixed number of places. Read the workshop, check the rule, and append with the read as the guard.

Three things make it work:

- **The model has an `Id` and is keyed by the event source.** A decision read refuses a model it cannot guard exactly. See [Admitted projections](#admitted-projections).
- **`GetDetached` returns the state and the guard.** You pass the guard to the append with `guardedBy`. `Instance` is `null` when no event created the model yet.
- **A rejected append is a result, not an exception.** Read again and decide again.

To tell a conflict from another failure, ask the result. A conflict names the model and key; `IsSuccess` also covers constraint violations.

## Unit-of-work lifecycle

`Get<T>(key)` enrolls into the ambient unit of work. `GetDetached<T>(key)` does not. `GetFor<T>(unit, key)` enrolls into the unit you pass, before it returns the value. You can also enroll a detached read with `IUnitOfWork.AddDecisionRead`.

| Topic | Behavior |
|---|---|
| Detached reads under [read protection](read-protection.mdx) | `GetDetached` is refused with `DetachedReadWhileReadsAreProtected` unless an advisory read allowance is open. A detached read is meant for a chosen append, and enrolling it silently would change which commit it guards |
| Who completes a protected unit | Its owner: `UnitOfWork.ClaimDecisionReadCommitOwnership`, then `CommitAsOwner` or `RollbackAsOwner`. Calling `Commit()` from application code after enrollment is rejected |
| Rollback and dispose | Once a claimed unit has enrolled a decision read, public `Rollback()` and `Dispose()` on an open unit are refused: only the owner can roll it back. During a pending commit, public and owner rollback throw `UnitOfWorkIsCompleting` in both Compatibility and Strict modes and keep the staged events. Disposal stays a no-op. A claim alone does not change rollback or disposal of a unit without enrolled reads, but owner rollback during a pending commit is still refused |
| Commit with no events | A protected commit with no events still validates the guard. A kernel too old to allow validate-only returns `DecisionReadValidateOnlyNotSupported`, never success |
| Staging after commit began | Units without decision reads keep their previous behavior by default: a late `AddEvent` or `AddEvents` stages events that cannot be appended, and each attempt logs an error with the correlation id and no event content. Protected units refuse late events in every mode |
| Strict policy | Set `ChronicleOptions.UnitOfWorkLifecyclePolicy = UnitOfWorkLifecyclePolicy.Strict` (also available through client and ASP.NET Core options) to reject staging as soon as commit begins, after commit failure, rollback or disposal. Strict rejection throws `UnitOfWorkIsCompleted` before it enumerates input or changes staged events. It will become the default in the next major release |

### Inspecting the outcome

- `IUnitOfWork.GetDecisionConflicts()` maps violated labels to the read model type and key without exposing boundaries.
- `IUnitOfWork.HasEnrolledDecisionReads` says that at least one decision read was enrolled, including through a direct `AddDecisionRead` call. On Chronicle's unit of work it stays true after commit, rollback or disposal. Custom implementations default to `false` for compatibility, so a `false` from one of those is not proof that it cannot enroll protected reads. The property does not grant permission to commit a protected unit without its owner capability.

## Admitted projections

Only a single Chronicle **projection** on the event log, keyed directly by the event source ID, with a nonempty finite set of event types (including removal types), can be protected. Empty keys, `*`, `#`, leading/trailing whitespace and event type IDs containing commas are refused. Routing keys must be empty or `$eventSourceId`; joins (including variants), children, nested projections, derivatives, event-property routing, all-event subscriptions and projections on other sequences are refused. A reducer is admitted under different rules; see [Reducers](#reducers). String keys without a converting format are admitted. GUID keys, including GUID concepts, require lowercase canonical `D` form. **All writers of event source IDs for GUID-keyed models must use this same canonical form**; non-.NET writers using alternate casing or formatting are outside this guarantee even if the requested key is canonical. Numeric and other converting key types, and models without a key property, are refused. `IDecisionReads.Admit<T>()` checks the projection shape without I/O; `Get` also validates the key. Unsafe shapes and keys throw `DecisionReadRefused` with a typed reason before reading.

The client captures the unfiltered event-log boundary *before* folding and uses it for the guard. The filtered tail and a first-use client/kernel definition comparison are **diagnostics**, not certificates of executing-projection agreement. An incomplete fold detected by the probe refuses with `FoldIncomplete`; a listed-definition disagreement refuses with `DefinitionMismatch`. The executing projection definition and initialization state must agree with the client's definition. Deployments changing definitions, including cross-silo cache convergence, must quiesce protected commands. Multiple reads of one key merge their event types and use their earliest boundary; an explicit competing scope on that key is refused, while the decision scope replaces an ordinary append-time default scope. Targets must match the event store, namespace and event-log sequence.

## Reducers

A [reducer](../reducers/index.mdx) or [self-reducing read model](../reducers/self-reducing-read-models.mdx) can be read as a decision read, with or without read protection. Chronicle does not use a projection session for it. The client fetches every event of the handled types for the source from the event log, runs the reducer over them, and checks that the fold reached everything it should have. The guard is the source ID and the reducer's event types, the same as for a projection. The read takes the same three attempts as a projection read.

`Admit<T>()` and `Describe<T>()` assess a reducer without I/O. A reducer that cannot be guarded exactly is refused with a typed reason before it runs:

| Reason | Why the reducer is refused | Fix |
|---|---|---|
| `NotEventLog` | The reducer observes an event sequence other than the event log | Read a model on the event log |
| `ReducerFilters` | The reducer filters its events by tag, event source type or event stream type, and a decision read cannot reproduce the filter exactly | Remove the filter, or use a projection |
| `ReducerDependencies` | A classic reducer has a constructor parameter other than `ILogger<T>`. Self-reducing read models are not subject to this rule | Remove the dependency, or record what the fold needs in the event |
| `NoEventTypes` | The reducer handles no event types | Add a handler |
| `UnsupportedEventTypeId` | A handled event type ID contains a comma | Rename the event type |
| `ReducerGeneration` | A handled event type is registered with more than one generation, the generation a handler declares is unavailable, or an event was revised to another generation | Handle one generation per event type, and register the generation |
| `ReducerDispatchIncomplete` | The reducer did not receive every fetched event of its handled types | Check the reducer's handlers for every handled event type |
| `InvalidKey` | The key is not a single event source ID | Pass the raw event source ID |
| `StreamScopeNotSupported` | A stream-scoped read was requested | Read the whole source |
| `FoldIncomplete` | After three attempts the fold had not reached the latest matching event | Try again |
| `Reducer` | The reducer cannot be resolved for the read model | Register the reducer |

A reducer that throws is not a refusal: the read fails with an `InvalidOperationException` that carries the reducer's messages. Reducer code runs with read allowances suspended, so a reducer that calls Chronicle reads inside a protected invocation is refused by the guards.

A reducer read costs the same as a projection read: it replays the source's whole history of the handled types on each attempt.

## Pinned generation delivery

A projection whose definition uses `Pinned` generation delivery cannot be read as a decision read while read protection is active. The decision fold runs with Compatibility delivery and could not honor the pinned generations, so Chronicle refuses with `GenerationDeliveryNotSupported` instead of folding something else. The refusal applies when a protected frame is active or the receiving unit enforces read protection; outside it, the read is not refused for this reason. `Describe<T>()` reports `UsesPinnedGenerationDelivery` so you can check without reading. Use Compatibility delivery for the projection, or read it through a plain read.

## Scoped to one event stream

When a decision concerns one stream within an event source, pass the source ID, stream type and stream ID to `Get<T>` or `GetDetached<T>`. The fold and its concurrency guard use the same stream filters; events on another stream do not invalidate the read. An optional event source type narrows both further.

<ChronicleClientTabs snippet="read-models/decision-reads/stream-scoped" />

The stream type and stream id are strings here. With an [event source definition](../event-sources/defining.mdx) you can take them from the definition, so the read and the append use the same values. See [Event sources and the Dynamic Consistency Boundary](../event-sources/dcb.mdx).

`AdmitForStream<T>()` admits the same finite, flat event-log projections as `Admit<T>()`, and also projections consistently keyed by `$eventContext(eventStreamId)` across their creation, update and removal events. A source-keyed projection keeps the source ID as its model key, but folds only the selected stream. A stream-keyed projection uses the stream ID as its model key; the concurrency label remains the **source ID**. For a GUID-keyed stream projection, use lowercase canonical `D` form for stream IDs on every append and read, just as source-keyed GUID projections require it for source IDs. Reading a stream-keyed projection without stream scope refuses with `StreamKeyRequiresStreamScope`. The kernel must explicitly acknowledge stream scoping; an older kernel refuses with `StreamScopeNotSupported` rather than silently folding the whole source. A stream-scoped read of a reducer is refused with `StreamScopeNotSupported`; a reducer folds the whole source.

The stream-scoped overload requires a specific stream type: `EventStreamType.All` refuses with `AllStreamsNotSupported`. `EventStreamId.Default` is allowed for event-source-keyed projections with a specific stream type, including stream types that use only the default ID. As in other Chronicle event filters, this default does not narrow by stream ID: the fold and guard cover every ID within that source and stream type. Stream-keyed projections require an explicit stream ID; the default refuses with `StreamKeyRequiresExplicitStreamId` because it could fold several instance keys together.

Multiple reads for the same source still merge at their earliest boundary and union their event types. If their stream type or stream ID differs, the merged guard widens. Outside a read-protection frame it drops **both stream values**, checking all streams of that source. Under a frame each value is kept only when the reads agree on it. Different source types are dropped in both cases, so all source types count. This can produce extra conflicts, but cannot miss a change affecting either read.

A materialized projection keyed only by stream ID can collide when two event sources use the same stream ID. Prefer a passive projection (`[Passive]`) for these decision folds, or use a composite key for materialization. Composite-key projections are not admitted for protected decision reads. Command-property binding belongs to Arc; Chronicle supplies the explicit read API.

## Limits and assumptions

The guarantee assumes a single ordered event-log writer, ordered primary storage reads, stable projection execution, and literal identity between source IDs and keys. Revise and redact do not advance the tail; migration generation replacement can bypass the grain; neither is guarded. Other event sequences, external data, clock values and definition changes are not guarded. A guard detects every matching event appended after its boundary, whoever wrote it. It only protects decisions that carry a guard: a writer that decides without one can still break the rule. The rule holds only when every writer that decides on it is guarded, or when it is a constraint, which the kernel checks for every append. A removal followed by recreation with nonempty defaults can fold differently from materialization even though the append guard still works. Each attempt makes two tail RPCs, activates a fresh projection session, folds the key's entire history and requests session dehydrate. A read may take up to three attempts. The first read of each model type also makes two definition-listing RPCs. Its cost grows with that history. The minimum supported kernel is Chronicle 19.0.0 with `ExpectsNoMatchingEvent` scope validation (introduced in 16.34); older kernels can silently skip an empty-log guard.

When the kernel renumbers an append after a duplicate-sequence collision, it validates the scopes again before writing, as of Chronicle 19.40.1, so a decision read's guard still applies on that path. Constraints are not run again there. Older kernels renumbered without validating again, so on those a duplicate grain activation or an unresolved earlier storage outcome could defeat this and existing concurrency scopes. Quiesce such writers when you must support a kernel older than 19.40.1. Writes that bypass the kernel's append path are never guarded.
