## The operator journey

An observer processes events for a projection, reducer or reactor. A failed partition holds back part of that work; it does not necessarily stop the whole observer. Diagnose the affected scope before choosing how much history to process again.

1. Monitor the [health endpoint](/chronicle/hosting/configuration/health-endpoint/) and configure [alerts on observer failures](/chronicle/hosting/alerting-on-observer-failures/) so you can investigate before a user reports stale output.
2. Follow [Diagnostics](/chronicle/operations/diagnostics/) to find the observer and partition in the correct event store and namespace. Read the exception and failing event sequence number, then check whether a recovery job is already running.
3. Use [Recovering from failures](/chronicle/operations/recovering-from-failures/) to choose between preserving the existing state with a retry and rebuilding it with a replay. Clearing quarantine can start processing again, so fix the cause and account for repeated side effects before releasing it.
4. Follow [Recover a failed partition](/chronicle/operations/recover-a-failed-partition/) to carry out the recovery through the Cratis CLI runbook and verify both processing progress and application output.

Chronicle automatically retries failed partitions with backoff, waiting longer between attempts. Intervene when the retry budget is exhausted or when the cause needs a code, data or dependency fix. A successful recovery request is only the start: the job and resulting output still need checking.
