Test a Cratis Chronicle slice by checking the events its command appends and the read model those events produce. A slice is one path through a feature, from an action to its resulting state. In-process scenarios let you check those two parts without starting a Chronicle server or database.

## Real engines, in-memory storage

The C# examples use `Cratis.Chronicle.Testing`. `EventScenario` runs the kernel append path with in-memory storage, including serialization and constraint validation. `ReadModelScenario<TReadModel>` runs the projection or reducer engine against supplied events. These are separate checks: appending through `EventScenario` does not start observers or update a read model for you.

The read-model harness also substitutes infrastructure such as projection storage and compliance services. It is not a running kernel with only its database replaced.

:::note[Client coverage]
.NET, Kotlin/Java and TypeScript provide in-process scenarios through their testing packages. Elixir provides `Chronicle.Testing` and `Chronicle.Testing.Case`, using an in-memory kernel and a synchronous dispatcher rather than the gRPC observation stream. The helpers do not have identical coverage; see [Testing](../testing/) before choosing a scenario for another client.
:::

```bash
dotnet add package Cratis.Chronicle.Testing
```

The examples below use the [Cratis Specifications](/testing-with-cratis/) style (`Establish`/`Because`/`should_`), but the scenarios work with any test framework.

## Test the events with EventScenario

Create an `EventScenario`, seed any pre-existing history with `Given`, and append through its `EventLog`. Assert on the `AppendResult` so the test checks whether the append was accepted, not just whether the call completed:

To test command behavior, pass the scenario's `EventLog` to the command code under test. The direct append above checks the append path; it does not invoke your command for you.

Constraints are discovered from the configured client artifacts. With a unique-ISBN constraint such as the one in [Enforce a unique value](./enforce-a-unique-value.md), seed a book and then append a duplicate. The expected result is a constraint violation:

Use `ShouldBeSuccessful`/`ShouldBeFailed` for the overall outcome and `ShouldHaveConstraintViolationFor` to identify the rejected rule. [Append result assertions](../testing/events/assertions) also covers concurrency violations and errors. Create a fresh `EventScenario` per spec and dispose it; calls on the same instance share its accumulated history.

## Test the read model with ReadModelScenario

Use `ReadModelScenario<TReadModel>` to check how recorded facts become state. It detects whether a reducer, fluent projection or model-bound attributes build the model, then applies the supplied history through the corresponding engine:

<ChronicleClientTabs snippet="scenarios/test-a-slice/read-model-spec" />

Here `Given` supplies the events and `Instance` exposes the resulting model. The assertion checks that borrowing the book changes its availability. If it fails, inspect the supplied history, read model declaration and mapping, such as `[SetFrom<T>]`/`[SetValue<T>]` attributes or reducer logic. Using the real engine does not rule out a mistake in the test setup.

## What this does and doesn't cover

Together these checks establish what the exercised code appends and how the supplied facts become state. They do not establish that a deployed observer catches up, that the network connection works, or that a production sink behaves as expected. Use integration tests with a real kernel for those boundaries.

They also do not exercise your HTTP surface or UI. Test those through your application framework rather than treating an append or projection assertion as proof of the whole feature.
