A [reactor](../reactors/) in Cratis Chronicle runs a side effect in response to a recorded event. Use one when returning a book should notify the next member on the waitlist, or when a reservation should produce a follow-up stock event. Unlike a projection that builds state, a reactor does work because a fact has happened.

## Write the reactor

With a Chronicle client configured in your C# application, define a class implementing `IReactor`. This marker interface has no methods to implement. Instead, write a handler whose first parameter is the event type you want to handle:

Chronicle discovers the reactor among the application types configured for its client and routes matching events to the handler. Here `context.EventSourceId` identifies the returned book, so the notification service can find its waitlist. Provide that service through your application's dependency injection setup.

## Be safe to repeat

A reactor may handle the same event again during replay or recovery. Make external effects idempotent: repeating the request must not send a second notification or charge a payment twice. Use the [delivery identity](../reactors/delivery-identity) as a stable key for the remote system or for your own effect receipts. A local receipt alone does not make a remote call atomic with recording that receipt.

If an effect should be skipped during replay, mark its handler or the whole class with `[OnceOnly]`. This excludes it from replays, not from every possible redelivery. See [OnceOnly](../reactors/once-only) before using it for a payment or notification.

In C#, Chronicle gives returned events idempotency keys when the connected kernel supports idempotent appends. Those keys prevent the same delivery's output from being appended again during recovery or catch-up. An older kernel without that capability appends the returned events without keys. If you change the returned output and deliberately want replay to append the new shape, raise the reactor's [effect epoch](../reactors/delivery-identity#when-to-bump-the-effect-epoch), the version number included in its returned-event keys. Do not raise it just to retry unchanged output.

## Need state? Pick the right consistency

Use the event's data first. If the notification also needs the book's title, read the model that holds it, using `context.EventSourceId` as the key.

A materialized read model is stored state maintained by a projection or reducer. It is the default and is [eventually consistent](../read-models/consistency.md), so it may not yet include the event being handled. Calling `IReadModels.GetInstanceById` or accepting the model as a handler parameter does not change that consistency.

When the reaction needs state that includes the triggering event, mark the read model `[Passive]`. Chronicle then computes it from the event log on demand rather than relying on the stored model. Make that choice on the read model definition before using the lookup below; the lookup alone does not request a strongly consistent read.

`Task<StockDecreased>` and collections of events work too. [Returning side effects](../reactors/side-effects) explains the supported return shapes and how to choose a different target event source. The example's `[OnceOnly]` skips the handler during replay; [Duplicate protection](../reactors/side-effects#duplicate-protection-for-returned-events) explains the separate key-based protection for returned output. A `ReactorScenario` records returned events by default; configuring it with the real side-effect handlers also exercises their keyed appends.
