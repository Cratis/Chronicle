# Read models and PII

Cratis Chronicle encrypts personally identifiable information (PII) in managed read models when their own schemas mark those fields as personal. An event annotation alone does not protect a projection destination. Use Chronicle's query methods to release, or decrypt, stored values; call release explicitly for raw storage, cached instances or watch streams.

:::note[The same mechanism also protects `[Encrypted]` values]
The projection pipeline and `IReadModels.Release` also handle `[Encrypted]` properties, using separate confidentiality keys. A document can contain both classifications on different properties, but subject erasure for PII does not delete confidentiality keys. Use [Security](../security/) to choose `[Encrypted]` key scopes for operational secrets rather than treating it as a substitute for personal-data erasure.
:::

:::note[Client coverage]
The `IReadModels` APIs described here are .NET APIs. Select your client in the examples, and check its [PII declaration support](./pii), [projection APIs](../projections/) and [reducer APIs](../reducers/) before applying the pattern. The kernel storage rules below do not imply identical client query or release APIs.
:::

## Observer decryption

The kernel releases events before delivering them to observers, including reactors, webhooks, reducers and projections. `Observer.Handle()` calls the event compliance handler, so individual observers do not need their own event-decryption code. This event path is separate from releasing a stored read model for a query.

The compliance identifier used for key lookup follows this rule: if an explicit `Subject` was set on the event at append time, that value is used. Otherwise, the `EventSourceId` is used as the fallback identifier. This mirrors the encryption key that was used when the event was originally written to the event log.

## Projections — `[PII]` required on the read model property

A projection copies values from events into a read model, but the kernel decides what to encrypt from the read model's own schema, not from the events the values came from. Marking an event property as PII does not mark the read model property it is mapped to. Without `[PII]` on that read model property, the projected value is stored in plain text, and it stays readable after the subject's key is erased.

Mark every read model property that holds PII, either with `[PII]` on the property or by giving it a concept type that is itself marked `[PII]` (see [Declaring PII on a concept](./pii-with-concepts)).

The read model's `Name` property receives `PersonName` from the event and carries its own `[PII]` declaration, so the managed sink stores it encrypted. Chronicle query methods release the value before returning `Employee` records; direct storage reads do not.

## Reducers — explicit `[PII]` required

Reducers follow the same rule as projections: you must annotate PII properties on the read model record with `[PII]`. Reducers also use arbitrary C# logic to compute state, so there is no mapping from event properties to follow.

<ChronicleClientTabs snippet="compliance/read-models/reducer-explicit-pii" />

The `[PII]` attribute on `Name` tells the kernel to encrypt that property before storage. Use the query and release paths below to obtain its plaintext value.

## Stored subjects

Every managed read model document written by Chronicle contains a reserved `__subject` field. It stores the default compliance identifier used for PII on that document. Existing single-subject documents need no other metadata and remain compatible.

A projection can compose PII from events belonging to different subjects. Chronicle derives that ownership from the events that populate each property and stores only the exceptions to the default in a reserved `__subjects` object:

```json
{
  "__subject": "employee-42",
  "__subjects": {
    "advisorName": "advisor-17"
  }
}
```

In this example, `advisorName` is encrypted, released, and erased under `advisor-17`; every other PII property falls back to `employee-42`. The map is maintained automatically as projection events replace values. No read model attributes or manual migration are required. Rows written before this capability have no `__subjects` field and continue using `__subject` for every property.

> **Do not** declare properties named `__subject` or `__subjects` in your read model records. Chronicle reserves both names for internal use.

## GDPR erasure

Use the Compliance API to erase a subject's key; [Erasing a subject](erasing-a-subject.mdx) describes the operation. Chronicle's release path then returns empty values for PII encrypted under that key. The stored documents still contain ciphertext: this is crypto-shredding, making encrypted data unreadable by removing its key rather than deleting each stored value.

This boundary covers data genuinely encrypted under the erased key. Historical plaintext, unmarked projection fields and independently retained copies remain readable. Authorization is also separate: release does not decide whether the caller may access personal data.

## Rebuilding after erasure

Projection and reducer replay can rebuild stored read models after erasure without authorizing a new key. Materialization writes an empty marker at the erased subject's PII boundary; it does not recreate the key or clear the erasure record that prevents new protection under that lifecycle. On release, an erased string leaf is empty and an erased protected array has no elements. Do not depend on a single null representation for erased protected objects. Public siblings and live subjects' protected values remain available. Per-property ownership keeps contributed PII under its originating subject, even when another subject owns the document.

:::caution[Replay over existing storage is not a scrub]
Replay applies emitted changes. It does not prove that stale fields, orphan documents, legacy wrong-subject ciphertext, or copies outside Chronicle have disappeared. For cleanup, drop and rebuild the affected read-model storage into a clean container, rebuild into a new container and switch readers after validation, or perform an audited migration that proves ownership and rewrites or removes every affected copy. Retire the old container deliberately; a clean destination does not remove it for you.
:::

Do not authorize a new lifecycle merely to replay historical data. Authorization is for a deliberate new lawful basis to protect future data, not a repair step for erased history — see [The encryption key lifecycle](key-lifecycle.mdx).

If event content itself must be removed rather than left as ciphertext, review [event redaction](../events/redaction). Neither operation proves that copies outside the affected storage have been removed.

## Querying

The .NET `IReadModels` query methods release marked fields before returning results:

<ChronicleClientTabs snippet="compliance/read-models/querying" />

When the subject's key has been erased, an encrypted `Name` string releases as an empty string. Other property types use the empty values described below. This behavior does not guarantee that every query succeeds: key-store, transport, schema or deserialization failures can still prevent a usable result.

That automatic decryption covers `IReadModels`' query methods. For an instance that arrived some other way — built from raw storage, restored from a cache, or delivered through `Watch`, which streams changes without releasing them — call `IReadModels.Release` yourself; see [Releasing PII](../read-models/releasing-pii).

### Property-level release and failures

The default schema release path handles decryption failures per property. These are the expected outcomes when that path completes:

| The stored value | What the caller gets |
|---|---|
| Encrypted under this subject | The decrypted value. |
| Encrypted, but the subject's key was deleted | The empty value of the property's type — the erasure case above. |
| Plaintext that does not have Chronicle's ciphertext shape | The value, untouched. |
| Ciphertext that fails decryption with the resolved subject's key | An empty value for that property, plus a kernel log entry naming the property, subject and likely cause. |

Schema release uses an empty string for a string, `0` or `false` for a non-nullable number or boolean, `null` for a nullable scalar, and an empty array or object for a protected container. Materializing that JSON into a particular concept or value-object type can still fail. Test erased values with your serializers rather than assuming every type accepts them.

An empty value alone is not proof of erasure: it can also be a genuine stored value or the result of a release failure. [Issue 4620](https://github.com/Cratis/Chronicle/issues/4620) discusses distinguishing erased values.

The third row covers plaintext resolved in memory for display and values stored before a property was marked `[PII]`. Chronicle checks the ciphertext shape before looking up a key. Plaintext that does not match that shape passes through unchanged, including after subject erasure.

A decryption failure in the fourth row can come from ciphertext paired with the wrong subject. This can occur in legacy data written before per-property ownership was tracked, or in data written outside managed projection sinks. New projection writes keep the ownership map with the ciphertext so joined PII releases under its originating event's subject.

These property-level fallbacks do not cover every failure. An instance without applicable metadata can pass through unchanged, and the .NET releaser returns the original instance on a service error; transport or deserialization failures can throw. Check application response paths explicitly. For a service caller that needs all-or-nothing release, see [Strict compliance release](pii#strict-compliance-release).

> [!NOTE]
> Applying protection normally fails the write if encryption fails; plaintext fallback is never acceptable. Stored read-model materialization handles only the specific `EncryptionKeyErased` failure from a PII handler as an empty marker. Key-store outages, other protection failures, and failures from non-PII handlers still fail the write.

## Composing read models outside Chronicle

Per-property ownership is storage metadata maintained by Chronicle's projection pipeline. If application code manually constructs an object from raw ciphertext, `IReadModels.Release` can only resolve the object's own `[Subject]` member or `Id` and cannot infer where each copied value originated. Prefer querying managed read models through Chronicle so their stored ownership metadata is honored before composition.
