# Read models and PII

Chronicle stores PII fields encrypted at rest in both the event log and managed read models (projections and reducers). The encryption and decryption is handled automatically by the kernel — your application code works with plaintext values at all times.

:::note[The same mechanism also protects `[Encrypted]` values]
Everything on this page about *how* a read model is encrypted and released — the projection pipeline, `IReadModels.Release`, the automatic decryption on every query — applies identically to `[Encrypted]` values, not only `[PII]` ones. A read model can mix both on the same document; each resolves under its own, disjoint key. What is specific to `[PII]` on this page is the GDPR mechanics: the `[Subject]`/erasure behavior below has no equivalent for `[Encrypted]`, because an operational secret has no data subject and nothing about it is ever erasable. See [Security](../security/) for `[Encrypted]` and its wider key scopes.
:::

:::note[Client coverage]
The C# examples on this page combine several mechanisms already covered elsewhere for their per-client support ([PII property annotation](./pii), [projections](../projections/), [reducers](../reducers/)) — this page's specific focus (marking projected properties as PII on the read model, and the `_subject`/GDPR-erasure mechanics) hasn't been individually re-verified per client yet.
:::

## Observer decryption

All observers — reactors, webhooks, reducers, and projections — receive decrypted events from a single, central decryption point in `Observer.Handle()`. This means encryption is applied consistently regardless of the observer type, and no observer implementation needs to handle decryption itself.

The compliance identifier used for key lookup follows this rule: if an explicit `Subject` was set on the event at append time, that value is used. Otherwise, the `EventSourceId` is used as the fallback identifier. This mirrors the encryption key that was used when the event was originally written to the event log.

## Projections — `[PII]` required on the read model property

A projection copies values from events into a read model, but the kernel decides what to encrypt from the read model's own schema, not from the events the values came from. Marking an event property as PII does not mark the read model property it is mapped to. Without `[PII]` on that read model property, the projected value is stored in plain text, and it stays readable after the subject's key is erased.

Mark every read model property that holds PII, either with `[PII]` on the property or by giving it a concept type that is itself marked `[PII]` (see [Declaring PII on a concept](./pii-with-concepts)).

The `Name` property is mapped from `PersonName` on the event, and carries `[PII]` itself, so it is stored encrypted in MongoDB. When a query returns `Employee` records, the kernel decrypts the values before they reach the caller.

## Reducers — explicit `[PII]` required

Reducers follow the same rule as projections: you must annotate PII properties on the read model record with `[PII]`. Reducers also use arbitrary C# logic to compute state, so there is no mapping from event properties to follow.

<ChronicleClientTabs snippet="compliance/read-models/reducer-explicit-pii" />

The `[PII]` attribute on `Name` tells the kernel to encrypt that property before storage and decrypt it on retrieval.

## Stored subjects

Every managed read model document written by Chronicle contains a reserved `__subject` field. It stores the default compliance identifier used for PII on that document. Existing single-subject documents need no other metadata and remain compatible.

A projection can compose PII from events belonging to different subjects. Chronicle derives that ownership from the events that populate each property and stores only the exceptions to the default in a reserved `__subjects` object:

```json
{
  "__subject": "employee-42",
  "__subjects": {
    "advisorName": "advisor-17"
  }
}
```

In this example, `advisorName` is encrypted, released, and erased under `advisor-17`; every other PII property falls back to `employee-42`. The map is maintained automatically as projection events replace values. No read model attributes or manual migration are required. Rows written before this capability have no `__subjects` field and continue using `__subject` for every property.

> **Do not** declare properties named `__subject` or `__subjects` in your read model records. Chronicle reserves both names for internal use.

## GDPR erasure

Deleting an encryption key is the Chronicle mechanism for GDPR erasure:

1. Delete the key for the subject (the data subject's identifier) via the Compliance API — see [Erasing a subject](erasing-a-subject.mdx).
2. Read models need no further step to stop exposing the data: reading them releases each PII value with the subject's key, and with the key gone the value comes back empty.

Read model documents written before the erasure still hold the ciphertext. Nothing can decrypt it once the key is gone, which is what crypto-shredding relies on.

When every member's protection can be resolved, the read model keeps updating after the erasure. Writing it for an erased subject — the next event that changes it, or a replay that covers the subject — replaces each of their PII values with an erased placeholder when the erasure fence refuses a key. No key is created and nothing of the value being written is kept, so the members that are not personal go on changing and the subject's personal data keeps reading as empty. A document rewritten this way no longer holds the old ciphertext. Erased values retain their declared types when released: plain strings are empty, non-nullable numbers and flags use their type defaults, and nullable values are null. This also applies to protected members of nested objects and collection elements. Whole protected objects and collections release as empty containers. Values belonging to other subjects remain encrypted at rest and release unchanged, including legitimate empty nullable strings. Non-PII members retain their values, including explicit nulls. See [The encryption key lifecycle](key-lifecycle.mdx).

Protection follows scalar `$ref` definitions and every `allOf` member declaration: if any declaration marks a member as PII, that member is protected. Unresolved references, conflicting declarations, ambiguous unions, unsupported dynamic or conditional members, and unavailable protection handlers fail closed. Such a write is refused rather than storing plaintext, even if this means the partition remains stopped after erasure. Schema-resolution failures also refuse release; they are not treated as per-value decryption failures. Constraint reindexing skips unreadable protected values regardless of their placeholder type, without skipping legitimate zero or false values.

For full erasure of event content, combine key deletion with [event redaction](../events/redaction).

## Querying

Read model queries are transparent to PII encryption. No changes to query code are needed:

<ChronicleClientTabs snippet="compliance/read-models/querying" />

Chronicle decrypts PII fields automatically before returning results to the caller. When the encryption key has been deleted for a subject, `Name` returns an empty string — the caller receives an `Employee` record with an empty name, never an exception or partial result.

That automatic decryption covers `IReadModels`' query methods. For an instance that arrived some other way — built from raw storage, restored from a cache, or delivered through `Watch`, which streams changes without releasing them — call `IReadModels.Release` yourself; see [Releasing PII](../read-models/releasing-pii).

### One property never fails the whole read

Once the schema's protection is resolved, decryption is handled per property, and a value that cannot be decrypted does not fail the read model or the query returning it:

| The stored value | What the caller gets |
|---|---|
| Encrypted under this subject | The decrypted value in its declared JSON type, including an empty string when that was the plaintext. |
| Encrypted, but the subject's key was deleted | A typed erased placeholder — the erasure case above. |
| Never encrypted under this subject | The value, untouched. |
| Encrypted under a *different* subject and missing ownership metadata | A typed unreadable placeholder for that property, plus an error in the Kernel log naming the property, the subject, and the likely cause. |

The third row matters when a `[PII]`-typed property is resolved in memory at the query edge — for display on a view whose own compliance subject is not that person — or when a property was marked `[PII]` after values had already been stored. Chronicle recognizes the shape of the values it encrypts, so a value it never encrypted is passed through rather than blanked or rejected.

The fourth row can occur for legacy data that was written before per-property ownership was tracked, or for data written outside Chronicle's managed projection sinks. New projection writes keep the ownership map with the ciphertext, so joined PII releases under the subject of the event it came from.

> [!NOTE]
> Applying PII behaves the opposite way, and deliberately so: if encryption fails on the way *in*, the operation fails. Storing a value that was meant to be protected, unprotected, is never an acceptable degradation.

## Composing read models outside Chronicle

Per-property ownership is storage metadata maintained by Chronicle's projection pipeline. If application code manually constructs an object from raw ciphertext, `IReadModels.Release` can only resolve the object's own `[Subject]` member or `Id` and cannot infer where each copied value originated. Prefer querying managed read models through Chronicle so their stored ownership metadata is honored before composition.
