# CHR0038: [Join] of a [PII] value crosses the compliance subject

## Rule Description

A join explicitly selects a property that differs from the read model's apparent compliance subject and copies a `[PII]` value through that boundary.

A join reads `TEvent` through the stream selected by the join key, but every append can supply an explicit runtime subject independently of that stream. The absence of a `[Subject]` declaration therefore does not prove equality. A declaration does not prove it either: its value can be null or empty, an append can override it, and historical events retain the subject stored when they were appended.

`CHR0038` preserves the established definite source boundary as an error: an explicit `on` names a different property from the read model's apparent subject. When `on` names the same apparent subject, or a valid child join omits `On`, source analysis still cannot prove the persisted runtime subjects equal, but that conservative expansion is reported as the warning [CHR0044](CHR0044) instead of widening this released error.

Join a value that is not `[PII]`, or resolve the personal value at the query edge under the subject that owns it. If the joined value is not in fact personal data, remove the `[PII]` marking from the event property (or from its concept type) so the compliance metadata matches reality.

Both spellings of the definite boundary are covered: the model-bound `[Join<TEvent>(on: ...)]` attribute, and the fluent `builder.Join<TEvent>(_ => _.On(...))` on an `IProjectionFor<T>`. For the fluent form, a `[PII]` value counts as reaching the read model through the join's Set/To, Add/Subtract, SetThisValue, `PropertyPath`, and AutoMap mappings. AddChild is not a join content mapping: Chronicle builds it as a separate child projection operation, so its own parent-key routing and child mappings are analyzed independently by [CHR0043](./CHR0043).

PII reach is recursive in both forms. A joined member counts when `[PII]` occurs directly, on its type, in an inherited member, or inside a nested value object, array, or collection element.

This rule covers the `[Join]` construct only. A projection that redirects its key onto another subject's stream reaches the same defect through a different route; that is [CHR0043](./CHR0043).

## Why This Rule Exists

Chronicle stores exactly one compliance subject per read model instance and releases every `[PII]` property on that instance under it. A joined value encrypted under another subject's key therefore cannot be decrypted. It is not confined to the one document either: the release runs at materialization, so the failure freezes *every* partition of the projection, and reading the read model through the CLI returns the same failure.

When a projection does slip through — built dynamically, or from a source the analyzer cannot see — Chronicle raises `ComplianceMetadataActionFailed`, naming the property, the subject it was released under, and this rule, rather than surfacing the underlying OpenSSL `oaep decoding error` on its own.

The rule is not only about the read failing. Materializing one person's data into a read model subjected to *another* identity puts that data outside the reach of their erasure — crypto-shredding the owner's key does not touch a copy sitting under a different subject. A cross-subject `[PII]` join is an erasure defect regardless of whether it can be decrypted, which is why this is an error rather than a warning.

The explicit different-property pattern has never been supported. This rule turns that established runtime failure boundary into a build failure without promoting the newly conservative same-apparent-subject cases to errors.

## Existing Stored Documents

Correcting the join only changes future projection work. It does not prove that documents already materialized under the wrong subject were removed, and replaying over the same container can leave stale copies behind. Before making an erasure claim, drop and rebuild the affected projection into clean storage, rebuild into a new container and switch readers, or perform an audited migration that proves the owner of every personal value and rewrites or removes every wrong-subject document.
