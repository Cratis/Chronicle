# CHR0043: Key redirection carries a [PII] value across the compliance subject

## Rule Description

A projection redirects its key onto another stream and carries a `[PII]` value from that stream onto the read model.

A read model document holds exactly one compliance subject. `UsingKey`, `UsingKeyFromContext`, `UsingParentKey` and `UsingParentKeyFromContext` — and the model-bound `[FromEvent]` and `[ChildrenFrom]` forms — can redirect a document away from the runtime subject stored with the event. A `[PII]` value arriving that way is re-encrypted under an identity that is not provably its owner's.

Declaring `[Subject]` on the event is not a suppression. Its runtime value can be null or empty, an explicit subject supplied to the append can override the declared value, and already-stored historical events retain the subject metadata they were appended with. Source syntax therefore cannot prove that a redirected event-property key equals every event's runtime owner. The analyzer does recognize the fluent safe controls that key directly from `EventContext.Subject` or `EventContext.EventSourceId`; those values are the runtime ownership context rather than a declaration about it.

PII reach is recursive. A mapped event member counts when `[PII]` occurs directly, on its type, in an inherited member, or inside a nested value object, array, or collection element.

Nothing fails at read time. The cost is erasure reach: crypto-shredding the owner's key does not touch a copy resting under a different subject, so the value survives an erasure that reports success.

Keep the personal value on a read model keyed and subjected by its owner, or resolve it at the query edge under the owner-scoped read model. Do not move it onto a request-, case-, tenant-, or other subject's document merely to make a query convenient.

## Existing Stored Documents

Fixing the projection prevents future wrong-subject materialization; it does not remove or re-encrypt copies already stored under the wrong subject. Before claiming erasure coverage, replace the affected read-model storage by dropping and rebuilding the projection into a clean container, rebuilding into a new container and switching readers, or performing an audited migration that proves the owner of every personal value and rewrites or removes each wrong-subject document. Replaying corrected code over the existing container is not sufficient evidence that stale copies are gone.

## Relationship to CHR0038

`CHR0038` refuses the same defect reached through a `[Join]`. This rule covers the key-redirection route to the same outcome. The storage side does not distinguish them.

## Severity

The default severity is **warning**, unlike `CHR0038`. This is a rollout signal, not a compatibility guarantee or an erasure grace period: repositories that treat warnings as errors can fail immediately, and affected persisted read models still require the cleanup above. Any later promotion to error is a separate compatibility decision; suppressing or retaining warning severity does not make the storage shape safe.

## Suppressing

Suppress with `#pragma warning disable CHR0043` around the declaration, or set `dotnet_diagnostic.CHR0043.severity = none` in `.editorconfig`. Suppressing leaves the value outside its owner's erasure — the defect is not decryptability, so nothing at runtime will report it.
