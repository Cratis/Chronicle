A self-reducing read model in Cratis Chronicle keeps its state and transitions on the same .NET type.
Declare public static `Reduce` methods when the next state depends on the previous state and a
separate reducer class adds no useful separation. Each method is a fold: it combines an event with
current state to produce the next state. Start with this form for new reducer code.

If a fold needs injected services or the model is a shared contract that must stay separate, use
`IReducerFor<T>` instead. [Choose how to build a read model](../projections/choosing-a-read-model-style.mdx)
compares both forms with projection mappings. Self reducers use the same storage, filtering, and
replay pipeline as instance reducers; their discovery and invocation differ.

:::caution[Check existing models when upgrading]
The static method shape is enough for discovery. If an existing concrete, non-generic model already
has a complete public static `Reduce(event, nullable current[, EventContext])` signature, Chronicle
recognizes it as a reducer without a marker. Check existing helpers and remove any competing builder
before registering the model. An almost-correct signature warns and is skipped by automatic discovery;
explicit registration rejects it.
:::

## Declare the transitions

Start with the state your caller needs, then declare public static `Reduce` methods on that concrete,
non-generic model. Each method receives an event and nullable current state and returns the next
state. No marker attribute or parameterless constructor is required:

<ChronicleClientTabs snippet="reducers/self-reducing-read-models/basic" />

The balance example adds an amount to the previous balance, starting from zero if no state exists.
Clearing returns `null`. In any self reducer, returning a new model creates or updates the instance;
returning `current` ignores the event; returning `null` leaves it absent or removes existing state.
An event after removal receives `null` and can recreate the model.

| Part | Supported shape |
| --- | --- |
| Declaration | Public static, non-generic method named `Reduce` |
| Parameters | `(event, current)` or `(event, current, EventContext)` |
| Event | Non-`object` class or interface dispatch target |
| Current | Exactly the containing model type, nullable or declared without nullable annotations |
| Result | The model or `Task` of the model, including nullable results |

Chronicle awaits an asynchronous result before applying the next event. Plain `Task`, `ValueTask`,
and `Task<object>` are not state results. By-ref, optional, `params`, extra service, and reordered
arguments are not supported. The current parameter must allow null because state can be absent;
a non-nullable declaration is an almost-correct signature, not a promise Chronicle can satisfy.

## Discovery and upgrades

A method named `Reduce` is not enough on its own: discovery requires the complete static shape.
Other shapes remain helpers, except that a static near miss whose current or result refers to its
model logs a warning and is skipped. Explicit registration rejects that near miss with
`InvalidSelfReducerSignature`. Fix the signature before relying on the model's transitions.

Once a type has a valid self-reduction method, invalid sibling `Reduce` declarations and malformed
replay hooks fail validation. A valid method still needs a matching event in that client's registry
before it creates an observer subscription. A type's presence in an assembly does not register it as
an event; use `[EventType]` or explicit event registration.

Types implementing `IReducer` or `IReducerFor<T>` always remain classic, even with a self-shaped static helper. Their instance activation, dispatch and plain-`Task` behavior are unchanged.

### Arc query endpoints

In an Arc application, keep `[ReadModel]`, the static `Reduce` methods, and query methods on the same
record. Arc's current automatic query discovery excludes methods taking the read model itself, so
a reducer method is not exposed as a query.

For an older Arc version without that exclusion, use `[ReadModel(RequireQueryAttribute = true)]` and
mark intended queries `[Query]`. Chronicle's discovery does not change an older Arc version's endpoint
discovery.

See Arc's [model-bound read models and queries](/arc/backend/csharp/queries/model-bound/) for the query contract.

## Register the model

Default discovery recognizes a valid self reducer in your application's artifact catalog. With
manual or explicit artifact registration, nominate the model before creating the store. Use the
existing generic or `Type` `RegisterReducer` APIs, and include the events it handles:

<ChronicleClientTabs snippet="reducers/self-reducing-read-models/explicit-registration" />

There is no separate self-reducer registration API. Matching explicit and discovered declarations
are combined; incompatible identities fail. For when a store captures its artifact catalog and what
happens on reconnect, follow [explicit artifact registration](../clients/dotnet/explicit-artifacts.md).

Remove a previous builder before switching a model to self reduction. In the same client catalog,
`AmbiguousReadModelBuilder` rejects another reducer, a fluent projection, or model-bound projection
mappings that also maintain the model. Configuration such as `[Passive]`, `[Reducer]`, sequence
selection, and filters does not by itself count as a projection builder.

## Configure observation and reads

Place reducer configuration on the model itself: `[Reducer]` controls identity, sequence, and activity.
Sequence, event-store, descriptive tag, and metadata-filter attributes keep their existing purposes.

<ChronicleClientTabs snippet="reducers/self-reducing-read-models/configuration" />

Read an instance with `eventStore.ReadModels.GetInstanceById<SelfAccountBalance>(eventSourceId)`.
Materialized reads use the stored state. Put `[Passive]` on the model for on-demand by-ID folding;
`[Reducer(isActive: false)]` only stops active maintenance and does not make reads passive. Compare
[passive reducers](passive-reducers.mdx) before changing the read behavior.

## Handler selection

Dispatch considers only concrete events registered in the owning client:

1. An exact event parameter wins.
2. Otherwise the nearest base-class handler wins over interface handlers.
3. Otherwise the uniquely most-derived matching interface wins.

Equally specific handlers throw `AmbiguousSelfReducerMethod`. This includes two handlers for the same parameter with and without context. Declaration order and method names do not break ties. Separate clients can select different event sets without sharing registry-dependent dispatch or fingerprints.

The implementation fingerprint includes selected handlers and replay hooks, including inherited bodies and async state machines, together with the registry's selected identities and generations. Existing kernel replay policy determines how changed implementations rebuild state.

## Optional replay hooks

Use replay hooks for work tied to replay notifications, not for computing each event's next state.
Each hook is optional and must be public static, non-generic, and return exactly `Task`. Global hooks
accept service arguments only; partition hooks require `Partition` first:

<ChronicleClientTabs snippet="reducers/self-reducing-read-models/replay-hooks" />

Chronicle resolves trailing class or interface service arguments through dependency injection in an
asynchronous scope for that notification. Events, `EventContext`, the model, and extra partition
arguments are not hook services. Missing service registrations fail. Chronicle awaits the hook and
scope disposal before later notifications; an absent hook creates no scope, and hooks do not require
activating a model instance.

Hooks follow the existing notification stream. A full replay sends global begin/end notifications; do not assume it also sends partition notifications. Failure does not guarantee a later end notification. Replay and delivery are not exactly-once operations.

## Reads, filters and preserved limits

Choose [passive reducers](passive-reducers) for on-demand reads, not for historical snapshots.
`GetSnapshotsById` returns no reducer history; a materialized snapshot is the current stored state.
A bounded `GetInstances(eventCount)` takes a prefix of event-type-selected events before metadata
filtering, not the first N accepted events. Empty or all-rejected histories produce no instance.

Passive reads and reducer scenarios use the same filters as active delivery: an event must match any
configured tag and each configured source/stream category. `Tag`/`Tags` label observers; they do not
filter events. There is no stream-ID subscription filter. Inbox forwarding preserves append tags and
source/stream routes for both classic and self reducers, but upgrading does not restore tags dropped
by an earlier release.

`Watch` supports reducers; `GetWatcherFor` remains projection-only. Failed folds do not notify
watchers, even if part of the batch succeeded. Successful folds notify them, including removal when
the result is null, but a notification does not prove that persistence succeeded.

A self reducer can participate in a [decision read](../read-models/decision-reads.mdx#reducers) if it
meets the admission rules, including observing the event log without metadata filters and handling
one generation per event type. An ordinary passive or materialized read does not guard a later append.
Container names follow the existing naming policy; there is no reducer `ContainerName` override.

Generation delivery, revisions, and personally identifiable information (PII) use the shared reducer
engine. Passive/history queries retain instance reducers' query-generation behavior; they do not gain
the generation-pinning guarantees of observer delivery. Use
[ReadModelScenario](../testing/read-models/scenario) for transitions and metadata filters, and
real-kernel specifications for encryption, erasure, storage, replay, and transport behavior.

## Diagnostics

If discovery misses a method, check `CHR0058` for an almost-correct signature and
[CHR0065](../code-analysis/CHR0065.mdx) for event folds with the wrong name or a missing `static`
declaration. `CHR0059` reports malformed hooks; `CHR0060` reports definite handler ties.

`CHR0061` reports definite builder conflicts within one type and warns about possible conflicts with
another builder. The runtime client's event registry, plugins, and artifact catalog determine which
builders and events actually participate; compile-time diagnostics cannot decide that membership.
The model holds the fold's result, not mutable reducer-service state.
