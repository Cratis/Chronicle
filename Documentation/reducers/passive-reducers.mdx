---
title: Passive and inactive reducers
description: Choose on-demand reconstruction or disable active observation without changing read semantics.
---

Use a passive read model when you want to reconstruct state from events on demand instead of maintaining a sink. Disabling a reducer's activity is a different choice: it stops observation, but does not change how the model is read.

## Choose the read behavior

| Configuration | Active observation | Sink | By-id read |
| --- | --- | --- | --- |
| Default | Enabled | Configured sink | Current materialized state, eventually consistent |
| `[Reducer(isActive: false)]` only | Disabled | Still configured | Materialized state; it may be absent or stale |
| `[Passive]` on the read model | Disabled | None | Reconstruct from the matching events |

For a [self reducer](self-reducing-read-models), the read model is also the reducer declaration, so place `[Passive]` on that same type. For a classic reducer, place it on the target model, not the reducer service.

### On-demand reads

Mark the read model `[Passive]`:

This disables active observation regardless of the reducer's `isActive` setting and selects on-demand reads through `IReadModels`. A sink collection cannot reconstruct passive state.

<ChronicleClientTabs snippet="reducers/passive-reducers/retrieving-state" />

No matching history, or a history whose events are all filtered out, returns absent state. A null reducer result deletes state; a later accepted event can recreate it. Source/stream filters and tag filters apply to both classic and self passive reads with the same OR-within-tags and AND-across-categories semantics as active delivery.

### Disable observation only

Use `isActive: false` when you want the observer registered but not running:

<ChronicleClientTabs snippet="reducers/passive-reducers/reducer-attribute" />

This does **not** make the model passive. Previously persisted state remains in its configured sink and is no longer maintained. By-id reads do not switch to event reconstruction unless the read model carries `[Passive]`.

## Bounded analysis, not arbitrary-date history

A bounded `GetInstances(eventCount)` reconstructs from a prefix of event-type-selected events. The prefix is taken **before** tag/source/stream metadata filtering; rejected events do not cause Chronicle to read farther to find N accepted events.

<ChronicleClientTabs snippet="reducers/passive-reducers/historical-snapshots" />

This is not a date-based snapshot query. `GetSnapshotsById` currently returns no reducer history; current materialized snapshots and historical projection snapshots are different read surfaces.

Changing `isActive` updates observer activity, not the model's read strategy. Adding or removing `[Passive]` changes sink selection and by-id reconstruction semantics. Treat that as a read-model configuration change; do not assume toggling `isActive` has the same effect.

## Passive reads are not guards

A passive read is fresh when you read it, but it does not note a position in the log and does not guard the append that follows. Another writer can append between your read and your write. To make a rule hold, use a [constraint](../constraints/index.md) or a [decision read](../read-models/decision-reads.mdx). A decision read can fold a reducer that has no filters and no constructor dependencies other than `ILogger<T>`, or a flat projection. See [Decision reads](../read-models/decision-reads.mdx#reducers). See [Choosing how a rule holds](../dynamic-consistency-boundary/choosing.mdx).

Neither passive nor inactive reducers enable stream-id subscription filtering or exactly-once delivery. A passive or inactive reducer can still be read as a [decision read](../read-models/decision-reads.mdx#reducers) under the same admission rules as any reducer. See [self-reducer limits](self-reducing-read-models#reads-filters-and-preserved-limits) for the shared boundaries.
