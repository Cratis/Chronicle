---
title: Choose passive or inactive Cratis Chronicle reducers
description: Use passive Cratis Chronicle reducers to reconstruct state on demand, or disable observation while keeping materialized reads. Understand the trade-offs.
---

A passive Cratis Chronicle reducer reconstructs a read model by folding its events on demand:
applying them in order to compute state rather than keeping a stored result up to date. Use it for
occasional reads when repeating the fold is an acceptable cost. An inactive reducer is different: it stops observing events but still reads from
its configured storage, which may be stale or empty.

## Choose the read behavior

A sink is the storage destination for materialized state. Choose whether you want to maintain that
state before choosing whether the observer should run:

| Configuration | Active observation | Sink | By-id read |
| --- | --- | --- | --- |
| Default | Enabled | Configured sink | Current materialized state, eventually consistent |
| `[Reducer(isActive: false)]` only | Disabled | Still configured | Materialized state; it may be absent or stale |
| `[Passive]` on the read model | Disabled | None | Reconstruct from the matching events |

For a [self reducer](self-reducing-read-models), the read model is also the reducer declaration, so place `[Passive]` on that same type. For a classic reducer, place it on the target model, not the reducer service.

### On-demand reads

In .NET, put `[Passive]` on the read model so normal by-ID reads fold its events on demand:

This disables active observation regardless of the reducer's `isActive` setting and selects
on-demand reads through `IReadModels`. Read through that API rather than querying a storage collection;
the passive model has no materialized sink.

<ChronicleClientTabs snippet="reducers/passive-reducers/retrieving-state" />

No matching history means no instance. The same is true if filters reject every event. During the
fold, returning `null` clears the computed state; a later accepted event can recreate it. Return
`current` unchanged if you only mean to ignore an event.

Both classic and self passive reads apply the same filters as active delivery. An event needs to
match any configured tag, plus each configured event source type and event stream type. See
[event metadata filtering](../events/filtering/index.md) when selecting the history to fold.

### Disable observation only

Use `isActive: false` when you want the observer registered but not running:

<ChronicleClientTabs snippet="reducers/passive-reducers/reducer-attribute" />

This does **not** make the model passive. Previously persisted state remains in its configured sink and is no longer maintained. By-id reads do not switch to event reconstruction unless the read model carries `[Passive]`.

## Bounded analysis, not arbitrary-date history

Use `GetInstances(eventCount)` to examine the state produced by a limited prefix of history. Chronicle
first selects events of the handled types and takes the prefix, then applies metadata filters.
Rejected events count toward the bound; they do not cause Chronicle to read farther for more
accepted events.

<ChronicleClientTabs snippet="reducers/passive-reducers/historical-snapshots" />

The argument is an event count, not a date or a count of accepted events. `GetSnapshotsById` returns
no reducer history. Use [projection snapshots](../read-models/getting-snapshots) when you need that
historical read surface rather than a reducer fold.

Changing `isActive` updates observer activity, not the model's read strategy. Adding or removing `[Passive]` changes sink selection and by-id reconstruction semantics. Treat that as a read-model configuration change; do not assume toggling `isActive` has the same effect.

## Passive reads are not guards

An on-demand fold does not protect a later write. Another writer can append between your read and
your append, so a balance reconstructed for display is not enough to enforce a spending rule. Use a
[constraint](../constraints/index.md) or a [decision read](../read-models/decision-reads.mdx) when the
rule must hold at append time. [Choosing how a rule holds](../dynamic-consistency-boundary/choosing.mdx)
helps you choose that boundary.

Passive and inactive reducers can both participate in
[decision reads](../read-models/decision-reads.mdx#reducers), but activity settings do not bypass
admission checks. Reducer decision reads require the event log, no metadata filters, one generation
per event type, and no constructor dependencies other than `ILogger<T>` for an instance reducer.
[Decision reads for reducers](../read-models/decision-reads.mdx#reducers) covers the remaining checks.

Neither passive nor inactive reducers add stream-ID subscription filtering or exactly-once delivery.
Keep the [shared reducer limits](self-reducing-read-models#reads-filters-and-preserved-limits) in mind
when changing a model from active maintenance to on-demand reads.
