A Cratis Chronicle reducer builds a read model by applying events to its previous state. Use one when
a view's rules are clearer as state transitions in code than as property mappings, such as updating
a displayed total only while an account is active.

For direct mappings, start with model-bound projection attributes; use fluent mappings when the
definition needs more structure. Counters and sums alone do not require reducer code. If you are
still choosing, [compare the read-model styles](../projections/choosing-a-read-model-style.mdx)
before writing a fold, the function that combines each event with the state so far.

## Key Concepts

A reducer observes events for each event source, such as an order or account, and keeps that source's
state separate. In the per-event form, Chronicle calls the selected method for each event in sequence
order. Its return value becomes `current` for the next event, even when several events arrive in one
batch. A [batch reducer](batches) instead receives the partition's events in one call.

Active reducers maintain materialized state: a stored result you can query without folding the history
again. A passive reducer computes state when you ask for it. Neither form gives you historical reducer
snapshots through `GetSnapshotsById`.

## When to Use Reducers

Choose a reducer when the next result depends on the previous result and a rule. An account balance
can ignore deposits after closure; an order summary can calculate a value differently depending on its
status. These transitions are explicit in your code and can be tested with an event history.

Reducers fold one event source at a time. If your view needs joins across sources or a total shared by
many sources, consider a projection rather than adding that coordination to a reducer.

An addition creates or updates the balance; clearing it returns `null`, removing the state. Start with this form for new reducer code, then follow
[self-reducing read models](self-reducing-read-models.mdx) to register and test it.

Use `IReducerFor<T>` when the fold needs injected services, instance behavior during replay, or must
live apart from a shared model contract. See the [separate-reducer guide](getting-started.mdx).

In .NET, a reducer class must target only one read model. Implementing two closed `IReducerFor<TReadModel>` interfaces, including through inheritance, throws `TypeMustImplementOnlyOneReducer` during default artifact discovery. Split the class into one reducer per read model. [CHR0057](../code-analysis/CHR0057) reports this before runtime.

If a contract assembly cannot reference Chronicle, the .NET client can explicitly nominate a plain
instance reducer and infer its single read model from supported method signatures. The existing
`RegisterReducer` APIs accept that form and a [self reducer](self-reducing-read-models); follow
[explicit artifact registration](../clients/dotnet/explicit-artifacts) for setup.

## Reading Your Reducer-Based Read Models

Use `IReadModels` to read the result by event source ID or retrieve a collection. Active maintenance
is asynchronous, so a stored result may lag the latest append. Choose passive reads when you need to
fold on demand, or [decision reads](../read-models/decision-reads.mdx#reducers) when an admitted reducer
must participate in guarding a later append.

- [Getting a Single Instance](../read-models/getting-single-instance) - Retrieve a specific instance by key
