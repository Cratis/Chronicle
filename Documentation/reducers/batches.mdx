<span id="reducing-events-in-batches"></span>

A batch method in Cratis Chronicle's .NET client updates a read model from one partition's delivered events in a single call. Use it when the transition needs to consider several events together rather than handle each event separately.

Chronicle delivers events in pages. A partition groups events for one event source, such as an account, and the client reduces each partition separately. The batch contains the observed event types from that partition in the current page, not its entire history. Your method folds those events in sequence order with the current read model and returns the next state.

## Declaring a batch method

The account example applies deposits and withdrawals to the balance so far. Each item exposes the event through `Event`, allowing the method to choose the transition by event type.

A batch method takes an `EventBatch` first and the nullable current read model second, and returns the read model or a task of it. The current model is `null` before the partition has state; returning `null` removes the read model. Declare each observed event type with `[Observes<TEvent>]`. Optional parameters can receive `BatchContext`, `CancellationToken`, and services.

On a [self-reducing read model](self-reducing-read-models) the batch method is a public static method named `Reduce`.
On a separate reducer implementing `IReducerFor<TReadModel>` it can have any name.

A reducer has per-event methods or one batch method, never both, because splitting its events between methods would
break the fold. The analyzers in `Cratis.Chronicle.CodeAnalysis` report these mistakes when you build, and Chronicle refuses to register a reducer that has one:

| Mistake | Rule |
| --- | --- |
| A method with `[Observes<TEvent>]` does not take an `EventBatch` | [CHR0069](../code-analysis/CHR0069.mdx) |
| A batch method has no `[Observes<TEvent>]` | [CHR0070](../code-analysis/CHR0070.mdx) |
| A per-event method takes a `BatchContext` | [CHR0072](../code-analysis/CHR0072.mdx) |
| A reducer has two batch methods, or a batch method and per-event methods | [CHR0074](../code-analysis/CHR0074.mdx) |
| A batch method does not take or return the read model, takes a parameter Chronicle cannot supply, such as an `EventContext`, or on a self-reducing read model is not public, static and named `Reduce` | [CHR0075](../code-analysis/CHR0075.mdx) |

A self-reducing read model's batch method with another name than `Reduce` is the one mistake registration cannot catch: the client does not discover it, so the read model never runs. Rely on CHR0075 for it.

[CHR0076](../code-analysis/CHR0076.mdx) warns about a pattern on an event type the batch method does not observe, since it never matches.

## Reporting outcomes

Throwing or calling `Fail` on the batch fails the partition without writing its new state. Calling `Defer` requests delivery again after the delay you supply, without failing the partition or writing state. Deferral requires kernel support; without it, the client reports a failure instead.

Other partitions in the page can still succeed. The client reduces partitions in parallel, while keeping each partition's events in order. Keep state changes local to the partition rather than relying on another partition finishing first.

Pages reach a reducer on every path: as events are appended, while it catches up, during a replay and when a failed partition is retried. A page can hold many event sources, and the kernel loads their current read models together and writes the new states of the partitions that succeeded together. A partition that fails or is deferred writes nothing and is delivered again from its stored state, while the others in the page are written.

## Page size and concurrency

Declare the page bounds and how many event sources are reduced at once with `[BatchSize]` on the reducer, or on a self-reducing read model:

<ChronicleClientTabs snippet="reducers/batches/batch-size" />

| Property | Meaning | Default |
| --- | --- | --- |
| `MaxEvents` | The most events in one page | 500 for a reducer with a batch method, 100 for one with per-event methods |
| `MaxBytes` | The most bytes of event content in one page, counted as the UTF-8 length of each event's JSON content | 0, so the kernel's maximum applies |
| `MaxDelayMilliseconds` | How long the kernel may wait to fill a live page. Accepted, but not applied yet | 0 |
| `MaxConcurrency` | How many event sources of one page are reduced at the same time | The processor count; `1` reduces them one after another |

`MaxConcurrency` applies to per-event reducers too, since the client folds each event source of a page separately either way.

The kernel honors `MaxEvents` and `MaxBytes` on every path: live, catch-up, replay and retry. It caps them with its own maximums, `maxEventsPerSubscriberCall` (100 by default) and `maxBytesPerSubscriberCall` (4 MiB by default), and a bound of zero takes the kernel's maximum. With the default configuration a page therefore holds at most 100 events, even for a reducer that declares 500; see [page bounds](../hosting/configuration/observers.md#page-bounds) to raise it. The current read models loaded for a page do not count toward `MaxBytes`. An event larger than `MaxBytes` is sent alone in its own page, so it never stalls its event source, and an event source whose events span two pages is reduced page by page, each from the state the page before it wrote.

The kernel does not yet apply `MaxDelayMilliseconds`: a live page holds what is already waiting. Chronicle refuses to register a reducer with a negative bound.

## Testing a batch reducer

`ReadModelScenario` from `Cratis.Chronicle.Testing` runs a batch reducer the same way as a per-event one: the events of one `Events(...)` call reach the batch method as one live page, with the state so far as the current read model.

<ChronicleClientTabs snippet="reducers/batches/testing" />

When the batch method fails the event source, through `Fail` or by throwing, reading the instance throws `ReducerFailed`. When it defers the event source, reading the instance throws `ReducerDeferred`, which carries the requested delay. For more on scenarios, see [testing read models](../testing/read-models/scenario.mdx).

For the per-event alternative and replay behavior, continue with [reducer event processing](event-processing).
