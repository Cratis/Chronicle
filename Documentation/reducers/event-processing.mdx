<a id="event-processing"></a>

Cratis Chronicle reducers apply each event to the state produced by the previous event for the same
event source. Use this guide when implementing a fold, the function that combines an event with
current state to produce the next state. Choose the handler shape and decide what a missing state
means, then return new state without mutating a result another reader may hold.

The examples use C# and .NET dispatch rules. TypeScript handlers also receive context as
`(event, current, context)`; Kotlin and Java can accept `EventContext` as a third parameter, and
Elixir receives a context map through `reduce/3`. Follow
[Getting started with reducers](getting-started) for each client's handler conventions rather than
copying C# syntax into another language.

## Event Processing Model

### Event Method Discovery

For a .NET instance reducer, Chronicle matches methods by parameter type, not method name. Put the
known event type first, the nullable current read model second, and an optional `EventContext` third.
Return the model or `Task<TReadModel>`, including nullable results. A descriptive name helps readers
find the transition but does not affect event matching.

<ChronicleClientTabs snippet="reducers/event-processing/method-discovery" />

### When more than one method matches

This section describes classic instance reducers. [Self reducers](self-reducing-read-models#handler-selection) use public static `Reduce` methods and uniquely most-specific dispatch; ambiguity fails rather than using method-name or context-overload tie-breaking.

A helper with the same reducer-shaped parameters can become a candidate for the same event. For
.NET instance reducers, Chronicle selects one method per event type using this precedence:

1. A public method takes precedence over a non-public method.
2. At the same accessibility, a method with more parameters takes precedence, so the context overload wins.
3. A remaining tie is resolved by method name in ordinal order, not reflection order.

A private method is still a valid reducer method when nothing else handles that event type — the precedence only decides between candidates, it does not disqualify any of them. If a helper is not meant to take part in dispatch at all, change its parameters so it no longer has the reducer shape.

### Event Source Isolation

Each event source has independent state. An order event receives that order's current model, not
another order's model. Events for the same source are processed sequentially; this isolation does not
provide ordering or coordination between different sources.

### Sequential Processing

Within a delivered batch, Chronicle applies events in sequence-number order. Each return value
becomes `current` for the next event. Retries and replay can deliver events again, so the fold must
not rely on being invoked only once.

## Current State Parameter

The `current` parameter represents the previously computed state for this event source.

### First Event

When an event source has no state yet, `current` is `null`. Initialize the model from an event that
can create it. For other events, declare a nullable return type such as `TReadModel?` and return
`null` if the model should remain absent.

<ChronicleClientTabs snippet="reducers/event-processing/first-event" />

### Subsequent Events

After creation, `current` contains the previous event's result. A C# record's `with` expression lets
you return a changed copy. If a later transition removes the model, the following event receives
`null` again, so null handling is not just a first-event concern.

## Error Handling

If a handler fails, Chronicle does not persist the successfully reduced prefix of that batch. In
.NET, failed folds do not notify watchers. A successful fold does notify them before the Kernel
persists its result, so `Watch` is still not a persistence-success signal
([#4817](https://github.com/Cratis/Chronicle/issues/4817)). Classic and self reducers share this behavior.

### Handling Invalid State

When there's no state to build on yet, return `null` from a nullable-returning handler (`TReadModel? Handle(...)`) to leave the read model unset:

<ChronicleClientTabs snippet="reducers/event-processing/skip-invalid-state" />

Note the difference between **skipping** an event and **removing** a read model: returning `null` when `current` was already `null` is a no-op, but returning `null` when `current` holds real state deletes that read model. To ignore an event without discarding existing state, return `current` unchanged instead.

## Best Practices

Keep the fold deterministic: compute from the event, its context, and the current state rather than
live external values. Do not send messages or write elsewhere from a transition; retries and replay
can repeat those side effects.

Test creation, updates, removal, and recreation, including events that arrive without prior state.
[ReadModelScenario](../testing/read-models/scenario.mdx) lets you check the resulting model through
the registered reducer.

## Concurrency Across Partitions (.NET client)

A partition is the unit of state and ordering, normally one event source. Within a partition, the
.NET client runs batches in arrival order. Different partitions of the same reducer can run at the
same time, so reducer code and its services must be safe for concurrent use. There is no ordering
across partitions. Replay begin and end notifications wait for work in flight; results are reported
to the Kernel one at a time.

`Reducers.MaxConcurrentPartitions` in
[`ChronicleOptions`](../configuration/chronicle-options#reducers) defaults to the processor count,
capped at 8. Set it to `1` when you need batches handled one at a time.
