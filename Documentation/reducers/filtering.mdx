---
title: Cratis Chronicle reducer event filtering
description: Limit a Cratis Chronicle reducer to events with matching tags, event source types, or stream types, without changing the reducer's state transitions.
---

<span id="filter-reducers-by-appended-event-metadata"></span>

Cratis Chronicle reducer filters select which events can update a read model by matching stored event metadata. Use them when the same event type serves several views, but one view should include only a tagged subset or a particular source or stream type.

Place filter attributes on a .NET reducer class, or on the model for a [self-reducing read model](self-reducing-read-models). Events must match both the reducer's observed event types and its metadata filters before they reach its transition methods. A nonmatching event is skipped for that reducer, not removed from the event store.

## Filter attributes

| Attribute | Filters by | Matches when |
|---|---|---|
| `[FilterEventsByTag("...")]` | Appended or static event tag | Any filter tag matches any tag on the appended event |
| `[EventSourceType("...")]` | Event source type set at append time | The event source type matches exactly |
| `[EventStreamType("...")]` | Event stream type set at append time | The event stream type matches exactly |

An event source type categorizes the source, such as `customer`; a stream type categorizes the stream, such as `fulfillment`. These are types, not individual source or stream IDs. Set the metadata when appending the event:

:::note[Client coverage]
Kotlin and Java use `@FilterEventsByTag`, `@EventSourceType`, and `@EventStreamType` on the reducer class. TypeScript uses `@filterEventsByTag(...)`, `@eventSourceType(...)`, and `@eventStreamType(...)` alongside `reducer()`. Elixir's `use Chronicle.Reducers.Reducer` does not expose these filter options.
:::

## Combine multiple filters

You can combine `[FilterEventsByTag]`, `[EventSourceType]`, and `[EventStreamType]` on the same reducer. Chronicle requires all filter categories to match:

<ChronicleClientTabs snippet="reducers/filtering/combine-filters" />

The reducer only receives events that match all three: the `premium` tag, the `order` event source type, and the `fulfillment` stream type. Multiple tags are alternatives within the tag category; they do not relax the source or stream requirements.

Without a source filter, `Unspecified` matches any source type. Without a stream filter, `All` matches any stream type. An explicit `Default` source filter matches only the default source type, not every source. Subscription filtering by an individual stream ID is not supported.

## Passive reads and forwarded events

The .NET client applies the same matching rules to passive reads and reducer scenarios for separate and self-reducing models, using stored or seeded metadata. When a collection read has an event-count limit, it selects that many events of the observed types before applying metadata filters. It does not keep reading until that many matching events have been accepted.

Inbox forwarding preserves tags and route metadata. Older inbox events affected by the tag-loss issue ([#4823](https://github.com/Cratis/Chronicle/issues/4823)) remain untagged and cannot match a tag filter. See [external-store route filters](external-event-store-subscriptions#forwarded-metadata-limitation) before relying on tags in an existing inbox history.
