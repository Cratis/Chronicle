Use a separate `IReducerFor<T>` when the fold needs injected services, instance behavior during replay,
or must live apart from its model. For application code, start with model-bound attributes, then fluent
mappings, then reducer code; a [self-reducing model](self-reducing-read-models.mdx) is the default for new
reducers. [Choose how to build a read model](../projections/choosing-a-read-model-style.mdx) explains the
choice; this guide shows the separate-class form.

## Prerequisites

Before you begin, ensure you have:

- A Chronicle-enabled application
- Basic understanding of events and event sourcing
- A read model class to reduce events into

These overload tables describe .NET instance-method dispatch. Kotlin and Java match the first
parameter's event type. TypeScript selects a method by the camelCase event-class name and passes
`(event, current, context)`; it awaits the result, so an `async` handler works. Kotlin awaits `suspend`
handlers. Elixir uses a `reduce/3` callback pattern-matched by event struct.

**Key Points:**

- In .NET, method names are unrestricted; the examples use `On` followed by the event type name
- The `@event` parameter is the specific event being processed
- The `current` parameter contains the existing state (null if no previous state exists)
- The `EventContext` parameter provides metadata like event source ID, occurred timestamp, and sequence number
- Both synchronous and asynchronous methods are supported

### .NET dispatch and diagnostics

In .NET, the event must be the first parameter and the nullable current read model the second. An
optional third parameter must be `EventContext`. Return the model or `Task<TReadModel>`, including a
nullable result. Returning null deletes or leaves the instance absent. Classic plain `Task` is also
accepted, but yields null state; a mutation-only `Task` handler does not retain current state. A method
taking the current model first and `object` second is not dispatched.

The .NET analyzers report unsupported signatures as **CHR0006** and event parameters without `[EventType]` as **CHR0007**, including `object` event parameters. If none of a reducer's methods can be dispatched, the client skips its kernel registration and logs a warning naming the reducer and explaining why its public reducer-like methods were skipped. The application still starts; correct the signatures so the reducer can observe events.

**Attribute parameters:**

- `id` - Custom identifier for the reducer (defaults to the fully qualified type name)
- `eventSequence` - The event sequence to observe (defaults to the event log)

## Event Processing

Reducer methods are called for each event matching the event type:

1. **Event Type Matching** - Chronicle calls the method that handles the specific event type
2. **Event Source ID** - Each method receives events for a single event source
3. **Sequential Processing** - Events are processed in the order they were appended

The `current` parameter in each method:

- Is `null` when no previous state exists for this event source
- Contains the current persisted state for this event source

## Best Practices

1. **Keep reducers deterministic** - Compute state from recorded facts. An injected clock or live rate service can return different values during replay; record time and rates in events when they determine the result.
2. **Handle null current state** - Always check if `current` is null for the initial state
3. **Use immutable state** - Create new instances rather than mutating the current state
4. **Process events in order** - The events are provided in sequence order; respect that order
5. **Consider performance** - For large event streams, optimize your reduction logic
