Cratis Chronicle reducer tags describe a reducer's purpose or domain so related definitions share recognizable labels. Use them to organize reducers without changing which events update their read models.

In .NET, `[Tag]` and `[Tags]` label the reducer class. For a [self-reducing read model](self-reducing-read-models), put the labels on the model instead. Neither form filters incoming events.

Kotlin and Java use repeatable `@Tag` annotations. TypeScript uses `@tag(...)` or `@tags(...)` on the reducer class. These labels are sent with the reducer's observer registration, the definition that tells Chronicle what the reducer observes.

If your goal is to limit delivery, use [Filter reducers and reactors by tag](../events/filtering/by-tag), [Filter reducers and reactors by event source type](../events/filtering/by-event-source-type), or [Filter reducers and reactors by event stream type](../events/filtering/by-event-stream-type).

## Best Practices

Choose names that a teammate would use to find related reducers, such as a business domain or a reporting purpose. Reuse the same spelling across those definitions; near-duplicate names split a group that readers expect to be together.

Keep a tag only if it adds a useful distinction. Adding every possible category makes the labels harder to scan without making the reducer's role clearer.

## What reducer tags change

Reducer tags are stored with the reducer definition. They do not activate a reducer, select it for execution, or change its read model's contents.

To make a read model include only tagged events, use an event filter instead. Continue with [Filtering by tag](../events/filtering/by-tag.mdx) for the delivery rule and append-time metadata it matches.
