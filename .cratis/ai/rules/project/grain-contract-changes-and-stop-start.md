## Grain contract changes and stop-start deploys

Kernel-internal grain contracts - grain interfaces, grain keys, grain payload types and their serializers, grain and
interface names, placement - may change in a minor release (decision 0037). A change that breaks cross-version grain
calls makes the release a **stop-start deploy**: every node is stopped, then the new version is started. What stays
compatible in every minor and patch: the client gRPC contract, persisted storage formats, and the Cratis.Choreography
job contracts.

### Shipping a change that breaks cross-version grain calls

No forwarding methods, duplicate overloads or dual code paths are needed. The pull request must:

1. Say `Requires a stop-start deploy: this release cannot share a cluster with <previous release>.` in the Changed or
   Removed bullet that describes the change (exact sentence; operators search the release notes for it).
2. Add a line to `.github/grain-compatibility-waivers.txt` naming the previous release tag and the reason, as the
   `v19.123.0` entry does. Grain Compatibility then skips its comparison and the **RollingUpgrade** shard logs that it is
   skipped for that release; both still run for every other release. Delete the line when a later release is cut.
3. Regenerate `OrleansContracts.txt` and `GrainPayloadContracts.txt` (commands below) and commit them.

Batch grain-contract changes into as few stop-start releases as practical: each one costs operators a full stop. Do not
break a contract that does not need to break. Never name an operator or environment in the notes.

### Keeping a release rolling-compatible

When you want a release that can still share a cluster with the previous one, silos of both releases call each other's
grains during a rolling upgrade. Orleans identifies a grain method on the wire by a hash of its interface, name and
**parameter types**, so adding a parameter - even an optional one that every caller still compiles against - makes it a
different method. The other release cannot decode the call, and the new silo crashes on startup with
`TypeLoadException: Unable to resolve type alias ("inv", ..., "<hash>")`. That is how 19.70 to 19.106 broke (#5272).

For every grain interface in `Source/Kernel/Core` (anything deriving from `IGrainWith...Key` or `IGrainObserver`):

| You want to | Do this |
| --- | --- |
| Add a method | Add it, and put `[Version(n)]` on that interface, one higher than its current version. No attribute means 0, so the first one is `[Version(1)]`; the current version of every interface is in `OrleansContracts.txt`. |
| Add a parameter, or change a parameter or return type | Do **not** edit the method. Add a new method beside it, raise `[Version]`, and have the old one forward to the new one. Remove the old one only in a stop-start release or a major. |
| Remove or rename a method | Keep it serving, and remove it only in a stop-start release or a major. |
| Rename or move a grain interface or grain class | Only in a stop-start release or a major. The full name is on the wire. |
| Change only a method's body or XML docs | Nothing; the wire identity is unchanged. |

`[Version]` routes a call that needs the new method to a silo that has it, instead of to an activation on an older
silo. Raise it only on the interface that gained a method, never on every interface at once: raising it everywhere
makes every call from a new silo seek a new silo and moves every grain during a rollout. Write it with a `using`, not
qualified in place, because inside a `Cratis.*` namespace `Orleans` resolves to `Cratis.Orleans`:

```csharp
using Orleans.CodeGeneration;

namespace Cratis.Chronicle.Projections;

[Version(1)]
public interface IProjectionsManager : IGrainWithStringKey
{
    // Existing methods unchanged, including this one, which now forwards to the new overload.
    Task Register(IEnumerable<ProjectionDefinition> definitions, ProjectionOwner? fullSetOwner = null, string? registrant = null, string? version = null);

    // New: the extra parameter is a new method, so the interface goes from version 0 to 1.
    Task Register(IEnumerable<ProjectionDefinition> definitions, ProjectionOwner? fullSetOwner, string? registrant, string? version, bool replayOnChange);
}
```

Beyond the interfaces:

- **Never move or rename a type a custom codec writes the name of** (the `Cratis.Orleans.Serialization` codecs). The
  name is on the wire; moving `ConceptSerializer` broke 19.4 to 19.13 (#4325).
- **For a rolling-compatible release, types passed between silos only gain properties.** `Source/Kernel/Core/GrainPayloadContracts.txt`, generated by
  the GrainCompatibility specs from the active grain interfaces, gates removed, renamed or retyped payload members, enum
  value changes and removed or moved wire identities. Custom-converter internals remain manual review. The comparison
  starts with the first release that carries the snapshot. On drift the specs write
  `GrainPayloadContracts.received.txt`: copy it over the snapshot and review the diff; never hand-edit it.
- **Treat a Cratis.Orleans major upgrade as a grain interface change.** Its job, job-step, worker and state-machine
  grain interfaces are outside this repository's `OrleansContracts.txt` and gate. Cratis.Orleans records and gates
  them the same way against its own latest release, so a minor or patch of it keeps them compatible; a major of it
  may break them, so take one only in a Chronicle major or a stop-start release.

`Source/Kernel/Core/OrleansContracts.txt` records every grain interface, its version, each method's wire identity and
every grain class. It is generated, never hand-edited - except to delete a retained removed method in a stop-start release or a major.
After changing a grain interface, regenerate it and review the diff:

```bash
dotnet format Source/Kernel/Core/Core.csproj analyzers --severity info --diagnostics ORLEANS0016 ORLEANS0017 ORLEANS0018 ORLEANS0019 ORLEANS0020 ORLEANS0022 ORLEANS0023 ORLEANS0024
```

The Orleans contract analyzer fails the Core build when source and manifest disagree. The **Grain Compatibility**
workflow fails a pull request whose manifest is not purely additive against the latest release; a pull request labeled
`major`, or one whose baseline release is in the waiver file, is exempt. The same workflow runs the payload drift spec and compares `GrainPayloadContracts.txt` against the
latest release. The **RollingUpgrade** integration shard replaces a cluster of the latest release with this build one
node at a time, and skips with a log line when that release is waived. Full guidance: `Documentation/contributing/kernel/grain-interfaces.mdx`.
